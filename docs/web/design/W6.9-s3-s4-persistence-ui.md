## 2. What is stored where

| Data | Where | Written by | Lifetime |
|---|---|---|---|
| Font bytes | OPFS `fonts/<id>.font` | main thread, from the user's `File` | until removed, Remove all, Clear all, or the site's data is cleared |
| Font record | OPFS `fonts/<id>.json`: `{format: 1, id, name, size, fontFormat, added}` (`added` is an ISO time) | main thread, **after** the bytes | same |
| The font in the engine | MEMFS `/fonts/<id>.<ext>` and the store's manifest (slice 2) | worker, on `fonts.add` | the worker's life |
| The tab's font list | `fontLibrary` state (main thread memory) | the library | the page's life |
| A font that could not be kept (session only) | the user's `File` object, held by the library | the library | the page's life |

`<id>` is the worker's sha256 of the bytes (`UploadedFontDto.id`), so the OPFS name, the MEMFS name
and a kept `FontRef.path` all derive from the content and match in every tab and every worker. One
record per font, not one shared index file: two tabs writing different fonts never rewrite the same
file, so no lock is needed. The list order is `added`, then `id`.

The worker's format decides the MEMFS extension (`fontstore.py:37`); OPFS keeps `.font` and the
format in the record, so nothing on disk depends on the user's file name.

No document content, password or secret is stored. `navigator.storage.persist()` is asked once,
after the first font is kept (W1.1 §6 line 161: "requested only when the user keeps fonts or
keys"); its answer is not shown (question 4).

## 3. Slice 3: persistence

### 3.1 Modules

- `web/app/src/storage/fontStore.ts` (new, OPFS only, no engine): `FONTS_FOLDER = 'fonts'`,
  `createFontStore(root = privateRoot, estimate = storageEstimate)` with:
  - `available(): Promise<boolean>`;
  - `list(): Promise<StoredFontRecord[]>`: records whose bytes file exists with the recorded size,
    in order; a bytes file with no record, older than one hour, is deleted (a write cut off by a
    crash); a younger one is left alone (another tab may be writing it);
  - `read(id): Promise<Blob | undefined>`;
  - `write(record, data: Blob): Promise<KeepOutcome>`, `KeepOutcome = 'kept' | 'no-space' |
    'unsupported' | 'failed'`: `fitsQuota` first, then the bytes, then the record, as autosave
    (`autosaveStore.ts:128-142`);
  - `remove(id): Promise<boolean>`: record first, then bytes (a cut-off remove leaves an orphan the
    next `list` cleans up); when the folder is then empty, it is removed too (non-recursive, so a
    font another tab just wrote stops it).
  Every call catches and returns an outcome; none throws (the autosave store's rule, `:5-6`).
- `storage/opfs.ts`: `DirectoryLike` gains `keys(): AsyncIterable<string>` (the browser's
  `FileSystemDirectoryHandle` has it); `BlobLike` gains an optional `lastModified`. A root without
  `keys` makes `list` return `[]` and `available` false.
- `storage/clearLocalData.ts:13`: `LOCAL_DATA_FOLDERS = [FONTS_FOLDER, 'secrets']`, importing the
  name, so the folder Clear all removes is the folder the store writes.
- `web/app/src/fonts/fontLibrary.ts` (new): the tab's one owner of uploaded fonts. It holds the
  list, talks to the engine and the store, and runs **one operation at a time** (a promise queue),
  so a sync, an add and a remove never interleave. A `useSyncExternalStore` hook gives the state to
  React (as `engineConnection.ts` does).

  ```ts
  interface FontLibraryState {
    readonly fonts: readonly LibraryFont[];   // UploadedFontDto plus kept: boolean
    readonly usedBytes: number; readonly maxBytes: number;  // from the worker's last reply
    readonly storage: 'persistent' | 'session' | 'unknown';
    readonly syncing: boolean; readonly busy: boolean;
  }
  interface FontLibrary {
    getState(): FontLibraryState; subscribe(listener: () => void): () => void;
    ready(): Promise<void>;                     // the current engine holds every kept font
    add(file: File): Promise<AddOutcome>;       // slice 4 maps outcomes to messages
    remove(id: string): Promise<RemoveOutcome>;
    removeAll(): Promise<RemoveOutcome>;
    bytes(id: string): Promise<Blob | undefined>;  // for W6.8b's preview face
    cleared(): void;                            // Clear all succeeded: tell other tabs
    onRemoved(listener: (id: string) => void): () => void;  // W6.8b drops its FontFace
  }
  ```
- `engine/engineConnection.ts`: `onReady(listener: (client) => void): () => void`, called after
  each successful `hello` of the current generation (`:138-145`), so the first start, Try again and
  a restart all reach it, and a replaced worker never does.
- `main.tsx`: `createFontLibrary({ engine, store: createFontStore() })` next to the engine, passed
  to `App` and on to `PreferencesDialog`.

### 3.2 Start-up and engine restarts

On each `onReady(client)` the library marks every font "not in this engine" and schedules a sync
when the page is idle (`requestIdleCallback` with a 2 s timeout, as the job pool's warm-up,
`engine/jobPool.ts:50`, `:69-75`):

1. `store.list()`. Nothing kept: no engine call, so fontTools is not installed for nothing.
2. For each record, one at a time: `store.read(id)`, then `fonts.add({name, data: await
   blob.arrayBuffer()})`. One call at a time keeps the worker free between fonts: an open or a
   render waits for at most one `fonts.add` (the worker answers one request at a time, S2 §2).
3. The reply's `font.id` must equal the record's `id`. A mismatch means the bytes changed on disk:
   the font is removed from OPFS and the user is told (`fonts.load.dropped`).
4. `INVALID_FONT`, `FONT_NOT_EMBEDDABLE` or `FILE_TOO_LARGE` (a later version is stricter): removed
   from OPFS, one toast per font, `fonts.load.dropped`. These can't succeed on a retry.
5. `FONT_STORAGE_FULL` (other tabs kept more than one worker takes), `NOT_SUPPORTED` (fontTools did
   not load), `OUT_OF_MEMORY`, a timeout: the font **stays in OPFS** and is listed as not loaded;
   one toast for the sync, `fonts.load.failed`. User data is never deleted on an error a reload
   could fix.
6. `syncing` goes false, `ready()` resolves, the list is the worker's (`fonts.list`).

Session-only fonts (§3.4) are re-sent from the held `File` in the same loop, so they survive an
engine restart too.

**Callers that send a `FILE` ref** (W6.8b's commit) `await fontLibrary.ready()` first; until the
sync ends, the guard would refuse the ref (`fontrefs.py`). The font picker lists only what the
library lists (S2 §7).

Why at idle and not on demand: the plan says "loaded at start-up" (plan.md:214, W1.5 §7), and idle
plus one-at-a-time keeps the viewer first. Question 1 offers on demand instead.

### 3.3 Adding a font (the library's part; slice 4 calls it)

1. `file.size > MAX_FONT_BYTES` (a hand copy of `limits.MAX_FONT_BYTES`, 50 MiB, with a comment, as
   `edit/images.ts:20`): outcome `tooLarge`, no engine call. The worker checks again.
2. `fonts.add({name: file.name, data: await file.arrayBuffer()})`. The buffer is detached by the
   send (`client.ts:121`), so the copy kept in OPFS is written from the `File` itself, never from
   the buffer.
3. On an `RpcError`: outcome `refused` with the code and `details` (slice 4 words them).
4. On success: if OPFS has no record for `font.id`, `store.write(record, file)`. `kept` gives
   `persistent`; `no-space` or `failed` keeps the font for this tab only (outcome `notKept`, with the
   reason); `unsupported` switches the library to `session` mode. A session font's `File` is held for
   re-sends.
5. `added: false` with a kept record: outcome `already`.
6. Broadcast `{kind: 'added', id}` (§3.6); on the first `kept` of the page, `persist()` (question 4).

Worker first, then OPFS: only bytes the validator accepted are ever kept, and a refused file leaves
nothing behind.

### 3.4 When OPFS is unavailable

`privateRoot()` rejects when the browser has no `getDirectory` (for example some private windows),
and a write throws `StorageUnsupportedError` when there is no `createWritable` (older Safari,
`autosaveStore.ts:90-93`). The library then sets `storage: 'session'`:

- fonts still work: they are in the worker, and re-sent from the held `File` after an engine restart;
- they are gone after a reload or when the tab closes;
- the user is told in the Fonts section by a standing hint, `fonts.storage.sessionOnly`, and, on
  each upload, by the outcome `notKept` (`fonts.upload.sessionOnly`), never by a repeated toast.

A browser that has OPFS but wipes it when a private window closes can't be detected; the guide says
so (§6).

### 3.5 Removing a font leaves no residue

`remove(id)`, inside the queue:

1. OPFS: `store.remove(id)` (record, then bytes, then the folder if empty). Done first, so the user's
   intent survives a reload even if step 2 fails.
2. Engine: `fonts.remove({id})`: the MEMFS file and the manifest entry go (`fontstore.py:124-136`);
   with 2b, the catalogue rescan drops its cache entry. A failure (`FONT_STORAGE_FULL` `{limit:
   "memory"}`) leaves the font usable until the tab closes; the outcome says so.
3. Main thread: the list entry and any held `File` go; `onRemoved` listeners run (W6.8b deletes its
   `upl-<id>` face from `document.fonts`).
4. Other tabs: broadcast `{kind: 'removed', id}`.

What stays, by design: text already typeset with the font keeps its embedded copy (W1.5 §7); the
wasm heap does not shrink (S2 risk 1); the engine's extracted-face LRU may hold the face until it is
pushed out, unreachable behind the guard (S2 question 7). Nothing in `localStorage` names a font id
in these slices; if W6.8b keeps a "last font" preference, it clears it in its `onRemoved` listener.

`removeAll()` runs `remove` for each font in order (S2 question 8), then removes the folder.

### 3.6 Other tabs

Each tab has its own worker, but OPFS is shared by the origin. A `BroadcastChannel('elanero.fonts')`
carries `{kind: 'added' | 'removed', id}` and `{kind: 'cleared'}`:

- `added`: the tab schedules an idle sync of that one font, so its picker offers it without a reload;
- `removed`: the tab calls `fonts.remove` on its own worker and drops the font from its list;
- `cleared`: the same for every font.

Messages carry ids only, never names or bytes. A browser without `BroadcastChannel` skips this; the
other tab then catches up at its next reload. (Question 3.)

### 3.7 Clear all local data

The font folder is already in `LOCAL_DATA_FOLDERS` (`clearLocalData.ts:13`) and removed with
`removeEntry(name, {recursive: true})` (`:64`), and the page reloads after a complete clear
(`PreferencesDialog.tsx:169-171`), which empties this tab's MEMFS. Slice 3 adds:

- the shared `FONTS_FOLDER` name (§3.1), with a test that the folder the store writes is in the list;
- in `App`, the dialog's `clearData` becomes `clearLocalData()` followed, when `complete`, by
  `fontLibrary.cleared()`, which broadcasts `cleared` before the reload, so other tabs drop their
  workers' copies;
- the Clear button is also off while `fontLibrary` is `busy` (slice 4, §4.5): an upload finishing
  after the clear would otherwise write the folder again.

A partial clear keeps today's message (`prefs.clearAll.incomplete`); fonts that were not removed
stay listed and kept.

### 3.8 Strings first shown in slice 3 (toasts from the sync)

- `fonts.load.dropped`: "{name} can no longer be used as a font and was removed from this browser."
- `fonts.load.failed`: "Some uploaded fonts could not be loaded. They are still kept; reload the page
  to try again."

## 4. Slice 4: the upload UI

### 4.1 Where it lives

A new **Fonts** section in Preferences, between Redaction and Shortcuts, as its own component
`prefs/FontsSection.tsx` (the dialog is 420 lines today). Font actions take effect at once, not on
Apply, like Clear all; the section's hint says so. W6.8b's picker gets an "Upload font…" row that
opens the same file input through a shared `fonts/useFontUpload.ts` hook; whichever of 8b-3 and
slice 4 lands second adds that row (PR #587 §4.3).

### 4.2 Layout

- Heading `fonts.section`; hint `fonts.hint`.
- When `storage` is `session`: `fonts.storage.sessionOnly` (a standing hint, not an alert).
- The list (`role="list"`): one row per font: the family names of its faces (`fonts.row.faces` with
  a count for a collection), the file name and size (`formatMegabytes`), "not loaded" when the sync
  could not load it (`fonts.row.notLoaded`), and a **Remove** button whose accessible name includes
  the font (`fonts.remove.label`). Empty: `fonts.list.empty`.
- Usage: `fonts.usage` "{used} of {max} used" from the worker's `used_bytes`/`max_bytes`.
- Buttons: **Upload font…** (`fonts.upload.button`) and **Remove all fonts…** (`fonts.removeAll`,
  off when the list is empty).
- A `role="status"` area for upload outcomes and a `role="alert"` one for failures, cleared at the
  next upload. While the sync runs, the list shows `fonts.loading` and the buttons are off.

### 4.3 The file picker

A hidden `<input type="file" multiple accept=".ttf,.otf,.ttc,.otc,font/ttf,font/otf,font/collection">`
labelled `fonts.upload.button`, cleared after each choice, as `CommentsImportDialog.tsx:181-191`
does. The types line `fonts.upload.accept` "TrueType and OpenType fonts (.ttf, .otf, .ttc, .otc), up
to {limit} each." sits under the button. Several files are added one after another; each gets one
outcome line.

### 4.5 Removal flow

Remove opens an inline confirmation in the row (the Clear all pattern, `PreferencesDialog.tsx:369-
391`: Keep takes focus, so Enter does not remove by accident). Remove all does the same at the
section's foot. During any font operation the section's buttons and the Privacy section's Clear
button are off (`busy`, §3.7). Removing is allowed with documents open: text already set keeps its
embedded copy; a later edit naming the font is refused by the guard and W6.8b's picker no longer
lists it.

## 8. Risks

1. **Start-up cost with many kept fonts.** 64 fonts, CJK among them, take seconds of worker time
   after start-up. One call at a time at idle bounds the delay to one `fonts.add`; the fontTools
   install happens only when a font is kept. If measured too slow, question 1's on-demand option.
2. **OPFS eviction.** Without `persist()`, the browser may evict best-effort storage under pressure;
   the fonts then vanish silently at the next load. `persist()` lowers the risk; the guide says to
   keep the font files.
3. **Two tabs, more than one worker's budget.** Each tab can keep up to 64 fonts; together OPFS can
   hold more. The extra fonts stay kept and show "not loaded" (§3.2 step 5); removing others frees
   room at the next sync.
4. **Private windows that keep OPFS only for the session.** Undetectable; covered by the guide.
5. **W6.8b depends on `ready()`, `bytes()` and `onRemoved`.** If 8b-3 lands first it needs slice 3;
   the interface in §3.1 is the contract.
6. **2b changes `fonts.list` faces to the catalogue's.** Same DTO, same filter rules; the library
   does not care.

## Questions for the owner

1. **When are kept fonts sent to a new engine?** At idle after every ready (start-up, Try again,
   restart), one at a time; or only on demand (when Preferences ▸ Fonts or the picker opens, or an
   edit names an uploaded font)? **Recommended: at idle after every ready**, as plan.md:214 and W1.5
   §7 say; on demand only if start-up measurements show a cost.
2. **Order of keeping: worker first, then OPFS?** **Recommended: yes.** Only accepted bytes are kept,
   and a refused file leaves nothing. A font the browser can't keep still works for the tab.
3. **Tell other tabs with a `BroadcastChannel` (ids only)?** **Recommended: yes** (~35 lines); without
   it, a removed font stays usable in another open tab until it reloads.
4. **Ask `navigator.storage.persist()` after the first kept font?** **Recommended: yes**, once per
   page, answer not shown (W1.1 §6). Chrome may grant it silently; Firefox may show its own prompt,
   which is the browser's, not ours.
5. **One record file per font, or one index file?** **Recommended: one per font**: no lock between
   tabs, and a cut-off write damages one font only.
6. **A font that fails at start-up.** Remove it only for permanent refusals (`INVALID_FONT`,
   `FONT_NOT_EMBEDDABLE`, `FILE_TOO_LARGE`, id mismatch) and keep it on anything else?
   **Recommended: yes.** User data is not deleted for an error a reload can fix.
7. **Where the upload UI lives.** Preferences ▸ Fonts now, the picker's row with 8b-3? **Recommended:
   yes**, as W1.5 §7 and W4.5 plan.
8. **The per-file limit on the main thread.** A hand copy of 50 MiB with a comment (as
   `MAX_IMAGE_BYTES`), or generate limits into `generated.ts`? **Recommended: hand copy now**; the
   worker check is authoritative and its reply carries `max_bytes`. Generating limits is a separate,
   app-wide change.
9. **Removal while documents are open.** Allowed (text already set keeps its embedded copy)?
   **Recommended: yes**; unlike Clear all, nothing is lost.
10. **Orphan bytes files** (a write cut off by a crash): delete them at `list` when older than one
    hour? **Recommended: yes**; younger ones may be another tab's write in progress.
