# W1.5: Editing tools in the browser

Stage: W1 (#134) · Role: design Opus 5.5; W6.7–W6.9 and W7.1 implement it (Haiku 5.5), reviewed by Sonnet 5.5 · Branch: `phase-w-w1.5-editing-tools` · Builds on [W1.1](W1.1.md) (workers, watchdog) and [W1.3](W1.3.md) (`content.*` and `annotations.*` actions, `ObjectRef`, `AnnotRef`). W1.2 owns the RPC envelope and W1.4 owns rendering, the text layer and text selection; this note refers to them and doesn't redefine them.

## Summary

The desktop's editing tools are thinner than the plan assumed. Hit testing is plain rectangle geometry over a list of page objects that is cached per page revision. The paragraph editor is a `QPlainTextEdit` laid over the block, showing the document's own font, and Python reflows the text only once, on commit (`Page.replace_text`). The web does the same: TypeScript hit-tests a per-revision object list fetched from the worker, and the paragraph editor is a native `<textarea>` with the page's font loaded through the CSS Font Loading API. **No keystroke goes to the worker**, so typing, IME, clipboard and in-editor undo are the browser's own and cost no round trip. Every change is one W1.3 action, and the worker never sees a gesture before it is complete.

## 1. Where each piece runs

| Piece | Runs in | Why |
|---|---|---|
| Page object list (`Page.content_objects()`) and comment list | worker, one call per page revision | the engine's object model; desktop caches it per revision too (`DocumentView.page_objects`) |
| Hit testing (which object or comment is under the pointer, handles) | TypeScript, over the cached lists | it's rectangle geometry; a round trip per mouse move would make hover feedback lag |
| Drag previews (move, resize, rubber band, shape and ink outlines, callout leader) | TypeScript, drawn on the overlay canvas of W1.4 | 60 fps feedback |
| Geometry that decides the committed result (fit matrix, default sizes, ink simplification, callout leader, stamp size, comment styles) | Python, in `actions` | shared with desktop; TS ports only what a preview needs to match (section 6) |
| Text typing, caret, selection inside the editor, IME, clipboard, in-editor undo | the browser, in a `<textarea>` | native, accessible and correct for every script and input method |
| Text layout and reflow of the edited paragraph | Python, on commit (`content.replace_text` / `content.add_text`) | the engine typesets with the PDF's font; desktop previews with Qt in the same way |
| Text selection on the page (for markup comments) | W1.4 | shared with copy and search |

This refines the plan's W1.5 line ("hit testing in the worker"): the *object model* stays in the worker, and the point-in-rectangle test runs on the front end over data the worker produced.

## 2. Hit testing and selection

**Data.** For each page the front end holds, keyed by `(handle, page, revision)`:
- `objects`: `PageObject` DTOs (`type`, `key`, `bbox`, `text`, `style`, `editable`, `reason`, `image_size`, `stroke`, `fill`), from `content.objects`;
- `comments`: `AnnotationModel` DTOs from `annotations.page`, **without** `image` and `file_data` (they can be megabytes; a `has_file`/`has_image` flag replaces them, and `annotations.file` fetches the bytes on request).

Both are fetched when a page with the Edit tool (or the Select tool, for comments) becomes visible, and refetched when an action reply or event reports a new revision for that page (W1.2 events, W1.4 invalidation). Revision-keyed entries are dropped when the revision moves on, so a stale list can't be hit-tested. The lists are small (a busy page has a few hundred objects), so no extra limit beyond W1.4's page cache.

**Rules (ported 1:1 from desktop, with shared test vectors, section 6):**
- `objectAt(page, p)`: of the objects whose `bbox` inflated by 2 screen pixels contains `p`, the one with the smallest area (an image wins over a large text block). `DocumentView.object_at`.
- `commentAt(page, p)`: the topmost (last in list order) comment, skipping replies, popups, non-comment types and hidden ones (`flags & 2`), whose bounds inflated by 3 screen pixels contain `p`. `DocumentView.annotation_at` and `annotation_bounds`.
- `handleAt`: with exactly one object selected, the 8 handles of its box (corners and edge midpoints), within 6 screen pixels. `edit._handles`, `HANDLE_PX`.
- Rubber band: objects whose `bbox` intersects the dragged rectangle.
- Cursor: I-beam over editable text, "not allowed" over non-editable text (with the `reason` as a tooltip), move cursor over other objects, resize cursor over a handle.

**Selection** is a list of `(page, key)` (objects) or `AnnotRef` (comments), held in the front end's document state. After a committed edit the keys change (they are valid for one revision), so the front end reselects the objects closest to where they went, as `EditObjectsTool._reselect` does, once the new list arrives.

## 3. Moving, resizing and deleting objects (W6.7a)

- **Move:** drag a selected editable object. The preview draws each box translated. On release, a drag below 0.5 pt in both axes is a click; otherwise `content.transform` with the selected `ObjectRef`s (each carrying the revision of the list it came from) and the matrix.
- **Resize:** drag a handle of a single selected object; the box's opposite edges stay put, minimum 4 px; the matrix maps the old box onto the new one (`_fit`). Committed as `content.transform`.
- **Rotate:** not offered. The desktop has no rotation handle and `transform_objects` re-typesets text at its new place; rotation would be a new feature for both apps, not a port.
- **Delete:** Delete or Backspace with objects selected → `content.delete`.
- **Image:** Replace (pick a file → `content.replace_image`), Export (`content.image_data` → download, name `image.<ext>` through `safe_name`).
- **Stale objects:** if the page changed between picking and releasing (for example an undo arrived), the action replies `STALE_OBJECT` (W1.3); the front end refetches the list, keeps no selection and shows "The page changed; try again." Nothing is applied.
- **Signed documents:** the first content edit of a signed document asks "Edit a Signed Document?" as `EditController.confirm_signed` does, once per document. `document.info` (W3.2) already reports `has_signatures`.

## 4. Adding text, images and shapes (W6.7b, W6.8a)

All use the desktop's `_RectTool` gesture: drag a rectangle on one page, or click for a default size (text 200×40 pt, image 200×150 pt, shape 120×80 pt), clamped to the page.

| Tool | After the gesture | Action |
|---|---|---|
| Add Text | opens the paragraph editor (section 5) on the rectangle, empty, with the style used last; clicking existing editable text edits it instead | `content.add_text` on commit, if the text isn't blank |
| Add Image | file picker (PNG, JPEG, TIFF, BMP, GIF, WebP) | `content.add_image` with the bytes and the rectangle |
| Rectangle, Ellipse, Line | none | `content.add_shape` with a `ShapeSpec` (stroke black, width 1.5, no fill; a line uses the two drag points) |

Creation tools are one-shot as on desktop: after a successful add the tool returns to Select.

## 5. The paragraph editor (W6.8a, W6.8b)

### Behaviour (port of `ui/view/text_editor.py`)

| Desktop (`InlineTextEditor`) | Web |
|---|---|
| `QPlainTextEdit` over the block, pale yellow background hiding the page text beneath, word wrap at the box width | `<textarea>` absolutely positioned over the block in the page overlay, same background, `white-space: pre-wrap`, `overflow-wrap: anywhere` |
| Box at least one line tall and 120×40 px | same minimums, from the font's line height |
| Opened with all text selected | same |
| Ctrl+Enter commits; Escape cancels; focus leaving the editor and its style bar commits | same; "leaving" ignores focus moving into the style bar, its pop-ups and the colour picker |
| Commits only if text or style changed | same (compare against the opening text and style) |
| Wheel scrolls the box's text when it overflows, else the page; Ctrl+wheel zooms the page | same; the editor forwards those wheel events to the viewport (W1.4 zoom) |
| Follows the page when zooming (re-placed and re-fonted) | same, on W1.4's zoom events |
| Ctrl+Z inside the editor undoes typing | the textarea's native undo; Ctrl+Z reaches the document's undo only when the editor is closed |
| IME, dead keys, clipboard | native; composition events need no handling, since nothing is sent before commit |

The editor has `aria-label` "Edit text" and the style bar is a labelled toolbar (W1.6 owns the patterns).

### The preview font

The desktop shows the block in the document's embedded font: `Page.font_program(name)` gives the program, `_private_copy` (fontTools) rejects a program without a `cmap` (MuPDF drops it when it subsets on save, and no renderer could map characters with it), and the font is registered privately. The web does the same with the CSS Font Loading API:

1. `content.preview_font(handle, page, font_name)` returns the program bytes, or nothing when it has no `cmap` or fontTools can't read it. The check moves from `ui/view/text_editor.py` to `services/fonts.py` as `preview_font_program(data) -> bytes | None` (W6.8a's Python part; the desktop's `_private_copy` calls it and keeps its Qt-specific renaming).
2. The front end loads it as `new FontFace("pdf-<sha1[:12]>", bytes)`; the family name is private to the page, so it can't shadow anything. A face the browser's font sanitiser rejects (bare CFF, Type 1) falls back as in step 3. Loaded faces are cached by hash for the tab's life.
3. Fallbacks, as desktop minus installed fonts: an uploaded font that matches the name (`installed_ref_for_font_name` over the upload catalogue), else the CSS generic family closest to the name (`family_of`: `sans-serif`, `serif`, `monospace`). The preview is a preview: the committed text is typeset by the engine with the real font.

### Style bar and font picker (W6.8b)

The bar above the editor carries font, size, bold, italic, colour and alignment, as `TextStyleBar`. The font picker lists three sections: **In this document** (`document.fonts`, names), **Standard** (Helvetica, Times-Roman, Courier, as `STANDARD_FONTS`), and **Uploaded** (the font catalogue of section 7). It has no "Installed" section (`system_fonts` off, W1.1 §3). Choosing a font sets `TextStyle.font_ref` (`STANDARD`, `DOCUMENT` or `FILE`); for an uploaded font the `FILE` ref's `path` is the worker's id for it (section 7). Bold and italic switch to the family's matching face when the catalogue has one, else they set the style flags.

### Commit and the substitution notice

Commit runs `content.replace_text(ObjectRef, text, style)` for an existing block or `content.add_text(page, rect, text, style)` for a new one. Both return a `FontChoice` (W1.3). When `substituted` is true the front end shows the desktop's notice: "The document's font can't show this text in this style; used *name* instead (missing: *chars*)." (message catalogue, W4.7). Refusals (`UnsupportedFeature`, `EngineError`, `STALE_OBJECT`) show as an error toast and leave the document unchanged. The toast offers "Copy text", so what the user typed isn't lost.

## 6. Comment tools (W7.1a)

Each desktop tool (`ui/tools/annotate.py`, `tool_for`) and how the web builds it:

| Tool | Gesture (TS) | Result |
|---|---|---|
| Highlight, Underline, Strikethrough, Squiggly | text selection (W1.4); applied on release, or from the contextual bar for an existing selection | one comment per page with the selection's quads; the first carries the selected text |
| Sticky note | click | note icon at the point, then the note popup |
| Text box | drag (default 180×40) then text | FreeText, black text, 12 pt |
| Callout | click the tip, drag the box, then text | FreeText with a leader line (`callout_line`) and an arrow at the tip |
| Pen | freehand stroke | ink, simplified with `simplify(points, 0.6)` |
| Rectangle, Oval, Line, Arrow | drag | square/circle/line; arrow = line with an open arrow at the end |
| Polygon, Polyline | click vertices, double-click to finish | polygon/polyline |
| Stamp | pick a standard or custom image stamp, click | stamp, 160×50 pt or `stamp_rect` for an image |
| Attach file | click, pick a file | file attachment with the file's name and bytes |

**Python builds the comment.** On desktop each tool builds the `AnnotationModel` itself (`new_model`, the `STYLES` table, `simplify`, `callout_line`, `stamp_rect`, the default sizes). To keep that logic in one place, W7.1a starts with a Python slice that moves these builders into `pdfeditor.actions.comment_tools` (`build_markup`, `build_note`, `build_text_box`, `build_callout`, `build_ink`, `build_shape`, `build_polygon`, `build_stamp`, `build_attachment`), moves the desktop tools onto them, and adds one action, **`annotations.create`**, whose args are the tool name, the page, the gesture's points, the text, the author and the tool's extra input (stamp name, image bytes, file name and bytes). It builds the model with the shared builder and executes the same `AddAnnotationCommand` as `annotations.add`, with the desktop's label ("Add Drawing", "Add Callout"...). If W2.1 slice (b) hasn't merged when W7.1a starts, the builders go in with slice (b) instead; either way the desktop uses them.

**What TS ports for previews**, with test vectors generated from the Python functions (a JSON file per function in `web/src/tools/vectors/`, written by a script in `scripts/` and checked with `--check` in CI, like `make_shortcut_docs.py`): `callout_line` and the callout default box, the resize `_fit` matrix, and the hit-test rules of section 2. Previews of ink, shapes and polygons are plain polylines and rectangles. A preview that drifts from Python only changes the drawing during the drag, never the stored result.

**Comments after creation** use the W1.3 actions: `annotations.transform` (Select tool move/resize, as `select._finish_annotation_drag`), `annotations.restyle` (contextual bar and inspector, with `merge_key`), `annotations.set_text`, `annotations.reply`, `annotations.reorder`, `annotations.delete`, `annotations.flatten`. Locked comments can't be moved, restyled or deleted, as on desktop.

## 7. Fonts (W6.9)

- **Upload:** the user picks TTF, OTF, TTC or OTC files (Preferences ▸ Fonts, or "Upload font…" in the font picker). The main thread checks the size (at most 50 MB per file), then sends the bytes to the worker with `fonts.upload(name, bytes)`. The worker writes them to the MEMFS font folder, reads them with the existing `read_faces` (fontTools), and refuses a file with no usable face (`INVALID_FONT`) or whose faces all forbid embedding (`FONT_NOT_EMBEDDABLE`, from `_embeddable`, the `fsType` check). On success it returns the faces, and the main thread stores the file in OPFS `/fonts/` (W1.1 §6).
- **Start-up:** the main thread sends the OPFS fonts to the worker after it starts (`fonts.load`, the same validation), so the catalogue is ready before the first edit; the viewer doesn't wait for it.
- **Catalogue:** `FontCatalog` scans only the upload folder on the web (W2.3's font source item). Its faces cross as DTOs (family, style, weight, italic, scripts, embeddable) plus an opaque `id`, which is the `FILE` ref's `path` inside the worker. Actions accept a `FILE` ref only when its path is inside the upload folder (`INVALID_ARGS` otherwise), so the front end can't name arbitrary MEMFS files.
- **Removal:** `fonts.remove(id)` and "Remove all fonts" (W1.1 answer 2) delete the file from MEMFS and OPFS. Text already typeset with the font keeps its embedded copy in the document.
- Licensing: embedding follows the font's `fsType` exactly as on desktop; the web adds nothing.

## 8. Calls

Names and deadline classes as reconciled in [W1.2 §17](W1.2.md): `snake_case` fields, documents named by `handle`, the W1.2 deadline classes.

The envelope, error format, binary transfer and deadline values are W1.2's. Deadline classes here: **interactive** (the user waits with the pointer down or right after release), **edit** (an action that may take longer on a big page), **background**.

| Call | Args | Reply | Binary | Deadline class |
|---|---|---|---|---|
| `content.objects` | handle, page | revision, `PageObject[]` | no | interactive |
| `content.image_data` | handle, `ObjectRef` | extension | out: image bytes | background |
| `content.preview_font` | handle, page, font name | found or not | out: font program | interactive |
| `document.fonts` | handle | font names used in the document | no | background |
| `annotations.page` | handle, page | revision, comment DTOs without file and image bytes | no | interactive |
| `annotations.file` | handle, `AnnotRef` | file name or image type | out: bytes | background |
| `fonts.upload`, `fonts.load` | name | faces, or `INVALID_FONT` / `FONT_NOT_EMBEDDABLE` | in: font file | background |
| `fonts.list` | — | uploaded faces | no | interactive |
| `fonts.remove` | id | — | no | background |
| `actions.run` with `content.*`, `annotations.*` (W1.3) and `annotations.create` (this note) | action name, args | `ActionResult` and change events (W1.2) | in: image, file or stamp bytes where the args have them | edit |

New error codes for W1.2's table: `INVALID_FONT`, `FONT_NOT_EMBEDDABLE`.

## 9. Latency budgets

Measured in W8.3 on the 200-page fixture, local machine, as p95:

| Interaction | Budget | How |
|---|---|---|
| Keystroke to glyph on screen, in the editor | one frame (16 ms) | native textarea, no RPC |
| Hover feedback (cursor, outline) | one frame | cached lists, TS hit test |
| Drag preview | 60 fps, no RPC during the drag | overlay canvas |
| `content.objects` for one page | 50 ms | measured in W6.7a; if it's slower on dense pages, prefetch the neighbours of the visible page |
| Editor open (double-click to caret, with the preview font) | 150 ms | `content.preview_font` in parallel with placing the box; show the fallback family until the face loads |
| Commit to re-rendered page | 500 ms | action plus W1.4's re-render of the visible tiles |

## Questions for the maintainer

**Answered 2026-11-17: all three as recommended.**

1. **No per-keystroke round trip.** The editor previews in the browser and Python reflows on commit, exactly like desktop. The plan's wording suggested layout from the worker while typing, which would add a round trip per keystroke and complicate IME. Recommended: as written.
2. **No rotation handle.** The desktop has none; adding one is a new feature for both apps. Recommended: leave it out, as on desktop.
3. **A new action, `annotations.create`,** so the web sends gestures and Python builds the comment with the desktop's own rules (styles, ink simplification, callout leader, stamp size). The alternative, building `AnnotationModel`s in TypeScript and calling `annotations.add`, would duplicate those rules. Recommended: add the action.
