# W6.3b: Combine reports real progress

Stage: W6 · Role: design Opus 5.5 · Branch: `phase-w-w6.3b-combine-progress` · Inputs: [W1.2](W1.2.md) section 8 (progress notices), [W1.6](W1.6.md) section 10 (job bar), `src/pdfeditor/webapi/jobs.py`, `src/pdfeditor/webapi/jobworker.py`, `src/pdfeditor/services/assembly.py`, `web/app/src/engine/`, `web/app/src/files/fileJob.ts`, `web/app/src/combine/`, PLAN.md W6.3 note.

PLAN.md's W6.3 note says: "progress is indeterminate because the job worker's progress notices are not sent to the page yet". This slice makes the combine job's bar determinate. It does not add page ranges, a bookmarks toggle or a real abort; those stay in the W6.3 note.

## 1. What already exists (reuse, do not invent)

Most of the path is already built and tested by split, reduce, export and print:

| Step | Where | State today |
|---|---|---|
| Service reports progress | `services/assembly.py` `merge(...)` calls `progress(n + 1, len(sources))` after each source | works |
| Job passes it on | `webapi/jobs.py` `_run_merge` passes `ctx.progress` to `merge` | works |
| Notice is shaped and throttled | `webapi/jobworker.py` `_Progress`: `{"v": 1, "notice": "progress", "id": <request id>, "data": {"done", "total", "status"}}`, at most one per 100 ms, the final one (`done >= total`) always sent | works |
| Pyodide to JS | `engine/loader.ts` job adapter (`withNotices`), `parseNotice` | works |
| Worker to page | `engine/worker-server.ts` posts `{kind: 'notice', id, notice}`; `engine/start.ts` routes it to the waiting call's `onNotice` and drops it once the call has ended | works |
| Notice to percent | `files/fileJob.ts` `progressPercent(notice)` (0 to 100, ignores other notices and `total <= 0`) | works |
| Bar | `feedback/jobRun.ts` `store.progress(token, percent)`; `JobProgress.tsx` is determinate once `percent` is set, text `job.percent` ("{percent}% done") | works |
| **Combine call** | `combine/merge.ts` `runMergeJob` calls `worker.call(request, buffers)` **without `onNotice`** | **gap** |
| **Combine flow** | `combine/run.ts` never calls `store.progress` | **gap** |

So no new message shape, no protocol change, no change to `rpc/generated.ts`. The notice is the W1.2 section 8 `progress` notice, unchanged.

## 2. What fraction is reported

**Unit: sources, plus one step for writing the result.** The merge loop works one source at a time (`insert_pages` per source), so a source is the finest step the service can report without changing `assembly.py`, which the desktop also uses. Pages would need every source opened up front to learn the total; see question 1.

Today the service's last notice (`done == total`) arrives before `set_outline` and `merged.to_bytes()`, which for a large result is a noticeable part of the job, so the bar would sit at 100% while work goes on. `_run_merge` therefore reports on a scale of `N + 1` steps (N = number of sources), the same way `_run_reduce` shifts its steps with `_shifted`:

- `ctx.progress(0, N + 1)` before writing the sources to the temporary folder, so the bar turns determinate at 0% at once (the throttle always lets the first notice through);
- the service's `(n + 1, N)` becomes `(n + 1, N + 1)` through a small local wrapper (not `_shifted`, whose step count is fixed to the reduce's five);
- `ctx.progress(N + 1, N + 1)` after `to_bytes()` returns.

**Rule: the last notice of a successful merge is `done == total`, that is 1.0, and it is sent after the bytes exist.** No notice is sent after it. A failed or cancelled merge ends without it. `done` never decreases.

Estimate: about 15 changed lines in `jobs.py`.

## 3. Forwarding in the worker to the page

Nothing to add in `engine/`: the job worker already forwards each notice with the call's id. The change is on the page side:

- `merge.ts`: `runMergeJob(worker, sources, onProgress?: (percent: number) => void)`. It passes an `onNotice` to `worker.call` that runs `progressPercent(notice)` and calls `onProgress` when the result is defined. Other notices are ignored, as in `fileJob.ts`.
- `run.ts`: passes `(percent) => deps.store.progress(token, percent)`. The store already ignores a token that is not the running job's, so a late notice after Cancel or after `finish` is harmless; `start.ts` also drops notices for a call that is no longer waiting.
- `progressPercent` is imported from `files/fileJob.ts`; no copy. (Question 2 asks whether to move it.)

Estimate: about 10 lines in `merge.ts`, about 5 in `run.ts`.

## 4. The dialog

The determinate bar is the app's job bar (`JobProgressHost`, mounted in `App.tsx`), as it is today for combine and for split, export and compress. The dialog does not draw a second bar. Its text:

- While `phase === 'working'`, the dialog shows a `role="status"` line with a new key `combine.running`: "Combining the files. The progress bar shows how far it has got." This matches `split.running`, `export.running` and `compress.running`.
- The bar's own text is the existing `job.working` ("Working") until the first notice, then `job.percent` ("{percent}% done"). With the 0 notice of section 2, "Working" shows only for the moment before the job worker boots and starts the job.
- No other new keys. `combine.label` stays the bar's label.

Estimate: about 6 lines in `CombineDialog.tsx`, 1 in `i18n/en.ts`.

## 5. Cancel, stated plainly

Cancel does not change. Merge has no `jobs.prepare`, so it has no `jobs.abort`; the bar's Cancel calls the `terminate` the flow registered, which **terminates the job worker**. The merge stops wherever it is, nothing is returned, and `runCombine` returns `{status: 'cancelled'}`. The Python cancel token is never seen by a merge in the browser. Progress does not make Cancel any gentler: it only shows how far the job had got before it was killed. A fresh job worker is started for the next combine, as today.

## 6. Test plan

**Python (host and Pyodide), `tests/unit/test_webapi_jobworker.py`:**

1. `test_job_run_merge_reports_progress_ending_at_the_total`: `job.run` merge of three sources (two PDFs, one image) through `jobworker.dispatch` with a notice sink. Asserts: every notice is `notice == "progress"` with the request's id; the first is `done == 0`; `total == 4` on all of them; `done` never decreases; the last is `done == total`; the reply is `ok` with a `new_document`. The merged bytes are checked with `record("page_count_pikepdf", out[0], pages=...)`.
2. `test_a_merge_cancelled_after_its_first_notice_is_cancelled`: a `notify` that cancels the token on the first notice (the pattern of `test_a_split_cancelled_during_its_run_stops_after_the_first_part` in `test_webapi_job_types.py`) gives `CANCELLED`, and no notice has `done == total`.

Throttling can drop middle notices, so the tests assert the first, the last and the order, not the count. If the run is fast enough to throttle everything but the first and last, the tests still pass.

**Host checks and skip budget (AGENTS.md).** These modules already avoid importing pikepdf or pypdfium2 at module level and use `tests.hostcheck.record` with the host half in `scripts/web_host_verify.py`. **Vitest:**

## 8. Risks

- **One big source dominates.** With per-source steps, a 500-page source among small ones holds the bar still for most of the job. Acceptable for this slice; question 1.
- **Writing the sources to the temp folder** happens after the 0 notice and before the first source step; with big inputs it is a pause at 0%. It is short compared with the merge itself, so no separate step.
- **Desktop callers of `merge`** are untouched, since the service does not change; only the web job rescales.
- **Notices after Cancel** cannot move a bar: `start.ts` drops them once `terminate` fails the pending call, and the store ignores a token that is not running. Covered by the `run.test.ts` test.
- **Import direction in the web app.** `combine/` importing from `files/fileJob.ts` adds a dependency between two feature folders. Harmless today; question 2.
- **Throttling hides steps** for fast merges. The final notice is never throttled, so the 1.0 rule holds.

## Questions for the maintainer

1. **Sources or pages as the unit?** Recommended: sources plus one write step, as above. Pages need `assembly.merge` changed (or every source opened twice) and a page count read before the job, for a smoother bar only on uneven inputs. Revisit if users report a stuck bar.
2. **Move `progressPercent` to `feedback/jobRun.ts`?** Recommended: yes, in this slice, as a two-line move with `fileJob.ts` re-importing it, since the bar's store is its natural home and it then serves every job flow. If the maintainer prefers the smallest diff, import it from `files/fileJob.ts` instead.
3. **Show "file 2 of 5" in the dialog instead of the generic running line?** Recommended: no. The notice's `total` includes the write step, so the count would read oddly at the end, and the sibling dialogs use the generic line; the percentage is on the bar.
4. **Give merge a real abort (prepare/abort) instead of terminating the worker?** Recommended: not in this slice. Terminating is what W3.7 decided for document-less jobs, it is immediate, and a fresh worker is cheap compared with the merge. Keep it in the W6.3 partial note as is.
