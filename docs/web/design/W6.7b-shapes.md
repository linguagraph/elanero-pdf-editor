# W6.7b slice 1: add shapes (rectangle, ellipse, line)

Stage: W6 · Role: design Opus 5.5; implementation Haiku 5.5, review Sonnet 5.5 · Branch: `phase-w-w6.7b-shapes` · Builds on [W1.5](W1.5.md) §2–4 (gesture, defaults, one-shot tools), [W1.3](W1.3.md) (`content.add_shape`), W6.7a (Edit tool, object cache, `edit/commit.ts`) and W7.1a (the comment layer's drag code, which this slice reuses).

## Summary

The engine side already exists and is tested: `ShapeKind`/`ShapeSpec` (`model/objects.py`), `Page.add_shape` (`engine/base.py`, `engine/mupdf/content.py`), the action `content.add_shape` (`actions/content.py`, a `SnapshotCommand` with the desktop's undo labels "Add Rectangle", "Add Ellipse", "Add Line") and a round trip for a filled rectangle (`tests/actions/test_content.py::test_round_trip_add_shape`). `actions.run` already converts the nested args (`from_json` handles the enum, `Color | None`, `Rect`, `Point`). So slice 1 is almost all front end: three tools on the Edit tab that draw a box (or two points) on one page and send one `actions.run`, plus a few lines of Python validation and the tests the existing round trip doesn't cover (ellipse, line, rotated page, the RPC path). Probing for this note found a **pre-existing engine bug on pages that are both rotated and cropped** (section 2.3); it is not fixed in this slice (Question 1).

## 1. The action and its arguments

Unchanged name and shape (W1.3): `content.add_shape`, args `AddShape(page: int, spec: ShapeSpec)`.

| Field | Type | Web sends | Notes |
|---|---|---|---|
| `page` | int | the page under the gesture (0-based) | `_check_page` refuses a page that doesn't exist |
| `spec.kind` | `"rectangle" \| "ellipse" \| "line"` | the tool | enum value strings |
| `spec.rect` | `{x0,y0,x1,y1}` visible-space points | rectangle and ellipse: the dragged box ∩ page | ignored for a line |
| `spec.start`, `spec.end` | `{x,y}` visible-space points | line: the press and release points | ignored for a box |
| `spec.stroke` | `{r,g,b,a}` or null | `{r:0,g:0,b:0,a:1}` | alpha is ignored by the engine (`Color.rgb()`) |
| `spec.fill` | `{r,g,b,a}` or null | null (a line never has one) | |
| `spec.width` | float, points | 1.5 | |

The web sends the desktop's fixed style (`AddShapeTool`: black, 1.5 pt, no fill), because the desktop has no shape-style UI either; stroke, fill and width stay in the args so a later style bar needs no RPC change. No change to `generated.ts`: `RunParams.args` is an untyped object, so the TS side gets a small typed builder (`edit/shapes.ts`, section 5).

**New validation in `actions/content.add_shape`** (about 12 lines, shared with desktop, before the snapshot): refuse (`Refused`) a `width` outside `0 < width ≤ 72`; a rectangle or ellipse whose `rect` is not normalised or has zero width or height; a line whose ends coincide. Web input is untrusted, and today a zero-area box or `width: 0` would write a valid but invisible path that still costs an undo snapshot. `from_json` already rejects NaN and infinities. Coordinates off the page are not refused (a PDF may draw outside its crop box; the web clamps before sending).

## 2. How the path is written

### 2.1 Where the code lives

`engine/mupdf/content.add_shape` (PyMuPDF is allowed only there), reached through `Page.add_shape`, which first calls `unshare_page` (copy-on-write for pages that share content, tested in `tests/engine/test_shared_objects.py`). No services module: there is no logic between the action and the engine. This slice does not change the drawing code.

### 2.2 Operators and colour spaces

PyMuPDF's `Shape` appends a new content stream (`commit(overlay=True)`), wrapping the existing content in `q … Q` so its graphics state can't leak into the shape. Each shape is its own `q … Q` block. Probed output (PyMuPDF 1.28.2):

| Kind | Path | Paint |
|---|---|---|
| rectangle | `x y w h re` | `S` (stroke only), `B` (stroke and fill), `f` (fill only) |
| ellipse | `m` then four `c` Béziers (κ ≈ 0.5523) | as above |
| line | `m` `l` | `S` |

Before the paint: `<width> w`, then `r g b RG` (stroke) and `r g b rg` (fill). Colours are **DeviceRGB**; no ICC profile or `/ColorSpace` resource is added. No `ExtGState` is written, since alpha is ignored (opacity is deferred).

### 2.3 Coordinate transform and the rotated-and-cropped bug

> Fixed by the engine change for issue #537 (`engine/mupdf/space.py`, design `rotated-crop-placement.md`). The strict xfail is removed.

Above the engine, coordinates are visible space (AGENTS.md). `add_shape` maps each point with `page.derotation_matrix` into MuPDF's unrotated space, and `Shape` then applies the page's `transformation_matrix` (the y flip and the crop-box offset). This is correct for unrotated pages (cropped or not) and for rotated pages without a crop box. Probing with pypdfium2 renders of a fill-red 100×60 box at visible (100,100):

| /Rotate | CropBox (36,50,559,806) | Drawn at (pdfium) | Listed by `content_objects` |
|---|---|---|---|
| 0, 90, 180, 270 | none | (100,100) ✓ | (100,100) ✓ |
| 0 | yes | (100,100) ✓ | (100,100) ✓ |
| 90 / 180 / 270 | yes | (64,64) / (136,64) / (136,136) ✗ | (100,100), wrong the same way |

PyMuPDF's `transformation_matrix` on a rotated page with a crop box drops the crop offset (on the probe page it reads `1 0 0 -1 0 756` at /Rotate 90, where /Rotate 0 gives `1 0 0 -1 -36 792`). Because `Page.pdf_matrix` and the `content_objects` reader use the same matrices, the writer and the lister agree with each other but not with the pixels, so the existing desktop shape tool, `add_text`, `stamp_image` (same `derotation_matrix` path in `pages.py`) and W6.7a's outlines are all off on such pages. A mapping that computes PDF user space directly (`x = crop.x0 + u.x`, `y = media.y1 − (crop.y0 + u.y)`, with `u` the derotated point) put the box right in all eight cases, but fixing only the writer would make the lister disagree with what it just wrote. It is an engine-wide fix with its own tests, so it doesn't belong in this slice (Question 1). Slice 1 adds a strict `xfail` test on `off_page_text` page 1 (rotation 90, crop box 50,50,550,750) that turns green when the engine fix lands.

## 3. The Command and its inverse

`content.add_shape` uses the shared `snapshot()` helper, so it runs in a disk-backed `SnapshotCommand` (in MEMFS on the web, within `WEB_SNAPSHOT_BUDGET`). Keep it. The add looks reversible (append a stream, then remove it), but it isn't, for three reasons:
- `commit(overlay=True)` also changes the existing content (the `q … Q` wrap), so the inverse would have to undo edits to streams it didn't create;
- `unshare_page` may copy shared content and resources first, and the inverse would have to re-share them;
- AGENTS.md rule 5 names content edits as `SnapshotCommand` operations, and every other `content.*` action is one, so undo and redo behave the same for all edits on a page.

The cost is a full in-memory save before each shape, plus another on the first undo. On a large document that is slow, and it is the same cost W6.7a's move already pays. A reversible "append content stream" command can come later if W8.3 measures it as a problem (listed under Risks).

## 4. Page revision and cache invalidation

- `engine/mupdf/content.add_shape` ends with `mark_page_changed(page.index)`: that bumps the page revision, drops the cached `MuPage` (`page.invalidate()`) and marks the sharing map dirty.
- `SnapshotCommand.changes()` reports `STRUCTURE`, so `webapi/events.changed_of` returns the revision of every page in `RunResult.changed.revisions`. Only page `page` actually moved. The front end passes the map to `scheduler.noteRevisions`, which re-renders the tiles of pages whose revision changed (W5.1b). The text layer and the W6.7a object cache are keyed by revision, so their old entries are never used again.
- Undo through the toast: `offerUndo`'s `onUndone` calls `noteRevisions(undone.changed.revisions)` and clears the edit object cache, as `edit/commit.ts` does (a snapshot restore reloads the document).
- No new cache and no new invalidation path.

### 5.2 Toolbar entry

The Edit tab already has the group `edit.shapes` with the commands `add-rectangle`, `add-ellipse` and `add-line` (labels "Rectangle", "Ellipse", "Line"), currently without handlers. This slice wires them, and the command palette and shortcuts get them for free. Each command is a toggle: choosing the tool that is on returns to Select. The tool is per tab (`viewTool.ts` module state) and mutually exclusive with Hand, crop box and Edit.

### 5.3 Drag maths

The same as the desktop `_RectTool.release`, reusing `comments/coordinates.ts` (`pagePointAt`, `rectBetween`, `cssBox`) and `edit/hitTest.ts` (`isClick`, `MIN_DRAG = 3`):

1. Press (button 0) on page `p`: `a = pagePointAt(offset, zoom, w, h)` (visible-space points, clamped to the page). Capture the pointer (`setPointerCapture`), so a drag that leaves the page keeps tracking. The comment layer instead ends the drag on `pointerleave`, which would cut a shape short.
2. Move: `b = pagePointAt(…)`. Preview `rectBetween(a, b)` for a box, or the segment a→b for a line.
3. Release: if `isClick(a, b)`, then `b = a + (120, 80)` (the desktop default size for all three kinds; a clicked line is that diagonal).
4. Box: `rect = rectBetween(a, b) ∩ [0,w]×[0,h]`. Line: `start = a`, `end = clamp(b)` to the page. The desktop leaves the default end unclamped; clamping keeps every point on the visible page. If the box has zero width or height after clamping (a click on the right or bottom edge), nothing is sent.
5. Escape during a drag cancels it with no RPC.

The page's zoom and size come from `DocumentView`, as for `CommentLayer`. The web has no view rotation, so visible space is the page box as drawn, and the engine handles /Rotate (section 2.3).

### 5.4 Keyboard fallback

Only the current page's `ShapeLayer` is focusable (`tabIndex=0`, the others `-1`), with `role="application"` and an `aria-label` (`edit.shape.layer`). Enter or Space places the default-size shape (box `(cx−60, cy−40, cx+60, cy+40)`, a line along that box's diagonal), centred on the page. Escape turns the tool off. Turning the tool on from the ribbon or palette does not move focus. F6 reaches the page region (W1.6), and Tab then reaches the layer. Placement by arrow keys is deferred (Question 3).

### 5.5 After the add

`addShape` sends one `actions.run`. On success it calls `noteRevisions`, offers Undo with the toast `edit.shape.added`, and sets the tool back to Select (W1.5 §4: one-shot). `BUSY` or `NOT_SUPPORTED`/`INVALID_ARGS` go through `reportRpcError`, and anything else shows `edit.failed`. The tool stays on after a failure, so the user can retry. A tab whose document is signed asks "Edit a signed document?" once per tab (shared with W6.7a), before the tool turns on.

## 10. Risks

- **Rotated and cropped pages** (section 2.3): shapes land offset by the crop origin, on desktop too. Scanned and imposed PDFs often have both. Mitigation: the strict xfail and the separate engine fix.
- **Snapshot cost on the web:** every shape saves the whole document into MEMFS. On a document near the 512 MiB snapshot budget, a few shapes evict older undo steps, and the save takes seconds under Pyodide (the `action` deadline class gives 30 s). Measured in W8.3; if it hurts, the reversible command.
- **`STRUCTURE` change on every add:** the reply lists every page's revision. Only the edited page re-renders (the others keep their revision), but a 2,000-page document sends a 2,000-entry map. Acceptable; if it isn't, `snapshot()` could take `changes=[Change(CONTENT, {page})]`, but `SnapshotCommand.changes()` prepends `STRUCTURE` anyway. Not changed here.
- **Signed documents:** a shape invalidates the signatures, as any content edit does. Covered by the shared warning, and saving stays incremental (AGENTS.md rule 7).
- **Overlay wrap:** `commit(overlay=True)` wraps existing content in `q … Q`. A malformed content stream with unbalanced `Q`s could render differently after the wrap. This is MuPDF behaviour already shipped on desktop, and the round trip on pikepdf and pdfium guards the common case.
- **Tool-state growth:** `ViewTool` gets three more values, and every `viewTool === …` check must stay exhaustive (`textLayerPassive`, CSS classes, the crop-box exit). Use a `isShapeTool(tool)` helper instead of three comparisons.

## Questions for the maintainer

1. **Rotated and cropped pages.** The engine places shapes (and text, stamps and the object list) off by the crop origin on pages that are both rotated and cropped, on desktop too. Recommended: open an issue now, fix it in a separate small engine PR (a crop-aware visible↔PDF mapping in `engine/mupdf`, used by the writers and by `content_objects`/`pdf_matrix`, with a rotation × crop matrix of tests), and land this slice with a strict xfail that the fix turns green. Fixing only `add_shape` here would make the lister disagree with what it just wrote.
2. **Lines in slice 1?** Recommended: yes. The action supports them, and the extra front end is about 20 lines, well within the budget.
3. **Keyboard fallback scope.** Recommended: Enter/Space for a default-size shape at the page centre, and Escape to stop, in this slice; arrow-key nudging comes later with W6.7a's keyboard move (the Edit tool has none either), so both tools get it in one change.
4. **Validation in the shared action** (width in (0, 72], non-empty box, distinct line ends). Recommended: yes, in `actions/content.py`, so the desktop gets it too. The desktop UI never sends such specs, so nothing changes for desktop users.
5. **After an add, back to Select or to the previous tool (for example Edit)?** Recommended: Select, as W1.5 §4 and the desktop's `tool_used` do; a "keep tools" preference is a separate, later item.
