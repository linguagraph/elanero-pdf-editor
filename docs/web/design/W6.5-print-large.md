### 2.1 The multi-page defect

`_run_print` returns one `FileDto` per page, and `dto.to_json` gives each its own marker (`$bin` 0, 1, 2, …). The job worker's reply carries all of them (`buffers`, loader.ts:258). `runPrintWorker` (printWorker.ts:52) reads only `result.buffer` and fails any file whose marker is not 0 ("only one binary value can cross"), so any range of two or more pages ends in an `INTERNAL` toast. The unit test hides it: `printJob.test.ts` fakes every page as `$bin: 0`. The e2e spec's header already names the cause. The design below removes the final-reply path for pages, which fixes it; §3.4 keeps a correct reader for the final reply anyway.

## 2. What stays as it is

- All prints run in the job worker (item 1). Moving 10 pages or fewer to the engine worker would add a second code path and block viewing during the render, for no gain the user would notice; see question 1.
- The iframe path (`printImages`) is unchanged: blob URLs are made only once all pages are in hand, and revoked on `afterprint`. All pages must exist when `print()` is called (W1.4 §11), so streaming bounds the **engine's** memory and the reply copy, not the main thread's.

## 3. Design

### 3.1 Partial notices: wire format

A job may post `partial` notices before its reply (W1.2 §17.4). Shape, next to the existing `progress` notice (W1.2 §8):

```json
{"v": 1, "notice": "partial", "id": <request id>,
 "data": {"index": 3, "name": "page-004.png", "mime": "image/png", "data": {"$bin": 0}}}
```

- One buffer per notice; `$bin` indexes the notice's own buffer list (always `0` for print).
- `index` is the 0-based position in the print order (not the page number), so the client can check order and count.
- Partials are **never throttled** (each carries data); `progress` notices stay throttled at 100 ms as today.
- The final reply is `kind: "files"`, `files: []`, `value: {"pages": N}`. The client fails the job if it received a different number of partials (a dropped notice must not print a short document).

### 3.2 Python side (`webapi`)

- `jobs.py` `_run_print`: replace `files.append(...)` with `ctx.report(dto.FileDto(...))` and return `JobOutput(files=(), value=dto.PrintValue(pages=len(pages)))`. `ctx.report` already exists on `core.jobs.JobContext` and `InlineRunner(on_report=...)`, so **no `core/` change**. Keep a running byte total and raise `FILE_TOO_LARGE` past `limits.MAX_JOB_BYTES`, so the 1 GiB cap the final-reply check gave still holds once pages bypass it.
- `dto.py`: `PrintValue(pages: int)` (frozen dataclass). `FileDto` is reused as the partial's `data`.
- `jobworker.py`: `dispatch(..., notify, cancel, partial: PartialSink | None = None)` with `PartialSink = Callable[[dict[str, object], list[bytes]], None]`. A new `_Partials(request_id, partial)` observer, passed as `InlineRunner(on_report=...)`, accepts only `dto.FileDto` (anything else is a programming error, logged and ignored), converts it with `dto.to_json(value, out)` and calls `partial(notice, out)`. Kept separate from `Notify` so the 40-odd existing `notify` call sites in tests stay as they are. A job type that reports nothing is unaffected.

### 3.3 Transport (`web/app/src/engine/`)

- `loader.ts` `JOB_ADAPTER_PY`: add `def partial(notice, out): on_partial(json.dumps(notice), memoryview(out[0]))`; the JS side copies the view with the existing `copyBytes` (a fresh, transferable `ArrayBuffer`) and destroys the proxy at once, so Pyodide's heap holds one page at a time. `makeDispatch`'s `onNotice` becomes `(notice: Notice, buffer?: ArrayBuffer) => void`; `EngineHandle`, `JobWorker` (fileJob.ts) and `WorkerClient.call` take the same widened callback (the extra parameter is optional, so current callers compile unchanged).
- `protocol.ts`: `NoticeMessage.buffer?: ArrayBuffer`.
- `worker-server.ts`: `onNotice(notice, buffer)` posts `{kind: 'notice', id, notice, buffer}` with `[buffer]` as the transfer list.
- `start.ts`: forwards `data.buffer` to the call's `onNotice`. Notices for a finished call are still dropped (a partial always precedes its reply, since `postMessage` keeps order within one worker).

### 3.4 Print client (`web/app/src/print/`)

- `printWorker.ts`: `runPrintWorker(worker, args, document, onProgress)` passes an `onNotice` that (a) feeds `progressPercent(notice)` (fileJob.ts) to `onProgress`, and (b) for `notice === 'partial'` validates the shape (`index` equals the count so far, `mime` is `image/png`, `$bin` is 0, buffer present) and pushes `{name, mime, data: buffer}`. On the reply it reads `value.pages` and fails with `INTERNAL` if it differs from the count. For robustness the final `files`, if any, are read with `readFileJobOutput` (fileJob.ts), which indexes `buffers` by `$bin`: the §2.1 defect cannot come back through that path.
- `printJob.ts`: passes `onProgress = (p) => store.progress(prepared.token, p)`, so the job bar shows a percent and Cancel as for split and export. On cancel the collected pages are dropped (no blob URL exists yet).

### 3.5 The question above 200 pages

- Threshold: `selected > LARGE_PRINT_PAGES` with `LARGE_PRINT_PAGES = 200`, where `selected` is the resolved page count (all pages, or the range's length after removing repeats). **200 pages: no question, Print starts at once. 201 pages: the question.** Same rule at 150 and 300 dpi (question 2).
- The passive hint stays while the user chooses (it already tells them before they press Print).
- On Print with `selected > 200`, the dialog's body switches to a confirmation step inside the same `Overlay` (no stacked modal, focus moves to the question's first button, Escape goes back to the form, not closed). The form's values are kept.
- Copy (plural via `tp`, `{count}` the page count, `{dpi}` the chosen resolution):
  - body: "Print {count} pages at {dpi} dpi? Every page is held in memory until the browser's print dialog opens, which can slow this tab down. A lower resolution or a page range uses less memory."
  - primary: "Print {count} pages" · secondary: "Back"
- "Back" returns to the form with the range field focused when the scope is a range, else the scope's radio. "Print {count} pages" runs the job exactly as today.

## 6. Risks

- **Main-thread memory is still unbounded by design.** 201 pages at 300 dpi is ~0.8–3 MB each, so up to ~600 MB of blobs before `print()`. The question warns; the 1 GiB cap refuses beyond. Browsers may also refuse or hang in `print()` on very large iframes; that is outside our control and the e2e stubs `print()`.
- **Copy per page across Pyodide.** `copyBytes` copies each page once out of the wasm heap; the old path did the same for all pages at the end, so peak engine memory drops from N pages to one.
- **Ordering assumptions.** Partial-before-reply relies on `postMessage` order within one worker, which the HTML spec guarantees; the count check catches a violation rather than printing a short document.
- **Widened `onNotice` signature** touches the shared job transport used by split, export, reduce and others. The parameter is optional and those callers ignore it; their existing tests cover regressions.
- **Timing of the 201-page e2e.** Rendering 201 simple pages in Pyodide may take tens of seconds per browser; keep the fixture's pages text-free (as `buildPdf` makes them) and allow 180 s, or mark the spec `slow` for the nightly run only.

## 7. Questions for the maintainer

1. **Keep every print in the job worker**, including 10 pages or fewer, instead of the spec's engine-worker path for small prints? Recommended: **yes**; one path, viewing never blocks, and the job worker's start-up cost is already paid by other jobs. Update W1.4 §11 and plan.md's W6.5 line to say "always the job worker".
2. **Same 200-page threshold at 300 dpi?** 300 dpi pages are about four times the bytes, so a dpi-weighted rule (ask above 50 pages at 300 dpi) would be closer to the memory risk. Recommended: **keep a flat 200** as specified, with the dpi named in the question's copy; revisit only if users hit memory failures below it.
3. **Accept MuPDF's PNG encoder** in the job worker instead of `OffscreenCanvas.convertToBlob` (W1.4 §11)? Recommended: **yes**; it runs off the main thread already, and adding a canvas encoder would mean moving raw pixels across the boundary for no gain. Amend W1.4 §11's wording.
4. **One PR or two?** The §2.1 fix (read `buffers` by `$bin`, un-fixme the two-page e2e) is ~20 lines and makes multi-page printing work today. Recommended: **ship it first as its own small PR**, then partial notices, progress and the question in the W6.5 PR, which ticks the item.
