# W0.1: PyMuPDF on Pyodide (go/no-go spike)

Stage: W0 (#133) · Role: design Opus 5.5, implementation Haiku 5.5, review Sonnet 5.5 · Branch: `phase-w-w0.1-pymupdf-pyodide`

## Question this task answers

Can the existing engine (`pdfeditor.engine` with the PyMuPDF backend) run in Pyodide well enough to build Elanero Web on it? The answer is a **go/no-go decision**, backed by a reproducible CI build of the wheel, a browser smoke test, a contract-test run and a results report.

## What we know before starting (2026-11-16)

- The desktop runs **PyMuPDF 1.28.2** (`uv.lock`), capped `<2` in `pyproject.toml`.
- PyMuPDF documents its Pyodide build as **experimental**: build with its upstream `scripts/gh_release.py` (`inputs_wheels_linux_pyodide=1`) and load with `pyodide_js.loadPackage(url)`. `micropip.install()` doesn't work (shared libraries). Upstream tests it in `.github/workflows/test_pyodide.yml`.
- Pyodide's current line is **314.x** (Python 3.14, Emscripten 5). The 0.29.x line (Python 3.13) still exists. PEP 783 lets `pyemscripten` wheels go on PyPI, but no PyMuPDF one was found. The only ready-made PyMuPDF wasm wheel found was 1.26.3 for Python 3.13 (conda channel).
- Most `tests/engine` files import `pikepdf` and/or `pypdfium2` (independent round-trip checks), which don't exist in Pyodide.

## Out of scope

Performance budgets (W0.2), CORS (W0.3), the full import audit (W0.4), the `webapi` package, the web wheel of `pdfeditor` (W2.6) and **any change under `src/`**. If the engine needs a code change to pass, record it as a finding. Don't make it here.

## Steps

### 1. Choose the wheel source (record the route taken)

Try in this order and stop at the first that gives **PyMuPDF 1.28.2** (or, failing that, the closest version, recorded as a skew finding):

1. The chosen Pyodide release's own package index: check `pyodide-lock.json` for a `pymupdf` entry and its version.
2. PyPI: a `pyemscripten` wheel of `pymupdf==1.28.2`.
3. Build it: PyMuPDF tag `1.28.2`, `./scripts/gh_release.py build` with `inputs_sdist=0 inputs_wheels_default=0 inputs_wheels_linux_pyodide=1`. **Use the MuPDF version that tag bundles.** Don't set `inputs_PYMUPDF_SETUP_MUPDF_BUILD` to MuPDF `master`, since the desktop and web engines must match.

Pyodide version: the newest stable **314.0.x** at implementation time. If 1.28.2 can't be built for 314 but can for 0.29.x, use 0.29.x and record it. Pin the exact Pyodide version in one place (`web/spike/versions.json`).

### 2. CI workflow `.github/workflows/web-spike.yml`

- Triggers: `workflow_dispatch` and PRs that touch `web/spike/**` or the workflow itself. It must **not** run on other PRs. `scripts/ci_changes.py` is not changed in this task.
- One job named **`pyodide-spike`** (never `changes`, `checks`, `test-windows` or `build`), on `ubuntu-latest`. Pyodide builds are Linux-only.
- Steps: check out; restore the wheel from `actions/cache`, keyed on PyMuPDF version + Pyodide version + workflow file hash; on a miss, build per step 1 (route 3) and save the cache; then run steps 3 and 4; upload the wheel, the JUnit XML and the results report as artifacts.
- Pin every action to a commit SHA and every tool version (emsdk comes from the Pyodide build environment; Node 22 LTS; `pyodide` npm package = the pinned version).
- Timeout 90 minutes. Record the cold build time.

### 3. Contract tests under Pyodide (Node)

Run in Node with the `pyodide` npm package. It's faster and more debuggable than a browser, and the engine code is the same.

- `web/spike/run_engine_tests.mjs`: load Pyodide; `loadPackage` the PyMuPDF wheel, `fonttools`, `pillow`, `pytest` (and `hypothesis`/`numpy` only if collection needs them and Pyodide has them); mount the repo read-only with NODEFS at `/repo`; put `/repo/src` on `sys.path`; run `pytest /repo/tests/engine -p no:cacheprovider --junitxml=/out/engine.xml -q` with the fixtures from `tests/fixtures/generated` (made on the host first with `scripts/make_fixtures.py`).
- Handle modules that need `pikepdf`/`pypdfium2` with a spike-only `conftest` plugin in `web/spike/pyodide_conftest.py`, loaded with `-p`. It installs a `sys.meta_path` finder that turns those imports into `pytest.skip("needs host-side verification")` at module level. Those modules are then **reported as "host-verified" skips, not failures.** Don't edit files under `tests/`.
- Write `out/engine.xml` and a JSON summary: passed, failed, errored, skipped by reason.

### 4. Browser smoke test (Playwright, Chromium)

Proves the real deployment shape: Pyodide **in a Web Worker** in a page served from a static server, with no SharedArrayBuffer.

- `web/spike/smoke/index.html` + `worker.js`: the worker loads Pyodide and the wheels from the same origin (a local static server in the test; nothing from a CDN). It imports `pdfeditor.engine.registry.get_engine()`, then on `tests/fixtures/generated` text fixture bytes it:
  1. opens it (`Engine.open(bytes)`);
  2. renders page 0 (`Page.render`) and checks the image is non-blank;
  3. edits text: the first text block from `content_objects()` → `replace_text(key, "Elanero web smoke")`;
  4. adds a highlight annotation (`add_annotation`);
  5. saves (`Document.to_bytes()`);
  6. reopens the bytes and asserts the new text is extracted (`text_page`) and the annotation is listed (`annotations()`).
  It posts the saved bytes and timings back to the page.
- `web/spike/smoke.spec.ts` (Playwright, Chromium only for the spike): runs the page, asserts each step reported OK, and writes the saved bytes to `out/smoke.pdf`.
- **Host-side verification** (the round-trip rule from AGENTS.md, done across the boundary): `web/spike/verify_host.py` (normal CPython, dev deps) opens `out/smoke.pdf` with **pikepdf** and renders page 0 with **pypdfium2**, and checks that the edited text and the annotation are there. This becomes the W1.7/W2.7 pattern.
- Also record the console and the worker's error output; a page-level error fails the test.

### 5. Results report

`docs/web/spikes/W0.1-results.md`, written by hand from the artifacts. It contains:

- the versions and route taken (Pyodide, Python, Emscripten, PyMuPDF, MuPDF), wheel size (raw and gzip), cold build time;
- the contract-test summary, with **every failure triaged** as (a) fixable in our code (file and reason), (b) a Pyodide limitation with a workaround (e.g. threads, OS paths), or (c) a blocker, plus which R1–R7 / A1–A15 features each affects;
- the browser smoke results per step;
- the recommendation: **GO**, **GO with conditions** (list them, each mapped to a task) or **NO-GO** (with the fallback from the plan: MuPDF.js + a TypeScript service layer).

## Go/no-go criteria

**GO** when all of these hold:

1. The wheel builds reproducibly in CI (cold build ≤ 90 min, then cached), at the desktop's PyMuPDF version, or at a version whose skew is recorded and judged harmless.
2. All six browser smoke steps pass in a Web Worker without SharedArrayBuffer, and the saved file passes the host-side pikepdf + pypdfium2 check.
3. Of the engine tests that run under Pyodide (not host-verified skips), **≥ 95 % pass**, and no failure is a (c) blocker for R1–R7.

**NO-GO** when the wheel can't be built for any maintained Pyodide line, or when opening, rendering, text editing or saving fails in a way with no workaround. Anything in between is **GO with conditions**.

## Edge cases to watch and record

- Python 3.14 (Pyodide 314) vs the desktop's 3.11: syntax or stdlib differences in our code.
- Threads: `threading.Thread.start()` raises in Pyodide. Tests that start threads fail as (b).
- MuPDF built-in fonts (CJK/Noto) may be left out of the Pyodide build to save size. Note text-edit fallbacks.
- `tempfile` and `tmp_path` on MEMFS/NODEFS should work. Note anything that writes outside them.
- Memory: note the wasm heap after the smoke test (`performance.memory` in Chromium, or Pyodide's heap size).

## Acceptance

- The workflow runs green on the PR (the `pyodide-spike` job), with the artifacts attached.
- The results report is committed with a clear recommendation, and W0.1 is ticked in `PLAN.md` and #133 only after the maintainer accepts the recommendation.
- No file under `src/` or `tests/` changed. Desktop CI unaffected.
- **Time box:** if route 3 hasn't produced a working wheel after about 3 days of effort, stop and write the report with what was learned (that is itself the answer).
