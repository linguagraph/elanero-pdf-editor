# W6.3b: Decision on password entry for locked Combine sources (#557)

**Status: decided by the owner's delegate (Opus 5.5) on 2026-11-22; no production code in this change.**

Inputs: issue #557, [W1.1](W1.1.md) sections 4, 6 and 10, [W1.2](W1.2.md) sections 12, 13 and 16, [W6.3b probe and previews](W6.3b-probe-previews.md) sections 3, 6, 10, 11 and Q1, `PRIVACY.md`, AGENTS.md (passwords are never logged or stored), and the code cited below (line numbers as of `718416c`).

## 1. Decision

**Build password entry now, but not as PR 2 was designed.** The exception that PR 2 asked for stays declined, and the hold on it stands. A Combine source password is never kept in the page and never sent to a job worker. Instead, Unlock sends the password once to the engine worker, which opens the file and returns an **unprotected copy** of it. The page then forgets the password, and the copy takes the file's place in the merge. This is the same rule the app already follows for open documents, so W1.2 needs no exception.

The earlier decision was to hold PR 2 because it needed an exception to the W1.2 rule (W6.3b-probe-previews.md:153, Q1 at :282). PR #539 left it out "pending the owner's decision on the W1.2 open-password rule". This decision does not reverse that hold. It declines the exception and unblocks #557 with a design that needs none. Section 3 gives the reasons from the code.

## 2. The rule, as the code enforces it today

The design notes put the W1.2 rule more loosely than the code does. These are the invariants in the code:

| Invariant | Where |
|---|---|
| A typed open password is used for one call and not kept in the page | `web/app/src/documents/openFile.ts:55-58` (comment) and `:74-77`; `documents/passwordRequest.ts:1-3` ("the password itself never enters this store") |
| The engine worker keeps the open password only in the registry, and only while the document is open; closing drops it first | `src/pdfeditor/webapi/registry.py:21-25`, `:78-84`, `:98-103`; `webapi/session.py:5-7`, `:76` |
| **A job worker never sees a password.** Encrypted documents reach jobs as a decrypted copy made by `jobs.prepare` | `webapi/jobs.py:944-946` (`DECRYPTED_COPY_OPTIONS`), `:1062-1068`; `webapi/jobworker.py:92-95`; `dto.JobRunParams` has no password field (`dto.py:843-849`) |
| Decrypted document bytes may pass through the page: the `jobs.prepare` reply carries the decrypted copy to the main thread, which forwards it to `job.run` | `jobs.py:1062-1068`, `dto.py:847-849`, W1.2 section 13 diagram (W1.2.md:233-240) |
| A decrypted or protected document is never written to browser storage | `webapi/save.py:39-44` (autosave skips protected documents, decision D2); `PRIVACY.md:23-26` |
| No secret goes into `localStorage` | `web/app/src/prefs/store.ts:1-3`, `:80-88` (keys naming a password are refused) |
| Error messages and logs carry no password | `webapi/errors.py:4`, `:154` (only unexpected errors are logged, with a fixed message); `webapi/combine.py:95-104` (fixed messages, `from None`) |
| Both workers lose their network globals before any engine code runs | `web/app/src/engine/networkLock.ts:4-10`, `engine/engine.worker.ts:11`, `engine/jobworker.ts:12` |

PR 2 as designed would break two of these. It kept the password in a page `useRef<Map>` until the dialog closed (W6.3b-probe-previews.md:155-157). It also sent the password to the job worker in `MergeSourceArgs.password` (:70, :84).

## 3. Why build, and why this design

**Why not keep holding.** Today an encrypted source cannot be combined on the web at all. The probe marks the row locked and Combine refuses it (`combine/probe.ts:24`, `combine/run.ts:59-60`), and the guide says so (`docs/guide/web.md:385`). The desktop can combine one (`ui/combine/panel.py:304-312`, `services/assembly.py:148`). W6.3 cannot be ticked without it (PLAN.md:601). The design below needs no exception to any rule, so there is nothing left for a hold to wait on.

**Why not PR 2 as designed (option A).** W6.3b Q1 compared two options: keep the password, or decrypt in the engine worker and hand the page an unprotected copy. It rejected the copy for three reasons. None of them holds against the code:

1. *"Keeps the decrypted bytes (worse than the password) in JS for longer."* The plaintext reaches the page anyway. The merge job returns the merged, unprotected file to the page (`jobs.py:720`, `combine/run.ts:161`), and the dialog keeps it in state until it closes (`CombineDialog.tsx:264`, `:402-409`). The merged file holds every chosen page of the protected source, so the copy only exposes earlier what the user is about to download unprotected. The password is the more sensitive of the two. It is a reusable credential that may open other files or accounts, while the copy reveals only this one document.
2. *"Writes a whole decrypted file."* The engine already does this for every job on an encrypted document (`jobs.py:1062-1068`). It is an accepted pattern, not a new one.
3. *"Doubles the page-side memory per protected source."* Combine already reads every source into page memory when it runs (`run.ts:148-150`). The copy adds at most `MAX_PROBE_BYTES` (64 MiB, `limits.py:57`) per unlocked row, and only between Unlock and the dialog closing. That cost is bounded, and section 7 accepts it.

**Against the threat model** (W1.1 section 10; its assets at W1.1.md:201 do not list passwords, a gap noted in section 9):

- **T, "A crafted PDF corrupts engine memory"** (W1.1.md:211). Workers are treated as possibly compromised. In option A, the password sits in the job worker next to every other source of the merge, any of which may be a crafted PDF from a stranger. In option B, the job worker never holds it. The password meets only its own file, in one engine-worker call, which is where every open password already goes (`session.py:53`).
- **E, XSS** (W1.1.md:220). In option A, any script that reached the page could read the password from the ref for as long as the dialog is open. In option B, it is exposed only for one call, as `openFile.ts` already allows. The CSP stays the main defence in both cases.
- **I, "Documents leave the device"** (W1.1.md:214). Today neither worker has network access (`engine.worker.ts:1-3`), so a password inside a worker cannot leave it. When translation adds its allow-listed wrapper to the engine worker, option B sends no password to any other place than today's open flow does.
- **I, "Leftovers on a shared computer"** (W1.1.md:216). The copy lives only in a JS `ArrayBuffer`, never in OPFS, `localStorage` or a Blob URL, and it is dropped with the dialog. Section 6 tests this.

**Option B also costs less.** It needs no `password` field on the merge args, no first pass over every source to tie a password error to a row, and no password state in the job store. The job's protocol does not change.

## 4. The data path of a password

1. **DOM.** The user types into an uncontrolled `<input type="password" autoComplete="off" spellCheck={false}>` on the locked row, outside any `<form>`. React state never holds the value.
2. **Unlock** (button or Enter). The handler copies `input.value` into a local `const`, sets `input.value = ''` at once, and makes exactly one call. Nothing is retried.
3. **RPC client.** `client.call('combine.unlock', {name, data, password})` encodes the params into a local JSON string (`rpc/client.ts:328-336`) and posts it with the file's bytes transferred. The client keeps no copy of the request: its promise closure holds `method`, `id` and timers, not params (`client.ts:338-372`). The local `const` from step 2 goes out of scope when the handler returns.
4. **Engine worker, JS.** The worker hands the request string to Python (`engine/loader.ts:129-137`) and keeps nothing.
5. **Engine worker, Python.** `dispatch` parses it into a frozen `CombineUnlockParams` (`webapi/__init__.py:266-276`). Recording stays off because the call names no handle (`__init__.py:128-142`), and the registry gets no entry. Under `ENGINE_LOCK`, `engine.open(data, password)` runs once. On success, `document.to_bytes(DECRYPTED_COPY_OPTIONS)` produces the copy and `document.close()` runs in `finally`. MuPDF's own copy of the password lives only inside that document, so closing it discards that copy. The params object is dropped when the handler returns.
6. **Reply.** `{page_count, data}` with the copy as the one reply buffer. The password is not in the reply, and the reply holds nothing derived from it.
7. **Page.** The copy goes into `unlocked: useRef<Map<number, ArrayBuffer>>` in `CombineDialog`, keyed by row id. It is deleted when the row is removed, and the whole map is cleared when the dialog closes or unmounts. `runCombine` sends `unlocked.get(id).slice(0)` in place of `file.arrayBuffer()` for that row, so a failed or cancelled job can run again without a second Unlock. The merge args never carry a password.

**Where the password is discarded:** in the page when the handler returns (step 3), in the engine's Python when dispatch returns (step 5), and in MuPDF when the document closes (step 5). JS strings and freed wasm memory cannot be zeroed. That limit is the same as `session.open`'s today, and it is not claimed otherwise.

**Wrong password:** `WRONG_PASSWORD` with a fixed message and `details: {}`, using `from None` (as in `combine.py:99-102`). The row stays locked and the attempt count goes up by one. After `PASSWORD_ATTEMPTS = 5` wrong answers (`organizer/insertFile.ts:11`) the field is disabled until the file is added again.

**Locked files above 64 MiB** cannot be unlocked in the browser. The engine-worker heap only grows (`limits.py:54-56`), and sending the password to a job worker instead would break the job-worker invariant. The probe marks such a row `unchecked/large` without opening it. When the job then finds it encrypted, the merge's existing `REFUSED`/`encrypted_source` (`jobs.py:575`, `:708-711`) gains `path: "args.sources[i]"`. The dialog shows on that row: "This file is protected and too large to unlock in the browser."

## 6. Tests

**Python** (`tests/unit/test_webapi_combine_unlock.py`, through `webapi.dispatch`; not `desktop_only`; pikepdf and pypdfium2 only through `tests.hostcheck.record`, with no new skip-budget entry):

- `encrypted.pdf` with `"user"` returns the right `page_count`. The returned bytes open in the engine with **no** password, `record("not_encrypted_pikepdf", data)`, and `record("text_contains_pdfium", data, page=0, text="Secret content")`. `"owner"` works too.
- `"nope"` gives `WRONG_PASSWORD` with `details == {}`. An empty password gives `WRONG_PASSWORD`. A 1,025-character password gives `INVALID_ARGS` on `params.password`. A `.png` name gives `INVALID_ARGS`. Size over `MAX_PROBE_BYTES` (monkeypatched) gives `FILE_TOO_LARGE`, with a spy proving `open` never ran. Garbage bytes give `OPEN_FAILED`.
- **Read-only and nothing kept:** `REGISTRY.passwords_kept()` (`registry.py:115-117`) and the registry size are unchanged. A spy shows every opened document was closed, including when `to_bytes` raises. `ENGINE_LOCK` is free afterwards.
- **No password in logs or replies:** `caplog` at `DEBUG` over every case, including a forced `INTERNAL` (`to_bytes` raising), has no record containing the distinctive passwords used (`"pw-Zq7!x"`, `"user"` checked as a whole token in messages). The serialized reply and error JSON do not contain them either.
- **The job worker never gets a password:** merge args with a `password` key on a source give `INVALID_ARGS` (strict args, W1.2 Q2), and `JobRunParams` has no password field.
- **Round trip:** merge `text.pdf` with the unlocked copy of `encrypted.pdf` and an image. Check page order by text in the engine, then `record("page_count_pikepdf", …)`, `record("not_encrypted_pikepdf", …)` and `record("render_pdfium", …)`.
- A locked source above the limit gives `REFUSED` with `reason: encrypted_source` and `path: "args.sources[1]"`. The existing compare refusal is unchanged.

**Vitest:**

- `probe.test.ts`: Unlock makes exactly one `combine.unlock` call. `WRONG_PASSWORD` gives attempts + 1 and no retry on any error. The 5th wrong answer sets `gaveUp`. A removed row's reply is ignored, and its copy is not stored.
- `CombineDialog.test.tsx`:
  - The field has `type="password"` and `autocomplete="off"` and is not inside a `<form>`. Its value is `''` right after Unlock.
  - After unlocking, the password string appears nowhere in `container.innerHTML`.
  - Spies on `localStorage.setItem`, `sessionStorage.setItem`, `navigator.storage.getDirectory`, `URL.createObjectURL` and every `console` method see no call during unlock and combine, and none whose arguments contain the password.
  - Removing the row and closing the dialog empty the `unlocked` map, which the next run's args show.
- `run.test.ts`: the job request string sent to the worker contains no `password` key and not the password. An unlocked row sends its copy, not `file.arrayBuffer()`. `encrypted_source` with a path becomes a row outcome with a quiet finish.
- E2E (optional, `npm run e2e:features`): unlock `encrypted.pdf` on its row, combine it with `text.pdf`, check the download's page count.

## 7. Risks accepted

- **The copy is plaintext in page memory** while the dialog is open (at most 64 MiB per unlocked row). The same plaintext is in the merged result anyway, and none of it is persisted.
- **Engine-worker heap growth.** Unlock holds the opened file and its copy at once, roughly twice the file, up to about 128 MiB at the limit. The heap high-water mark rises once per session. A probe already costs about this much. If W8.3's memory numbers show trouble, lower the unlock limit separately from the probe limit.
- **Desktop difference.** The desktop keeps the password on `CombineEntry` (`ui/combine/model.py:51`). That is fine on the desktop, which has no page or XSS boundary. This note does not change the desktop.
- **The combined file has no password**, as on the desktop (`services/assembly.py:136`). The row and the guide say so.

## 8. What would make this decision wrong

- A wasm-heap measurement showing the copy cannot be made within the budget for ordinary files. The fallback is a dedicated one-shot job worker for Unlock alone. That would weaken the job-worker invariant to "only a worker that opens this one file, and is discarded", and it needs its own decision.
- Any need to keep the source's encryption in the output. That is W7.5's Encrypt on the result, not a reason to carry the source password.

## 9. Factual errors found in the existing notes (for a follow-up docs PR)

1. **W1.2 section 13, "Encrypted documents"** (W1.2.md:253), the `job.run` signature (`:226`, `:239`) and the session row (`:218`, "needed for job copies") say the engine returns the open password in the `jobs.prepare` reply and that `job.run` takes `password?`. The code does the opposite. `jobs.prepare` writes a decrypted copy, and the job worker never sees a password (`jobs.py:944-946`, `:1062-1068`; `jobworker.py:92-95`; `JobRunParams` has no `password`, `dto.py:843-849`). The registry password is used for **saving** (`save.py:64-71`), not for job copies.
2. **W6.3b-probe-previews.md:153** says Combine cannot follow the rule "because the job worker has no engine-worker session to borrow a password from". No job worker borrows passwords: jobs on open documents get decrypted copies (item 1), and that pattern is what this decision uses.
3. **W6.3b-probe-previews.md:54** says `needed_password` is `password is not None` with "no second open". The shipped probe does a second open without the password (`combine.py:63`, `:69-80`).
4. **W1.1 section 10, row I** (W1.1.md:214) says the engine worker's `XMLHttpRequest` is wrapped to allow the translation origins. Today the engine worker drops all network globals, as the job worker does (`engine.worker.ts:1-3`, `:11`). The wrapper is still to come with W6.6.
5. **W1.1 section 10** lists no password among its assets (W1.1.md:201), although open and source passwords are handled across the trust boundaries B2 and B3. A follow-up should add the asset and a row that points to this note.
