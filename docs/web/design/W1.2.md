# W1.2: RPC protocol spec

Stage: W1 (#134) · Role: design Opus 5.5 · Branch: `phase-w-w1.2-rpc-protocol` · Builds on [W1.1](W1.1.md) (workers, watchdog, jobs) and [W1.3](W1.3.md) (actions and their argument types). Implemented in W3 (`pdfeditor.webapi`, `web/src/worker`, the TypeScript client).

This note fixes the wire format between the main thread and the two workers: the envelope, versioning, errors, binary data, events, progress, cancellation, deadlines, the chunked-call and job protocols, the Python↔JS boundary inside a worker, and how TypeScript types are generated from Python. It names the calls at group level. W1.4 (rendering, text layer) and W1.5 (hit testing, editing sessions) name the detailed calls of their groups, following the rules here.

## 1. Channels

| Channel | Between | Carries |
|---|---|---|
| Engine channel | main thread ↔ engine worker | every call on open documents, plus the engine side of jobs |
| Job channel | main thread ↔ job worker | job runs and their progress |

Both are the worker's own `postMessage` (dedicated workers, so nothing else can reach them; W1.1 §10). The workers never talk to each other; the main thread relays (W1.1 §1). No `window` `message` listener exists.

## 2. Envelope

Messages are structured-cloneable objects posted with a transfer list. Field names are `snake_case` in Python and on the wire; the generated TypeScript types use the same names, so nothing is renamed at the boundary.

```ts
// main -> worker
interface Request  { v: number; id: number; method: string; params: Json; buffers: ArrayBuffer[] }
// worker -> main, exactly one per request
interface Reply    { v: number; id: number; ok: true;  result: Json; events: Event[]; buffers: ArrayBuffer[] }
interface Failure  { v: number; id: number; ok: false; error: RpcError; events: Event[] }
// worker -> main, unsolicited or tied to a running request
interface Notice   { v: number; notice: "progress" | "ready" | "fatal"; id?: number; data: Json }
```

- `v` is the protocol version (section 3). A message with another `v` is rejected (section 3).
- `id` is a per-channel counter starting at 1, assigned by the main thread. Replies come back in the order the worker handled the requests; since the worker is single-threaded and runs one request at a time, that is also the order they were sent. The client still matches by `id`, never by order.
- One request is in flight per worker at a time from the worker's view, but the client may queue many: it posts them at once and the worker's message queue serialises them. Renders queue behind a long action; W1.4 decides the client-side priority queue (for example dropping renders for pages that scrolled away before they are posted).
- `buffers` holds every binary value of the message (section 5). The transfer list is exactly `buffers`, so binary data moves without copying between threads.
- `events` are the state changes the call caused (section 7). A failed call can carry events too (for example `blocked`).
- Notices: `progress` (section 8), `ready` (the worker finished booting; carries the `hello` data of section 3), `fatal` (the Python runtime aborted or ran out of memory; the client treats the worker as dead, W1.1 §7).

## 3. Versioning

The front end and the workers are built together and served from the same versioned directory (`app/py/<build-id>/`, W1.1 §9), so normally they can't disagree. They can when the service worker serves a cached page of one build and the network or another cache entry serves worker files of another (a half-activated update, a bug in the cache list). The protocol makes that loud instead of subtly wrong:

- `PROTOCOL_VERSION` is one integer in `webapi/dto.py`, bumped on any change that isn't purely additive to an existing message. It is generated into TypeScript (section 14), so both sides carry the same constant from the same build.
- The worker's first message is the `ready` notice with `{protocol, build_id, python, pyodide, pymupdf, mupdf}`. The client compares `protocol` and `build_id` with its own. On a mismatch it terminates the worker and shows "Elanero was updated. Reload to continue." with a Reload button; no call is ever sent to a mismatched worker.
- Every message carries `v`. A worker receiving another `v` replies `PROTOCOL_MISMATCH` and handles nothing else; this is a backstop for the handshake.
- There is no compatibility window between versions. Nothing on the wire is stored, so the only persisted data are OPFS files (autosave sidecar, stored keys), which carry their own `format` field, and the stable action names of W1.3.

## 4. Errors

```ts
interface RpcError { code: ErrorCode; message: string; details: Json }
```

`code` is stable and is what the front end translates (W4.7). `message` is English, for logs and the "Details" disclosure; it never contains document content beyond what the user typed or a file name. `details` holds structured values the message catalogue can interpolate (`{max_bytes, size}` for `FILE_TOO_LARGE`, `{page}` for `STALE_OBJECT`).

| Code | Raised by (Python) | Meaning for the front end |
|---|---|---|
| `INVALID_REQUEST` | `webapi.dispatch`: unknown method, malformed envelope | a bug; logged, generic error shown |
| `INVALID_ARGS` | the JSON converter (section 6): missing, unknown or mistyped field; `details.path` names the field | a bug or a stale front end; generic error |
| `PROTOCOL_MISMATCH` | `v` differs | reload prompt (section 3) |
| `NO_DOCUMENT` | unknown or closed handle | the tab is gone; close its view |
| `PASSWORD_REQUIRED` | `engine.base.PasswordRequired` | ask for the password and call again |
| `WRONG_PASSWORD` | `PasswordRequired` on a call that supplied one | ask again |
| `OPEN_FAILED` | `OpenError` | "not a PDF or damaged" |
| `SAVE_FAILED` | `SaveError` (includes failed verification on reopen) | document stays dirty |
| `REFUSED` | `actions.Refused` | show `message` key with `details` |
| `BUSY` | `actions.Busy`, or a session refusing while a task runs | "wait for X to finish"; `details.task` |
| `NOT_SUPPORTED` | `actions.NotSupported`, `engine.base.UnsupportedFeature` | hide or disable the command |
| `STALE_OBJECT` | `actions.StaleObject` | re-hit-test and retry once; otherwise tell the user the page changed |
| `STALE_CURSOR` | a chunked call's cursor no longer matches the document (section 9) | restart the chunked operation |
| `STALE_JOB` | `jobs.apply`/`jobs.abort` with an unknown token (the engine restarted) | drop the result, tell the user |
| `CANCELLED` | `core.jobs.Cancelled` | silent |
| `FILE_TOO_LARGE`, `TOO_MANY_PAGES`, `RENDER_TOO_LARGE`, `IMAGE_TOO_LARGE` | `webapi.limits` (W1.1 §7) | explain the limit (`details` has it) |
| `OUT_OF_MEMORY` | `MemoryError` caught in dispatch | suggest closing documents; the worker may be restarted (W3.9) |
| `ENGINE_ERROR` | any other `EngineError` | generic "the PDF engine reported an error" with details |
| `TRANSLATION_OFFLINE`, `TRANSLATION_QUOTA`, `TRANSLATION_AUTH`, `TRANSLATION_CONFIG`, `TRANSLATION_TOO_LONG`, `TRANSLATION_SAME_LANGUAGE`, `TRANSLATION_SERVICE` | the `services.translation.base` errors, one each | the existing desktop messages, translated |
| `INTERNAL` | any other exception | generic error; the traceback goes to the worker console only, never to `message` |

`webapi/errors.py` holds the mapping as one ordered table (most specific class first), and a test asserts every code in the generated `ErrorCode` union is reachable from it and has a message-catalogue entry (W4.7).

## 5. Binary data

**On the wire.** Any `bytes` value in params or a result is replaced in the JSON by a marker `{"$bin": i}`, where `i` indexes the message's `buffers`. This one rule covers everything: a PDF to open, saved bytes, render pixels, `AnnotationModel.file_data` and `.image`, `pages.insert_file` data, font files, job documents and job outputs. Small values use the same path (no base64 anywhere), so there is one code path to test. A buffer may be referenced only once; the converter rejects a reused or unreferenced index (`INVALID_ARGS`).

**Ownership.** Buffers are transferred, so the sender loses them. The client copies nothing it must keep: for example, the bytes of a freshly opened file are read from the `File`, transferred to the worker, and gone from the main thread.

**Pixels.** A render result is a `$bin` buffer of tightly packed RGBA rows (`width * 4` bytes each; the worker removes any stride padding, as the W0.2 harness did) plus `{width, height}`. The main thread wraps it in `ImageData` and calls `createImageBitmap`. W1.4 decides whether the bitmap is made in the worker (`OffscreenCanvas`-free path: `createImageBitmap` is available in workers) and transferred instead; the envelope allows both, because an `ImageBitmap` is also transferable and would go in a separate `bitmaps` list. W1.4 owns that choice; if it picks bitmaps, it adds `bitmaps: ImageBitmap[]` to `Reply` with the marker `{"$bitmap": i}`.

## 6. JSON mapping of Python types

One converter in `webapi/dto.py`, `to_json(value)` and `from_json(tp, data)`, driven by `typing.get_type_hints`, used for every request params type, every result type and every W1.3 args dataclass. The same table drives the TypeScript generator (section 14).

| Python | JSON | TypeScript | Notes |
|---|---|---|---|
| `bool` | `true`/`false` | `boolean` | `int` is not accepted where `bool` is expected, nor the reverse |
| `int` | number | `number` | must be a safe integer (|n| < 2^53); `bool` rejected |
| `float` | number | `number` | finite only; `int` accepted and converted; NaN and infinities rejected |
| `str` | string | `string` | |
| `bytes` | `{"$bin": i}` | `Bin` (`{ $bin: number }` on the wire; the client API hands out `ArrayBuffer`) | section 5 |
| `Enum` with `str` values | its value | union of string literals | all model enums are `str`-valued today |
| `IntFlag` (`FontFlags`) | number | `number` | the only flag type; bits documented in the generated comment |
| `X \| None` | value or `null` | `X \| null` | a missing optional field takes its dataclass default |
| `tuple[X, ...]`, `frozenset[X]` | array | `X[]` | frozensets are sorted on output, so replies are deterministic |
| `tuple[X, Y]` | fixed-length array | `[X, Y]` | e.g. `AnnotationModel.line_endings` |
| `dict[str, X]` | object | `Record<string, X>` | only `str` keys (W1.3 rule 1); `AnnotationModel.extra` |
| `datetime` | ISO 8601 string with offset | `string` | replies only (comment dates); W1.3 forbids it in args |
| dataclass | object with one key per field | `interface` | unknown keys rejected; missing fields without a default rejected |

`from_json` is strict: it rejects unknown keys, wrong types and out-of-range numbers with `INVALID_ARGS` and a `details.path` such as `args.marks[2].rect.x0`. The front end is trusted code, but strictness catches version skew and bugs at the boundary rather than deep in the engine. `AnnotationModel.id` is accepted and ignored in args, as W1.3 rule 2 says; a test pins that.

Types the converter refuses at import time (a test walks every reachable type): `list`, `dict` with non-`str` keys, `Path`, callables, `Any`, `object`, unions other than `X | None`, and anything from `pdfeditor.engine` except plain dataclasses and enums.

## 7. Events

Every reply (and failure) carries the events its call produced, so the front end never polls. `webapi/registry.py` subscribes to each `DocumentSession` once and buffers what the session emits during the call; dispatch drains the buffer into `events`.

```ts
type Event =
  | { kind: "changed"; handle: string; changes: Change[]; revisions: Record<string, number> }
  | { kind: "state";   handle: string; state: DocState }
  | { kind: "saved";   handle: string }
  | { kind: "closed";  handle: string }
  | { kind: "blocked"; handle: string; task: string };

interface Change   { kind: "content" | "structure" | "metadata" | "outline" | "annotations"; pages: number[] }
interface DocState { page_count: number; structure_version: number; dirty: boolean; busy: string;
                     can_undo: boolean; can_redo: boolean; undo_label: string; redo_label: string;
                     require_full_save: boolean }
```

- `changed` mirrors `SessionEvent(CHANGED)` and `core.commands.Change`. `revisions` gives the new `Page.revision` of each changed page (keys are page indices as strings, a JSON necessity), so W1.4's tile keys update without another call.
- `structure_version` increases on every `structure` change (pages added, removed, reordered, or a snapshot restore). The front end refetches page sizes and labels (`session.pages`) when it changes, and chunked cursors from before it become stale (section 9).
- `state` is sent, coalesced to one per document per call, whenever any of its fields changed. It replaces the desktop's `DIRTY` event and adds what the web needs to enable Undo, Redo and Save without asking.
- `blocked` mirrors `BLOCKED`; the same call also fails with `BUSY`.

## 8. Progress

`{notice: "progress", id, data: {done, total, status}}`, tied to the request `id` it reports on. `total` 0 means indeterminate. `status` is a short English string from the existing `job.status` callbacks (used today for OCR stages); W4.7 may map known statuses to catalogue keys later.

- **Job worker:** the `CancelToken` and progress callbacks of `core.jobs` are unchanged. The job worker's progress callback posts a notice directly (a synchronous `postMessage` from Python through `js`, which works while Python runs). It is throttled to at most one notice per 100 ms per job.
- **Engine worker, long single calls** (open, save, a large `actions.run`): same mechanism, same throttle. The client uses it to show progress and to know the worker is alive (a progress notice resets the watchdog deadline of that request, section 10).
- **Chunked calls:** progress comes in each slice's reply (section 9), not as notices.

## 9. Chunked calls

For read-only work that splits by page (W1.1 §1): search, the text of a range, thumbnails in bulk, the comment list, the space audit.

```ts
params: { handle: string; cursor: string | null; budget_ms: number; ...callSpecific }
result: { items: T[]; cursor: string | null; done: number; total: number }
```

- The first call passes `cursor: null`. Each reply returns the items found in this slice and the next `cursor`, or `null` when finished.
- The worker stops a slice after `budget_ms` (default 100, range 20–1000) or a call-specific item cap, whichever comes first, always finishing the page it is on.
- **Cursors are stateless:** an opaque string encoding the position and the `structure_version` it was made for (for example `"v3:p120"`). The worker keeps nothing between slices, so cancel is simply not asking for the next slice, and an abandoned operation leaks nothing.
- If `structure_version` changed since the cursor was issued, the call fails with `STALE_CURSOR`; the front end restarts (search) or rebuilds (thumbnails). Content-only changes don't invalidate cursors: a search that already passed an edited page doesn't revisit it, which matches desktop behaviour for a running search.

## 10. Deadlines (the watchdog)

Soft deadlines per call class (W1.1 §1). When one passes, the client shows the Wait / Restart engine dialog; it never terminates the engine worker itself. A progress notice for the request resets its deadline. The job worker has no deadlines: a job shows progress, and Cancel always terminates it.

| Class | Deadline | Calls |
|---|---|---|
| `instant` | 3 s | `hello`, `session.info`, `session.pages`, `session.capabilities`, `actions.available`, `save.mark_saved`, `fonts.list`, `fonts.remove`, `translate.set_key` |
| `render` | 5 s | the render and thumbnail calls of W1.4; hit tests of W1.5 |
| `slice` | 5 s | every chunked call (a slice is ~100 ms of work; 5 s means something is wrong) |
| `edit` | 10 s | W1.5's edit-session calls, `actions.undo`, `actions.redo` (a snapshot restore of a large file) |
| `action` | 30 s, plus 1 s per 10 pages | `actions.run`, `jobs.prepare`, `jobs.apply`, `fonts.add` |
| `io` | 15 s, plus 1 s per 4 MB of the file | `session.open`, `save.save_bytes`, `save.autosave_bytes` |
| `network` | 20 s | `translate.run` (the transport's own timeout is 15 s, so a timeout normally comes back as `TRANSLATION_OFFLINE` first) |

The class of each method is part of the generated method table, so the client needs no hand-written list. The numbers are starting points; W8.3 tunes them from measurements on the 1000-page fixture.

## 11. Python ↔ JS inside a worker

The worker's JS calls one Python function, `webapi.dispatch`, per request:

```python
def dispatch(request_json: str, buffers: list[JsProxy]) -> tuple[str, tuple[bytes, ...]]:
    """Handle one request; returns the reply (or failure) JSON with its events, and the reply's
    buffers in $bin order. Never raises: every exception becomes a Failure."""
```

```js
// worker.js, per request (sketch)
const out = dispatch(JSON.stringify({ v, id, method, params }), buffers.map((b) => new Uint8Array(b)));
const replyBuffers = [];
try {
  const json = out.get(0);                    // a str converts to a JS string
  const bufs = out.get(1);
  try {
    for (let i = 0; i < bufs.length; i++) {
      const b = bufs.get(i);
      const view = b.getBuffer("u8");         // zero-copy view into the wasm heap...
      try { replyBuffers.push(view.data.slice().buffer); }  // ...one copy out of it
      finally { view.release(); b.destroy(); }
    }
  } finally { bufs.destroy(); }
  postMessage({ ...JSON.parse(json), buffers: replyBuffers }, replyBuffers);
} finally { out.destroy(); }
```

Rules:
1. **No `PyProxy` outlives a call.** Every proxy the JS receives is destroyed in a `finally` in the same call. Python never stores a `JsProxy`: incoming buffers are copied into `bytes` (`buf.to_bytes()`) at once and the proxies dropped. Leaked proxies pin wasm memory and are the usual Pyodide leak.
2. **One copy each way** for binary data: JS → Python `to_bytes()`; Python → JS `getBuffer` + `slice`. (The W0.2 harness went through a MEMFS file, which costs two copies.)
3. **Params cross as a JSON string**, parsed by Python's `json` and then `from_json`. Replies cross as a JSON string built by `json.dumps(to_json(...), allow_nan=False, separators=(",", ":"))`. Strings are cheap to move between the runtimes and leave no proxies behind.
4. **Notices from inside Python** (progress, `fatal` is posted by JS) use one function the worker JS installs before importing `webapi`: `post_notice(json: str)`. Python calls it through `js`; it is the only JS function Python calls, besides the translation transport's `XMLHttpRequest` (W2.4).
5. **GC:** after each request the worker JS schedules `webapi.idle()` 1 s after the queue drains, which runs `engine_lock.collect()` (W1.1 §2).

A test in W3.2 opens and closes a document 200 times and renders 500 tiles, then checks that the wasm heap returns to within 10% of its baseline and that Pyodide's live `PyProxy` count (debug build or `pyodide.ffi` counters) is unchanged.

## 13. Job protocol

```
main                       engine worker                          job worker (warm)
 |-- jobs.prepare --------->|  validate args; if mutating:           |
 |   {handle, job, args}    |    session.begin_task(label)           |
 |<-- {token, label,        |  bytes = doc.to_bytes(SNAPSHOT_OPTIONS)|
 |     mutating, document} -|                                        |
 |------------------------------- job.run {job, args, document, password?} -->|
 |<------------------------------ progress notices -------------------------|
 |<------------------------------ {result} ---------------------------------|
 |-- jobs.apply ----------->|  SnapshotCommand(label, load_state)    |
 |   {handle, token,        |  require_full_save |= result flag      |
 |    document, flags}      |  end_task(label)                       |
 |   or jobs.abort -------->|  end_task(label)  (cancel, failure)    |
```

- `job` is a job type name: `action` (runs a W1.3 action marked `long`, with `args = {name, args}`), `reduce_size`, `audit`, `compare` (two documents: the second is a `$bin` in args), `split`, `merge` (no `handle`; sources in args), `export`, `print_pages`. W3.7 owns the list; each type has params and result dataclasses like any call.
- **Results** are one of: `{kind: "document", document, label, require_full_save, value}` (mutating jobs: applied with `jobs.apply`), `{kind: "new_document", document, name}` (merge: opened as a new tab with `session.open`), `{kind: "files", files: [{name, mime, data}]}` (split, export, reduce size, print), `{kind: "report", value}` (audit, compare).
- **Read-only jobs** skip `begin_task`; `jobs.prepare` still produces the copy and a token, and `jobs.abort` (or a later `jobs.prepare`) forgets the token.
- **The token** is a random string held by the engine's registry with the handle and label. `apply` or `abort` with an unknown token fails with `STALE_JOB` (the engine worker was restarted while the job ran). Tokens are single-use.
- **Cancel** terminates the job worker, then the client sends `jobs.abort` so the session stops being read-only, then starts a fresh job worker in the background (W1.1 §1).
- **Encrypted documents.** Snapshot bytes keep the document's encryption (`SNAPSHOT_OPTIONS` has `decrypt=False`), so the job worker needs the open password. The engine worker returns it in the `jobs.prepare` reply only for encrypted documents; the client passes it straight into `job.run` and drops it. The job worker saves its result with the same options, so `load_state` in the engine worker works exactly as an undo does.
- **Fonts.** At boot the client sends `job.init {fonts}` with the uploaded fonts read from OPFS, so a job that draws text (stamping) finds the same fonts as the engine worker.
- **Applying a result** reuses `SnapshotCommand` with `operation = lambda doc: doc.load_state(result)` and the action's label, so undo and redo behave as on desktop. `require_full_save` is ORed in, never cleared, by an applied job (W1.3 §2).

## 14. Generated TypeScript (single source of truth)

`scripts/make_web_types.py` (host CPython, no Qt, no browser) imports `pdfeditor.webapi.dto` and `pdfeditor.actions`, walks every params, result, event and args type with the table of section 6, and writes:

- `web/src/generated/rpc.ts`: `PROTOCOL_VERSION`; one `interface` per dataclass; string-literal unions per enum; `ErrorCode`; the `Methods` map `{ [method]: { params; result; deadline } }`; the `Actions` map `{ [action name]: args type }` from the W1.3 registry, with each action's `requires` and `long` flags;
- `web/src/generated/validate.ts`: one small generated guard per type (`isDocState(x): x is DocState`), used by the client on every reply and event (W1.1 §10: replies from a worker are untrusted). Generated code, so the app needs no runtime schema library.

Both files are committed. `make_web_types.py --check` exits 1 when they differ from what it would write, and a unit test in the desktop suite runs it (as `make_shortcut_docs.py --check` is tested today), so drift fails the `checks` job of any PR that touches Python DTOs. Generated files start with a "do not edit" header naming the script.

Field documentation: each dataclass field's comment (the `#` comment on its line) is copied into a TSDoc comment, so the TypeScript types explain themselves.

## 16. Questions for the maintainer

**Answered 2026-11-17: all three as recommended.**

1. **The open password stays in the engine worker's memory** while the document is open, so jobs on encrypted documents can open their copy (section 13). The alternative is to give the job worker a decrypted copy, which means proving that every job result re-encrypts correctly when applied. Recommended: keep the password in worker memory, never in JS state or storage.
2. **Strict argument checking** (`INVALID_ARGS` on any unknown field) even though the front end is our own code. Recommended: yes; it turns version skew and bugs into clear errors at the boundary.
3. **No compatibility between protocol versions**: a mismatch forces a reload. Recommended: yes; nothing on the wire is persisted, so supporting old versions would buy nothing.

## 17. Reconciliation with W1.4 and W1.5

W1.2, W1.4 and W1.5 were written in parallel. Where they differ, this section decides, and W1.4/W1.5 point here.

1. **Spelling.** Field names are `snake_case` and documents are named by `handle` (section 2). W1.4's tables write `doc`, `scaleMilli`, `tileX`, `tileY`, `tilePx`, `startPage`, `pagesDone`, `widthPt`, `heightPt`; read them as `handle`, `scale_milli`, `tile_x`, `tile_y`, `tile_px`, `start_page`, `pages_done`, `width_pt`, `height_pt`.
2. **Deadline classes** are the ones in section 10. W1.4's `short` is `instant`, its `chunk` is `slice`, its `job` means a job-worker job (no deadline, progress only). W1.5's `interactive` is `instant` (or `render` for hit-test data), `background` is `io`, `edit` is `edit`.
3. **Bitmaps (W1.4's choice).** The engine worker makes the `ImageBitmap` and transfers it. `Reply` gains `bitmaps: ImageBitmap[]`, referenced by `{"$bitmap": i}` with the same single-reference rule as `$bin`.
4. **Partial job results (W1.4's print).** A job may post `partial` notices before its final result, each with its own `$bin` buffers (one printed page each). The final result then carries only the summary. The client handles each partial at once and lets it go, so memory stays bounded.
5. **Call names** added to section 12:
   - `session.pages` is W1.4's `session.page_sizes` (one name: `session.pages`, which also returns each page's `revision`).
   - `render`: `render.page`, `render.tile` (W1.4 §Calls); thumbnails are `render.page` at thumbnail scale.
   - `text`: `text.layer`, `text.extract`, `text.search` (W1.4).
   - `print`: `print.render` (W1.4; a job above 10 pages, otherwise an engine call with the `slice` class per page).
   - `edit` (W1.5): `content.objects`, `content.image_data`, `content.preview_font`, `document.fonts`, `annotations.page`, `annotations.file`. `annotations.page` gives one page's comments for hit testing; `comments.list` stays the chunked list for the comments panel.
   - `fonts`: W1.5's `fonts.upload` and `fonts.load` are both `fonts.add {name, data}` (a new upload, or a font read back from OPFS at start-up); `fonts.remove` takes the font's name.
6. **Error codes** added to section 4: `INVALID_FONT` (fontTools can't read the file) and `FONT_NOT_EMBEDDABLE` (its embedding rights forbid it), both raised by `fonts.add`.
7. **Actions.** W1.5 adds the action `annotations.create` (W1.3 now lists 42 actions); it goes through `actions.run` like the others.
