# W1.3: The actions layer (`pdfeditor.actions`)

Stage: W1 (#134) · Role: design Opus 5.5; W2.1 implements it (Haiku 5.5, slices (a)–(e)), reviewed by Sonnet 5.5 · Branch: `phase-w-w1.3-actions-layer` · Builds on [W1.1](W1.1.md) §2.

## Why

The desktop UI decides which Command to build, its label, its grouping and its side effects (for example `require_full_save` after a redaction). The web can't call that code, because it lives in Qt controllers. This note moves those decisions into a Qt-free layer that both front ends call, so they exist once. The desktop behaviour doesn't change: the same Commands, labels and undo steps.

## 2. The API

Package `src/pdfeditor/actions/`:

| Module | Contents |
|---|---|
| `base.py` | `ActionResult`, the errors, `ActionSpec`, the helpers `execute_all` and `snapshot` |
| `__init__.py` | `REGISTRY`, the `action` decorator, `run(session, name, args)`, `available(session)` |
| `pages.py`, `comments.py`, `redaction.py`, `security.py`, `marks.py`, `document.py`, `content.py` | One function and one args dataclass per action. The `annotations.*` actions live in `comments.py`, because a module named `annotations` clashes with `from __future__ import annotations`; `annotations.flatten` lives in `document.py` and `document.sanitize` in `security.py`, so each W2.1 slice owns its own modules. Action names don't depend on module names. |

### Functions

Each action is a plain function: `def rotate(session: DocumentSession, args: RotatePages) -> ActionResult[None]`. The desktop calls these functions directly, with typed arguments. The registry exists for the web (look-up by name) and for tests (every action is registered and has a valid args type).

```python
@dataclass(frozen=True, slots=True)
class ActionResult(Generic[T]):
    label: str              # the undo label, as today ("Rotate 3 Pages Right")
    value: T                # the action's own result: new indices, a count, a VerificationReport,
                            # a FontChoice, the names of added comments... (None if nothing)
    executed: bool = True   # False when there was nothing to do (e.g. no annotations to flatten)
```

Actions return data, not messages. Each front end words its own notices (the desktop's existing strings move nowhere; the web uses its message catalogue). Example: `content.replace_text` returns the `FontChoice`, and the desktop's `run_edit` wrapper keeps showing "used X instead".

### Errors (`actions/base.py`)

```python
class ActionError(Exception):           # code is a stable string the web maps to a message
    code: str
class Refused(ActionError): ...         # "REFUSED": e.g. deleting every page (replaces PageOpError)
class Busy(ActionError): ...            # "BUSY": the session is read-only while a task runs
class NotSupported(ActionError): ...    # "NOT_SUPPORTED": a required capability is off
class StaleObject(ActionError): ...     # "STALE_OBJECT": the page changed since the object was picked
```

`EngineError` and `UnsupportedFeature` from the engine pass through unchanged; `webapi/errors.py` maps them.

**Busy.** `DocumentSession.execute` refuses silently (it emits `BLOCKED` and returns) while a task runs. An action must not report success in that case, so every action starts with `ensure_idle(session)`, which raises `Busy`. The desktop's behaviour stays the same: its wrappers catch `Busy` where they used to rely on the `BLOCKED` event, and the event is still emitted for the views.

### Helpers

```python
def execute_all(session: DocumentSession, commands: Sequence[Command], label: str) -> bool:
    """One undo step: the command itself when there is one, a MacroCommand when several,
    nothing when none. Returns whether anything ran."""

def snapshot(session: DocumentSession, label: str, op: Callable[[Document], R]) -> R:
    """Run ``op`` as one SnapshotCommand and return what it returned."""
```

`execute_all` replaces the `commands[0] if len(commands) == 1 else MacroCommand(label, commands)` idiom that appears 7 times in `ui/`. `snapshot` replaces `page_ops.run`, `run_edit`'s core and the `counted: list[int]` closures.

### Session side effects

Side effects that the controllers apply after executing move into the action, so neither front end can forget them:
- `redaction.apply` and `document.sanitize` set `session.require_full_save = True`.
- `redaction.apply` runs `services.redaction.verify` and returns its report.

On the web, a long action may run in the job worker on a throwaway session over a copy (W1.1 §1). The job result then carries that session's `require_full_save`, and the engine worker ORs it into the real session when it applies the bytes. W3.7 implements this.

### Registry

```python
@dataclass(frozen=True, slots=True)
class ActionSpec:
    name: str                          # "pages.rotate"
    args: type                         # the args dataclass
    fn: Callable[[DocumentSession, Any], ActionResult[Any]]
    requires: tuple[str, ...] = ()     # capability names (engine or platform), e.g. ("redact",)
    long: bool = False                 # may run in the web job worker on large documents

REGISTRY: dict[str, ActionSpec]

def action(name: str, *, requires: tuple[str, ...] = (), long: bool = False): ...
def run(session: DocumentSession, name: str, args: object) -> ActionResult[Any]: ...
def available(session: DocumentSession) -> list[str]: ...  # names whose requirements hold
```

`run` checks that `args` is an instance of the spec's type and that the capabilities hold (`NotSupported` otherwise), then calls the function. `available` is what `webapi`'s capabilities reply sends, so the front end greys out what the engine and platform can't do. Capability names are the field names of `engine.base.Capabilities` and of `core.platform.PlatformCapabilities` (W2.2), checked by a test so a typo can't silently disable an action.

`long=True` marks actions that can take seconds on a large document: `pages.trim_white_margins`, `annotations.flatten`, `redaction.apply`, `document.sanitize`, the `marks.*` actions. The desktop ignores the flag (it runs them as today). W3.5 decides per call whether `webapi` runs one inline or in the job worker (for example above 50 pages).

### Names

`<group>.<verb>` in `snake_case`, stable once released, since the web front end, its tests and any saved preferences refer to them. The full list for W2.1 is the "Moves to" column above (41 actions, plus `annotations.create` added by W1.5: 42). A name never changes meaning; a changed behaviour gets a new name.

## 3. Argument dataclasses

One frozen dataclass per action, in the action's module, named after the action in `PascalCase` (`pages.rotate` → `RotatePages`). Rules, so W1.2 can convert them to and from JSON mechanically and generate TypeScript types:

1. Field types are limited to: `bool`, `int`, `float`, `str`, `bytes`, `Enum` subclasses (by value), `tuple[X, ...]` and fixed-length `tuple[X, Y]`, `dict[K, X]` where `K` is `str` or a str-valued `Enum` (JSON object keys), `X | None`, and dataclasses from `pdfeditor.model` (or `services` types that are plain dataclasses, such as `MarkStyle`, `HeaderFooter`, `Watermark`) built from the same types. `datetime` is allowed only as `AnnotationModel.created`/`modified` (ISO 8601, W1.2 §6); elsewhere the action stamps times itself. No `dict` with other keys, no `list` (use `tuple`), no `Path`, no other `datetime`, no callables, no engine objects.
2. Pages are 0-based indices. Comments are named by `AnnotRef(page: int, name: str)` (their `/NM`), never by the engine's numeric `id`, which is an engine detail. The action resolves names to ids. `AnnotationModel` is accepted where a whole comment is passed (add, update), with `id` ignored.
3. Content objects are named by `ObjectRef(page: int, key: str, revision: int)`. Object keys are valid for one page revision (`engine/base.py`), and on the web the page can change between picking and acting, so the action raises `StaleObject` if `revision` no longer matches `Page.revision`. The desktop passes the current revision, so for it nothing changes.
4. Inputs that today come from the UI's state become arguments: the author (`view.author`), the redaction `MarkStyle` (read from `QSettings` by the controller), the selected pages, `replace_existing` for marks, the file bytes and name for `pages.insert_file`. Defaults that are data, not UI, move into `actions` with them: the comment tool styles (`ui/tools/annotate.STYLES`) become `actions.annotations.DEFAULT_STYLES`, and the helpers `restyled` (`ui/panels/inspector.py`) and `annotate_transform` (`ui/main_window.py`) move into `actions.annotations`.
5. `UpdateAnnotationCommand`'s `merge_key` (the inspector merges a run of edits to one field into one undo step) is an optional field of `RestyleAnnotations`.

A test in slice (a) walks every registered args type and fails on a field type outside rule 1. W1.2 adds the JSON round trip of each type.

## 4. What stays in the UI

Dialogs, confirmations ("Replace or add?", "Flatten N comments?"), `QSettings`, file pickers, the clipboard, notifications and selection changes after an action (the action returns what's needed, for example the names of pasted comments). Read-only queries that today sit in `ui/` and that the web will need move to `services` in the slice that needs them: `MainWindow._flattenable` (count of comments that flatten would burn in), `ProtectController._all_marks` (redaction marks of a document).

### Shortcuts (slice (f), correcting the plan)

The plan says W2.1 moves `ACROBAT_DEFAULTS` out of `ui/shortcuts.py`. That table has only 5 entries: most default shortcuts are set on each `QAction` where it is created, and some come from Qt's platform `StandardKey`s. Moving the table alone wouldn't give the web the shortcuts. Instead, `scripts/make_shortcut_docs.py`, which already reads every command's default shortcut from a live main window to generate the guide page (with a `--check` test), also writes `web/src/generated/shortcuts.json` (command id → default key sequences, in the portable `Ctrl+Shift+P` text form). The same `--check` keeps it in step. The desktop stays the source of truth and nothing in `ui/` moves.
