# W0.2: Load size and speed

Stage: W0 (#133) · Role: design Opus 5.5, implementation Haiku 5.5, review Sonnet 5.5 · Branch: `phase-w-w0.2-load-speed` · Builds on the W0.1 spike (`web/spike/`, PR #144); start after it is merged, and merge `origin/main` first.

## Question this task answers

Does the Pyodide + PyMuPDF stack meet the plan's budgets, and where does the time and memory go? Budgets (plan, decision 10): **first load ≤ 40 MB compressed**, **first rendered page ≤ 6 s cold and ≤ 2 s warm** on a mid-range laptop, **main thread never blocked > 50 ms**. This is measurement only; optimisations are recommended in the report, not made.

## Out of scope

Any change under `src/` or `tests/`. The real app, service worker and PWA (W4). Optimising anything. Translation (W0.3) and the import audit (W0.4).

## Fixtures

The existing `large_1000` fixture is text only, which flatters rendering. Add to `scripts/make_fixtures.py` (the place AGENTS.md requires) a `perf_mixed(pages)` builder writing `perf_mixed_10.pdf`, `perf_mixed_200.pdf` and `perf_mixed_1000.pdf`. Each A4 page has:

- a heading and a paragraph of the existing `LOREM` text in two fonts: a base-14 font and one embedded TrueType font that the script already builds or bundles;
- one embedded photo-like image, 1200×800 RGB JPEG, generated deterministically with Pillow (a seeded gradient plus noise, quality 80). Use a different seed every 10 pages, so the file isn't one shared image object;
- a few vector shapes (rectangles, a Bézier curve, a filled polygon).

Register the three in the builder table and honour `--skip-large` for the 1000-page one. Also use the real sample `tests/fixtures/real/scanned_dryer_manual.pdf` (scanned pages, image heavy) as a fourth case.

## Metrics

All timings are the median of **5 runs** (report the min and max too), measured with `performance.now()` in the worker and on the main thread.

| ID | Metric | How |
|---|---|---|
| M1 | **First-load bytes** | For two asset sets: the *viewer set* (Pyodide core files actually fetched: `pyodide.mjs`, `pyodide.asm.js`, `pyodide.asm.wasm`, `python_stdlib.zip`, `pyodide-lock.json`; the PyMuPDF wheel; a `pdfeditor` zip) and the *full set* (plus `fonttools`, `pillow` and their dependencies from the lock file). Report each file raw, gzip -9 and brotli -q 11, and the totals. GitHub Pages serves gzip, so **gzip is the budget figure**. The `pdfeditor` zip is a spike stand-in for W2.6: `src/pdfeditor` without `ui/`, `services/signing/`, `services/ocr.py`, `services/pdfa.py`, `services/store_updates.py`, `services/file_association.py`, `services/export/office.py`, `data/tessdata/` and `__pycache__`. The list and the zip builder live in **`web/spike/web_package.py`**, shared with W0.4 (whichever task lands first creates it, with exactly the excluded set defined in `docs/web/design/W0.4.md`). Also report the size of the `data/` part on its own. |
| M2 | **Cold start to first page** | New browser context (empty HTTP cache), on a static server with gzip and `Cache-Control: max-age=31536000, immutable`. Mark these points: page load → worker created → Pyodide ready → packages loaded → `pdfeditor` imported → engine ready → document opened → page 1 rendered (in Python) → `ImageBitmap` received on the main thread. Run on localhost, so no network time, and also report the **computed download time** of the M1 gzip bytes at 20, 50 and 100 Mbit/s. Budget: localhost time + download at 50 Mbit/s ≤ 6 s. |
| M3 | **Warm start** | Same browser context, page reloaded (HTTP cache warm). Same marks. Budget ≤ 2 s. Note: the real app adds a service worker (W4.6). Record whether Pyodide's own compiled-wasm cache helps. |
| M4 | **Job worker start** | With the engine worker ready, spawn a second worker with the same bootstrap, warm, and post it the bytes of `perf_mixed_200`. Time until it has opened them (engine ready + open). This is the cost of cancellable jobs (plan, decision 5). |
| M5 | **Render** | Per fixture, at scale 1.0 and 2.0 (HiDPI): pages 1–10 in order, then 20 random pages (fixed seed). Report the median and p95 for Python render time (`Page.render`) and for end-to-end time (request posted → `ImageBitmap` on the main thread, transfer included). |
| M6 | **Other operations** | Per fixture: open time, `text_page()` time per page (median of 10 pages), search one word across the whole document (`services/search.py`), and `to_bytes()` (full save) time. |
| M7 | **Memory** | The wasm heap size (`pyodide._module.HEAP8.buffer.byteLength`), read via a worker message, at each point: after Pyodide ready, after open, after rendering all M5 pages, after `to_bytes`, and after closing the document and running `gc.collect()`. In Chromium, also `performance.memory.usedJSHeapSize` on the main thread. Flag growth after close (a leak signal). Run the 1000-page fixture last and note any out-of-memory error. |
| M8 | **Main-thread blocking** | A `PerformanceObserver` for `longtask` on the main thread during the whole M2 and M5 runs. Report the count and the longest. Budget: none > 50 ms that is caused by our code. Tasks during the initial script evaluation are listed separately. |

## Environments

1. **CI**: GitHub `ubuntu-latest`, Chromium (Playwright). Record the CPU model (`/proc/cpuinfo`) and core count. CI numbers are for trends only, since runners vary.
2. **The maintainer's Windows laptop** (this repo's dev machine). This counts as the "mid-range laptop" for the budget verdict. Take the wheel from the W0.1 CI artifact (`gh run download`), and record the CPU, RAM and browser version. Run Chromium; also run Firefox and WebKit (Playwright) for M2, M3 and M5 on the 10-page fixture only, to spot outliers early.

## The report (`docs/web/spikes/W0.2-results.md`)

- environment details for each run;
- the M1–M8 tables, with each budget marked **met** / **missed by X**;
- where cold start goes (a bar per phase as a Markdown table is enough), and the three biggest items in M1;
- concrete recommendations ranked by gain, each mapped to a later task. Examples to evaluate, not assume: lazy-load fonttools/Pillow only when editing (W2.6/W3.1), trim `data/` for the web zip, split the PyMuPDF wheel, pre-render page 1 during package loading, the size of the render cache that fits the memory budget (W1.4), and a page-count or size limit for the warning (W3.9);
- an answer to: is decision 5 (a disposable job worker) affordable, given M4 and the doubled memory in M7?
