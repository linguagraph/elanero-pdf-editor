That matters for focus: the dialogs return focus to the button that opened them (`layout/Overlay.tsx:15-17`), and an import that turns an empty panel into a list must not remove that button.

## 4. Refresh after undo, redo and save

The list is the engine's, read again on a change. Three paths reach it today:

1. **A page revision moves** (any comment change, an import, an undo from a toast): `subscribeRevisions` → `noteChange` (`controller.ts:99-105`).
2. **Undo and Redo** through the ribbon, menu or keys: `onHistoryStep` calls `comments?.noteChange()` (`App.tsx:613-616`) as well as moving the revisions, so a history step that changed only names still reads the list.
3. **Save**: no page revision moves, but a full save gives every unnamed comment a real `/NM` (`actions/base.py:113-122`, `document.py:752-755`), so the panel's names are stale until it reads again. `saveTab` calls `noteChange` (`App.tsx:500`).

The gaps, fixed in slice 2 together with the test:

- **Save As** (`saveAsCopy`, `App.tsx:504-511`) makes the same full save on the open document (`session.py:296-318`: `prepare_full_save` runs for `copy`), but does not call `noteChange`.
- **A blocked download** (`download-blocked`, `saver.ts:40`) also ran the save in the engine; neither path refreshes on it.

Rule: after Save or Save As of the shown session, refresh when the outcome is `saved` or `download-blocked` (the engine saved). A small helper keeps the two call sites the same:

```ts
// A save that reached the engine names unnamed comments (a full save), so the list is read again.
const afterSave = (tab: DocumentTab, outcome: SaveOutcome) => {
  if ((outcome.status === 'saved' || outcome.status === 'download-blocked') &&
      tab.handle === session?.handle) comments?.noteChange();
};
```

A stale name is not harmful in the meantime (actions follow renames through `current_name`), but the list and the actions must agree after the step, and the test pins it.

## 6. Risks

- **Two entry points for one dialog** (ribbon and panel). Both set the same App state, so there is one dialog and one job; the risk is only of a test checking one path. The App test covers both.
- **The App test's fake engine grows.** Keep the new answers in the new `describe`'s own engine wrapper (as `savingEngine` wraps `drawingEngine`), so the other App tests are not touched.
- **Debounce timing in tests.** The controller waits 150 ms (`controller.ts:18`); the App tests wait with `until` on the recorded calls, never with fixed sleeps.
