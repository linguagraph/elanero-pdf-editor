# W6.8b: style bar and font picker (design)

Stage: W6 · Role: design Opus 5.5; implementation Haiku 5.5, review Sonnet 5.5 · Branch: `phase-w-w6.8b-font-picker` · Builds on [W1.5](W1.5.md) §5 and §7, [W6.9 slice 1](W6.9-font-validate.md), and the desktop's `TextStyleBar` (`ui/view/text_editor.py`) and `FontPicker` (`ui/font_picker.py`).

Status: design only. No production code in this PR.

## Summary

The style bar sits above W6.8a's in-place textarea and sets font, size, bold, italic, colour, alignment and line spacing for the paragraph being edited. The font picker has three sections: **In this document**, **Standard** and **Uploaded**, with no Installed section (W1.5 §5, W1.1 §3). Nothing is sent to the worker while the user styles: the bar only changes the textarea's preview and the style that W6.8a's commit sends with `content.replace_text` or `content.add_text`. The engine already resolves every kind of `FontRef` and reports substitutions (`FontChoice`), so the Python side needs only a guard on `FILE` refs and one small fix to the substitution report. The work is split into three PRs (section 10) because it is over 400 lines and the Uploaded section needs W6.9 slice 2.

**Dependencies.**
- **W6.8a (the in-place editor) must be merged first, all of it.** Only its S1 (fontTools on the web, #478) and S2 (`content.preview_font`, #482) are on main. The textarea, the preview-font loader, the commit and cancel rules, and the substitution notice are not built yet. 8b-1 and 8b-2 plug into those pieces and can't start before them.
- **W6.9 slice 2 (worker storage and the catalogue: `fonts.add`, `fonts.list`, `fonts.remove`, opaque face ids, the `FILE` ref check) must be merged before 8b-3**, the Uploaded section. 8b-1 and 8b-2 do not depend on it. Section 4.3 says what the picker does before uploads exist.

## 2. How the picker applies a font (the W6.8a commit path)

The editor keeps two `TextStyleJson` values: `opening` (the block's `TextStyleDto`, or for Add Text the last style used, else Helvetica 11 pt) and `current`. The bar edits `current` only. Nothing reaches the worker until W6.8a commits (Ctrl+Enter, or focus leaving the editor and its bar). W6.8a's rule "commit only if the text or the style changed" compares `current` with `opening` field by field, including the ref.

On commit, `edit/textStyle.ts` builds the `style` arg with the desktop's `TextStyleBar.text_style()` rule, so both apps send the same thing:

| Picked | `style.font` | `style.font_ref` | Engine path |
|---|---|---|---|
| The block's own font, untouched | the block's font name | `null` | reuse the embedded program; base-14 fallback |
| Another font of this page (section 4.1) | that font's name | `null` | same: `font_program(page, name)` finds it by `font_key` |
| A standard font the user chose | `Helvetica`, `Times-Roman` or `Courier` | `{kind: "standard", name, path: "", index: 0}` | the matching base-14 face for bold/italic |
| The default standard font of new text, unchanged | `Helvetica` | `null` | as desktop (`_initial_default`) |
| An uploaded face (8b-3) | the family name | `{kind: "file", name: family, path: <face id>, index}` | `load_file_font`, embedded if it covers the text |

`size` is clamped to 4–144 pt and rounded to 0.1, `line_height` to 0.8–3.0 and rounded to 0.01, as on desktop. `char_spacing` and `word_spacing` are passed through from `opening` unchanged (the desktop bar has no fields for them). All four `FontRef` fields are always sent, so `from_json` never relies on defaults.

The reply's `FontChoice` goes to W6.8a's notice code, extended as in section 5.

## 3. What the engine does with each font (no change in 8b except 5.2)

- **Document font** (`font_ref` null): `font_program(page, name)` looks for an embedded program with that name **on the current page only**. If the program's Unicode `cmap` covers every non-space character, it is reused (`embedded_reused`), with `_single_codepoint_cmap` fixing the ToUnicode map. Otherwise the text is set in the base-14 face closest to the name (`family_of` → sans, serif or mono, plus bold/italic), and `substituted` is true.
- **Standard font**: MuPDF's built-in base-14 clone (the URW Nimbus faces in MuPDF) for the family and bold/italic. It is **embedded**: `_html_setup` adds the program to the layout archive, so the saved file carries a subset of it and shows the same in every reader. These fonts cover Latin-1 and a little more, not Cyrillic, Greek or CJK; characters they lack come back in `missing`.
- **Uploaded font** (8b-3): `load_file_font(path, index)` splits a collection face out and checks fsType again (`_check_embeddable`, `UnsupportedFeature` on `restricted`/`bitmap_only`). If it covers the text it is embedded (subset on save); if not, the engine falls back to the document font, then base-14, with `substituted` and `missing` set.
- **Embedding restrictions on the document's own fonts.** The engine does **not** check the fsType of a program already embedded in the PDF before reusing it, on desktop either. W6.9's parity rule (its question 3) says changes to the licence rules apply to both apps in their own issue, so 8b keeps this behaviour (question 4).
- **Subset document fonts.** Most embedded fonts are subsets. Text using only glyphs already in the subset reuses it; anything else falls back to base-14 with the notice. The picker marks subset fonts (section 4.1) so this doesn't surprise the user.

## 4. The font list

### 4.1 In this document

**Source: the W6.7a object cache, not `session.fonts`.** The list is the distinct `style.font` names of the text blocks in `content.objects` for the page being edited, which the Edit tool has already loaded. The block's own font comes first, then the others in name order (case-insensitive, after stripping a subset tag).

Why the page and not the whole document: the engine resolves a document font on the current page only (`font_program` walks `page.fz.get_fonts`). A font listed from another page would quietly fall back to base-14 on commit. Listing only what the engine can use keeps the picker honest (question 1). Why not `session.fonts`: it walks every page under the `action` deadline and is refused while a task runs; the object cache is already in memory and costs no call.

Display rules:
- A name with a subset tag (`ABCDEF+`) is shown without the tag and with the suffix "(subset)", and its tooltip says "Only part of this font is in the file. Characters it lacks are set in a standard font." The ref keeps the name as the engine reported it.
- Names are untrusted text from the file: rendered as text, truncated to 64 characters with an ellipsis in the list (full name in the tooltip).
- If `content.objects` was `truncated`, the list may miss fonts; no message (the edited block's font is always present).
- A page with no text blocks (Add Text on an empty page) shows no "In this document" section.

**Bold and italic for document fonts.** The engine can't make an embedded program bold. So for a document font, Bold and Italic are enabled only when the page has a sibling font of the same family with the other weight or slant; toggling then switches `style.font` to that sibling. The family match is a pure function, `siblingFont(name, bold, italic, pageFonts)`: strip the subset tag, split at the last `-` or `,`, and match a style suffix from a fixed list (`Bold`, `BoldMT`, `Italic`, `Oblique`, `BoldItalic`, `BoldOblique`, `It`, `BdIt`, `Bd`, with `MT`/`PS` trailing). Without a sibling, the buttons show the block's state and are disabled, with the tooltip "This font has no bold (italic) face on this page. Choose a standard or uploaded font." This differs from the desktop, which leaves them enabled and, without an installed copy, changes nothing until a fallback happens (question 2).

### 4.2 Standard

Always shown, the desktop's three entries and labels: "Sans (Helvetica)", "Serif (Times)", "Mono (Courier)", sending `Helvetica`, `Times-Roman`, `Courier`. Bold and italic are always enabled (base-14 has all four faces per family). The labels go through `t()`; the names sent are fixed.

No Symbol or ZapfDingbats: the desktop doesn't list them, and `family_of` maps them to sans.

### 4.3 Uploaded (8b-3), and before uploads exist

After W6.9 slice 2 the section lists the catalogue's families from `fonts.list` (family, style, weight, italic, scripts, face `id`, `index`), one row per family, sorted by name. Picking a family selects the face matching the current bold/italic (the desktop's `cached_catalog().find(family, bold, italic)`, ported as a small TS function over the list), and Bold and Italic are enabled per family as on desktop: bold when some face has weight ≥ 600, italic when some face is italic. Refused faces never reach the list (W6.9 drops them at upload). The section's last row, "Upload font…", is added by W6.9 S4 when that slice lands (or by 8b-3 if S4 is first, opening S4's dialog).

The textarea previews an uploaded face with `new FontFace("upl-<id>", bytes)`, the bytes read from OPFS by the main thread (W6.9 S3 stores them there). Until the face loads, the preview uses the generic family from `family_of`.

**Before W6.9 slice 2 is merged** (8b-1 and 8b-2 ship this way):
- The picker has no Uploaded section, and no placeholder text: a section that can't do anything is noise.
- The worker refuses any `FILE` ref coming through `actions.run` with `INVALID_ARGS` (`args.style.font_ref`, reason `font_not_uploaded`). Today the generic `from_json` would let a web caller name any MEMFS path, and `load_file_font` would read it. W1.5 §7 says only the upload folder is allowed; with no folder yet, nothing is. The check sits in `webapi/actions.py` (desktop untouched), as a predicate S2 replaces with "the id is in the catalogue". Code: about 20 lines.

### 4.4 The picker widget

An editable combobox (`role="combobox"`, `aria-autocomplete="list"`, `aria-expanded`, `aria-controls`) over a popup `role="listbox"`. Each section is `role="group"` with `aria-labelledby` its heading; headings are not options, so arrow keys skip them (as desktop). Typing filters by "contains", case-insensitive, over the shown names; empty sections hide; nothing matching shows "No fonts match". Options are drawn in the UI font: loading every document font to draw its own name would cost a `content.preview_font` call per font.

## 5. Missing glyphs: fallback and warnings

### 5.1 What the user sees

W6.8a shows the substitution notice when `substituted` is true (W1.5 §5). 8b refines the message by case, all as a non-blocking notice with **Undo** (runs the document undo) next to W6.8a's "Copy text":

| Reply | Message |
|---|---|
| `substituted`, `name` differs from the requested font, `missing` non-empty | "*{font}* can't show some of this text, so *{used}* was used instead. Missing: *{chars}*." (W6.8a's text) |
| `substituted`, `name` differs, `missing` empty | "*{font}* couldn't be reused here, so *{used}* was used instead." |
| `substituted`, `name` is the requested standard font (a standard font lacking glyphs: the engine keeps it) | "*{font}* has no characters for: *{chars}*. They may not show. Choose an uploaded font that has them." |
| `embedded_reused` or no substitution | no notice |

`{chars}` shows at most 20 characters, then "and {count} more". Characters are shown as text; control and private-use characters as `U+XXXX`.

There is no check before commit in 8b: the engine is the one place that knows the font's coverage, and the commit already reports it. A pre-commit hint for uploaded faces (desktop marks installed fonts "(no cyrillic)" using `text_scripts`) is left out (question 3).

### 5.2 Engine fix (shared with desktop, 8b-1)

`_font_for_known` sets `substituted` but not `missing` when the document's own program can't cover the text, so the notice has no characters to show for the most common case (a subset). 8b-1 computes `missing = _missing_chars(buffer, wanted)` there when `original_embedded` is true (about 6 lines). The desktop notice gains the same detail, which is a fix there too. Test: the existing `test_replace_text_in_a_subset_font_reports_substitution` also asserts `missing`.

## 6. The style bar

### 6.1 Layout

One row above the textarea, in the page overlay, the same width as the editor or wider (at least 360 px), flipped below the box when there is no room above, and kept inside the viewport horizontally. On narrow screens (< 480 px) it wraps to two rows. Order, as desktop:

`[Font ▾ 180px] [Size 4–144] [B] [I] [Colour] [Align ▾] [Line spacing]`

- **Size**: `<input type="number" min="4" max="144" step="0.5">`, with "pt" after it. An out-of-range value is clamped on blur, not refused.
- **Bold, Italic**: toggle buttons (`aria-pressed`), icons `bold` and `italic` from the existing icon set (check that `npm run icons` has them; add the desktop's SVGs if not). Disabled per section 4 (`aria-disabled` with a tooltip, so they stay focusable and explain themselves).
- **Colour**: a button showing "A" underlined in the colour, wrapping `<input type="color">` (as `MarkStyleFields`). `hexToColorJson` and `colorInputValue` reused; the wire colour has no alpha.
- **Align**: a `<select>` with Left, Centre, Right, Justify.
- **Line spacing**: number input 0.8–3.0, step 0.1.

The textarea updates its CSS live from `current`: `font-family` (the preview face, or the generic of `family_of`), `font-size` (points × zoom), `font-weight` and `font-style` (only for standard and uploaded fonts; a document font previews its own face), `color`, `text-align`, `line-height`. No inline styles: the values go through CSS custom properties set from a class plus `element.style.setProperty`, which the CSP allows (`style-src 'self'` restricts style elements and attributes in markup, not CSSOM calls); the implementer checks this against `csp.test.ts` and uses the pattern `ShapeLayer.tsx` uses if it differs.

### 6.2 Keyboard and focus

- The bar is `role="toolbar"` with `aria-label` "Text style", one tab stop and roving focus (Left/Right, Home/End), per the W1.6 patterns. Inside the combobox and the number inputs, Left/Right move the caret, not the toolbar focus (W1.6's rule for text fields in toolbars).
- **Into the bar:** Tab from the textarea (the bar follows the textarea in DOM order), and **Alt+F10** (the ARIA practice for "go to the toolbar"). **Back:** Shift+Tab from the bar's first stop, or **Escape** in the bar when no popup is open, returns focus to the textarea with its selection kept. Escape in an open picker closes the popup only. Escape in the textarea cancels the edit (W6.8a).
- **Shortcuts in the textarea:** Ctrl+B and Ctrl+I toggle bold and italic when enabled (default prevented, which also stops Firefox's bookmarks sidebar); when disabled, they do nothing and announce the tooltip text. Ctrl+Enter commits from anywhere in the bar too.
- **Focus rule (W6.8a):** focus moving between the textarea, the bar, the picker's popup and the colour input is not "leaving". The editor's container gets `data-editor-scope`, and W6.8a's blur handler checks `relatedTarget` against it. The native colour dialog may blur the window without a `relatedTarget`: the bar sets a `picking` flag while the colour input is open (as desktop's `TextStyleBar.picking`), cleared on `change`/`blur` of the input.
- Tab from the last stop of the bar leaves the editor, which commits (W6.8a rule).

## 11. Risks

1. **W6.8a's shape is not final.** The editor component, its commit function and its notice code don't exist yet, so the integration lines above are estimates and the file names may change. 8b-1 starts from whatever W6.8a merges; if W6.8a already includes a bar skeleton, 8b-1 shrinks.
2. **Page-scoped document fonts.** Users may expect every font in the document. The page list is what the engine can actually reuse (question 1). A font used only on another page is not offered.
3. **Name-based sibling matching** can miss unusual names (no bold offered) or match a wrong face (a "Bold" sibling of a different design with the same prefix). Missing is safe; a wrong match only changes which embedded program the user sees after commit, and Undo restores it. The table-driven tests pin the rules.
4. **Standard fonts lack non-Latin glyphs.** A user typing Cyrillic in Helvetica gets row 3 of section 5.1 and text that may not show. Until uploads exist (8b-3), there is no font on the web that can show it unless the page has one.
5. **No fsType check when reusing the document's own embedded fonts** (section 3), on both apps. Left as is for parity (question 4).
6. **Native colour dialog and focus.** Browsers differ on whether opening `<input type="color">` blurs the page; the `picking` flag covers it, and Playwright on three browsers (W8.1) is the real check.
7. **Ctrl+B / Ctrl+I.** Some browsers reserve shortcuts; `preventDefault` works for these two in Chromium, Firefox and WebKit at the time of writing, but this needs the Playwright check.
8. **`FILE` ref guard on the web.** Before 8b-2 merges, `actions.run` would already accept a `FILE` ref with any MEMFS path (a gap, not reachable from the UI). If W6.9 S2 lands first it should add the check itself; whichever is first adds it, and the other reuses it.
9. **Preview versus result.** The preview of a standard font uses the browser's generic family, not the URW face the engine embeds, so line breaks can differ a little until commit. This is W1.5's accepted "the preview is a preview".

## Questions for the maintainer

1. **Which document fonts to list: the current page's (from the object cache), or every embedded font in the document (`session.fonts`, plus an engine change so `font_program` can reuse a font from another page)?** Recommended: **the current page's** now. It needs no new call and no engine change, and never offers a font that would silently fall back. Document-wide reuse is an engine feature for both apps, for its own issue.
2. **Bold and italic on a document font with no sibling face: disable them (this design), or leave them on as desktop does, where they change nothing unless the text falls back?** Recommended: **disable with an explaining tooltip** on the web, and file a small desktop issue to do the same, since a pressed Bold that doesn't make the text bold is a bug report waiting to happen.
3. **Pre-commit glyph hint for uploaded fonts** (desktop's "(no cyrillic)" from `text_scripts` and the face's `scripts`)? Recommended: **not in 8b**; the commit's `missing` report and Undo cover it. Add it later with a TS port of `text_scripts` checked against shared vectors, if users ask.
4. **fsType of fonts already embedded in the PDF:** keep reusing them whatever their licence bits (today's behaviour on both apps), or refuse to reuse `restricted`/`bitmap_only` programs and fall back with a notice? Recommended: **keep parity in 8b**; open a separate issue for both apps, since it changes desktop behaviour and needs its own tests.
5. **Split into 8b-1, 8b-2, 8b-3 as in section 10?** Recommended: **yes.** 8b-3 is small and could instead be folded into W6.9 S4 (the upload UI), which also touches the picker; folding saves one PR if S4 is built after 8b-2.
6. **Where the `FILE` ref guard lives:** `webapi/actions.py` (web only, desktop untouched) or the shared `content.replace_text`/`add_text` actions? Recommended: **`webapi/actions.py`**. The desktop legitimately sends installed-font paths.
