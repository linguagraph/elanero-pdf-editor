# W5.3: Links in the document view

Stage: W5 · Role: design Opus 5.5; implementation Haiku 5.5, review Sonnet 5.5 · Branch: `phase-w-w5.3-link-ui` · Builds on the merged `session.links` call (#519, `src/pdfeditor/webapi/session.py` `page_links`), the navigation history (#248, `web/app/src/view/navigation.ts`, `navHistory.ts`), the threat model ([W1.1](W1.1.md) rows S and I of the outputs boundary B7), the dialog list ([W1.6](W1.6.md) "Open link") and the security specs ([W1.7](W1.7.md) §6). The plan's rule (docs/web/plan.md, security): only `http`, `https` and `mailto` open, after a confirmation that shows the target; everything else is blocked.

## Summary

Each mounted page gets a link layer: one transparent, focusable element per link, placed from the visible-space rect that `session.links` returns, scaled the way the text layer is scaled, and shown only for the page revision it was read at. A link to a page in this document jumps there (to the target's top when the link gives one) and is recorded in the tab's navigation history. A web or mail link is parsed in TypeScript, checked against a three-scheme allow-list, and opened only after a confirmation dialog that shows the parsed address as text; Open calls `window.open(href, '_blank', 'noopener,noreferrer')`. Anything else gives a short status message and opens nothing. No PDF-derived string reaches an `href`, `innerHTML` or a URL sink other than that one `window.open`, after the check.

## 1. Scope

**In:**

- Link annotations as `session.links` reports them: `goto` (same document), `uri`, and `unsupported` (named actions, GoToR, Launch, JavaScript and anything else; file names and launch targets never leave Python).
- Following a link by pointer (mouse, pen, touch tap) and by keyboard; screen-reader names.
- Link jumps recorded in the existing per-tab history (Back and Forward already exist).
- The confirmation dialog, the scheme allow-list, refusal messages.
- The user-guide update (`docs/guide/web.md`, `docs/guide/web-accessibility.md`) and the PLAN.md tick.

**Out:**

- Creating, editing or deleting links (link authoring is not in the web set).
- Detecting URLs in the page text (no auto-linking from the text layer); a URL printed on the page without a link annotation stays plain text.
- Showing links in the Comments panel or as annotations: `Link` annotations stay out of `comments.list`, and the comment layer is not involved.
- Form widgets and their actions (forms authoring is out of scope; widgets only render).
- Opening other documents (GoToR) or embedded files from a link; named actions (NextPage, PrevPage...) and JavaScript actions.
- Positions in the navigation history: the history keeps pages (#248), so Back returns to the page's top, not the exact scroll position.
- A "don't ask again" option in the dialog.
- Changing the desktop's link handling (see question 9).

## 2. Data and placement

**Call.** `session.links {handle, page}` → `{revision, links, truncated}` (`LinksResult` in `web/app/src/rpc/generated.ts`). Each `LinkDto` has `rect` (`RectDto`, points, visible space, top-left origin, already rotated: #519 fixed rotated pages), `kind` (`"goto" | "uri" | "unsupported"`, typed as `string` in the generated file), `page` (0-based, null when missing or out of range), `top` (target y, null when absent) and `uri` (raw, at most 2048 chars; empty unless `uri`). At most 500 links per page; `truncated` says more existed. Degenerate rects are already dropped in Python. `session.links` must be added to the `PageRpc` method union in `web/app/src/engine/engineConnection.ts`.

**Kind narrowing.** Because `kind` is a plain `string`, the TypeScript side narrows it in one function (`classifyLink`, §5): any value other than `goto` or `uri` is treated as unsupported, so a future engine kind can never fall through to an open.

**Cache and the revision check.** A `LinkCache` (`web/app/src/links/linkCache.ts`) holds one list per `page:revision`, where the revision is `scheduler.revisionOf(page)`, the value the page canvases, `PageTextLayer` and `EditLayer` already use. It follows `edit/objectCache.ts`'s rules, which are the strictest of the page overlays:

- a reply is shown only when `reply.revision === revision` (the `EditLayer` rule: "the list only counts for the revision its keys belong to"); an answer at a newer revision is not stored under the older key, and the next render asks again;
- a newer revision of a page drops that page's older lists;
- a failed request is forgotten, so the next ask retries; the page then simply has no links;
- at most 300 lists (the text layer's `MAX_TEXT_LAYERS`), oldest evicted first.

The cache is made with `useMemo(() => new LinkCache(rpc, handle), [rpc, handle])` beside `textLayers` in `DocumentView.tsx`, so it lives exactly as long as the text-layer cache. `session.links` has the `render` deadline, so it queues like a render.

**Placement.** `PageLinkLayer` (`web/app/src/links/PageLinkLayer.tsx`) is rendered inside each `.doc-page`, after `PageTextLayer`, so it is on top of the text spans. Each rect is scaled with `pointsToCss` from `web/app/src/comments/coordinates.ts` (points × zoom × `CSS_PX_PER_POINT`), the same factor `placeLines` in `text/textLayer.ts` uses, so a link and the text it covers line up at every zoom and DPR. Rects are relative to the page box, so tiles, the scaled scroll space and the spreads layouts need nothing extra. The web view never rotates (rotation 0 in every cache key), so no view-rotation step is needed. Links are sorted by `(y0, x0)` so DOM order, tab order and screen-reader order follow reading order.

**When the layer is on.** Only with the Select or Hand view tool and no gesture tool. It is not rendered (rather than made passive) while the Edit tool, the crop-box tool, a comment tool or the mark/redact tool is on, so those tools get every press and the page offers no tab stops that do nothing. The predicate is `textLayerPassive(...) || tool === 'edit'` negated, in one helper next to `textLayerPassive`.

**Look.** Transparent by default (the PDF draws its own link appearance). `cursor: pointer`; a 1 px outline on hover; the standard 2 px `--color-accent-text` focus ring on `:focus-visible`; under forced colours the focus ring uses `Highlight`. A `title` gives the target on hover (the address for a URI, "Page {label}" for a goto), as a browser's status bar would; it is text, never markup.

## 3. Pointer, keyboard and screen readers

**Pointer.** The scroller's `onPointerDown` starts a text selection (press on a text span) or a pan (anywhere else, decision D2 of W1.4 §10), and the pan sets pointer capture on the scroller. With capture, the browser sends the `click` to the scroller, not to the link, so links cannot rely on `onClick`. Instead a small "tap" rule in the scroller:

- `onPointerDown`: if `event.target.closest('.page-link')` matches, remember `{pointerId, x, y, link}`; then run the existing selection/pan handling unchanged (a press on a link is not on a text span, so it pans).
- `onPointerUp` with the same `pointerId`: if the pointer moved at most 4 CSS px (`LINK_TAP_SLOP`), follow the link; otherwise it was a pan and nothing is followed. `pointercancel` (a touch scroll, for one) forgets the press.

This works the same with capture (mouse, pen; Hand pans with capture too) and without it (touch, where the pan hook does nothing and the `pointerup` bubbles from the link). The rule is a pure function in `links/linkTap.ts` so it is tested without a DOM. Consequence: a drag cannot start a text selection on link text; it can start next to it (question 1).

**Keyboard.** Each link is `<span role="link" tabIndex={0}>`, never an `<a href>`: a real `href` would let middle-click, drag-to-tab, "copy link address" and the context menu's "open in new tab" reach the raw URI without the check and the dialog. Enter follows the link (links do not respond to Space, as in HTML). `role="link"` already matches the view's `INTERACTIVE_SELECTOR`, so the scroller's arrow, page and space keys do not act while a link has focus. Focus inside a page pins it (`setFocusedPage`), as for any page content. Tab moves through the links of the mounted pages in DOM order; F6 and Esc are unchanged.

**Screen readers.** Each link has an `aria-label` built with `t()`:

| Kind | Name |
|---|---|
| goto with page | "Go to page {label}" (`pageLabelFor(page, labels)`, so documents with labels say "Go to page iv") |
| goto without page | "Link with no destination" |
| uri | "Link to {address}" where address is the parsed host for http/https, or the href for mailto; "Link (address not valid)" when it does not parse |
| unsupported | "Unsupported link" |

The anchor text itself stays in the text layer, which a screen reader already reads (question 4 is about adding it to the name). Status messages (§5, §6) go to a `role="status"` live region in the view, so they are announced politely.

## 4. Following a goto link

1. `classifyLink` returns `{action: 'goto', page, top}` when `kind === 'goto'` and `page !== null`, else `{action: 'notice', notice: 'noTarget'}`.
2. The layer calls the new `DocumentView` prop `onLinkGoTo(page, top)`. `App.tsx` passes a handler that does what `goTo` does today: `recordTabJump(activeId, viewState.page - 1, page)`, then `viewRef.current?.scrollToPage(page, top ?? undefined)`. The history lives in `App.tsx` (`navHistory.ts` is per tab id, and the view does not know the tab id), so the view only reports. Without the prop (tests), the view scrolls itself and records nothing.
3. `scrollToPage(index, topPt?)` gains an optional second argument: the scroll target is `scrollTopForPage(...)` plus `clamp(topPt, 0, pageHeightPt) × zoom × CSS_PX_PER_POINT`. The single-page layout uses the same addition on its scene. `DocumentViewHandle.scrollToPage` keeps its one-argument form working.
4. History: `recordJump` keeps its rule (a move of one page or less is not recorded), so a link to the next page or within the page is not in Back's list (question 3). Back and Forward (status bar buttons and the `back` / `forward` commands) need no change.

## 5. Following a URI link

**Classification (`links/linkTarget.ts`, pure).**

1. Strip leading and trailing ASCII whitespace and C0 controls (what the URL parser does anyway; done first so the empty check is honest). Empty → malformed.
2. Parse with `new URL(text)`, **without a base**. A relative reference (no scheme, `www.example.org`, `/path`, `#x`) throws and is malformed: with a base it would resolve against the app's own origin, which is never what the document meant (question 2).
3. Decide on the **parsed** `url.protocol`, never on a prefix of the raw string. The WHATWG parser removes tabs and newlines anywhere and lower-cases the scheme, so `java\nscript:` and `JaVaScRiPt:` both parse to `javascript:` and are refused; a raw-string check would disagree with what the browser would navigate to.
4. Allow-list: `ALLOWED_SCHEMES = new Set(['http:', 'https:', 'mailto:'])`. Anything else (`javascript:`, `data:`, `file:`, `blob:`, `vbscript:`, `ftp:`, `intent:`, custom app schemes) → `{action: 'notice', notice: 'blocked', scheme}`.
5. `http:`/`https:` also need a non-empty `url.hostname`; `mailto:` needs a non-empty `url.pathname`. Otherwise malformed.
6. Result for an allowed link: `{action: 'confirm', href: url.href, scheme, host: url.hostname}`. Everything after this uses `url.href`, the serialized form, not the raw string.

**Why `url.href` is the string shown and opened.** The parser punycodes the host (`xn--...`), so a homograph host shows as what it really is, and it percent-encodes non-ASCII and controls in the path, query and fragment, so `href` is plain ASCII: no bidi overrides (U+202E) or invisible characters can make the shown address read differently from the opened one. What the dialog shows is exactly what `window.open` receives.

**The confirmation dialog (`links/LinkConfirmDialog.tsx`).** Built on `Overlay` like `edit/signedWarning.tsx` (react-aria: focus trap, Esc and outside tap cancel, focus returns to the link):

- Title: "Open link?"
- First line: for http/https, "This document wants to open a page on **{host}**." (the host in bold, the part a user must check, and it exposes `https://bank.example@evil.example` as `evil.example`); for mailto, "This document wants to start an email."
- The full address in a read-only, selectable box: `dir="ltr"`, monospace, `overflow-wrap: anywhere`, max height with its own scroll (2048 chars fit). Plain React text; no anchor, no `href`.
- A warning: "Links in a document can lead anywhere. Open it only if you trust this document."
- Buttons: **Cancel** (first, initial focus) and **Open link**. The desktop asks the same question every time (`main_window.open_external_link`).

**Opening.** The Open button's `onPress` calls, synchronously in the handler (so the click's user activation is still valid and the popup is not blocked), `window.open(href, '_blank', 'noopener,noreferrer')`, then closes the dialog. Why both features:

- `noopener`: the new page gets `window.opener === null`, so it cannot navigate the app's tab (reverse tabnabbing: a page swapping the editor for a look-alike that asks to "re-open" the file or for a password), and it runs in its own browsing-context group, not sharing a process or event loop with the engine's page.
- `noreferrer`: no `Referer` header, so the target site does not learn the app's URL or that the visitor came from a PDF in Elanero. The page's `<meta name="referrer" content="no-referrer">` (W4.1) already covers this; the feature makes the call correct on its own. `noreferrer` also implies `noopener` in every browser, but both are named for the reader and for engines that differ.
- With `noopener`, `window.open` returns `null` by design, so a null return is not reported as a failure.

`mailto:` goes through the same call (question 5). The CSP does not govern top-level navigation, so nothing in `csp.ts` changes; `require-trusted-types-for 'script'` would additionally block a `javascript:` navigation if one ever slipped through.

**Refusals and malformed links.** No dialog opens; the live region shows one line and nothing is opened:

- blocked scheme: 'This link was not opened: "{scheme}" links are blocked.' The scheme comes from `url.protocol` (only letters, digits, `+`, `-`, `.`), cut to 20 characters;
- malformed: "This link was not opened: its address is not valid." (the raw text is not echoed);
- unsupported kind: "This kind of link does not work in the web version.";
- goto without a page: "This link does not lead to a page in this document."

The message clears after 8 seconds or at the next link action. The raw URI is never logged.

## 10. Risks

- **Pointer capture swallows clicks.** Handled by the tap rule (§3); a change to the pan hook must keep `pointerup` reaching the scroller. Tested in the view test and the e2e.
- **Text selection on link text.** A drag that starts on a link pans instead of selecting. Acceptable and consistent with D2, but users may notice (question 1).
- **Tab-stop flood.** A page can hold 500 links and several pages are mounted, so Tab may take long to cross a link-dense page. F6 and the page field still jump; a roving-focus model is a later option.
- **Structure changes.** The cache is keyed by page index and revision. If a reorder or delete moves a page to another index without a new revision at that index, a stale list could show on the wrong page. The render cache has the same key and the same risk; the implementer must check that structure changes bump the revisions of every moved index (`noteRevisions`), and otherwise also key the cache on `App.tsx`'s `structureRevision`.
- **Popup blocking.** `window.open` must run synchronously in the Open handler; an `await` before it loses user activation in Safari and Firefox.
- **mailto behaviour differs by browser.** Some open a blank tab next to the mail client; acceptable (question 5).
- **Spoofing in the dialog.** Mitigated by showing the parsed host and the ASCII `href`; a long URI is scrolled, not truncated, so the end of it can always be read.
- **Overlaps.** A link rect over a comment or a widget: the link layer is on top in Select and Hand, the comment tools hide it. Widgets are out of scope.
- **PR size.** At the edge of the budget; the S2a/S2b split in §8 is the fallback.

## Questions for the maintainer

1. **Press on link text: follow, or select?** A tap follows; a drag that starts on a link pans and cannot select its text. Recommended: as designed (Acrobat follows links under the Select tool, and it matches D2); selecting link text by starting the drag beside it.
2. **Scheme-less URIs (`www.example.org`).** Common in real PDFs. Recommended: treat as malformed and show the message; adding `https://` silently changes the target the dialog promises to show. If you prefer, a later change can offer "Open https://www.example.org?" in the same dialog.
3. **Short link jumps in the history.** `recordJump` ignores moves of one page or less, so a link to the next page or to a footnote on the same page is not in Back's list. Recommended: keep the rule now; record positions (page plus top) in a follow-up, after which every link jump can be recorded.
4. **Anchor text in the link's name.** The names say where a link goes, not its visible text. Recommended: ship the names in §3 now; a follow-up can read the anchor text from the text layer cache (`readyIndex`) and use "{text}, go to page {label}".
5. **mailto through `window.open`.** Recommended: yes, one code path with the same `noopener,noreferrer` features; assigning `location.href` would risk unloading the app if a browser has no mail handler.
6. **Confirm every time?** Recommended: yes, every web and mail link, every time, as the plan and the desktop do; no per-host or per-session memory.
7. **Links under the Hand tool.** Recommended: active (Acrobat does this); a drag still pans.
8. **More than 500 links on a page (`truncated`).** Recommended: no UI; a `console.debug` line without the URIs. Such pages are rare and the first 500 work.
9. **Desktop parity.** The desktop opens any URI scheme after its confirmation (`main_window.open_external_link` → `QDesktopServices.openUrl`). Recommended: a separate desktop issue to apply the same allow-list there; not in this web PR.
10. **Hover outline.** Recommended: an outline only on hover and focus, never always-on, so pages look as their authors made them.
