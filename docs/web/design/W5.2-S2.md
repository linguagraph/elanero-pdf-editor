# W5.2 S2: editing bookmarks in the web panel

Design note for slice S2 of W5.2 (PLAN.md: "pending: the web bookmark editing panel (#517's S2
and S3)"). S1 (#517) put five index-addressed outline actions in the engine. S2 lets the web
Bookmarks panel (`web/app/src/bookmarks/BookmarksPanel.tsx`) call four of them: rename, delete,
move and set destination. S3 adds `outline.add`.

Status: design only. Nothing here is implemented yet.

## 1. Scope

**In S2**

- Rename a bookmark in place (F2 or the toolbar's Rename): `outline.rename`.
- Delete a bookmark with its subtree (Delete key or toolbar): `outline.delete`.
- Move a bookmark up or down among its siblings, indent it (make it the last child of the sibling
  above) or outdent it (make it the next sibling of its parent), by keys or toolbar:
  `outline.move`.
- Point a bookmark at the page now shown in the view (toolbar only): `outline.set_destination`.
- An Undo toast after each edit (`offerUndo`), and a reload of the list after each edit, undo or redo.
- A toolbar that is shown only when the engine has `outline_write`.
- The expansion state follows the edit (a moved entry keeps its open or closed state; it is not
  reset to the file's flags).

**Not in S2**

- Adding a bookmark (`outline.add`): S3, with the empty-state "Add" button and the title from the
  selected text.
- Drag and drop. It can be a later slice: keyboard and toolbar moves are the accessible path and
  come first.
- Click-to-rename on an already selected row, double-click rename, and a context menu.
- Multi-select, and editing style, zoom or URI. Writing `is_open` back to the file: expansion stays
  view state, so expanding never makes the document dirty.
- The y offset of the current view for Set destination (see Q2). S2 sends `y: null` (page top).
- Changes to the desktop panel, which keeps using `document.set_outline`.
- Engine or RPC changes. `generated.ts` does not change: the edits go through the existing
  `actions.run`.

## 2. Contracts used (checked against the code)

`actions.run` takes `RunParams { handle: string; name: string; args: Record<string, unknown> }`
and returns `RunResult { label, executed, value, changed, state }` (`web/app/src/rpc/generated.ts`).
The `args` are converted by each action's dataclass in `src/pdfeditor/actions/outline.py`:

| name | args (exact keys) | label (undo) |
|---|---|---|
| `outline.rename` | `{ index: number, expect_title: string, title: string }` | Rename Bookmark |
| `outline.delete` | `{ index: number, expect_title: string }`; removes the subtree | Delete Bookmark |
| `outline.move` | `{ index: number, expect_title: string, parent: number \| null, position: number }` | Move Bookmark |
| `outline.set_destination` | `{ index: number, expect_title: string, page: number, y: number \| null }`; clears `uri` | Set Bookmark Destination |

All four have `requires=("outline_write",)` and commit one `SetOutlineCommand`, so each is one
undo step with a real inverse. `value` is `null` for all four.

- `index` is the entry's place in the depth-first flat list. It is the same order as the panel's
  `session.outline` entries: `outline_entries` walks `flatten()` (`OutlineItem.walk`, pre-order)
  and the actions walk `entries()` (an iterative pre-order). Both read `document.outline()`.
- `expect_title` is the title exactly as `session.outline` returned it (not trimmed again).
- A rename's `title` is stripped by the engine and must be 1 to 1000 characters after stripping.
- `page` is zero-based. `y` is in visible-space points from the page top; `null` is the page top.
- A no-op (same title, same slot) returns `executed: false`, with no undo step.

Errors (from `actions/outline.py` and `actions/base.py`):

| Code | When | Panel response |
|---|---|---|
| `STALE_OBJECT` | the title at `index` is not `expect_title` | reload; info toast `bookmarks.stale` |
| `INVALID_ARGS` | index or page out of range, empty or too long title, move into own subtree, position outside the list | `reportRpcError` (the panel prevents these, so this means a bug or a race) |
| `REFUSED`, `details.reason = "outline_too_deep"` | the edit would nest deeper than 32 levels | `reportRpcError`, mapped to the new `error.REFUSED.outlineTooDeep` |
| `BUSY` | a job is running (`ensure_idle`) | `reportRpcError` (`error.BUSY`) |
| `NOT_SUPPORTED`, `NO_DOCUMENT`, others | | `reportRpcError` |
| not an `RpcError` | | error toast `bookmarks.editFailed` |

## 3. Interaction design

### Current row

The tree already has a roving tab stop (`activeIndex`: the focused row, or the first row). S2
calls that row the **current row**. It gets `aria-selected="true"` and a highlight class
(`bookmarks-row--current`) so it stays visible when the focus is in the toolbar. It is a
single-select tree whose selection follows focus. A click on a row makes it current and goes to
its page, as today.

### Toolbar

A `role="toolbar"` strip above the tree, `aria-label={t('bookmarks.actions')}`, rendered only when
`outline_write` is true. It uses text buttons, as the Organize panel does (no new icons). The
buttons wrap in a narrow panel. Each button acts on the current row.

| Button | Key on the row | Disabled when |
|---|---|---|
| Rename | F2 | no rows; an edit is running |
| Delete | Delete | same |
| Move Up | Alt+Shift+Up | the row is the first of its siblings |
| Move Down | Alt+Shift+Down | the row is the last of its siblings |
| Indent | Alt+Shift+Right | the row has no sibling above it |
| Outdent | Alt+Shift+Left | the row is top level |
| Set to Current Page | (none) | no rows; an edit is running |

Each button has `aria-keyshortcuts` set to its key (for example `"Alt+Shift+ArrowUp"`), so screen
readers announce the key. The tooltip (`title`) shows the key too. The buttons are plain tab stops,
as in the Organize toolbar.

Keys are handled in the row's existing `onKeyDown`. `treeAction` (in `tree.ts`) gets three new
action kinds: `rename`, `delete` and `move` (with `direction: 'up' | 'down' | 'in' | 'out'`). It
returns them only for the exact chords (F2 with no modifiers; Delete with no modifiers;
Alt+Shift+Arrow with no Ctrl or Meta). The row handler calls `preventDefault()` for every key it
uses. That matters for two document-level listeners that both check `event.defaultPrevented`:

- the command palette's shortcut listener, where Alt+Left and Alt+Right are Back and Forward;
- the Edit tool's Delete listener (`DocumentView.tsx`), which would otherwise also delete the Edit
  selection.

React dispatches at the root container, before the event bubbles to `document`, so
`preventDefault()` in the row handler is seen by both.

Why Alt+Shift+Arrow rather than Alt+Arrow: Alt+Left and Alt+Right are the app's Back and Forward
(`web/src/generated/shortcuts.json`) and the browser's history keys. In the tree they would silently
turn "go back" into a document edit. Alt+Shift+Arrow is the outline promote and demote chord of
Word's outline view, and it is free in the app. See Q1.

### Inline rename

- F2 or Rename swaps the row's title span for `<input type="text" maxLength={1000}>` with
  `aria-label={t('bookmarks.rename.label')}`. The value is the current title. It gets focus with
  all the text selected.
- Enter commits. Escape cancels. Blur commits, as the desktop's `QTreeWidget` editor does.
  An Escape sets a flag first, so the blur that follows does not commit.
- Commit trims the value. If it is empty, or the same as the title, no call is made (the same as
  cancel). Otherwise `outline.rename` runs.
- The input's `onKeyDown` and `onClick` call `stopPropagation()`. Then the row's tree keys
  (arrows, Home, End, Space, Enter) and its click-to-navigate do not fire while editing. Global
  shortcuts already skip text inputs (`isTextEntry` in `CommandPalette.tsx`). Ctrl+Z inside the
  input is the browser's own text undo.
- While the input is open, the toolbar is disabled.

### Delete

There is no confirmation: the step can be undone, and the toast says what went. The toast counts the
nested entries (`tp('bookmarks.deleted', nested)`). See Q3.

### Moves (the arithmetic)

Everything is worked out on the flat `OutlineEntry[]` (`level` is 1 for top level) by pure
functions in a new `bookmarks/outlineEdit.ts`:

- `subtreeEnd(e, i)`: the first `j > i` with `e[j].level <= e[i].level`, else `e.length`. The
  subtree of `i` is `[i, subtreeEnd)`, and its size is `n = subtreeEnd - i`.
- `parentOf(e, i)`: the nearest `j < i` with `e[j].level < e[i].level`, or `null` at level 1.
- `childrenOf(e, p)`: the flat indices of `p`'s children (level `p.level + 1` within
  `(p, subtreeEnd(p))`). For `p = null`, the entries at level 1.
- `slot` is the entry's position in `childrenOf(e, parentOf(e, i))`.

`outline.move` reads `parent` as a flat index **before** the move and counts `position` in the
parent's child list **after** the entry has left it. So for entry `i` with parent `p`, sibling
list `S` and slot `s`:

| Move | Allowed when | `parent` | `position` | Why |
|---|---|---|---|---|
| Up | `s > 0` | `p` | `s - 1` | After `i` leaves, `S[s-1]` is still at slot `s-1`; inserting there puts `i` before it. |
| Down | `s < len(S) - 1` | `p` | `s + 1` | After `i` leaves, `S[s+1]` moves to slot `s`; inserting at `s+1` puts `i` after it. |
| In (indent) | `s > 0` | `S[s-1]` (flat index, `< i`, so it does not shift) | `len(childrenOf(e, S[s-1]))` | `i` is not a child of `S[s-1]`, so the count does not change when `i` leaves. `i` becomes its last child. |
| Out (outdent) | `p !== null` | `parentOf(e, p)` (or `null`) | slot of `p` among its own siblings, `+ 1` | `i` leaves `p`'s list, not the grandparent's, so `p`'s slot does not change. `i` lands right after `p`'s whole subtree. |

Outdent leaves the entry's later siblings under `p`. The entry lands after all of them, which is
what the engine's single move does. "Adopting" the later siblings, as some outliners do, would
take several moves and several undo steps (see Q4).

`applyMove(e, i, parent, position)` predicts the new flat list on the client. It returns
`{ entries, order, moved }`: `order[newIndex] = oldIndex`, and `moved` is the entry's new flat
index (for focus). It works like this:

1. Cut the span `[i, i+n)`.
2. Find the parent in the rest: `P' = P` if `P < i`, else `P - n`.
3. The insertion point is the flat index of the parent's `position`-th remaining child. If there is
   none, it is `subtreeEnd(rest, P')`, or `rest.length` at top level.
4. Shift each level in the span by `(parentLevel + 1) - e[i].level`, then insert the span.

`applyDelete(e, i)` cuts the span. Expansion indices `< i` stay, indices in the span drop, and
indices `>= i+n` subtract `n`.

The prediction is not trusted blindly. After the reload, the panel compares the reloaded list's
fingerprint with the prediction's (section 5). On a mismatch (another change got in between), the
file's flags apply, and the focus is clamped to the last row.

### Set to Current Page

The panel gets a new prop, `currentPage` (zero-based: App passes `viewState.page - 1`). The action
sends `{ page: currentPage, y: null }`. The toast says the page: "Bookmark now goes to page {page}."
The row's `aria-disabled` (for an entry without a page) clears after the reload, because the entry
now has a page.

## 4. Accessibility

- **Roles.** These stay: `tree`, `treeitem`, `aria-level`, `aria-expanded`, `aria-disabled`. New:
  `aria-selected` on the current row (and `aria-multiselectable` is not set). The toolbar gets
  `role="toolbar"` with a label, and each button gets `aria-keyshortcuts`. The rename input gets
  its own `aria-label`. `aria-posinset` and `aria-setsize` are left to the browser, which computes
  them from `aria-level` in a flat tree. Chromium and Firefox do this. It is checked with axe in
  the feature spec (section 7).
- **Focus after each edit.** The panel records where the focus was before the edit (a row, the
  input, or a toolbar button) and a target flat index:

  | Edit | Target row |
  |---|---|
  | Rename (commit or cancel) | the same row; focus goes back from the input to the row |
  | Delete | the next sibling (its new index is `old - n`), else the previous sibling, else the parent; with no rows left, the panel's header toggle button |
  | Move | the moved entry (`moved` from `applyMove`); its new parent is added to the expanded set, so it is visible |
  | Set destination | the same row |
  | STALE_OBJECT reload | the same index, clamped to the visible rows |

  If the focus was in the tree (or the rename input), it goes to the target row once the reloaded
  rows have rendered (a `pendingFocus` ref handled in an effect on `entries`). If the focus was on
  a toolbar button, it stays there, so repeated Move Down clicks work. The exception is a button
  that is now disabled (for example Move Up at the top): then the focus goes to the target row, so
  it is never lost to `<body>`. The target row becomes the current row in every case.
- **Rows keep their DOM nodes.** Rows are already keyed by flat index. Since S2 reloads in place
  rather than remounting (section 5), a row that keeps its index keeps its DOM node, and its focus,
  across a reload. That is also the case after Ctrl+Z.
- **Announcements.** Each successful edit's toast is the announcement: toasts render with
  `role="status"` (`ToastRegion.tsx`), and errors use `role="alert"`. The move toast says where the
  entry went, because a move can leave the focused node in place (for example an outdent whose new
  index is unchanged) and then a screen reader announces nothing new: "Moved "{title}" to level
  {level}, position {position} of {count}." Delete says how many nested entries went with it.
- **Busy.** While an edit is running, the toolbar buttons are disabled and the edit keys are
  ignored. Navigation keys still work. `aria-busy="true"` is set on the tree.
- **Forced colours.** The current-row highlight uses `Highlight` or `SelectedItem` system colours
  under `forced-colors: active`, as the existing rows' focus ring does.

## 5. Data flow

```
key / button
  -> plan (pure: outlineEdit.ts)        target args, predicted entries, focus target
  -> runBookmarkEdit (runEdit.ts)       actions.run { handle, name, args }
       ok, executed  -> offerUndo('info', text, { rpc, handle, history: reply.state.history,
                                                  onUndone: props.onHistoryStep })
                     -> store the remapped expansion under the predicted fingerprint
                     -> bump the panel's reload token
       ok, !executed -> nothing (no toast, no reload)
       STALE_OBJECT  -> info toast bookmarks.stale; bump the reload token
       other error   -> reportRpcError / bookmarks.editFailed
  -> reload: session.outline -> setEntries; expansion = expandedOf(tab, entries) ?? initialExpanded
  -> pendingFocus effect focuses the target row
```

- **One reload path.** The load effect's dependencies become `[rpc, handle, tabId, revision,
  reloadToken]`. `revision` is a new prop. App passes its `structureRevision` and stops using it as
  the panel's `key`, so the panel stays mounted across Undo and Redo. App's `onHistoryStep` already
  bumps `structureRevision` when `changed.changes` has kind `outline` (Ctrl+Z, the ribbon, and now
  the toast's Undo, through the new `onHistoryStep` prop). A reload keeps the old rows on screen
  until the reply arrives; there is no "Loading" flash.
- **Expansion keyed by content, not by count.** `expansion.ts` keys a tab's saved expansion by the
  entry count today, which is wrong after a move (same count, indices permuted). S2 keys it by a
  fingerprint: a 32-bit FNV-1a hash of each entry's `level` and `title`, plus the count. Each tab
  keeps the last 8 fingerprints. Before an edit, the current expansion is saved under the current
  fingerprint. After a successful edit, the remapped expansion is saved under the predicted
  fingerprint. An Undo then reloads the old outline, whose fingerprint finds the pre-edit
  expansion, and a Redo finds the post-edit one. An unknown fingerprint falls back to the file's
  flags, as a new outline does today. Page numbers are not in the fingerprint, so Set destination
  keeps the expansion.
- **Capability.** The panel reads `session.capabilities` with `session.outline` in its load effect.
  `editable = engine.outline_write === true`; a failed read counts as false (the toolbar is
  hidden), as `contentEditOf` does in `useDocuments.ts`.
- **No double sends.** `busy` is set before `actions.run` and cleared in `finally`. Every edit
  reads `index` and `expect_title` from the entries currently shown, never from a stale closure.

## 11. Risks

- **Key chords.** Alt+Shift on Windows switches the input language, but only on press and release
  with no other key, so Alt+Shift+Arrow does not trigger it. A screen reader in browse mode can
  take arrow chords; the `tree` role puts NVDA and JAWS in focus mode. The Playwright spec checks
  that the keys arrive in all three browsers. If the maintainer picks Alt+Arrow (Q1), Alt+Left in
  the tree no longer reaches Back, so the guide must say so.
- **Duplicate titles.** `expect_title` cannot tell two entries with the same title apart if the
  list shifted between them. The result is a wrong but undoable edit. A server-side outline
  revision would close this gap (it is the brief's open decision 3, deferred).
- **Prediction drift.** `applyMove` copies the engine's rule. If they ever differ, the fingerprint
  check falls back to the file's flags, and the focus goes to the clamped index: the edit is still
  right, only the view state is off. The reference-tree test pins the rule.
- **Lossy rewrite.** `set_toc` rewrites the whole outline, so the first edit can drop targets the
  model does not hold (Launch, Named, GoToR). The desktop does the same; it is recorded in S1.
- **Signed documents.** An outline edit is saved incrementally, so the signature survives, but the
  edit shows as a change after signing. The desktop bookmarks panel does not warn. S2 follows the
  desktop (Q5).
- **Large outlines.** Each edit reloads the whole outline and hashes it (O(n)), which is fine for
  thousands of entries. The tree is not virtualised; that is a W5.2 read-only concern, not new here.
- **Focus during reload.** If the reply is slow and the user moves on, `pendingFocus` is dropped
  when the focus has left the panel, so the panel never steals focus back.

1. **Move keys: Alt+Arrow or Alt+Shift+Arrow?** The task said Alt+Arrow, the earlier brief said
   Alt+Shift+Arrow. Alt+Left and Alt+Right are the app's Back and Forward and the browser's history
   keys. **Recommended: Alt+Shift+Arrow** for all four moves. The change is one line in
   `treeAction` if you prefer Alt+Arrow.
2. **Set destination: page top or the current view's y?** `DocumentViewHandle` has no location
   getter today. **Recommended: `y: null` (page top) in S2.** S3 adds a `location()` getter to the
   view handle, since `outline.add` needs the same value, and then switches Set destination to it.
3. **Confirm before deleting an entry with children?** **Recommended: no.** The Undo toast is
   enough, and the toast names the count. The desktop does not confirm either.
4. **Outdent: leave the later siblings under the old parent, or adopt them?** **Recommended: leave
   them** (one engine move, one undo step). Adopting needs a new engine action.
5. **Warn on signed documents?** **Recommended: no**, matching the desktop bookmarks panel and the
   incremental save. If you want parity with the Edit tool instead, it is about 15 more lines (a
   per-tab "warned" set and `bookmarks.signed.*` keys) and would push the slice over budget, so it
   would be its own slice.
6. **Backspace as Delete on macOS?** **Recommended: no.** Delete only (Fn+Backspace on a Mac
   keyboard), plus the toolbar button, so a stray Backspace never deletes a subtree.
7. **Toolbar: text buttons or icons?** There are no indent or outdent icons in
   `src/pdfeditor/data/icons/`. **Recommended: text buttons now**, like the Organize panel. Icons
   need new SVGs, the licence entries and `npm run icons`, and that is a polish slice.
8. **Drag and drop:** is it still wanted for W5.2, or does W5.2 tick after S3 with keyboard and
   toolbar moves only? **Recommended: tick W5.2 after S3**, and track drag and drop as a separate
   follow-up item.
