## 2. Scope decision

**Decision: the web gets user-editable shortcuts (this is what #330 delivers), and the desktop gets
one small slice that brings its conflict rules level with the web's. The desktop editor is not
rebuilt.**

Why:

- The desktop already has the feature, tested and documented (`PLAN.md:236`,
  `docs/guide/preferences.md:62-67`). Rebuilding it would buy nothing.
- W1.6 §9 (`W1.6.md:218`) already promised the web this, and the web otherwise matches the desktop's
  Keyboard Shortcuts screen. Leaving it out keeps a visible parity gap for a small cost (about 740
  lines over four web slices, section 10).
- The web needs stricter rules than the desktop (browser-reserved keys), and the desktop has two
  real holes (menu mnemonics, multi-chord sequences). Sharing one rule set is cheaper to explain in
  the guide and to test than two.
- No sync between desktop and web. They store keys in different places for different products, and a
  sync would need an account or a file format. Out of scope; a later "export/import shortcuts" can
  reuse the portable key strings both already use.

## 3. Storage

Local only. Shortcuts are not secrets and nothing is sent anywhere.

| Platform | Where | Format |
|---|---|---|
| Desktop | `QSettings` group `shortcuts` (unchanged). Windows: `HKCU\Software\pdfeditor\pdfeditor\shortcuts`; elsewhere Qt's native location for organisation and app `pdfeditor` | one value per command id, `"A|B"`; `""` = no keys; absent = default (`shortcuts.py:85-91`, `:109`) |
| Web | `localStorage["elanero.shortcuts"]` | JSON, below |

Web value:

```json
{ "version": 1, "bindings": { "fit-width": ["Ctrl+Alt+W"], "crop-pages": [] } }
```

Decisions:

- **Key name `elanero.shortcuts`.** It passes the secret-name guard (`store.ts:82-101`; a name such as
  `elanero.shortcutKeys` would be refused because of the word `keys`), and the `elanero.` prefix means
  "Clear all local data" removes it with no extra code (`clearLocalData.ts:8`).
- **Its own key, not a field of `elanero.prefs`.** Preferences are written as one record by the
  Preferences dialog's OK (`store.ts:226`); the shortcut editor applies each change at once, like the
  desktop's (`preferences.py:244`). Separate keys keep a Cancel in Preferences from undoing a shortcut.
- **Only overrides are stored**, as on the desktop. A release that changes a default reaches every user
  who didn't override that command.
- **Writes go through `writeStoredValue`** (`store.ts:106-114`), which never throws. When the write
  fails (private window, quota), the change applies for this page view and the dialog says it could
  not be saved.
- **Other tabs:** a `storage` event for `elanero.shortcuts` re-reads the bindings, so all open tabs
  agree. (Preferences don't do this today; shortcuts do, because a key that behaves differently in
  two tabs is confusing.)

## 4. Data model

One table per platform, keyed by the shared command id (`action_id` on the desktop, the registry id on
the web, the same strings by `registry.ts:3-5`).

| Field | Desktop source | Web source |
|---|---|---|
| action id | `action_id(action)` (`shortcuts.py:37-42`) | `CommandDef.id`, plus `command-palette` (`commands/shortcuts.ts:11`) |
| default keys | `ShortcutManager.defaults[id]` (Qt keys + `ACROBAT_DEFAULTS`) | `WEB_SHORTCUT_OVERRIDES[id] ?? sharedKeys(id)` (today's `effectiveKeys`) |
| user keys | `QSettings shortcuts/<id>`, absent = default | `bindings[id]` in `elanero.shortcuts`, absent = default |
| effective keys | user ?? default | user ?? default |

Web module: `web/app/src/commands/bindings.ts` owns this table and exposes `defaultKeys(id)`,
`userKeys(id)`, `effectiveKeys(id)` (moves here from `shortcuts.ts`, same signature), `assign(id, keys)`,
`reset(id?)`, `check(id, chord)` (section 5) and `subscribe(listener)`. It is plain TypeScript (no
React) so Vitest drives it directly; React reads it with `useSyncExternalStore`.

Key strings stay in Qt's portable form on both sides: modifiers in the order `Ctrl+Alt+Shift+`, then
the key name used by `shortcuts.json`. "Ctrl" means ⌘ on macOS, as today (`shortcuts.ts:69`). The web
recorder writes this form; `parseChord` (`shortcuts.ts:43-56`) reads it. A canonical formatter
(`formatChord(parseChord(s))`) is the comparison key, so `ctrl+shift+p`, `Shift+Ctrl+P` and
`Ctrl+Shift+P` are one chord and `PgDn` equals `PageDown`.

Decisions:

- **One chord per binding, one binding per assignment.** The editor assigns one key, like the desktop
  (`shortcuts.py:219`); defaults with two keys (Close, Redo) keep both until changed, and Default
  restores both. Multi-chord sequences (`Ctrl+K, Ctrl+S`) are refused: the web matcher has no
  sequence state, and prefix clashes are hard to explain.
- **Which ids are editable on the web:** every visible registry command that the web runs from a
  shortcut, plus `command-palette`. Dropped commands (`DROPPED_IDS`, `catalog.ts:46`) never appear.
  Commands hidden by a capability are listed only when visible, but conflict checks cover them all,
  so enabling a capability later cannot create a clash.
- **Not editable:** the fixed keys in section 5 (F6, Escape, Enter, Delete, panel keys). They are not
  registry commands and stay hard-wired.

## 5. Conflict rules

`check(id, chord)` returns one of `ok`, `warn(reason)` or `refuse(reason)`. Assign is disabled on
`refuse`; `warn` shows the reason and still allows Assign. The desktop gets the same classes where they
apply (slice D).

| Class | Keys | Result | Where it comes from |
|---|---|---|---|
| Duplicate | a chord another command holds now (user or default) | refuse: "Ctrl+E is already used by Properties. Remove it there first." | desktop rule, `shortcuts.py:213-218` |
| Browser keeps it | Ctrl+W, Ctrl+F4, Ctrl+Tab, Ctrl+Shift+Tab, Ctrl+N, Ctrl+Q, Ctrl+Shift+N, Ctrl+Shift+T, Ctrl+Shift+I, Ctrl+Shift+C (the W1.6 table), plus Ctrl+T, Ctrl+L, Ctrl+R, F5, F11, F12, Ctrl+Shift+J, Alt+F4, Alt+D, Alt+F | refuse (web only): "Your browser uses this key itself." | `W1.6.md:205-214`; the additions are common browser keys not yet probed, recorded by the probe in slice W3 |
| Browser may keep it | Ctrl+1 to Ctrl+9, Ctrl+0, Ctrl++, Ctrl+-, Ctrl+=, Ctrl+E, Ctrl+K, Ctrl+D | warn (web only): "Some browsers use this key; it may not work everywhere." | the second group, `W1.6.md:216` |
| App keys | Tab, Shift+Tab, Escape, Enter, Space, Backspace, Delete, the arrow keys, Home, End, PgUp, PgDn alone or with Shift; F6, Shift+F6; the Bookmarks panel keys | refuse: "Elanero needs this key for moving around and editing." | `useFocusRegions.ts:87`, `DocumentView.tsx:587`, `:682`, `:702`, `BookmarksPanel.tsx:63-70`; WCAG 2.1.1 and 2.1.2 (keyboard navigation must keep working) |
| OS keys | Alt+Tab, Alt+F4, Ctrl+Alt+Delete, the Windows key and macOS Control combinations | refuse: the recorder does not accept the Meta (Windows) key or the macOS Control key in v1 | the matcher has no Meta form; fixes error 4 above at the same time |
| Desktop menus | Alt+ a menu mnemonic letter (`main_window.py:738-742`) | refuse (desktop only) | slice D |

Unmodified letters and digits stay allowed (Hand tool is `H`, Select is `V`): shortcuts never run while
focus is in a text field (`CommandPalette.tsx:115`) and the paragraph editor stops keys
(`ParagraphEditor.tsx:156`). The recorder shows a warn for them: "Typing this letter runs the command
when no text box has focus."

Two further rules:

- **Ctrl+O, Ctrl+S and Ctrl+P are always prevented on the web**, bound or not, so moving Save off
  Ctrl+S never lets the browser's own Save dialog open over the app. This generalises the Save case at
  `CommandPalette.tsx:116-117`. They can still be assigned to another command.
- **Stored values are checked on load.** A stored chord that no longer parses, that is now in the
  "browser keeps it" or "app keys" class, or whose id no longer exists is ignored (the default applies)
  and dropped on the next write. If a new release gives command B a default that a user already put on
  command A, A keeps it (user keys win in matching) and B's row shows "Conflict: also used by A" until
  the user changes one of them. Nothing is reassigned silently.

## 6. Keeping help, menus and the list in sync

Rule: **every place that shows or matches a key reads `effectiveKeys`, and nothing else.**

- Web consumers moved onto `bindings.ts`: `commandForEvent` (`shortcuts.ts:87-100`), palette rows
  (`CommandPalette.tsx:234`), `ShortcutList`, `HelpButton`, `CollapseChevron`, and the ribbon's
  `CommandButton`, which today reads `registry.shortcut` (error 3). `registry.shortcut` is renamed
  `defaultShortcut` and kept for the tests that compare the registry with the table
  (`commands.test.ts:113-116`). A Vitest test fails if any file under `src/` outside `commands/`
  imports `sharedKeys` or `defaultShortcut`.
- React components re-render on a change through `useSyncExternalStore(subscribe, …)`, so the ribbon,
  palette and dialog update the moment Assign is pressed.
- Desktop: unchanged. Menus show `QAction` keys natively; tooltips and the ribbon help tooltip refresh
  through `ShortcutManager.changed` (`main_window.py:377-378`).
- The guide's `docs/guide/keyboard-shortcuts.md` lists the **defaults** and stays generated from
  `manager.defaults` (`make_shortcut_docs.py:79`); its intro already says how to change keys.
  `docs/guide/web.md` (Shortcuts section and the Preferences bullet at `:73`) explains the web editor
  and the refused keys; `docs/guide/preferences.md:62-67` gains the desktop's new refusals (slice D).
- `shortcuts.json` stays defaults only; user keys never go into generated files.
- One entry point: the `keyboard-shortcuts` command (app menu, ribbon, palette) opens the editable
  dialog, as on the desktop (`main_window.py:1189-1190`). The palette's own list view stays as a quick
  read-only view with a "Change shortcuts…" button that opens the dialog.

## 7. The settings screen: keyboard and screen readers

Web dialog (in the existing `Overlay`, which traps focus, closes on Escape and returns focus to its
opener, `layout/Overlay.tsx:15-16`):

1. **Filter** (`<input type="search">`, label "Filter commands"), first in the Tab order, focused on
   open. Filtering announces "N commands" in a polite live region.
2. **Command table**: a native `<table>` with a caption, columns Command, Keys, Status. Rows are
   selected by a radio-style button in the Command cell (`aria-pressed` or a radio group), so the table
   stays a plain table to screen readers and needs no grid keyboard model. Keys are shown with `<kbd>`
   in the platform form (Cmd on macOS, `displayKeys`). Status reads "Default", "Changed" or
   "Conflict: also used by X".
3. **Key recorder**: a button, "Record new shortcut for Fit Width". Pressing it enters recording mode:
   the button's name becomes "Press the new keys, or Escape to cancel", and the next non-modifier
   keydown is captured (`preventDefault`, `stopPropagation`). Tab and Shift+Tab are **never** captured,
   so the recorder is not a keyboard trap (WCAG 2.1.2); Escape cancels recording only, and does not close
   the dialog (it is stopped before the `Overlay` sees it). Letters and digits are read from
   `event.code` (Alt on macOS changes `event.key`, see `shortcuts.ts:76-80`).
4. The result of `check` is shown under the recorder and announced: `ok` and `warn` in a polite live
   region ("Ctrl+Alt+W. Press Assign to use it."), `refuse` with `role="alert"`.
5. **Assign**, **Remove**, **Default** (this command) and **Reset all…** buttons. Reset all asks for
   confirmation in place (the pattern of Clear all local data, `PreferencesDialog.tsx:369-370`), and
   focus moves to the confirm button and back. After Assign, Remove or Default, focus stays on the row's
   button and the live region says what changed.
6. All text through `t()` with keys in `en.ts`; no inline style (CSP rule in AGENTS.md).

The ribbon's hidden description of each command (`Ribbon.tsx:460-463`) carries the effective key in
platform form, so screen readers announce the user's key.

Desktop (slice D only): `QKeySequenceEdit` keeps Qt's behaviour, but the GUI test checks that Shift+Tab
leaves the editor and that the clash message is set on a label the accessibility tree exposes (the
message label gets `setAccessibleName`). If Qt captures Tab inside the editor (not verified here), the
dialog adds a note "Shift+Tab leaves the key box" under it rather than changing Qt's widget.

## 8. Migration and reset to defaults

- **Web:** there is no earlier data, so nothing migrates. `version: 1` lets a later format change
  read old data; an unknown version is ignored (defaults apply) and left untouched until the user makes
  a change, so a downgrade between versions never wipes a newer file.
- **Desktop:** no change to the stored format. Slice D's new refusals apply to new assignments only; an
  existing stored key in a newly refused class keeps working (the user chose it) and its row shows a
  warning. Nothing stored is rewritten.
- **Reset:** per command (Default) and all (Reset all) on both platforms. On the web, Reset all removes
  `elanero.shortcuts`, and Preferences ▸ Clear all local data removes it too. The web's static
  overrides (`shortcuts.web.ts`) are part of the defaults, so a reset restores Alt+G for Go to Page, not
  the desktop's Ctrl+Shift+N.
