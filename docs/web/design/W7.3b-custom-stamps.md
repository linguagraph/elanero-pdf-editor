## 1. Goal and scope

W7.3 slice S6 (#681) shipped the 14 standard stamps on the web. Owner decision 5 moved custom
image stamps to this item. Goal: the web's Stamp menu matches the desktop's (`stamp_menu.py:53-73`):
standard stamps, then the user's own PNG or JPEG stamps with thumbnails, **Add Custom Stamp…**
and **Remove Custom Stamp**. A placed custom stamp is the desktop's: a `/Stamp` annotation with
`/Name /ImageStamp`, the picture embedded as its appearance, sized by `custom_stamps.stamp_rect`.

Out of scope:
- Sharing a library between the desktop (`data_dir()/stamps`) and the browser. They are separate stores.
- Renaming or reordering stamps (the desktop has neither in its menu).
- Stamps from PDF, SVG, TIFF or other formats (the desktop takes PNG and JPEG only, `custom_stamps.py:19`).
- Dynamic stamps (date and name). Editing a placed stamp's picture.
- Any change to the standard stamps of S6.

## 3. The stamp library (main thread, OPFS)

The engine never holds the library. A stamp's bytes go to the engine only when it is placed, in
that one `annotations.create`. So unlike fonts, nothing needs re-sending at start-up or after an
engine restart, and there is no sync.

### 3.1 Storage

| Data | Where | Notes |
|---|---|---|
| Picture | OPFS `stamps/<id>.img` | the user's bytes, unchanged |
| Record | OPFS `stamps/<id>.json`: `{format: 1, id, label, size, type: "png" \| "jpeg", width, height, added}` | written **after** the bytes |
| Session-only stamps | the `File`, held in memory | when OPFS is unavailable (§3.5) |

`<id>` is the SHA-256 of the bytes (`crypto.subtle.digest`, 64 lowercase hex). The same picture added
twice is one stamp (question 7). The list order is `added`, then `id`, like the desktop's order of
adding (`prefs.custom_stamps`). `label` is the file name without its extension, `_` → space
(desktop `CustomStamp.label`), trimmed, at most 100 characters, and `"stamp"` when empty. It is shown
as text and never used as a path.

Module: `storage/stampStore.ts`, `STAMPS_FOLDER = 'stamps'`, with `available`, `list`, `read`,
`write`, `remove`. To avoid copying ~120 lines, `fontStore.ts`'s record-store core is extracted into
`storage/recordStore.ts` (generic over the record check and the bytes extension) and used by both.
`fontStore.test.ts` must pass unchanged. `clearLocalData.ts`: `LOCAL_DATA_FOLDERS = [FONTS_FOLDER,
STAMPS_FOLDER, 'secrets']`. After the first stamp is kept, `requestPersistence()` (fontStore.ts:239)
is called once, as for fonts.

### 3.2 Checks on Add (all before anything is written)

1. File chosen with `pickFile('image/png,image/jpeg,.png,.jpg,.jpeg')`. Cancel does nothing.
2. `file.size > MAX_STAMP_BYTES` (20 MiB, a copy of `custom_stamps.MAX_IMAGE_BYTES` kept equal by
   hand with a comment, as `edit/images.ts:18-20` does): `stamp.custom.tooLarge`.
3. `imageSize(bytes)` (new `comments/imageSize.ts`, a port of `custom_stamps.image_size`, header
   only, no decode) is `null`: `stamp.custom.wrongType`.
4. `width × height > MAX_IMAGE_PIXELS` (25 MP, a copy of `webapi/limits.py:63`):
   `stamp.custom.tooManyPixels`. This matches the watermark picture check (W7.3 decision 3).
5. The library already has 64 stamps, or adding would pass 256 MiB in total (question 3):
   `stamp.custom.libraryFull`.
6. `store.write`: `no-space` → `stamp.custom.noSpace` and kept for this tab only; `failed` →
   `stamp.custom.saveFailed` and kept for this tab only; `unsupported` → session mode (§3.5).

On success the stamp tool turns on with the new stamp (desktop `add_custom` calls `on_choose`), and
the live region says `stamp.custom.added`. If the id is already stored: `stamp.custom.already`, and
that stamp is chosen.

### 3.3 Remove

**Remove Custom Stamp ▸ <label>** removes the record, then the bytes, then the folder if it is empty
(fontStore order). There is no confirmation, as on the desktop. Toast `stamp.custom.removed`: "Custom
stamp “{name}” removed. Stamps already placed are not changed." If the removed stamp was the current
one, the tool falls back to **Approved** and turns off. `remove` returns `false` →
`stamp.custom.removeFailed`. The submenu is disabled when the library is empty (desktop
`remove_menu.setEnabled`).

### 3.4 Other tabs

The menu re-reads `store.list()` every time it opens (the desktop rebuilds on `aboutToShow`), so a
stamp added in another tab appears with no `BroadcastChannel`. Placing a stamp another tab removed
fails at `store.read` with `stamp.custom.unreadable` (the desktop's wording), and that stamp leaves
the menu.

### 3.5 When OPFS is unavailable

When `privateRoot()` rejects or there is no `createWritable`: stamps are kept for the tab (`File`
objects) and a standing menu note `stamp.custom.sessionOnly` says they go when the tab closes. Add
and place work as normal (question 5).

## 4. The menu (`comments/stampTool.tsx`)

The desktop's order and wording (`stamp_menu.py:53-73`): the 14 standard stamps, a separator, one
item per custom stamp (thumbnail + label), **Add Custom Stamp…** (`stamp.custom.add`), **Remove
Custom Stamp** (`stamp.custom.remove`, a react-aria `SubmenuTrigger` listing the labels). Thumbnails
are `<img alt="">` (the label is the name) with `decoding="async"`, from
`URL.createObjectURL(blob)`, sized by the CSS class `stamp-menu-thumb` (24 px, no inline style). The
URLs are revoked when the menu closes. The keyboard works as in S6: arrows, Enter, typeahead on
labels, and → / ← to open and close the submenu.

The chosen stamp becomes `ChosenStamp = {kind: 'standard', name} | {kind: 'custom', id, label}` (it
replaces the bare `StandardStamp` in the tool state). The ribbon's Stamp toggle uses the last chosen
stamp, as today.

## 5. Placing: `annotations.create` with image bytes

Python (`actions/comment_tools.py`):
- `CreateAnnotation` gains `image: bytes | None = None` (from a `$bin` buffer through `from_json`,
  as `content.add_image`'s `data`).
- With `tool == STAMP` and `image` set: `stamp` must be `""` (else `Refused`). Then `_check_image`
  (moved from `actions/content.py` to a shared `actions/images.py`, reasons unchanged). Then
  `custom_stamps.image_size(image)`; `None` → `Refused(reason="image_format")`. This keeps PNG/JPEG
  on the desktop too, where `caps.image_formats` is `None`. A click outside the page → nothing (as S6).
- New `build_image_stamp(page, rect, data, label, author)`: `DEFAULT_STYLES[STAMP]`, `image = data`,
  `icon = IMAGE_STAMP`, `contents = label`. Rect = `stamp_rect(point, size)` (≤ 200 pt, not clipped,
  desktop parity). Undo label "Add Stamp". `text` carries the label (already checked by `_check_text`).
- The desktop `StampTool.press` calls `build_image_stamp` for its custom branch, so the model is
  built in one place (the reuse principle, as S6 did with `build_stamp`).
- Regenerate `rpc/generated.ts` (`python scripts/make_web_types.py`).

Web (`comments/placement.ts`): for a custom stamp, `store.read(id)` (or the held `File`), then
`args.image = await blob.arrayBuffer()` and `text = label`. Each placement reads the bytes again,
because a sent buffer is detached (`rpc/client.ts:121`). The live region says `stamp.placed` with
`{name}` = the label. Engine refusals are worded by the existing `error.REFUSED.image*` keys.

## 6. Signed documents

A stamp is a comment. On the desktop, comment tools do not go through `confirm_signed`; only the
content-edit tools do. On the web, S6 places standard stamps on a signed document with no check, and
saving adds an incremental update. The brief for this note said "refuse, as for other edits", but no
comment tool refuses today. This note recommends treating custom stamps exactly like standard stamps
(question 2). If the owner wants a refusal or the once-per-tab warning (`edit/editTool.ts`), it should
apply to all stamps, standard ones included, in one change.

## 10. Risks

- **Main-thread decode for thumbnails.** A 25 MP JPEG thumbnail costs a full decode in the page.
  `decoding="async"` keeps the main thread free. The byte limit makes this rare.
- **Engine-worker memory.** `add_stamp_annot` decodes in the engine worker. The 25 MP limit (checked
  again in the engine) is the guard, as for `content.add_image`.
- **A stamp used in many documents** embeds its full bytes each time (the desktop's reason for 20 MiB).

## 11. Questions for the owner

1. **Byte limit: 20 MiB (desktop library) or 50 MiB (watermark)?** Recommended: 20 MiB on the main
   thread, mirroring `custom_stamps.MAX_IMAGE_BYTES`. The engine keeps the web caps (50 MiB, 25 MP)
   and PNG/JPEG only.
2. **Signed documents: refuse, warn, or allow?** Recommended: allow, exactly like standard stamps (no
   refusal, no warning). This is desktop parity; the desktop's warning covers only content edits. Any
   change applies to all stamps in a separate item.
3. **Library limits.** Recommended: 64 stamps and 256 MiB in total, the font store's numbers, plus
   `fitsQuota`.
4. **Confirm before Remove?** Recommended: no, as on the desktop. A toast says stamps already placed
   are unchanged.
5. **No OPFS (some private windows).** Recommended: stamps for this tab only, with a standing hint, as
   uploaded fonts do.
6. **Thumbnails in the menu?** Recommended: yes (desktop parity), 24 px `<img>` from a blob URL.
7. **The same picture added twice.** Recommended: one stamp (content id). Tell the user it is already
   there and choose it. The desktop makes a "name (2)" copy, but a duplicate is no use.
