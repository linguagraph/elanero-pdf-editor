# W9.1 (#770): the quarantined pool-reuse browser test

**Status: proposed, for owner approval; no production code in this change.**

Part of #770. After #783 and #784, one test of the nine PR-level browser specs is still
quarantined: "the job pool reuses one job worker for two jobs, and the reused worker stays locked
down" in `web/app/e2e/engine-load.spec.ts`. This note finds its cause and plans the fix.

The browser specs were not run for this note: there is no PyMuPDF wasm wheel locally. Everything

## Root cause hypothesis

The test is wrong, not the pool. With the engine worker locked down, the test sees two `blob:`
workers without fetch (the engine worker and the one job worker) and counts both as job workers.
The count of 2 is exactly the reported failure, and it would be 2 on every runner, not only a cold
one. It is not a timing issue.

### How to confirm it in CI

On the implementation PR branch, before the fix to the count, one diagnostic commit is enough: drop
the `test.fixme` and log, for each `blob:` worker, its index and `typeof fetch`. The `web-browser`
job runs because the PR changes `web/` (ci.yml lines 120-130). Expected log: two workers, both
`'undefined'`, the first being the engine worker. Then the fix commit replaces the diagnostic on the
same branch, and the next `web-browser` run must pass the test. The owner checks that run by hand,
since `web-browser` is not a required check (AGENTS.md, auto-merge gate). The diagnostic commit is
optional; the fix alone passing is also evidence, and the PR body links both runs if both exist.

## Design of the fix

### Options

1. **Test-side, count starts in the harness (recommended).** Wrap the pool's `start` in
   `newPool()` (harness.ts lines 157-168) with a counter, and return it in `PoolReuseReport` as
   `started`. The spec asserts `report.started === 1`. This counts what the pool did, not what
   Playwright happened to see, so it does not depend on worker events or on which globals each
   worker removes. The lockdown check then reads every `blob:` worker and expects all four globals
   to be `'undefined'` in each (both workers lock down now), and expects exactly two `blob:`
   workers in total (one engine worker, one job worker), which is the visible cross-check that no
   second job worker started.
2. **Test-side, tell workers apart by order.** The engine worker is started first, so take
   `workers.slice(1)` as the job workers. Smaller, but it leans on the order of Playwright's
   `worker` events, which the poolCancel test (line 157-159) already shows can lag.
3. **Pool-side or worker-side marker.** Give the job worker a global or a worker `name` the test
   can read. That changes production code for a test's sake, and a marker global in a locked-down
   worker is a new thing to review for W8.6. Not needed.

Recommendation: option 1. The pool code does not change.

### Spec changes (option 1)

- Remove `QUARANTINE_POOL` (lines 10-13) and the `test.fixme` (line 114).
- Replace lines 124-142: assert `report.started` is 1; collect the `blob:` workers, expect two;
  for each, expect fetch, XMLHttpRequest, WebSocket and importScripts to be `'undefined'`. Update
  the comment so it no longer says the engine worker keeps fetch.
- `PoolReuseReport` (harness.ts lines 170-174) gains `started: number`; `poolReuse` reads the
  counter after the two runs.

## Risks

- The hypothesis is wrong and the pool does start a second worker on the runner. Then
  `report.started` is 2 and the test still fails, but now with a count from the pool itself, which
  is the evidence the next design needs. The slice stops there and is reported; it is not widened
  into a pool change.
- The engine worker's lockdown changes again (for example a gated fetch, as `translationNet.ts`
  hints, engine.worker.ts line 4). The per-worker globals check would then fail for the engine
  worker. Mitigation: the check is for the job worker's lockdown; if that happens, the spec checks
  the job worker as the second `blob:` worker. Acceptable for now.
- `web-browser` is not a required check, so a red run could merge unnoticed. The auto-merge gate
  requires the hand check.
