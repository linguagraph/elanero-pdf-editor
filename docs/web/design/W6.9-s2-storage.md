# W6.9 slice 2: worker font storage and the catalogue (design)

Status: proposed, for review. Design only: no production code in this change.
Scope: slice 2 of W6.9 (plan.md: "W6.9 [I] R1c Font upload"; W1.5 §7; W1.1 §6; W1.2 §15 item 5;
[W6.9-font-validate.md](W6.9-font-validate.md) §14 "S2").

Slice 1 (#525) added `fonts.validate` and `validate_font_bytes`, and shipped `services/fonts.py` on
the web. This slice keeps validated fonts in the **engine worker's** memory file system, lists and
removes them, puts them in a `FontCatalog`, and lets text actions name them with a `FILE` font ref
(only inside the upload folder).

**Not in this slice:**
- **OPFS persistence and start-up load (slice 3).** Nothing here survives a reload or an engine
  restart. The front end stays the owner of the fonts (OPFS, from slice 3) and re-sends them with
  `fonts.add`.
- **The upload UI (slice 4).** The Preferences ▸ Fonts list, "Upload font…", the font picker's
  "Uploaded" section (with W6.8b), and the `docs/guide/` page.
- Uploaded fonts in **job-worker jobs** (header/footer, watermark): refused in this slice (§7).

## 2. The calls

All three take no handle, emit no events and need no session lock. They call no MuPDF code, so
they do not need `ENGINE_LOCK` either. The worker answers one request at a time, so a store change
can't run alongside an action that reads a font file.

| Call | Params | Result | Deadline class | Binary |
|---|---|---|---|---|
| `fonts.add` | `name`, `data` | `FontAddResult` | `action` (as `fonts.validate`) | in: the font file |
| `fonts.list` | (none) | `FontListResult` | `instant` | no |
| `fonts.remove` | `id` | `Empty` | `instant` | no |

```python
@dataclass(frozen=True, slots=True)
class FontAddParams:
    name: str    # the user's file name, for display only; never a path; 1 to 255 characters
    data: bytes  # the whole file, one $bin buffer

@dataclass(frozen=True, slots=True)
class UploadedFontDto:
    id: str                              # sha256 of the bytes, 64 lowercase hex characters
    name: str                            # the file name of the first fonts.add of these bytes
    format: str                          # "truetype", "opentype" or "collection"
    size: int                            # bytes
    path: str                            # the FontRef path: "/fonts/<id>.<ext>"
    faces: tuple[FontFaceDto, ...]       # slice 1's DTO; embeddable, usable faces only
    refused: tuple[RefusedFaceDto, ...]  # slice 1's DTO; collection faces the licence refuses

@dataclass(frozen=True, slots=True)
class FontAddResult:
    font: UploadedFontDto
    added: bool          # False when these bytes were already stored (nothing changed)
    used_bytes: int      # the store's total after the call
    max_bytes: int       # limits.MAX_FONT_STORE_BYTES

@dataclass(frozen=True, slots=True)
class FontListResult:
    fonts: tuple[UploadedFontDto, ...]   # in the order they were added
    used_bytes: int
    max_bytes: int

@dataclass(frozen=True, slots=True)
class FontRemoveParams:
    id: str
```

`path` is in the DTO so the front end builds `FontRef{kind: "file", name: family, path, index}`
without assembling paths itself. The path is deterministic (content name), so a ref the front end
kept (a preference, the last style used) is still valid after slice 3 re-sends the same bytes to a
new worker.

### `fonts.add`, step by step

1. `name` 1 to 255 characters, else `INVALID_ARGS` (`{path: "params.name"}`), as `fonts.validate`.
2. `len(data) > MAX_FONT_BYTES`: `FILE_TOO_LARGE` `{max_bytes, size}`, before any parsing.
3. `id = sha256(data).hexdigest()`. If `id` is stored: return it with `added: false`, without
   parsing again (the same bytes gave this result in this worker).
4. Quotas (§5): too many fonts, or `used + size > MAX_FONT_STORE_BYTES`: `FONT_STORAGE_FULL`,
   before any parsing.
5. `validate_font_bytes(data, name)`: the slice 1 rules exactly (`INVALID_FONT {reason}`,
   `FONT_NOT_EMBEDDABLE {reason, faces}`, `NOT_SUPPORTED` without fontTools, `MemoryError` to
   `OUT_OF_MEMORY`). The mapping is shared with `fonts.validate` (one helper in `webapi/fonts.py`).
6. Write `/fonts/<id>.tmp`, then `os.replace` to `/fonts/<id>.<ext>`, where `ext` comes from the
   format, never from the user's name: `truetype` `.ttf`, `opentype` `.otf`, `collection` `.ttc`
   (an OTC is read by the same `TTCollection` code, so `.ttc` is right for it). An `OSError` while
   writing removes the temp file and gives `FONT_STORAGE_FULL` (`{limit: "memory"}`); a
   `MemoryError` gives `OUT_OF_MEMORY`.
7. Record the manifest entry (`name`, `format`, `size`, `refused`) and rescan the catalogue (§4).
   If the catalogue has no face for the new path (it shouldn't: the reader runs the same rules),
   the file is deleted again and the call fails with `INVALID_FONT {reason: "unreadable"}`.

The user's file name is never used on disk, so no path tricks are possible, and a re-upload of the
same file is a no-op.

### `fonts.list`

The manifest's entries in insertion order, each with its faces **from the catalogue**
(`catalog.faces()` filtered by path), so the list shows exactly what the ref guard accepts. A
fresh worker lists nothing.

### `fonts.remove {id}`

- `id` must match `^[0-9a-f]{64}$`, else `INVALID_ARGS` (`{path: "params.id"}`).
- An `id` that isn't stored is a no-op (the front end's list may be stale after a restart, and
  slice 3's "Remove all" loops over OPFS, which can hold fonts this worker never got). Idempotent
  like `jobs.abort`.
- Deletes the file, drops the manifest entry, rescans the catalogue (the cache drops the entry).
- Text already typeset with the font keeps its embedded copy (W1.5 §7). A later action that names
  the removed font is refused by the guard (§6). Undo and redo restore snapshots (bytes), not refs,
  so they still work.
- `load_file_font`'s LRU may keep an extracted face of a removed file until it is pushed out
  (8 entries). It can't be reached again (the guard refuses the path first). Evicting it would need
  an engine call and isn't worth one here (question 7).

No `fonts.clear`: slice 4's "Remove all fonts" calls `fonts.remove` per font, and clearing site
data reloads the page, which empties MEMFS anyway (question 8).

## 3. Where it lives

New module `webapi/fontstore.py` (about 140 lines), the worker's one store:

```python
UPLOAD_DIR = PurePosixPath("/fonts")  # MEMFS root folder, outside /home/pyodide and data_dir()

@dataclass(frozen=True, slots=True)
class StoredFont:
    id: str; name: str; format: str; size: int; path: str; refused: tuple[FontFace, ...]

class FontStore:
    def __init__(self, root: Path) -> None: ...      # creates root; empty manifest
    def add(self, name: str, data: bytes) -> tuple[StoredFont, bool]: ...
    def remove(self, font_id: str) -> None: ...
    def fonts(self) -> list[StoredFont]: ...
    def faces_of(self, font: StoredFont) -> list[FontFace]: ...
    @property
    def catalog(self) -> FontCatalog: ...
    used_bytes: int

def store() -> FontStore: ...                 # the worker's store, made on first use
def use_root(root: Path | None) -> None: ...  # tests: a fresh store in tmp_path; None resets
def check_font_refs(value: object, path: str) -> None: ...     # §6, actions.run
def check_no_file_refs(value: object, path: str) -> None: ...  # §7, job specs (same walker)
```

`webapi/fonts.py` gains the three handlers (about 60 lines) and keeps `validate`. The store raises
`FontRejected` and a small `StoreFull(limit, ...)`; the handlers map them to `RpcFailure` as
`validate` already does (not in `errors._MAPPING`: only these calls raise them).

Why `/fonts` and not `data_dir() / "fonts"`: the upload folder must be a fixed, short prefix for
the guard (§6) and must not be swept by anything that manages `data_dir()` (snapshots, recovery).
W1.1 §6 and W1.5 §7 both name `/fonts/`. Pyodide's root is MEMFS, so `mkdir("/fonts")` works; the
web-pytest run proves it (§9). On the desktop the webapi is never imported by the app, and tests
point the store at `tmp_path` with `use_root`.

## 4. The catalogue

`FontCatalog(folders=[UPLOAD_DIR], cache_path=UPLOAD_DIR / "catalog.json", reader=read_upload_faces)`.

Two small additions to `services/fonts.py` (about 25 lines):

- `FontCatalog.__init__` takes `reader: Callable[[Path], list[FontFace]] = read_faces`, and `scan`
  calls `self._reader` instead of `read_faces`. The desktop passes nothing, so it is unchanged.
- `read_upload_faces(path) -> list[FontFace]`: `validate_font_bytes(path.read_bytes(), str(path))`
  and its embeddable faces (each `FontFace.path` is the stored path), or `[]` on `FontRejected`,
  `ImportError` or `OSError`. So the catalogue applies the upload rules (outlines, a non-empty cmap,
  fsType), not `read_faces`'s looser ones, and lists only faces an action may use. One copy of the
  rules.

Rescans are cheap: the cache (inside the folder, ignored by `_iter_font_files` since `.json` isn't a
font suffix) means a rescan after `add` reads only the new file, and one after `remove` reads none.
The cache is in MEMFS, so it never outlives the worker; that is fine, since the fonts don't either.

The module docstring's note that `needsFontTools` is true only for `actions.run` is updated (§8).

### Which calls read the catalogue

| Reader | What it uses | Slice |
|---|---|---|
| `fonts.list` | `faces()` by path | this one |
| The `FILE` ref guard in `actions.run` (§6) | `face_for(ref)` | this one |
| `content.add_text` / `content.replace_text` | not the catalogue: the engine embeds from `ref.path` with `load_file_font`, after the guard | this one (unchanged code) |
| Reusing an uploaded font after reopening (`installed_ref_for_font_name(store().catalog, name)`, as the desktop's text editor does) | `find`, `faces_of`, `families` | W6.8b |
| Font picker "Uploaded" section, script coverage (`text_scripts`) | `families`, `faces_of`, `FontFace.scripts` | W6.8b / slice 4 (through `fonts.list`) |

## 5. Quotas

`webapi/limits.py`:

```python
MAX_FONT_BYTES = 50 * 1024**2          # per file (slice 1, unchanged)
MAX_FONT_STORE_BYTES = 256 * 1024**2   # all uploaded fonts in one worker
MAX_UPLOADED_FONTS = 64                # files
```

Why: MEMFS lives in the wasm heap, which only grows and warns at 1.5 GiB (`HEAP_WARN_BYTES`), and the
heap also holds open documents (up to 1 GiB each) and undo snapshots (`SNAPSHOT_BUDGET_BYTES`,
512 MiB). 256 MiB takes five of the largest single-weight CJK collections or hundreds of Latin
fonts. 64 files bounds the catalogue and the list reply. `fonts.add` also holds the buffer, the
Python `bytes` and the MEMFS copy at once (3 × 50 MiB at worst), which the per-file cap bounds.

The front end must keep OPFS within the same budget (slice 3 reads `max_bytes` from the replies,
so the number isn't copied by hand). OPFS's own `QuotaExceededError` is slice 3's, on the main
thread, and is not this code.

## 6. `FILE` refs only from the upload folder

`check_font_refs(value, path)` walks a converted argument value (dataclasses, tuples, lists, by
`dataclasses.fields`) and checks every `FontRef` of kind `FILE`:

- its `path` matches `^/fonts/[0-9a-f]{64}\.(ttf|otf|ttc)$` exactly (no `..`, no normalisation
  needed, no other folder);
- `store().catalog.face_for(ref)` is a face (the font is stored now, and `index` is one of its
  usable, embeddable faces).

Otherwise `INVALID_ARGS` with `{path: "<arg path>.font_ref"}` and the message "the font is not an
uploaded font, or it was removed". `STANDARD` and `DOCUMENT` refs are not touched.

Called in `actions.run` right after `from_json` (about 3 lines). This also closes today's gap,
where any `FILE` path reached `load_file_font`.

## 7. Workers: the engine worker, restarts and jobs

- **The store is per engine worker.** It starts empty. Slice 3 re-sends every OPFS font with
  `fonts.add` at start-up and after every engine restart (`restart.ts`): the new worker's MEMFS is
  empty. Because paths are content names, refs kept by the front end are valid again once the
  re-send is done. Until then the guard refuses them: slice 3/4 must wait for the re-send before
  offering uploaded fonts (and W6.8b's picker shows only what `fonts.list` returns).
- **The job worker** is disposable (plan decision 5): a cancelled job terminates it and its MEMFS,
  and a new one starts empty. It never holds uploaded fonts in this slice. The only jobs that
  typeset with a `FontRef` are the long actions `marks.header_footer` and `marks.watermark`
  (`HeaderFooter`, `Watermark`). `_convert_action` calls `check_no_file_refs` (the same walker),
  and any `FILE` ref gives `NOT_SUPPORTED` `{path}` ("uploaded fonts can't be used here yet"). The
  check runs at `jobs.prepare` in the engine worker, so the user hears it before a job starts.
  Sending the font bytes with the job (extra `$bin` buffers that the job worker writes to its own
  `/fonts/` before running, and which have to be re-sent with every job, since a cancel discards
  them) is future work, when the marks UI offers uploaded fonts (question 5).
- No other job type typesets text with a ref (compare, export, print, split, merge, extract,
  comments export use base-14 fonts or none).

## 8. `loader.ts`

```ts
// The requests that need fontTools: the text edits, and the calls that read an uploaded font.
const FONTTOOLS_METHODS = new Set(['fonts.validate', 'fonts.add']);

export function needsFontTools(request: string): boolean {
  ... parsed.method in FONTTOOLS_METHODS, or actions.run with a FONTTOOLS_ACTIONS name
}
```

`fonts.list` and `fonts.remove` read only the catalogue in memory (the rescan after remove reads no
file), so they don't need it. The job worker has no `ensureFontTools`, and gets no fonts call.
Since the install is memoized and resolves even when it fails, a failed install gives `fonts.add`
the `NOT_SUPPORTED` reply of slice 1. Vitest: `fonttools.test.ts` gains the two methods (true) and
`fonts.list` (false); `worker-server` already awaits `ensureFontTools` for every request
`needsFontTools` accepts.

## 9. Errors

| Code | Call | When | `details` |
|---|---|---|---|
| `INVALID_ARGS` | add, remove, actions.run | bad `name`, bad `id`, a missing/unused buffer, a `FILE` ref outside the store | `{path}` |
| `FILE_TOO_LARGE` | add | over `MAX_FONT_BYTES` | `{max_bytes, size}` |
| `FONT_STORAGE_FULL` (**new**) | add | over `MAX_UPLOADED_FONTS` (`limit: "count"`), over `MAX_FONT_STORE_BYTES` (`limit: "bytes"`), or MEMFS refused the write (`limit: "memory"`) | `{limit, max_fonts, max_bytes, used_bytes, size}` |
| `INVALID_FONT` | add | slice 1's reasons | `{reason}` |
| `FONT_NOT_EMBEDDABLE` | add | slice 1's rule | `{reason, faces}` |
| `NOT_SUPPORTED` | add; jobs.prepare | fontTools not loaded; a `FILE` ref in a job | none; `{path}` |
| `OUT_OF_MEMORY` | add | `MemoryError` while hashing, parsing or writing | none |

`FONT_STORAGE_FULL` is a new code (question 3): `FILE_TOO_LARGE` says "this file is too large",
which is wrong when the file is small and the store is full, and the user's fix differs (remove
fonts). It goes in `webapi/errors.py` (`ALL_CODES`, not in `UNUSED_CODES`, since this slice raises
it), `rpc/errors.ts` (`{ messageId: 'error.FONT_STORAGE_FULL', action: 'dismiss' }`), and `en.ts`.
`test_webapi_errors.py` checks that it is declared, mapped and named in a test.

## 14. Risks

1. **Heap growth.** MEMFS files live in the wasm heap, which never shrinks. Removing a font frees the
   space for reuse but not to the browser. The 256 MiB budget, plus `load_file_font`'s LRU (up to 8
   extracted faces, a few MiB each, tens for CJK), is the worst case on top of the documents. The
   heap warning (W2.3) still shows it.
2. **Fonts gone after a restart.** Until slice 3, a restart (or reload) loses the store, and refs
   the front end kept are refused. No UI uses uploaded fonts before slice 4, so no user meets this.
3. **Header/footer and watermark can't use uploaded fonts** (job worker, §7). Desktop parity gap,
   stated in the guide in slice 4.
4. **Duplicate family names** (two uploads both "Arial"): refs carry the path, so actions are exact;
   `find` by family (W6.8b reuse after reopen) picks one. W6.8b decides how the picker shows them.
5. **The rescan reads a new CJK file a second time** (validation, then the catalogue reader), a few
   seconds under Pyodide in the worst case, within `action`'s 30 s. If measured too slow, the store
   can seed the catalogue's cache from the validation result instead (a later optimisation).
6. **Stricter-than-desktop catalogue** (slice 1 question 7) also applies to the web catalogue: same
   rules for add and list, by design.
7. **`/fonts` on Pyodide's root MEMFS.** Expected to work (the root is MEMFS); the Pyodide-only test
   proves it. Fallback: `/home/pyodide/fonts`, with the guard pattern changed to match.

## Questions for the maintainer

1. **The font id.** The sha256 of the bytes (path `/fonts/<id>.<ext>`), or the path itself as W1.5 §7
   says? **Recommended: sha256 as `id`, and `path` as a separate field.** The id is short, fixed and
   the same across workers, so slice 3 can name OPFS files by it and a kept ref stays valid.
2. **Upload folder.** `/fonts` at the MEMFS root, or `data_dir() / "fonts"`? **Recommended: `/fonts`**
   (W1.1 §6, W1.5 §7; a fixed prefix for the guard, not swept with `data_dir()`).
3. **Store full.** A new `FONT_STORAGE_FULL` code, or reuse `FILE_TOO_LARGE`? **Recommended: new
   code**; the message and the user's fix differ.
4. **Budgets.** 64 fonts and 256 MiB per worker, mirrored by slice 3 in OPFS? **Recommended: yes.**
5. **Uploaded fonts in jobs** (header/footer, watermark). Refuse with `NOT_SUPPORTED` now, or send
   the font bytes with each job? **Recommended: refuse now.** No web UI offers them there yet; the
   bytes-with-job design belongs with the marks UI that needs it.
6. **The catalogue's reader.** Give `FontCatalog` a `reader` and use the upload rules, or keep
   `read_faces` and filter in the store? **Recommended: `reader`.** One copy of the rules, and the
   catalogue lists only what the guard accepts.
7. **Evict the engine's extracted-face cache on remove?** **Recommended: no.** The removed path is
   refused before it is used, the LRU holds 8 entries, and evicting needs a new engine call.
8. **A `fonts.clear` call for "Remove all fonts"?** **Recommended: no.** A loop over `fonts.remove`
   is enough for a few dozen fonts, and clearing site data reloads the page.
9. **Re-adding the same bytes under another name.** Keep the first name and return `added: false`?
   **Recommended: yes**; renaming isn't a feature, and slice 3 stores one OPFS file per id.
