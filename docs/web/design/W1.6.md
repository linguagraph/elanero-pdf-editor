# W1.6: UI/UX design

Stage: W1 (#134) · Role: design Opus 5.5 · Branch: `phase-w-w1.6-ui-ux` · Builds on [W1.1](W1.1.md) (capabilities, save modes, watchdog) and [W1.3](W1.3.md) (actions, the generated shortcut table). W1.4 (viewport) and W1.5 (editing tools) are designed in parallel and own the page area and the tools' interaction.

The web app should feel like the desktop app: the same ribbon, rails, panels, contextual bars, toasts and command palette, with the same names and icons, so the user guide and the user's habits carry over. Where the browser forces a difference (reserved keys, no native menus, file handling, narrower screens), this note says what the web does instead.

Same regions and order as desktop (`ui/main_window.py`, `ui/focus_regions.py`): ribbon, left rail and panel, page area, right rail and panel, status bar, notifications. Differences:

- **No menu bar.** The desktop's menu bar is already hidden behind the ribbon's ☰ button. The web keeps the ☰ app menu only (section 6).
- **Document tabs move into the top bar,** next to the quick-access buttons, to save a row of height in a browser window that already has the browser's own tab strip and address bar.
- **The start page** replaces the page area and both rails while no document is open (section 3).

The web uses the desktop's seven, in the desktop's order.

**Behaviour carried over from `ui/ribbon.py`:** the quick-access buttons (Select, Hand, Undo, Redo, Save); the "Search tools" box (command search) at the tab row's right end; the "?" help button (opens the user guide page of the current tab, on the docs site); collapsing the ribbon to its tab row (double-click a tab, or the chevron); icons-only "compact" mode. When the row is too narrow, whole groups move into a "»" overflow menu from the right, never single buttons (a `ResizeObserver` measures the row).

## 3. Start page and document tabs

**Start page** (port of `ui/start_page.py`): a large Open button, the drop zone ("Drop PDF files here"), quick actions, recent files.

| Desktop quick action | Web |
|---|---|
| Combine files | yes |
| Compare files | yes |
| Create from Office | hidden (`office_import`) |
| OCR a scan | hidden (`ocr`) |

Recent files on the web are **names and dates only**, stored in `localStorage` (W1.1 §5): no first-page previews (they would need the file, which the web doesn't keep), and clicking one opens the file picker with a hint ("Pick report.pdf again"). Each entry has a remove button, and the list has "Clear". While the engine is still loading (first visit), the start page shows the load stages in place of the quick actions (W3.1); a file opened during loading is queued.

**Document tabs:** one tab per open document, a dot on unsaved ones, a close button, middle-click closes, drag to reorder, and an overflow menu when they don't fit. Closing a dirty tab asks Save / Don't save / Cancel. A `beforeunload` handler warns when any document is dirty (the browser shows its own generic text). A second open of the same file name opens a second tab (the web can't tell whether two picks are the same file).

## 7. Theme, icons and brand assets

**Tokens.** `ui/style/tokens.py` is pure Python (`ui/__init__.py` and `ui/style/__init__.py` import no Qt), so a build script can call `build_colors(scheme, accent)` directly. New script `scripts/make_web_tokens.py` writes `web/src/generated/tokens.css`:

- one block per (scheme, accent preset): `:root[data-scheme="dark"][data-accent="teal"] { --color-window: …; --color-accent-text: …; … }`, with every field of `Colors` as `--color-<field-with-dashes>` and every field of `Metrics` as `--metric-<field>` in `px`;
- 2 schemes × 8 presets of `ACCENT_PRESETS` = 16 blocks (a few KB);
- `--check` exits 1 when the committed file differs, run by a unit test as for `make_shortcut_docs.py`, so a token change on desktop can't silently skip the web.

The contrast derivation (`ensure_contrast`) therefore runs only at build time. The web offers the 8 presets and no free colour picker: a custom accent would need the derivation ported to TypeScript (§16, question 3). "Follow Windows" has no web equivalent; the default is Blue.

**Scheme:** Light, Dark or System (the default, from `prefers-color-scheme`, followed live). **High contrast:** under `@media (forced-colors: active)` the app uses system colours (`Canvas`, `CanvasText`, `Highlight`, `ButtonText`…) and borders instead of fills, which is what the desktop does for Windows high contrast. **Night mode** (page inversion) is a view setting, not a theme (W1.4).

**Icons:** the 108 Lucide SVGs in `src/pdfeditor/data/icons` (ISC licence, kept with them). A build step turns them into one TypeScript module of React components (`web/src/generated/icons.tsx`), with `currentColor` strokes, so icons follow the theme and no SVG markup is ever injected at run time (W1.1 §10). Same file set as desktop, so icon names match; no `lucide-react` dependency.

**Brand assets** (copied by the web build from `data/branding/elanero`, since W1.1 drops branding from the wheel):

| File | Size | Used for |
|---|---:|---|
| `icons/platform/favicon.ico` | 8.6 KB | Favicon |
| `icons/png/elanero-32.png` | 2.7 KB | Top bar logo |
| `icons/png/elanero-128.png` | 25 KB | Start page and loading screen |
| `icons/png/elanero-256.png`, `elanero-512.png` | 84 KB, 284 KB | PWA manifest icons (W4.6) |
| `branding/elanero-wordmark.png` | 118 KB | About dialog, loaded when it opens |

The splash SVGs (841 KB each) and the other sizes are not shipped. The start of the app (first paint) loads only the favicon, the 32 px and the 128 px images (about 36 KB).

## 8. Responsive behaviour

Target: a desktop browser window, down to tablet width (768 px, iPad portrait), with touch.

| Width | Ribbon | Left panel | Inspector | Other |
|---|---|---|---|---|
| ≥ 1280 px | full (icons and labels) | docked | docked (collapsed to its rail by default) | as desktop |
| 1024–1279 px | compact (icons only, labels in tooltips) | docked | overlay over the page area | |
| 768–1023 px | collapsed to its tab row; tapping a tab shows its row as a drop-down until a command runs | overlay drawer (rail stays) | overlay | document tabs collapse to a drop-down list; quick-access keeps Undo, Redo, Save |
| < 768 px | as 768 | rail hidden behind ☰ | overlay | a dismissible notice: "Elanero works best on a wider screen". Viewing, searching and comments work; nothing is blocked |

The user's own choices (ribbon collapsed or compact, panel open) apply on top and are kept. Overlays close on Esc and on a tap outside.

**Touch** (`pointer: coarse`): targets at least 44 × 44 px (ribbon buttons, rail icons, contextual bar, handles), no hover-only affordances (tooltips also on long press), pinch zoom and two-finger pan in the page area (W1.4), and the contextual bar appears after a selection ends rather than following the finger.

## 9. Commands, palette, shortcuts and preferences

**Command registry** (W4.3). Every command is declared once in TypeScript: `id` (the desktop `action_id`, for example `save-as`, so ids match `shortcuts.json` and the guide), label key, icon, the action or handler it runs, the capabilities it needs (W1.3 `available()` plus the browser facts of W1.1 §3), whether it needs a document, and its checked state if it toggles. The ribbon, ☰ menu, contextual bars, context menus, palette and shortcuts all read from the registry, so a command hidden by a capability is hidden everywhere at once.

**Command palette** (Ctrl+Shift+P, as desktop `CommandPalette`; the "Search tools" box in the ribbon opens the same list): fuzzy search over labels and aliases, shows each command's shortcut and tab, disabled commands listed with the reason, Enter runs, recent commands first.

**Shortcuts.** Defaults come from `web/src/generated/shortcuts.json` (W1.3 slice (f)), filtered by the commands the web has. Some keys never reach a web page, because the browser keeps them; the web defines replacements in `web/src/shortcuts.web.ts`, a small override table (command id → replacement keys, or none). A unit test checks that every id in the override table exists in `shortcuts.json`.

| Desktop key | Command | Why it can't work on the web | Web default |
|---|---|---|---|
| Ctrl+W, Ctrl+F4 | Close | Browser closes its tab | Alt+W |
| Ctrl+Tab, Ctrl+Shift+Tab | Next / Previous Document | Browser switches tabs | Alt+PgDn / Alt+PgUp |
| Ctrl+N | New Window | Browser opens a window | command dropped |
| Ctrl+Q | Exit | Browser quits | command dropped |
| Ctrl+Shift+N | Go to Page | Browser opens a private window | Alt+G |
| Ctrl+Shift+T | Crop Pages | Browser reopens a closed tab | none (palette, ribbon) |
| Ctrl+Shift+I | Insert Pages | Opens the browser's developer tools | none |
| Ctrl+Shift+C | Comments List | Opens the developer tools' element picker | none |

A second group may or may not reach the page depending on the browser and platform: Ctrl+1/Ctrl+2/Ctrl+6 (tab switching in some browsers), Ctrl+0/Ctrl++/Ctrl+- (page zoom), F6/Shift+F6 (address bar), Ctrl+E, Ctrl+K, Ctrl+D. The app calls `preventDefault` on them and keeps the desktop keys, and W4.3 adds a Playwright probe on Chromium, Firefox and WebKit (Windows and macOS keys) that records which keys arrive. Any key that doesn't arrive in a supported browser gets a replacement or "none" in the override table, decided in W4.3 from the probe's result. Ctrl+O, Ctrl+S, Ctrl+P and Ctrl+F do reach pages and are taken over (the app's own open, save, print and find). On macOS, Ctrl means ⌘ throughout, as Qt does on desktop.

Users can change shortcuts in Keyboard Shortcuts (as desktop `ShortcutsDialog`: Default, Reset All), stored in `localStorage`. Assigning a key from the "never arrives" list is refused with an explanation.

**Preferences** (W4.5), stored in `localStorage`, never secrets: appearance (scheme, accent preset, ribbon compact), author name for comments, default zoom and page layout, comment defaults, redaction mark style (the desktop keeps it in `QSettings`; W1.3 passes it as an argument), translation (service, languages; keys live in memory or the encrypted store, W1.1 §6), uploaded fonts (list, remove, "Remove all fonts"), language, and "Clear all local data" (preferences, recent names, fonts, stored keys, autosaves). The grouping follows the desktop `PreferencesDialog` pages; options that only make sense on desktop (Windows accent, file association, Store updates, OCR languages, signing) are absent.

## 10. Feedback: toasts, job centre, loading

Ports of `ui/toasts.py` and `ui/job_center.py`:

- **Toasts** stack at the bottom right of the page area, avoid the canvas pill, carry at most one action (Undo; where desktop offers Show folder, the web offers Download again), and time out unless hovered or focused. Kinds: info, success, error. Errors from RPC codes are worded through the catalogue (section 11).
- **Job chip** in the status bar: the running job's label and progress; clicking opens the job list with Cancel per job (W1.1: Cancel terminates the job worker). Queued jobs show "Waiting".
- **Read-only while a job runs:** when a mutating job blocks edits (W1.1 §1), editing commands are disabled with the tooltip "Wait until <job> has finished".
- **Loading screen** (first visit): the logo, the load stages (W3.1) with a progress bar, and a link to "What's different on the web".

## 11. Message catalogue (W4.7)

- One flat JSON file per language, `web/src/i18n/<lang>.json` (start with `en.json`), keys `area.item` (`ribbon.tab.organize`, `command.save-as.label`, `error.PASSWORD_REQUIRED`, `toast.redaction.verified`), values with `{name}` placeholders.
- Plurals as an object keyed by `Intl.PluralRules` categories: `{"one": "{count} page", "other": "{count} pages"}`. A formatter of about 50 lines on `Intl.PluralRules` and `Intl.NumberFormat`/`DateTimeFormat`; no i18n library.
- Every RPC error code (W1.2) has an `error.<CODE>` entry; a unit test fails when a code has no message in `en.json`.
- A test fails when code uses a key that `en.json` lacks; other languages fall back to English per key.
- Labels for commands come from the catalogue by command id. Undo labels arrive in English from Python (W1.3, answered). The desktop's Qt `.qm` catalogues are a different toolchain and are not shared in v1.
- `lang` and `dir` are set on `<html>`; layout uses logical CSS properties (`margin-inline-start`) so a right-to-left language needs no rework later.

## 12. Accessibility

Target: WCAG 2.2 AA, matching what the desktop does in Phase U10.

| Element | Pattern |
|---|---|
| Ribbon tabs | `tablist` / `tab` / `tabpanel`; Left/Right move between tabs, as desktop |
| Ribbon row | each group a `toolbar` with `aria-label` = group caption; roving tabindex, arrows inside a group, Tab to the next group |
| Toggle tools (Select, Hand, comment tools) | `aria-pressed` |
| Split buttons (Marks) | button plus `aria-haspopup="menu"` arrow button |
| Rails | `toolbar` of buttons with `aria-expanded` and `aria-controls`; the badge is part of the accessible name ("Comments, 6 items"), as desktop |
| Document tabs | `tablist`; close buttons labelled "Close report.pdf" |
| Page area | `region` named "Document"; each page `group` named "Page 3 of 12"; the text layer (W1.4) gives screen readers the page text |
| Toasts | `role="status"` (`aria-live="polite"`); errors `role="alert"` |
| Job chip | `progressbar` with value text |
| Dialogs | `dialog` with `aria-modal`, labelled by the title; focus trap; focus returns |
| Palette | `combobox` with a `listbox` |

**Keyboard:** everything reachable without a mouse. F6/Shift+F6 cycle the regions in the desktop order (`ui/focus_regions.py`), remembering the last focus in each; Esc in a panel returns to the page; a "Skip to document" link is the first tab stop. Focus is always visible (`--color-accent-text` ring, 2 px, meets the 3:1 non-text rule by construction of the tokens).

**Motion:** under `prefers-reduced-motion: reduce`, no animated panel slides, toast slides or smooth scrolling.

**Contrast:** the tokens are AA by construction (section 7); axe-core runs on every screen in CI (W8.5), in both schemes.

## 13. Front-end libraries

- **React 18 + TypeScript + Vite**, as the plan says.
- **React Aria Components** (Adobe, Apache-2.0, compatible with AGPL-3.0) for the hard accessible widgets: tabs, toolbars with roving focus, menus, dialogs with focus trapping, combobox/listbox, tooltips, drag and drop for tabs and thumbnails. Writing these correctly by hand is a large, error-prone job, and these are tested with screen readers on all target browsers. It is unstyled, so the look comes only from our tokens.
- **Styling:** plain CSS files (CSS modules) using the token variables. No CSS-in-JS runtime, no Tailwind: the CSP has no `style-src 'unsafe-inline'`, and libraries that inject `<style>` elements at run time would be blocked. React's `style={{…}}` sets properties through the CSSOM, which the CSP allows, and is used only for computed geometry (positions, sizes).
- **State:** React's own state and context, plus a small store module for documents and jobs; no state library.
- Nothing else for the shell. Every addition goes through the review checklist (pinned, licence, size).

Alternatives considered: Radix UI (MIT; fine, but weaker drag-and-drop and no toolbar pattern), Fluent UI React (heavier, imposes its own theme system and CSS-in-JS), hand-written widgets (most risk for accessibility).

## 16. Questions for the maintainer

**Answered 2026-11-17: all four as recommended.**

1. **Component library: React Aria Components** (Apache-2.0) for the accessible widgets, styled only with our tokens. Recommended: yes. Alternatives: Radix UI, or no library.
2. **Signed documents on the web:** signature validation needs pyhanko and cryptography, which the web doesn't ship. Recommended: no Signatures panel; a signed document shows an info bar ("This document is signed. Save keeps the signatures valid; to check them, use the desktop app."). Alternative: a read-only list of signature fields without validation.
3. **Accent colour: the 8 presets only** on the web (contrast is derived at build time). Recommended: yes. Alternative: a free colour picker, which needs `ensure_contrast` ported to TypeScript with shared test vectors.
4. **Below 768 px**: show the app with a "works best on a wider screen" notice and nothing blocked. Recommended: yes. Alternative: a blocking "use a larger screen" page.
