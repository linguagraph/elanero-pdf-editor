## 2. Fonts panel

**What it lists.** One row per font object the pages use, exactly the rows of `session.fonts`: name (subset tag removed), type, encoding, embedding, pages. Order is the engine's (case-insensitive by name, `session.py:248`); the panel does not re-sort.

**Embedding** is one column with three values, as on the desktop (`properties.py:177-179`):

| `embedded` | `subset` | Shown |
|---|---|---|
| true | true | Embedded subset |
| true | false | Embedded |
| false | (false) | Not embedded |

The engine marks `subset` from the name tag alone (`document.py:503`), so a tagged name with no font file would read "Embedded subset" with `embedded: false`. The panel follows the desktop and checks `subset` first. This is an engine-wide quirk, not changed here.

**Pages** are shown 1-based and compact (`1-3, 7`), with a TS port of `page_ranges` (`properties.py:43-56`). No web helper formats ranges today (`pages/pageRanges.ts:76` and `print/printRange.ts:24` only parse). Shared test vectors with the desktop function keep the two equal.

**Read-only.** Nothing in the panel changes the document: no `actions.run`, no Undo. There is no font export and no "Show Text in This Font" in this item (question 2).

**"For editing" column: not on the web** (question 1). The desktop value depends on `installed_ref_for_font_name(cached_catalog(), …)` (`properties.py:63`), and the web has no installed-fonts section (plan W6.8b: "no installed-fonts section"). A web version would need the W6.9 uploaded-font catalogue, which is not finished (PLAN.md W6.9).

**Loading.** `session.fonts` walks every page under the `action` deadline, so it is called **only when the Fonts tab is first shown**, never when the dialog opens. The result is kept for the life of the dialog (the dialog body remounts on each open, `PropertiesDialog.tsx:65-66`, so it is read afresh next time). States:

- loading: `properties.fonts.loading` in a `role="status"` element;
- `BUSY`: inline `properties.fonts.busy` ("Another task is running. Show the fonts again when it has finished.") with a **Retry** button; no toast, since the dialog stays usable;
- any other error: the shared `reportRpcError` toast (as `apply.ts:31-34`) and inline `properties.fonts.failed`;
- empty list (an image-only file, `test_webapi_properties.py:158-160`): `properties.fonts.none`.

**Size.** No cap is needed for the table: rows are font objects, and real files have tens to a few hundred. If a file has thousands, the table still renders as plain DOM rows; a cap is not proposed without a measured problem.

## 3. PDF version panel ("Advanced")

The desktop puts the version with the other file facts on its Advanced tab (`properties.py:126-163`). The web does the same: one **Advanced** tab, not a panel for the version alone (question 3).

### 3.1 What it shows

All from `DocInfo` (already loaded when the dialog opens, no new call):

| Row | Field | Value |
|---|---|---|
| PDF version | `pdf_version` | as reported, e.g. "1.7"; `properties.empty` ("Not set") when `""` (`dto.py:68`) |
| Pages | `page_count` | number |
| Tagged PDF | `is_tagged` | Yes / No |
| Has forms | `has_forms` | Yes / No |
| Digitally signed | `has_signatures` | Yes / No |
| Contains JavaScript | `has_javascript` | Yes / No |
| Repaired on open | `is_repaired` | Yes / No |
| XMP metadata | `has_xmp` | Yes / No (the desktop does not show this row; the web has the field, so it shows it) |

**File size is not shown.** The engine reads it from a path (`document.py:353-354`), and the web opens from bytes, so `DocumentInfo.file_size` is `None` there and `DocInfo` has no such field (question 4).

### 3.2 Can the version be changed? No.

- No engine call or save option sets it: `SaveOptions` has no version field (`engine/base.py:123-135`), and the only other mention of a version in the services is the PDF/A check that reads it (`services/pdfa.py:231`).
- The desktop shows it read-only too (`properties.py:130`).
- So the row is plain text, not an input, and the guide says the version is the one the file reports.

What is **not verified**: whether a full save keeps the header version, and whether MuPDF's `format` follows a catalog `/Version` that is newer than the header. The existing host check covers only an incremental save (`test_webapi_properties.py:216`, `:220`). Slice A adds a test that does a full save (`"copy"`) of `text_multipage` and of `encrypted` (re-encrypted on save) and pins `pdf_version` before and after, in MuPDF and with `pdf_version_pikepdf`. If MuPDF changes the version on a full save, the test records the actual rule and the guide states it. The panel itself does not change.

## 4. Security panel

### 4.1 What it shows

From `session.security` (instant, no password in or out):

| Row | Field | Value |
|---|---|---|
| Security | `encryption` | "No security" (`security.none` wording) for `none`; otherwise the method label: AES-256, AES-128, RC4 128-bit, RC4 40-bit, Unknown. AES-256 and AES-128 reuse `security.method.*` (`en.ts:439-440`); the RC4 and unknown labels are new keys. |
| Permissions | `permissions` | Only when encrypted: one row per permission, all eight, each "Allowed" or "Not allowed". Six reuse `security.perm.*` (`en.ts:450-455`); `accessibility` ("Content for accessibility tools") and `print_high_quality` ("High-quality printing") are new keys. |
| Permissions password entered | `owner_access` | Only when encrypted: Yes / No. "No" means the restrictions apply in this session; "Yes" means this session may change security (`security/RemoveSecurityDialog.tsx:47` uses the same flag). |
| On next save | `pending`, `pending_method` | Only when a change is queued: "Security will be set to {method}" or "Security will be removed", the same meaning as the desktop (`properties.py:150-157`). |
| Digitally signed | `has_signatures` | Repeated here only if the owner wants it (it is on Advanced); recommended: **not repeated**. |

The desktop lists six permissions and only those allowed (`properties.py:136-149`). The web lists all eight with a state each, because a list of only the allowed ones reads as nothing to a screen reader when everything is refused ("Allowed: nothing"). This is the one deliberate difference (question 5).

### 4.2 Encrypted documents: what the web can and cannot show

- **A file with an open (user) password** must be opened with that password first (`session.py:55-60`; `PASSWORD_REQUIRED` / `WRONG_PASSWORD`). Until then there is no handle and no dialog, so the panel only ever describes a file that is open.
- **The password itself is never shown, stored or logged.** It stays in the worker's registry entry while the document is open (`webapi/registry.py:3-4`, `:23-25`) and is dropped on close (`:98-103`). No call returns it: `SecurityResult` has no password field (`dto.py:264-276`), and `UnlockParams.password` is never echoed (`dto.py:249`). The panel adds no state that holds one. The existing Playwright check that a password does not reach storage or the console (`e2e/features/security.spec.ts:113-146`) is extended to open the properties dialog and the Security tab before it inspects.
- **Whether the file needs a password to open is not shown.** The engine reports the method and permission bits, not whether the user password is empty: `encrypted_owner_only.pdf` (empty user password, `scripts/make_fixtures.py:220-233`) and `encrypted.pdf` (user password "user", `:205-217`) both read as `aes-256`. Showing it would need a new engine fact (question 6). The panel never infers it from the page's own open flow.
- **Permissions after the owner password.** `permissions` comes from MuPDF's `permissions` bits (`document.py:367`, `:1136-1146`). Whether MuPDF reports the file's bits or all-allowed after `authenticate(owner)` is **not verified**. Slice C adds a Python test that opens `encrypted.pdf` with the user password, reads `session.security`, unlocks with the owner password, reads it again, and pins the result. If the bits change after unlocking, the panel labels them as "the file's restrictions" only before unlocking and adds the line "You entered the permissions password, so these restrictions do not apply to you" after; the wording is chosen once the test shows the behaviour.
- **Unknown or RC4 methods** show their label; nothing else is different. The web can only write AES (`security.ts:17`), which concerns the Encrypt dialog, not this panel.

### 4.3 Read-only

The panel changes nothing and has no buttons. Changing security stays in the existing Encrypt with Password and Remove Security commands (W7.5), which the panel names in one hint line: `properties.security.hint` ("To change the security, use Protect ▸ Encrypt with Password or Remove Security."). Buttons that jump to those dialogs are question 7.

### 4.4 No unlock here

The panel does not offer the owner-password step (`OwnerUnlock.tsx`). Unlocking is a step towards changing security, and that is the job of the security dialogs. Keeping it out means the properties dialog never has a password field.

## 9. Questions for the owner

1. **Fonts: show a "For editing" column on the web?** The desktop's column depends on installed fonts, which the web does not have. *Recommended: no, not in W7.6.* Revisit after W6.9 (uploaded fonts) with a column based on the document and uploaded fonts only.
2. **Fonts: add "Show Text in This Font"?** It needs a text-selection-by-font path the web does not have. *Recommended: no, not in W7.6;* a separate issue if wanted.
3. **Tabs: four (Description, Advanced, Fonts, Security) or the desktop's three with security rows on Advanced?** *Recommended: four.* It keeps Advanced short and gives screen-reader users a direct way to the security facts. The desktop could adopt the same later.
4. **File size: add it?** The engine has no size for a document opened from bytes. It could be the length of the opened bytes (a new `DocInfo.file_size`, a small engine change), but after edits that is no longer the size the file would have. *Recommended: no row for now;* the Compress dialog shows the original and reduced sizes (`compress.result.sizes`).
5. **Permissions: list all eight with Allowed/Not allowed (web), or only the allowed six (desktop)?** *Recommended: all eight with a state each,* for clarity and screen readers; align the desktop in a later desktop change if the owner likes it.
6. **Show whether the file needs a password to open?** It needs a new engine fact (for example, whether the empty user password authenticates), read without ever exposing the password. *Recommended: no, not in W7.6.* The user already knows, because they had to type it; adding an authentication attempt to a read call is a risk for little gain.
7. **Buttons from the Security tab to Encrypt with Password and Remove Security?** *Recommended: no, a one-line hint naming the commands.* Keeps the dialog read-only on that tab and avoids nesting dialogs; the commands are one step away on the Protect tab and in the command palette.
8. **Can W7.6 be ticked with the Playwright spec merged but not yet passing in `web-e2e` (blocked by #567)?** *Recommended: no.* Follow AGENTS.md: tick only after a passing chromium run; until then the PLAN note says "pending: a passing Chromium run", as for W6.2, W6.4 and W6.5.

## Owner decisions

Decided on 2026-11-22. All eight follow the recommendation.

1. **"For editing" column:** no, not in W7.6. The web has no installed-font catalogue, so the column would have nothing true to say; revisit after W6.9 with document and uploaded fonts only.
2. **"Show Text in This Font":** no, not in W7.6. It needs a select-by-font path the web lacks; it is new feature work, not a properties panel, and goes in a separate issue if wanted.
3. **Tabs:** four (Description, Advanced, Fonts, Security). It keeps Advanced short and gives keyboard and screen-reader users one step to the security facts; the desktop is not changed in W7.6.
