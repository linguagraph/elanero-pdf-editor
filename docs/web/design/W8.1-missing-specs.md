## 2. The specs

Every spec follows the existing pattern in `features/support.ts`: `test.describe('engine staged')`
with `test.skip(!STAGED, …)`, `watchPage` collecting CSP and page errors (asserted empty at the end),
`openApp` and `openPdf` for the setup, `saveDownload` for Save, a reopen in `context.newPage()`, and
`recordHostCheck` for the pikepdf and pypdfium2 halves (replayed by `scripts/web_host_verify.py`
through the `@host_check` names in `tests/hostcheck.py`). All named host checks below already exist;
none is added.

Waits use what the app already says, never `waitForTimeout`: the toast text of each action (the
strings in `src/i18n/en.ts`), a dialog becoming hidden, a `status` region, `expect.poll` on a log
an init script writes, and the download event. Job-backed steps (split, compress, print) get the
120 s timeout the existing job specs use.

### 2.1 `features/bookmarks.spec.ts` (new, ~150 lines)

Fixture `outline.pdf` (6 pages; Chapter 1 to 3, each with two sections; Roman page labels).

Scenario, one test, panel opened from the rail's Bookmarks button:

1. **Rename** Chapter 2 through Bookmark actions, Rename, to `Part Two`. Wait for
   `Bookmark renamed.`
2. **Move** Section 3.2: Move Up. Wait for `Moved "Section 3.2" to level 2, position 1 of 2.`
3. **Set destination**: jump to page 2 (page jump box), select Section 2.2, Set to Current Page.
   Wait for `Bookmark now goes to page 2.` (the toast names the page number, not the label).
4. **Delete then Undo**: delete Section 1.2 (wait for `Deleted "Section 1.2".`), press the toast's
   Undo, and check the row is back. This covers the panel's undo path without a host assertion on it.
5. **Add**: with no row selected, Add (the empty-selection case appends at the top level,
   `after: null` in W5.2-S3 section 2). Wait for `Added "Page 2" for page 2.`
6. Save, reopen the download, open the panel, and check the ten titles in order from the tree.

Assertions: the panel tree after each step (role `treeitem`, names and `aria-level`); after reopen,
the same tree. Host checks on the saved bytes:

- `outline_pikepdf` with `expected` = `[[1,"Chapter 1"],[2,"Section 1.1"],[2,"Section 1.2"],
  [1,"Part Two"],[2,"Section 2.1"],[2,"Section 2.2"],[1,"Chapter 3"],[2,"Section 3.2"],
  [2,"Section 3.1"],[1,"Page 2"]]`.
- `outline_pdfium` with the same rows plus page indexes: Section 2.2 now goes to index 1, Page 2 to
  index 1, the others unchanged.
- `page_count_pikepdf` with `pages: 6`.

If the implementer finds that Add with no selection does not append at the top level, the spec
follows the implemented rule (S3's table) and the expected list moves with it; the design does not
change the app to suit the test. The y offset (`outline_top_pikepdf`) is left out: it depends on the
scroll position at the click, which is the flakiest input here. A follow-up can add it with a jump to
a fixed page top first.

### 2.2 `features/links.spec.ts` (new, ~140 lines)

Fixtures `links_rotated.pdf` (page 1 rotated 90, with a goto link, an https link and an unnamed
destination; page 2 with a `javascript:` link and a Launch link) and `outline.pdf` (goto and https
links on an unrotated page).

`window.open` is stubbed by an init script (as print.spec.ts stubs `window.print`) that logs its
arguments and opens nothing, so the run makes no third-party request.

Tests:

1. **Goto on a rotated page**: click the link element named `Go to page 2` in
   `.page-link-layer`; the view moves to page 2 (the page jump box reads 2); Back in the status bar
   returns to page 1 (history, W5.3). Also checks the link's box overlaps its anchor text line's box,
   which is the rotation check S1 made in unit tests.
2. **https link asks first**: click `Link to …example.org…`; the `Open link?` dialog shows
   `This document wants to open a page on example.org.` and the full address. Cancel: dialog hidden,
   the open log is empty, focus is back on the link. Click again, Open link: the log holds one call
   with `https://example.org/`, `_blank`, and `noopener,noreferrer`.
3. **Refused links**: on page 2, `javascript:` shows the notice
   `This link was not opened: "javascript:" links are blocked.`; the Launch link shows
   `This kind of link does not work in the web version.`; the unnamed destination on page 1 shows
   its notice. No dialog opens and the log stays empty.

No host checks: the flows only read the document (as text.spec.ts). This is the spec that most
needs Chromium first: popup and `noopener` handling differ by browser.

## 3. Running on Chromium only

The features config keeps its three projects; nothing about the required checks changes (`web-e2e`
and `web-a11y` are not required, and the PR-time `web` job does not run the features config).

- **Locally, no change needed**: `npm run e2e:features -- --project=chromium`. Playwright's project
  filter is the switch; the webServer builds once and only the Chromium project runs.
- **A named script** (1 line in `package.json`): `"e2e:features:chromium": "playwright test -c
  playwright.features.config.ts --project=chromium"`, so the command in AGENTS.md is one word to
  type and cannot be mistyped into a three-browser run.
- **No environment switch in the config.** An `E2E_BROWSERS` variable would duplicate the project
  filter and add a second way to get it wrong. Recommended against (Question 1).
- **The workflow**: `web-e2e.yml` gets a `workflow_dispatch` input `browsers` (choice: `chromium`,
  `all`; default `chromium`). The matrix reads
  `fromJSON(inputs.browsers == 'all' && '["chromium","firefox","webkit"]' || '["chromium"]')`, and
  the schedule (where `inputs.browsers` is empty) keeps all three by testing
  `github.event_name == 'schedule'` first. About 6 changed lines. The job name pattern
  `web-e2e (<browser>)` stays the same.

AGENTS.md's Web version section gets one sentence: run the features on Chromium with
`npm run e2e:features:chromium`; Firefox and WebKit run in the nightly.

## 4. What runs on web-e2e on demand, and what it needs

On `workflow_dispatch` with `browsers: chromium`, all of section 2.1 to 2.6 except
long-document.spec.ts run, and the host replay checks every saved file.

The run needs the PyMuPDF wheel **in the Actions cache under web-pytest's key** (`pymupdf-<ver>-
pyodide-<ver>-<hash of web-pytest.yml and web/spike/versions.json>`). On a miss the job stops with
its message and does not build the wheel (a cold build is up to two hours). So: if `web-pytest.yml`
or `versions.json` changed since the last `web-pytest` run on main, run `web-pytest` on main first
(workflow_dispatch), then web-e2e. A cache saved from a PR branch is not visible to a dispatch on
main, so the warm-up must be on main.

long-document.spec.ts lives under the main config. To run it on demand, the Chromium leg gets one
more step after the features run: `npx playwright test long-document.spec.ts` (with
`if: matrix.browser == 'chromium'`, ~5 lines). Its server is the main config's own (ports 4173 and
4174), so it does not clash with the features server on 4175. The alternative, moving the spec into
`e2e/features`, would change which config owns it and run it on all three browsers nightly, which
W1.4 did not plan for; not recommended.

Locally the same needs apply: `npm ci` in `web/spike` and `web/app`, `python scripts/make_fixtures.py`,
`python scripts/build_web_wheel.py`, the staging command from AGENTS.md with a local PyMuPDF wasm
wheel, `npx playwright install chromium`, then the Chromium script, then
`python scripts/web_host_verify.py web/app/test-results/host-checks.json`. Delete
`test-results/host-checks.json` before a run, or old entries are replayed too.

## 5. Flaky timing: the rules for these specs

- Wait on the app's own signals: toasts (`bookmarks.*`, `Copied to clipboard.`, `Redactions
  applied.`), `role="status"` text, a dialog's visibility, the download event, the print log via
  `expect.poll`. No `waitForTimeout`, no fixed sleeps.
- A toast can still show from the previous step with the same text: check the count changes or use
  a text that names the item (as `cropAllPages` already does).
- One `waitForEvent('download')` per click, inside `Promise.all` with the click.
- Pointer drags (text, Mark Text) take the line's bounding box after `toBeVisible`, with `steps: 10`,
  as text.spec.ts does; the line must be in the viewport first.
- The features config keeps `workers: 1` (the manifest is written whole) and `retries: 1` on CI. A
  test that passes only on retry is reported in the PR, not ignored.
- Job steps get 120 s; engine start keeps `openApp`'s 180 s.

## 7. Questions for the maintainer

1. **Chromium only for now?** Recommended: yes. Run these specs on Chromium locally and by dispatch;
   leave Firefox and WebKit to the nightly, and treat a nightly failure there as an issue, not a
   blocker for these PRs. Use the project filter, not an environment variable.
2. **When may a test be `test.fixme`?** Recommended: only with a linked issue in its reason string
   (`'…; see #NNN'`). The existing WebKit fixmes in crop, save-as and print get issues in PR 2.
3. **The dispatch default.** Recommended: `browsers: chromium` for `workflow_dispatch`, all three for
   the schedule.
4. **long-document.spec.ts in web-e2e?** Recommended: yes, as a Chromium-only step under the main
   config, not moved into `e2e/features`.
5. **`@smoke` tags now?** Recommended: not in these PRs. W8.1 plans PR-time runs with a `@smoke`
   subset, but no PR job runs the features yet; tag when that job is designed (split test 4 and the
   link refusal test are the natural first ones).
6. **Bookmark Add placement.** Recommended: the spec follows whatever S3 implements for an empty
   selection and states it in a comment; if it is not "append at top level", the expected list in
   2.1 changes, not the app.
