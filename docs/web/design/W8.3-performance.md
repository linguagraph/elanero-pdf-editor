# W8.3 Performance tests in CI

Status: proposed, for owner approval; no production code in this change.

Plan item: PLAN.md W8.3, docs/web/plan.md W8.3 (decision 10, W1.7 §8, W1.4 §14).

## 1. What exists today

- **Desktop timing budgets.** `tests/benchmarks/test_ui_budgets.py` measures window first paint, first paint of a
  1000-page document, the scroll frame time and the theme switch. Each is the median of 5 runs, and the limits are
  about 2.5x the baseline, scaled by `PDFEDITOR_PERF_FACTOR` (1.5 on Linux).
- **Desktop smoke benchmarks.** `tests/benchmarks/test_benchmarks.py` covers open, render, search and first paint plus
  scroll on `large_1000`, with generous fixed limits.
- **When they run.** `ci.yml` runs both only nightly (03:00) and on release. Pull requests skip them with
  `--ignore=tests/benchmarks` (#104: a busy runner fails them on its own).
- **Where the limits live.** Hard-coded in the test modules. Results go only to stdout, so nothing tracks a trend.
- **Web size check.** `web/app/scripts/check-size.ts` with `budget.ts` (40 MB gzip) runs only in `web-deploy.yml`, on
  pushes to main. W1.7 §8 wanted it on every web PR. The PR gate in `ci.yml` builds the app without the engine
  assets, so a size check there would measure the wrong set of files.
- **Web timing harness.** `web/spike/perf*` (W0.2) runs in `web-spike.yml` (`pyodide-perf`) against the spike page,
  not the app. It records numbers for trends and never fails a run.
- **Long-document log.** `web/app/e2e/long-document.spec.ts` logs sharp-page time and long tasks "for W8.3" but does
  not enforce anything.
- **Blocker.** The engine does not load in the CI Playwright runs yet (#567, W8.1). Every browser timing below
  depends on fixing that.

- **Pyodide load time.** W2 is the gated number. The app also emits `performance.mark` at each load stage (download,
  Pyodide start, PyMuPDF import, open, paint), reported as trends, so a regression in W2 points to its stage.
- **Memory ceiling.** Only the web wasm heap (W9) is measured. `measureUserAgentSpecificMemory` needs cross-origin
  isolation, and a desktop RSS ceiling needs psutil (not a dependency); tracemalloc cannot see MuPDF's own memory.
  The desktop ceiling is deferred (Q5).
- **Exe size.** The exe size budget stays in the build job, which already checks it.

### 2.2 How it is measured without flaky results

1. **Repeats and medians.** At least 5 runs per metric. Only the median (or the median of per-run maxima) is
   compared, never a single run. The first run of each process is a discarded warm-up, except where cold is the
   point (W3).
2. **Paired comparison for web timings (W2, W4 to W6).** CI runners vary by about 40% (W0.2), so absolute times do
   not gate.
   - `web-perf` builds two commits in the same job: the **baseline commit** pinned in the budget table (the last
     release tag) and HEAD.
   - It runs them interleaved (A B A B ...) on one runner with persistent profiles, as in W0.2.
   - It fails when HEAD's median is more than 15% **and** more than 300 ms slower. Both conditions must hold, so small
     metrics cannot fail on noise.
3. **Absolute limits on desktop (D1 to D5) stay generous.** About 2.5x the dev baseline times the runner factor,
   which matches the observed 239 to 347 ms spread with headroom.
4. **One retry.** A perf step that fails is rerun once, serially, in the same job. The run fails only if both
   attempts fail, and both sets of numbers are kept in the results file, so a retry cannot hide a real regression.
5. **Isolation.** Perf runs are serial: the existing conftest skips them under xdist. They get their own job. The web
   metrics run on Chromium only; Firefox and WebKit timings are recorded as trends only, by hand.
6. **The 4 s absolute gate (decision 10).** Not run in CI. It is a release step on the reference laptop, written into
   `RELEASING.md` (W9.6).

### 2.3 Which runs

- **Desktop (D1 to D6).** These stay where they are: the nightly and release runs of `ci.yml`. They are not run on
  PRs, as AGENTS.md says. A results step is added (2.5).
- **W1 size check.** Every web PR. It is deterministic and takes seconds. It moves into the `web-pytest` job, which
  already has the cached PyMuPDF wheel and builds the web zip: that job stages the engine assets, builds the app and
  runs `check-size.ts`. `web-deploy.yml` keeps its own check.
- **New `web-perf.yml` (W2 to W9).** Runs nightly at 05:00, after `web-e2e` at 04:00 has warmed the wheel cache, and
  can be started by hand. It is **not run on PRs** during a 14-night trial. After the trial, if no night failed
  without a real cause, it may run on PRs that touch its watched paths (the worker bootstrap, view, rpc, engine-asset
  staging, `src/pdfeditor/**` and the budget table), added to `ci_changes.py`. It is never a required check (Q1).
- **Release.** `release.yml` calls `web-perf` for the release commit, against the previous release. A failed check
  blocks the release, as the desktop budgets do.

### 2.4 Where the budgets are stored

- **One table, `tests/perf/budgets.json`.** One entry per metric with `id` (D1 ... W9), `unit`, `kind` (absolute,
  paired, trend, ceiling, hard), `limit` or `pct`/`abs_ms`, `baseline_ms` with its date and machine, and a `note`.
  The file also holds `baseline_ref` (a git tag) and the runner factors.
- **Readers.** The desktop tests read their limits from the table instead of module constants. The web harness reads
  the same file by relative path. `budget.ts` keeps its constant, and a test asserts that it equals the W1 row.
- **Consistency test.** `tests/unit/test_perf_budgets.py` (desktop CI, every PR, deterministic) checks that every
  metric a harness emits has a row, every row has an emitter, and every `kind` has the fields it needs.
- **Review.** The file is added to CODEOWNERS. A PR that raises a limit or moves the baseline must link the run that
  justifies it.
- **Release step.** `RELEASING.md` gains "move `baseline_ref` to this tag".

### 2.5 Trend log

- Every perf run writes `perf-results.json` with one record per metric: id, samples, median, commit, runner image,
  date and attempt. Each run is uploaded as an artifact kept for 90 days.
- `scripts/perf_trend.py` (stdlib only, `actions: read`) downloads the last 14 nightly result artifacts of the same
  workflow and prints a table in the job summary: the metric, tonight's value, the 14-night median, the change and a
  small text spark.
- It flags drift above 10% over 7 nights as a warning in the summary, not a failure.
- Nothing is committed and no write permission is needed (Q3).

## 4. Risks

- **#567 (no engine in CI).** Blocks S3 to S5. S3 keeps the e2e rule of skipping when the engine assets are not
  staged, but `web-perf` fails, not skips, when they are missing, so a quiet green cannot happen.
- **Building the baseline needs its wheel.** When the baseline commit pins a different PyMuPDF, the cache key
  differs. The paired comparison is then skipped with a summary notice, only absolute and trend metrics run, and the
  run passes with a warning.
- **Runner images change.** The runner image is recorded in each record. The trend script resets its window when the
  image changes.
- **Pinned baseline grows stale.** `baseline_ref` moves only at a release, so the paired limit compares with the last
  shipped version, which is the regression that matters to users.

## 5. Owner questions

1. **Should `web-perf` run on PRs?** Recommended: not at first. After 14 nightly runs with no failure lacking a real
   cause, run it on PRs that touch the watched paths, never as a required check.
2. **What should the paired comparison use as its baseline?** Recommended: the last release tag, pinned in the budget
   table and moved at each release, rather than the PR's merge base. Nightly runs have no merge base, and this
   catches slow drift.
3. **Where should the trend log live?** Recommended: workflow artifacts kept for 90 days, with the job summary built
   from the last 14. No bot-written branch, no write permission.
4. **How should the scroll long-task gate work?** Recommended: the median of each run's longest task must be at most
   50 ms, instead of "no task over 50 ms in any run". One slow runner hiccup would otherwise fail the night.
5. **Should a desktop memory ceiling be added now?** Recommended: no. Measure the web wasm heap only (W9). Revisit a
   desktop RSS ceiling if psutil is added for another reason.
