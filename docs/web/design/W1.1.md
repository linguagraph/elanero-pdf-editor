# W1.1: Overall web architecture

Stage: W1 (#134) · Role: design Opus 5.5 · Branch: `phase-w-w1.1-architecture` · Inputs: [plan](../plan.md), the W0 spike reports in [`../spikes/`](../spikes/).

This note fixes the shape of Elanero Web: the processes (workers) and what runs where, the layers and their import rules, capability flags, files, storage and memory, packaging, build and hosting, and the threat model. The other W1 notes fill in parts of it: W1.2 the wire format of the RPC, W1.3 the `actions` layer, W1.4 rendering, W1.5 editing tools, W1.6 the UI, W1.7 tests. Where this note refines a plan decision, the plan is corrected in the same PR (see "Plan corrections").

## 1. Runtime topology

```
Main thread (TypeScript, React)                       owns: UI, DOM, files, OPFS writes of
  app shell, views, tools, panels, dialogs             autosave, the watchdog, job lifecycle
  RpcClient ── engine channel ───────────────┐
  JobRunner ── job channel ─────────────┐    │
                                        │    │
Job worker (one, kept warm)             │    │    Engine worker (one per browser tab)
  Pyodide + PyMuPDF + pdfeditor         │    │      Pyodide + PyMuPDF + pdfeditor
  pdfeditor.webapi.jobworker  <─────────┘    └──>   pdfeditor.webapi (dispatch)
  no network, no OPFS                                 every open document, its undo stack,
  gets a copy of the bytes per job                    snapshots (MEMFS), uploaded fonts (MEMFS)
```

Decisions:

1. **One engine worker per browser tab, holding every open document.** Not one per document: each worker costs about 181 MiB of wasm heap and 2.6 s to start (W0.2, M4), and the desktop already serialises all engine work through one process-wide lock. Documents are separate `DocumentSession`s in a registry inside `webapi`, addressed by a string handle.
2. **One job worker per tab, started after page 1 of the first document is shown, and kept warm.** It is not per document (plan decision 10 said "once per document"; refined here): the cost is the Pyodide start, not the document, and a job opens its bytes in about 1 ms (M4). It runs one job at a time; further jobs queue in the main thread. After a cancel it is terminated and a fresh one is started in the background. It is also terminated after 10 minutes without a job and started again on demand, to give back its heap.
3. **The main thread coordinates.** It relays bytes between the two workers as transferred `ArrayBuffer`s (no copy), so it alone knows which jobs run and can cancel them. The workers never talk to each other directly.
4. **Nothing PDF-shaped is parsed on the main thread.** PDF bytes go from the file straight to the engine worker. The main thread sees only DTOs (plain JSON values) and pixel buffers.
5. **A second browser tab is a second, independent app instance** with its own workers. Nothing is shared between tabs except the OPFS store (section 6), whose files carry the tab's id so two tabs never write the same file.

### Two patterns for long work

The engine worker runs Python synchronously, and without `SharedArrayBuffer` (GitHub Pages can't send COOP/COEP headers) it can't be interrupted. Long work therefore takes one of two forms:

- **Chunked calls in the engine worker** for read-only work that splits by page: search, thumbnails, the text of a page range, the comment list, the space audit. The front end asks for a slice (for example 20 pages or about 100 ms of work, whichever comes first), shows progress, and asks for the next slice. Renders and other calls run between slices; cancel means "stop asking". No copy of the document is needed.
- **Jobs in the job worker** for monolithic operations: optimize/compress, redaction apply, sanitize, compare, flatten of a large document, split, merge, export (images, text, DOCX), print rendering of more than a few pages, stamping across many pages. The job gets a copy of the document bytes; cancel terminates the worker.

A **mutating job** (optimize, redaction apply, sanitize, flatten, stamping) makes the session read-only for its duration with the existing `DocumentSession.begin_task` / `end_task` (edits are refused with the `BLOCKED` event, as on desktop). When it finishes, the engine worker applies the result bytes as one `SnapshotCommand` whose operation is `doc.load_state(result)`, so it is undoable exactly like on desktop; flags the job reports (for example `require_full_save` after redaction) are set on the session at the same time. A **read-only job** (compare, export, split, print) works on a copy and doesn't block editing. This is less restrictive than desktop, where every task blocks edits because it reads the live document.

### The watchdog

A worker stuck in Python (a pathological content stream, an engine bug) can only be stopped by terminating it. Every RPC call has a soft deadline (W1.2 sets the values per call; renders a few seconds, actions longer). When it passes, the main thread shows "Elanero is still working on this" with **Wait** and **Restart engine**. It never kills the engine worker by itself, because that loses the undo history. Restart terminates the worker, starts a new one and reopens every document from its last autosave (section 6), saying what is lost (changes since that autosave, and the undo history). The job worker has no such dialog: a job shows progress, and Cancel always terminates.

## 2. Layers

```
pdfeditor.ui | pdfeditor.webapi     desktop front end | browser RPC facade (independent siblings)
pdfeditor.actions                   NEW (W2.1): named operations -> Commands, shared by both
pdfeditor.services
pdfeditor.core
pdfeditor.engine
pdfeditor.model
```

The import-linter contract in `pyproject.toml` becomes (W2.1 slice (a) adds `actions`; W3.2 adds `webapi`, and until the package exists the contract names only existing modules):

```toml
[[tool.importlinter.contracts]]
name = "Layered architecture"
type = "layers"
layers = [
    "pdfeditor.ui | pdfeditor.webapi",
    "pdfeditor.actions",
    "pdfeditor.services",
    "pdfeditor.core",
    "pdfeditor.engine",
    "pdfeditor.model",
]

[[tool.importlinter.contracts]]
name = "Web and shared layers stay Qt-free"
type = "forbidden"
source_modules = ["pdfeditor.webapi", "pdfeditor.actions"]
forbidden_modules = ["PySide6", "shiboken6"]
```

`pdfeditor.webapi` is also added to the "Only the mupdf backend may import PyMuPDF" contract's `source_modules`, and `pdfeditor.actions` too.

**What lives where.**

| Layer | Holds | Doesn't hold |
|---|---|---|
| `actions` | One function per user-level operation (`actions.pages.rotate(session, args)`), its argument dataclass, the Command it builds (including `SnapshotCommand` labels and `MacroCommand` grouping), and a registry from a stable action name to (args type, function). Pure Python, usable headless. | Anything about Qt, RPC, JSON or the browser. |
| `webapi` | Request dispatch, DTO conversion (model ↔ JSON), the document registry, error-code mapping, resource limits, chunked-call cursors, the job-worker entry point, the web platform setup (secret store, HTTP opener, paths). | Feature logic. If `webapi` needs a decision that isn't a format conversion, it belongs in `actions` or `services`, and the desktop uses it too (plan, reuse principle). |
| `web/src` (TypeScript) | Presentation, input handling, the RPC client, file I/O, OPFS, printing, PWA. | PDF logic. Geometry that must match the desktop (layout, hit testing, text reflow) either runs in the worker or is ported with shared test vectors (W1.4, W1.5 decide each case). |

**`webapi` modules** (W3 builds them; names fixed here so W1.2–W1.5 can refer to them):

| Module | Role |
|---|---|
| `webapi/__init__.py` | `dispatch(request_json: str, payload: memoryview \| None) -> tuple[str, bytes \| None]`: the single entry point the worker's JS calls. |
| `webapi/dto.py` | Frozen dataclasses for every request and reply; the source for the generated TypeScript types (W1.2). |
| `webapi/errors.py` | Stable error codes and the mapping from exceptions (`EngineError`, `SaveError`, `PasswordRequired`, `Cancelled`, limits) to `{code, message, details}`. |
| `webapi/registry.py` | Open documents by handle; events (page revisions, dirty state, undo/redo labels) collected per call and returned with the reply. |
| `webapi/session.py`, `render.py`, `text.py`, `actions.py`, `save.py` | The call groups of W3.2–W3.6. |
| `webapi/jobs.py`, `webapi/jobworker.py` | Job specs and results (engine side), and the job worker's own dispatch. |
| `webapi/limits.py` | Resource limits (section 7). |
| `webapi/platform.py` | `configure_web()`: sets the platform capabilities, injects the secret store, the translation opener and the data roots. Called once at worker start-up. |

**Python ↔ JS boundary in the worker.** Requests and replies cross as JSON strings, and binary data as one optional buffer beside them, so no `PyProxy` outlives a call (proxies that leak hold wasm memory and are the usual Pyodide leak). The worker's JS turns the returned bytes into an `ArrayBuffer` and transfers it to the main thread. W1.2 specifies the envelope.

**Engine lock and GC in the worker.** `ENGINE_LOCK` stays; it costs nothing single-threaded and keeps shared code unchanged. Automatic cyclic GC stays disabled (`install_manual_gc`), and the worker calls `engine_lock.collect()` when it has been idle for a second, as the desktop window timer does.

## 3. Capability flags

Two sources, plus browser facts the front end detects itself:

1. **`engine.capabilities`** (exists). On the web the MuPDF backend reports the same flags as on desktop except `ocr`, which is false because the OCR path is off in the web build (W0.1 C2).
2. **`pdfeditor.core.platform.capabilities`** (new, W2.2): a frozen dataclass set once at start-up (`core.platform.configure(PlatformCapabilities(...))`; the desktop default is all true where the desktop can do it). Fields and web values:

| Flag | Desktop | Web | Effect when false |
|---|---|---|---|
| `linearize` | true | false | "Fast web view" hidden; `optimize.linearize` not offered |
| `ocr` | true | false | OCR actions hidden |
| `signing` | true | false | Sign/certify hidden (existing signatures still shown and preserved) |
| `system_fonts` | true | false | `system_font_dirs()` returns `[]` |
| `office_import` | true if LibreOffice found | false | Office-to-PDF hidden |
| `threads` | true | false | Code that would start a thread runs inline (the W2.5 runner) |
| `pdfa` | true | false | PDF/A conversion hidden (needs pikepdf); added to the plan's list here |

3. **Browser facts** (TypeScript only, never sent to Python): `fileSystemAccess` (save in place), `fileHandling` ("Open with"), `opfs`, `print`. These change only what the front end offers.

The webapi `capabilities` reply merges (1) and (2) into one object. Every front-end action declares the flags it needs, and the command registry (W4.3) hides or disables it. No code tests `sys.platform == "emscripten"` outside `webapi/platform.py`.

## 4. Data flow of the main operations

**Open.** File picker, drag and drop, or `launchQueue` (File Handling API) → the main thread reads the `File` into an `ArrayBuffer` (size checked against the limit first) → transferred to the engine worker → `session.open` (`DocumentSession.open(bytes)`). A password-protected file replies `PASSWORD_REQUIRED`; the front end asks and calls again with the password, which is used once and not kept in JS after the reply. The reply carries the handle, info and page sizes; the first render request follows at once (W3.1 starts the document read while the packages load).

**Edit.** A tool or dialog calls `actions.run(handle, name, args)`. The worker validates `args` against the action's dataclass, runs the action (which calls `session.execute`), and replies with the changes: page revisions bumped, structure changed, dirty flag, undo/redo labels. The front end invalidates the affected tiles and panels. Undo and redo are calls of their own.

**Save.** `save.save_bytes(handle, mode)` runs `DocumentSession.save_bytes()` (W2.3), which shares the incremental-or-full decision with `save()`, then reopens the bytes in the engine to verify them, then returns them. The main thread writes them:

| Mode | When | Incremental allowed |
|---|---|---|
| `in_place` | Save, and the document came from a File System Access handle with write permission | yes (signed documents keep their signatures, as on desktop) |
| `in_place` (download) | Save, without a writable handle: the file downloads under its own name, for the user to replace the original | yes; the UI says the copy must replace the original for signatures to stay valid |
| `copy` | Save as, Download a copy | no (full rewrite, as desktop Save As) |

Counting the download fallback of Save as in place is deliberate: the alternative, a full rewrite, would silently break existing signatures in every browser without the File System Access API (Firefox, Safari). After a successful write the main thread calls `save.mark_saved(handle)`, which clears the dirty flag; a failed or cancelled write leaves it dirty.

**Jobs.** Section 1. The job spec names a job type and its arguments (DTOs), plus the document bytes, which the engine worker produces with `Document.to_bytes()` and transfers out.

## 5. Files and names

- Open: `<input type=file>`, drag and drop, the File Handling API in Chromium. Several files can be open at once (tabs, W4.2).
- Save: the File System Access API where it exists, otherwise a download. Download names go through `services.assembly.safe_name`.
- Recent files: names and dates only, in `localStorage`. On Chromium, the File System Access handle of a recently opened file is also kept (in IndexedDB `elanero-recent`, pruned to the list limit), so a recent row reopens the file with no dialog (issue 756). A handle is an opaque browser reference: no bytes are stored. Other browsers keep the file picker, the browser limit.
- Outputs of split, export and attachments: several downloads, or one ZIP built in the job worker with `zipfile`.

## 6. Storage

| Data | Where | Lifetime |
|---|---|---|
| Open documents, undo stacks | engine worker memory | until the document closes |
| Undo snapshots (`SnapshotStore`) | MEMFS in the engine worker (file contents live in JS `ArrayBuffer`s, not in the wasm heap) | until the document closes; budget in section 7 |
| Autosave copy | OPFS `/autosave/<tab-id>/<doc-uid>.pdf` plus a small `.json` (name, time, page count) | written when dirty and idle, at most once a minute (as desktop `Autosaver`); deleted on close and after a clean save. A tab that finds another tab's files older than a day, with no live tab owning them (a `BroadcastChannel` ping), offers them for recovery and then deletes them |
| Uploaded fonts | OPFS `/fonts/`, copied into MEMFS (`FontCatalog` folder) at worker start | until the user removes them in Preferences (fonts are not documents) |
| Translation keys | worker memory by default; optionally OPFS `/secrets/`, encrypted with AES-GCM under a key derived from a user passphrase (PBKDF2, WebCrypto) | memory: the tab's life; stored: until removed |
| Preferences, recent file names | `localStorage` | until cleared; never secrets or document content |
| App assets (Pyodide, wheels, JS, icons) | service worker cache, versioned | until the next app version is activated |

OPFS is written by the main thread (asynchronous OPFS API, works in every target browser), from bytes the engine worker posts. The workers don't touch OPFS. On the web, `core.paths.data_dir()` resolves under MEMFS (`/home/pyodide`); W2.3 makes its root injectable, and `webapi/platform.py` sets it. `navigator.storage.persist()` is requested only when the user keeps fonts or keys.

## 7. Memory budget and resource limits

wasm32 caps each worker at 4 GiB of linear memory in Chromium and Firefox, less in practice on Safari and iPad. Measured baselines (W0.2): engine worker 200 MiB after one small document, 314 MiB after 1000 pages; job worker 181 MiB idle.

Budgets (defaults in `webapi/limits.py` and the front end's config, tuned in W3.9 and W8.3):

| Item | Default | On exceeding |
|---|---|---|
| File size | warn above 200 MB, refuse above 1 GB | warning dialog / `FILE_TOO_LARGE` |
| Total open documents | warn when the engine heap passes 1.5 GiB | suggest closing documents |
| Snapshot store per tab | 512 MiB of MEMFS | oldest snapshots dropped, "undo history shortened" shown (W2.3) |
| Render request | at most 16 MP per tile and 64 MP per page image (print, export) | `RENDER_TOO_LARGE`; the caller tiles or lowers DPI |
| Decompressed image / page work | MuPDF's own limits plus the watchdog | error or the watchdog dialog |
| Main-thread tile cache | `ImageBitmap`s up to 256 MiB of pixels (W1.4 refines) | LRU eviction |
| Job worker | one job at a time; the document copy counts against the same 1.5 GiB warning | queue |

A `MemoryError` or an aborted wasm runtime in the engine worker is handled like a stuck worker: restart and reopen from autosave (W3.9).

## 8. Packaging

- **Pyodide 314.0.8** (CPython 3.14), pinned, served from our origin. Plan decision 11 said "3.12+"; it is 3.14, and the Pyodide CI job (W2.7) covers it while the desktop stays on 3.11.
- **PyMuPDF 1.28.2**, the desktop's pin, built in CI by the W0.1 route (`pymupdf-1.28.2-cp314-none-pyemscripten_2026_0_wasm32.whl`), with the two source patches until a release has them (W0.1 C3). A Pyodide bump means a new wheel build (C5). The wheel's sha256 is recorded in the build and checked before deployment.
- **fontTools and Pillow** from the Pyodide distribution, loaded only when a feature needs them (font upload, text editing, image export; W2.6). The viewer set loads without them.
- **`pdfeditor` web wheel** built by `scripts/build_web_wheel.py` (W2.6) from the same source tree, installed without dependencies, containing the 95-module web set (`web/spike/web_package.py` becomes `scripts/web_package.py` or the build script's own list), `pdfeditor.webapi` and `pdfeditor.actions`, and `data/` without `tessdata` and without branding (the front end loads the few brand images it needs as web assets).
- **Front end**: Vite build of `web/` into hashed asset names.

## 9. Build and hosting

- Static hosting on GitHub Pages at `/elanero-pdf-editor/app/`, built by `scripts/build_site.py` next to the landing page and guide (W9.2). Layout:
  - `app/index.html` (CSP meta tag; no inline scripts);
  - `app/assets/<name>-<hash>.js|css`;
  - `app/py/<build-id>/` for Pyodide's files, the wheels and a trimmed `pyodide-lock.json`;
  - `app/sw.js`, scope `app/`, caching the versioned files listed in a build manifest.
- **Compression risk.** W0.2's 32 MB figure assumes gzip on the wire. GitHub Pages compresses some content types, and it is not established that it compresses `.whl` and `.wasm`. W9.2's preview deployment must measure the transfer size. If they arrive uncompressed (about 40 MB raw), the build stores them gzip-compressed under another name and the worker inflates them with `DecompressionStream("gzip")`, which every target browser supports. This is a must-check of W9.2, recorded in the plan.
- No CDN and no third-party requests (plan). Workers are same-origin module workers.

## 10. Threat model (STRIDE)

**Assets:** the user's documents and anything derived from them (text, renders, autosaves); translation API keys; the integrity of the app code; the user's browser and device. **Adversaries:** the author of a malicious PDF (most likely); a network attacker (TLS mitigates); a compromised dependency or build input; another website in the same browser; a malicious or compromised translation service.

**Trust boundaries:** (B1) network → our origin (app assets); (B2) PDF bytes → engine and job workers; (B3) workers → main thread (RPC replies); (B4) main thread → translation services; (B5) service worker cache; (B6) OPFS and `localStorage`; (B7) outputs: links, clipboard, downloads, the print iframe.

| | Threat | Mitigation | Task |
|---|---|---|---|
| **S** | A PDF link pretends to go somewhere else | Only `http`, `https` and `mailto` open, after a confirmation showing the real target; opened with `noopener,noreferrer` | W5.3 |
| S | Another page posts messages that look like RPC | Dedicated workers are reachable only by their creator; the app registers no `window` `message` listener; every reply is schema-checked | W3.8 |
| S | A lookalike site hosts a copy of the app | Out of our control; About shows the official URL and the source commit | W4.1 |
| **T** | Tampered app assets in the cache or the build | Pinned versions with hashes (npm lockfile, Pyodide release sha256, PyMuPDF wheel sha256 recorded by CI); the service worker caches only files in the build manifest and checks each one's sha256 before caching; `npm ci` only | W4.6, W9.1 |
| T | A crafted PDF corrupts engine memory | MuPDF runs inside wasm in a worker: no DOM, no direct JS objects. The worker is treated as compromised-capable: the main thread validates every reply against the schema and treats every string as untrusted | W3.8, W8.4 |
| T | A crafted PDF causes the saved file to differ from what is shown | Save verifies by reopening; the round-trip tests (W1.7) | W3.6 |
| **R** | Disputes about what was changed | Out of scope (no server, no logs). Existing signatures are preserved by incremental in-place saves (section 4) | — |
| **I** | Documents leave the device | No backend, no analytics, no third-party requests. CSP `connect-src` lists only our origin and the three translation origins. Workers get the same CSP (see below). Job workers have `fetch`, `XMLHttpRequest`, `WebSocket` and `importScripts` removed before Pyodide loads; the engine worker's `XMLHttpRequest` is wrapped to allow only the three translation origins | W3.1, W4.1 |
| I | Translation sends more than the user chose | Opt-in with a one-time consent; only the selected text; keys never logged, never in URLs, kept in memory unless the user stores them encrypted | W2.4, W6.6 |
| I | Leftovers on a shared computer | Autosaves deleted on close and after a clean save; stale ones offered and then deleted; no document data in `localStorage`; the service worker never caches documents; blob URLs revoked after use | W4.2, W4.6, W6.5 |
| I | Referrer and window leaks through outgoing links or requests | `<meta name="referrer" content="no-referrer">`; links open with `noopener` | W4.1, W5.3 |
| **D** | Decompression bombs, huge pages, pathological content streams freeze the tab or exhaust memory | All PDF work off the main thread; resource limits (section 7); the watchdog (section 1); `MemoryError` and wasm aborts lead to a restart with recovery; the fuzz corpus (W8.4) | W3.9, W8.4 |
| D | Many large files fill OPFS | Autosave per document only, deleted on close; `storage.estimate()` checked before writing; failure to autosave is a warning, not an error | W2.3 |
| **E** | XSS through PDF-derived strings (annotation text, bookmarks, metadata, file names, link URIs, error details) | React text rendering only; no `innerHTML`, `dangerouslySetInnerHTML`, `eval` or `new Function`; Trusted Types required by the CSP; SVG icons compiled into components at build time, never injected as markup | W4.1, review checklist |
| E | PDF JavaScript, launch actions, embedded files run code | PDF JavaScript is never executed (W3.2 verifies, with a fixture, that the wasm build doesn't run it); launch actions are ignored; attachments are only saved on request, never opened | W3.2, W7.9 |
| E | Clickjacking the app in a frame | A meta CSP can't set `frame-ancestors`, so the app refuses to start when `window.top !== window.self` | W4.1 |
| E | A malicious dependency | Few dependencies; lockfiles with hashes; `npm audit`, `pip-audit`, Dependabot; no install scripts in CI (`npm ci --ignore-scripts` where the package allows) | W9.1 |

**Workers and the CSP.** A meta-tag CSP applies to the document, but a dedicated worker loaded from a URL gets its policy from that script's response headers, and GitHub Pages sends none, so a worker would run without any CSP. Workers are therefore created from a `blob:` URL that only imports the same-origin worker module: a worker created from a local scheme inherits its creator's policy, so the document's CSP (including `connect-src`) applies inside it. The CSP gains `worker-src 'self' blob:`. Pyodide's start-up may need `'wasm-unsafe-eval'` only; if it also needs `'unsafe-eval'`, W3.1 records why and the review decides. A Playwright test (W8.1) checks from inside each worker that a `fetch` to a non-listed origin is blocked.

## 11. Plan corrections (applied in this PR)

- Decision 5 and 10: one job worker per tab (not per document), kept warm, idle-terminated after 10 minutes; one job at a time; mutating jobs block edits through `begin_task`, read-only jobs don't; chunked engine-worker calls for search, thumbnails and similar read-only work.
- Decision 4: platform flags add `pdfa`.
- Decision 11: Pyodide 314.0.8 is CPython 3.14.
- Decision 7: OPFS is written by the main thread; uploaded fonts persist in OPFS until removed.
- W3.1: workers start from `blob:` URLs so the CSP applies inside them; network globals removed in the job worker.
- W9.2: measure the wire size of the wheels and the wasm, and fall back to pre-compressed files with `DecompressionStream` if Pages doesn't compress them.
- CSP (review checklist): add `worker-src 'self' blob:` and the no-referrer meta tag.

## 12. Questions for the maintainer

**Answered 2026-11-17: all three as recommended.**

1. **Save without a writable handle counts as in place** (section 4), so signed documents saved in Firefox and Safari stay incremental. The alternative is to always do a full rewrite there and warn that signatures break. Recommended: as written.
2. **Uploaded fonts persist** in OPFS until removed. The alternative is to forget them when the tab closes, which is more private but makes the user upload them again each time. Recommended: persist, with a "Remove all fonts" button.
3. **The watchdog never kills the engine worker by itself.** Recommended: as written, since killing it loses the undo history.
