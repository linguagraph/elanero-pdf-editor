## 2. Design

### 2.1 What is recorded per run

There is no new writer. The trend script reads the files the harnesses already write. It normalises each metric
and run to one **trend point**:

| Field | Desktop source (list format) | Web source (object format) |
|---|---|---|
| `metric` | record `id` (must be a row in `budgets.json`) | record `id` (same) |
| `value` | record `median` (ms) | median of the HEAD samples of every round of one attempt, recomputed from the round files |
| `samples` | count of record `samples` | count of the samples it pooled |
| `date` | record `date` | top-level `date` |
| `runner` | record `runner_image` | top-level `runner` |
| `commit` | record `commit` | top-level `commit` |
| `attempt` | record `attempt` | the `attempt-N` folder (the file's own `attempt` is the constant 1) |
| `series` | `desktop-windows` or `desktop-linux` (from the artifact name) | `web-chromium` |
| `run` | the workflow run id and its conclusion | same |

- **Web attempt rule.** Attempt 1 is used. Attempt 2 is used only when attempt 1 has no complete set of five round
  files. Baseline-side files are ignored: the trend is HEAD over time.
- **The marks** (W2's load stages) are not trended in S5. They stay in the artifact (section 6, Q5).
- **W1** (bytes, deterministic, hard gate in `web-pytest`) is not trended.
- **Two small writer fixes, in S5.** `perf.spec.ts` takes `attempt` from `PERF_ATTEMPT`, which `web-perf.yml`
  sets from its existing `ATTEMPT`. Its `runner` becomes `ImageOS-ImageVersion`, as on desktop. Then both formats
  carry the same facts, and the folder rule above becomes a fallback.

### 2.2 Where it is stored (recommended: workflow artifacts, read by a separate trend workflow)

| Option | For | Against |
|---|---|---|
| **Workflow artifacts, 90 days (recommended)** | No write permission and no bot commits. The web artifacts already exist. Matches the approved Q3 in W8.3-performance.md (line 149). | History is limited to 90 days. Each report downloads 14 small zips (a few KB each). |
| A file in the repo | Unlimited history, diffable. | CI would have to commit (`contents: write`, a bot identity, and conflicts with PRs), against Q3 and the plain-push rules. |
| A data branch (`perf-data`) | Unlimited history, outside main. | Same write permission and bot pushes; a second branch to protect. |

History older than 90 days is kept by the release step (section 2.5), which pastes the trend table into the release
PR. That gives one durable point per release without any CI write.

**Where the trend step runs: a new `perf-trend.yml` triggered by `workflow_run` (a change from the S5 row; Q1).**
The S5 row says "trend steps in `ci.yml` nightly and `web-perf.yml`". Reading other runs' artifacts needs
`actions: read`. A job in a called workflow cannot hold more than its caller grants. So inline steps would need
`actions: read` on `web-perf.yml` (breaking `test_web_perf_workflow.py` lines 67-68) and on the `ci` and `web-perf`
jobs in `release.yml`. Instead:

```yaml
# .github/workflows/perf-trend.yml (sketch)
on:
  workflow_run:
    workflows: ["CI", "Web perf (W8.3)"]
    types: [completed]
  workflow_dispatch:
    inputs: { run_id: { type: string, required: true } }
permissions: { contents: read, actions: read }
jobs:
  perf-trend:
    if: >-
      github.event_name == 'workflow_dispatch' ||
      (github.event.workflow_run.event == 'schedule' &&
       github.event.workflow_run.head_branch == 'main' &&
       github.event.workflow_run.head_repository.full_name == github.repository)
    runs-on: ubuntu-latest
    steps:
      - checkout (main, the default for workflow_run; never the triggering run's code)
      - python scripts/perf_trend.py --run-id <id> >> "$GITHUB_STEP_SUMMARY"   # GH_TOKEN: github.token
```

- `workflow_run` runs the default branch's file in the default branch's context, so the token has only these two
  read scopes. A run from a pull request never matches the `if`.
- A release's calls to `ci.yml` and `web-perf.yml` are part of the release run, not runs of those workflows, so they
  do not trigger it. A release stays out of the nightly window by construction.
- The gated workflows keep `contents: read`. The only edit to them is two upload steps in `ci.yml` and the
  `PERF_ATTEMPT` line in `web-perf.yml`.
- The cost is that the trend table sits in its own run ("Perf trend"), linked from the notice, not in the nightly
  run's summary.

**Desktop uploads (in `ci.yml`).** `test-windows` and `test-linux` each get one `actions/upload-artifact` step
(the SHA already pinned in the file), `if: always() && github.event_name != 'pull_request'`. They are named
`perf-desktop-windows-<run_id>-<attempt>` and `perf-desktop-linux-...`, `retention-days: 90`,
`if-no-files-found: warn`, path `.perf/perf-results.json`. These steps run on release too, so a release keeps its
desktop numbers as well.

### 2.3 `scripts/perf_trend.py`

- **Python stdlib only, plus the `gh` CLI** that hosted runners already have (Q2). `gh` handles the token and the
  artifact-download redirect, so the script never handles `GITHUB_TOKEN` and never forwards it to the blob host.
  Commands: `gh run list --workflow <file> --branch main --event schedule --status completed --limit 15 --json
  databaseId,headSha,createdAt,conclusion` and `gh run download <id> --pattern <prefix>-* --dir <tmp>`.
- **Split for testing.** `fetch` (subprocess, about 40 lines, with an injectable runner) only puts files in a temp
  directory. `load`, `window`, `drift` and `render` are pure functions over parsed JSON.
- **Window.** For each (series, metric): tonight's point, plus up to 14 earlier scheduled runs of the same workflow,
  newest first. A run whose artifact is gone (expired) or missing is listed as "no data", not skipped silently.
- **Runner reset.** Only points whose runner **OS part** (`ImageOS`, such as `ubuntu24` or `win25`) matches
  tonight's stay in the window. An `ImageVersion` change does not reset the window, because GitHub updates images
  about weekly and a 14-night window would never fill. It is marked in the table (`image updated <date>`) so that a
  jump on that night has its cause shown (Q3).
- **Table, per series.** The columns are metric, tonight, the 14-night median, the change in percent, the change in
  ms, a spark of up to 15 points (`▁▂▃▄▅▆▇█`, scaled per row) and a status. Every string from an artifact (commit,
  runner) is checked against `^[0-9a-f]{7,40}$` or `^[A-Za-z0-9._-]{1,40}$` before it goes into the Markdown. A value
  that fails is shown as `?`. A metric id that is not in `budgets.json`, or a value that is not a finite number,
  makes its record count as invalid, and the run shows a warning.
- **Drift rule (design 2.5: "above 10% over 7 nights").** Let R be the median of the latest 7 points, tonight
  included, and P the median of the 7 before them. The warning fires when R − P > 1 ms and, when P > 0,
  (R − P) / P > 10%. With fewer than 10 points, the status is `collecting (n/10)` and no warning fires. With P = 0
  (W7 today), only the 1 ms rule applies. The floor of 1 ms matches the web's whole-ms rounding and stops 5 ms
  desktop metrics such as D3 from warning on noise (Q4).
- **Reporting, not failing.** Each drift writes a `::warning title=perf-trend::<series> <metric> +N% (R vs P ms)`
  annotation and a row marked `drift` in the summary. The exit code is 0 for any drift. It is non-zero only when the
  script itself cannot work (`gh` fails, or no input at all). Then the "Perf trend" run is red. It is not a required
  check and never affects CI or web-perf (Q6).
- **Local use.** `python scripts/perf_trend.py --run-id <id>` works with the owner's own `gh` login. `--dir <path>`
  reads already-downloaded files with no network, which is what the tests use.

### 2.4 How a regression is reported, end to end

1. The nightly run (`ci.yml` 03:00, `web-perf.yml` 05:00) finishes and uploads its results, pass or fail.
2. `perf-trend.yml` starts on its completion, builds the table for that run's series, and posts the warnings.
3. A gate failure (the absolute desktop limits, the paired web rule) is still reported by the gated run itself, as
   today. The trend only adds the slow-drift view that the gates cannot see.
4. The owner reads the trend at each release (section 2.5), or whenever a warning annotation appears in the Actions
   list.

## 5. Risks

- **The 90-day artifact limit.** The repository's retention setting can lower 90 days. Then the window shrinks, and
  the table shows "no data", not a wrong median. The release PR tables keep the long history.
- **`workflow_run` quirks.** It fires only for the file on the default branch, so the workflow cannot be tried on
  the PR branch. The first real run is the dispatch after merge (section 4). Its `head_branch` is the branch name,
  so the `head_repository` check is what keeps fork branches named `main` out.
- **Tampered artifacts.** Only scheduled runs on main of this repository are read, the content is parsed as JSON
  only, and every string is checked before it goes into Markdown. Nothing from an artifact is executed or put into
  a shell command.
- **Noise and false warnings.** Hosted runners vary by up to ~40% (W0.2), so the median of 7 is compared with the
  median of 7, not single nights, and it only warns. If warnings still prove noisy in the first 14 nights, the 10%
  can be raised in a later PR (Q4).
- **Nightly CI is red today** (the scheduled `ci.yml` runs on 2026-11-25 and 2026-11-26 failed). The uploads use
  `if: always()`, and the trend workflow runs on any conclusion, so the desktop trend still collects. Each point
  shows its run's conclusion.
- **Format drift between the two writers.** Both formats are covered by the tests above. A later change to either
  writer that the loader cannot read fails `test_perf_trend.py` only if the tests use the writer's real output, so
  the fixtures in the test are copied from the run 45820032101 artifact and from a real `.perf/perf-results.json`.

## 6. Owner questions (each with a recommended answer)

1. **A separate `perf-trend.yml` on `workflow_run`, instead of steps inside `ci.yml` and `web-perf.yml`?**
   Recommended: **yes.** The gated workflows and `release.yml` keep `contents: read`, and a trend failure can never
   turn CI or a release red. The cost is one more workflow and a summary in its own run.
2. **May `perf_trend.py` call the `gh` CLI (preinstalled on hosted runners) instead of raw stdlib HTTP?**
   Recommended: **yes.** It avoids handling the token and the redirect to the blob host in our code. The script
   stays stdlib-only in Python.
3. **Reset the window on an OS change only, and just mark image-version updates?** Recommended: **yes.** Image
   versions change about weekly, so a reset on each would keep the window from filling.
4. **Drift rule: median of the last 7 against the 7 before, above 10% and above 1 ms, warning only.** Recommended:
   **yes.** Revisit the 10% after 14 nights.
5. **Trend the W2 load-stage marks now?** Recommended: **not in S5.** They stay in the artifact. Add them as rows
   in a follow-up if W2 drifts and the stage is not obvious.
6. **Should a drift warning ever fail a run?** Recommended: **no.** Warning annotations and the release-PR tables
   only. The gates remain the absolute desktop limits and the paired web rule.
7. **Which machine is the "reference machine" for the 4 s gate?** Recommended: the owner's Windows laptop, with its
   CPU, RAM, OS and browser version written into the RELEASING.md step once, and Chromium (the same as CI). This is
   the only question S5 cannot answer from the repository. The step can be written with a placeholder that the owner
   fills in, so it does not block the slice.
8. **Does run 45820032101 (a dispatch, unpaired) count as "the first green web-perf run on main" for ticking S4?**
   Recommended: **no.** Wait for the first green **scheduled** run, which is the nightly path S4 delivers. It is not
   needed before S5 is implemented, only before W8.3 is ticked.
