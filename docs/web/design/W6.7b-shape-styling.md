Stage: W6 · Role: design Opus 5.5; implementation Haiku 5.5, review Sonnet 5.5 · Branch: `phase-w-w6.7b-s3-shape-style` · Builds on [W6.7b slice 1](W6.7b-shapes.md) (the shape tools, `edit/shapes.ts`, `ShapeLayer`) and the Redaction Properties dialog (W4.14), whose "style of the next mark" model this note copies.

**Status: approved by the owner on 2026-11-22 (recommended answers); no production code in this change.**

## Summary

`PLAN.md:606` lists "shape styling" as the last pending part of W6.7b. The item comes from slice 1's deferred list ([W6.7b-shapes.md](W6.7b-shapes.md) §9: "Shape style UI (stroke and fill colour, width, opacity) … The desktop has none of these for page-content shapes"). Checking the code again confirms that: **the desktop has no control that changes a page-content shape's style**. What it has is three style fields on its shape tool, which nothing ever sets. So "matching the desktop's options and no more" means those three fields (outline colour, fill colour or none, line width) for the **next** shape, and nothing for shapes already on the page. That needs **no new action, no RPC change and no new Command**: `content.add_shape` already takes all three. The change is a small validation addition in the shared action, a "Shape Style…" dialog on the web, and tests. It fits in one slice of about 300 lines. A second, optional slice gives the desktop the same dialog, so that the web is not ahead of the desktop (Question 1).

### 1.2 What the engine and the action already accept

- `ShapeSpec(kind, rect, start, end, stroke: Color | None = BLACK, fill: Color | None = None, width: float = 1.0)`: `src/pdfeditor/model/objects.py:84-92`.
- `content.add_shape` (a `SnapshotCommand` via `snapshot()`, labels "Add Rectangle", "Add Ellipse", "Add Line"): `src/pdfeditor/actions/content.py:164-168`, `:272-280`.
- `_check_shape` refuses a width outside `(0, 72]`, non-finite coordinates, an empty box and a line with equal ends; it does **not** check paint (a spec with `stroke=None, fill=None` passes): `src/pdfeditor/actions/content.py:171`, `:174-194`. Its refusals carry no `reason`.
- The engine writes `color=` and `fill=` as DeviceRGB through PyMuPDF `Shape.finish`, and **ignores alpha** (`Color.rgb()`): `src/pdfeditor/engine/mupdf/content.py:876-897`. No `ExtGState` is written, so opacity is not possible without an engine change.
- `Color` clamps every channel to `[0, 1]` in `__post_init__`: `src/pdfeditor/model/color.py:7-21`. `from_json` refuses non-finite numbers with `INVALID_ARGS`: `src/pdfeditor/webapi/dto.py:1130-1131`.
- There is **no action that restyles an existing path**: the content actions are `transform`, `replace_text`, `add_text`, `add_image`, `add_shape`, `delete`, `replace_image` (`src/pdfeditor/actions/content.py:200-308`). The object list reports a path's paint only as two booleans (`PageObject.stroke`, `PageObject.fill`, `src/pdfeditor/model/objects.py:55-56`), not its colours or width.

### 1.3 What the desktop offers

- `AddShapeTool` carries `self.stroke = Color(0, 0, 0)`, `self.fill: Color | None = None`, `self.width = 1.5`, and drops the fill for a line: `src/pdfeditor/ui/tools/edit.py:385-409` (fields at `:392-394`, the line rule at `:403`). The stroke is typed `Color`, never `None`: the desktop tool always draws an outline.
- Nothing assigns those fields. The only matches for `.stroke =`, `.fill =`, `.width =` under `src/pdfeditor/ui` are the tool's own constructor, the redaction dialog and the comment inspector (`ui/dialogs/redaction.py:38`, `ui/panels/inspector.py:63`). The tool is built fresh each time it is chosen (`ui/edit_controller.py:50-55`).
- The Edit ribbon has the groups Edit, Add, Shapes (the three tools) and Objects; no style control: `src/pdfeditor/ui/edit_controller.py:103-117`.
- The desktop's colour, line and opacity controls ("A comment or shape selected", `ui/contextual.py:5`; `ui/panels/inspector.py:121`) act on **annotations** only: the inspector binds `annotation_selection_changed` and edits `AnnotationModel` fields (`ui/panels/inspector.py:22`, `:29-34`, `:131-135`, `:172-184`). They are the Comment tab's drawing tools (W7.1a/W7.1b), not page-content shapes.

## 2. What "shape styling" means here

Exactly the desktop tool's three fields, applied to **shapes drawn from now on**:

| Option | Values | Applies to |
|---|---|---|
| Outline colour | any RGB colour; default black | all three kinds |
| Fill | none (default), or any RGB colour | rectangle and ellipse; a line never has a fill (desktop rule, `ui/tools/edit.py:403`) |
| Line width | points, above 0 and at most 72 (the action's `MAX_SHAPE_WIDTH`); default 1.5 | all three kinds |

One style for all three tools, as the desktop's text tool keeps one `last_style` for every new text box (`ui/tools/edit.py:319`). The style is not document state: changing it changes nothing in the open document and is not an undo step (the Redaction Properties model, `web/app/src/redaction/RedactionPropertiesDialog.tsx:1-4`).

**Not included**, because the desktop has none of them and most need engine work:
- opacity (the engine drops alpha; it would need an `ExtGState` writer);
- "no outline" (the desktop tool's stroke is never `None`);
- restyling a shape already on the page (no action exists; the object list has no colours or width; it would be a new `content.restyle_path` that rewrites operators in an existing stream);
- dashes, arrowheads, line caps and joins, rounded corners, polygons, freehand;
- a per-kind style, and remembering the style across sessions (Questions 2 and 3).

## 3. Engine change and undo

### 3.1 Actions and arguments

No new action and no change to `AddShape` or `ShapeSpec`. The web sends the style in fields it already sends:

```json
{"page": 0, "spec": {"kind": "rectangle", "rect": {"x0": 100, "y0": 500, "x1": 200, "y1": 560},
 "stroke": {"r": 1, "g": 0, "b": 0, "a": 1}, "fill": {"r": 0, "g": 0, "b": 1, "a": 1}, "width": 6}}
```

No `$bin` buffer. `generated.ts` does not change (`RunParams.args` is untyped; the TS builder in `edit/shapes.ts` stays the typed side).

### 3.2 Validation added to `_check_shape` (shared with the desktop, about 10 lines)

The web now sends user-chosen styles, so two cases that were unreachable before become reachable from untrusted input:

| Case | Today | Proposed |
|---|---|---|
| `stroke` and `fill` both `null` (a box draws nothing) | passes, writes an invisible path, costs a snapshot | `Refused(…, reason="shape_no_paint")` |
| A line with `stroke: null` | passes, invisible | `Refused(…, reason="shape_no_paint")` |
| A line with a `fill` | passes to PyMuPDF, which fills the open path's degenerate area | the action drops it (`dataclasses.replace(spec, fill=None)`), matching the desktop tool, so neither caller can draw one |
| `width` outside `(0, 72]` | `Refused` without a reason | same message, now with `reason="shape_width"` |
| A colour channel outside `[0, 1]` | clamped by `Color` | unchanged: clamped, not refused (a colour input can only give `[0, 255]` anyway) |
| A non-finite channel | `INVALID_ARGS` from `from_json` | unchanged |

Error codes on the web: `REFUSED` with `details.reason`; `web/app/src/rpc/errors.ts:68-85` (`REFUSED_REASON`) gains `shape_no_paint` → `error.REFUSED.shapeNoPaint` and `shape_width` → `error.REFUSED.shapeWidth`. The dialog prevents both cases, so a user sees them only if the UI is bypassed.

### 3.3 Undo command

Unchanged: `content.add_shape` stays a disk-backed `SnapshotCommand` with the labels "Add Rectangle", "Add Ellipse" and "Add Line" (`actions/content.py:164-168`, slice 1 §3 gives the reasons). A styled shape is one undo step, as now. Choosing a style is not a Command (no document mutation, AGENTS.md rule 5 does not apply), so Undo after closing the dialog undoes the last document edit, not the style.

### 3.4 Engine (`engine/mupdf`) and the PDF written

No change. With a fill, the paint operator becomes `B` (stroke and fill) instead of `S`, and the block gains `r g b rg` (slice 1 §2.2 table, `engine/mupdf/content.py:891-895`). DeviceRGB only.

## 4. The web UI

### 4.1 Where the controls go

The web ribbon renders commands only (`web/app/src/ribbon/Ribbon.tsx:85-88`, `commands/catalog.ts`), and there is no floating style bar yet (W6.8b adds the text one). So, as Redaction Properties does for redaction marks (`catalog.ts:247`, `App.tsx:290`, `App.tsx:960`):

- a new command **`shape-style`** ("Shape Style…") in the group `edit.shapes`, after Line; enabled by `CAN_EDIT_CONTENT` like the three tools (with the same disabled reason), not a toggle; in the command palette for free;
- it opens **`edit/ShapeStyleDialog.tsx`** in the shared `Overlay` (`layout/Overlay`), with:
  - **Outline colour**: `<input type="color">`, reusing `colorInputValue` from `redaction/MarkStyleFields.tsx:37-42` (moved to a shared `theme/colorInput.ts` if the reviewer prefers; it is 6 lines);
  - **Fill**: a checkbox "Fill" (off by default) and, enabled while it is on, a colour input; a note under it: "Lines are never filled.";
  - **Line width**: `<input type="number" min="0.25" max="72" step="0.25">` with the unit "pt" in its label;
  - a small preview swatch (an inline SVG rectangle drawn from the draft; CSS classes only, no inline style, per the CSP rule);
  - **OK** and **Cancel**. OK stores the style and closes; Cancel and Esc discard the draft.
- The style lives in module state in `edit/shapeStyle.ts` (`currentShapeStyle()`, `setShapeStyle()`), for the session, shared by all tabs (as the desktop's class-level `last_style`). `shapeGesture` and `centredGesture` read it instead of the constant `SHAPE_STYLE` (`shapes.ts:41-46`); a line still gets `fill: null`. The TS `ShapeSpec.fill` widens from `null` to `ColorJson | null`.

Choosing a style does not turn a tool on, and an open tool stays on: the next shape uses the new style.

### 4.3 Keyboard and screen reader

- The dialog is a modal `Overlay` (focus trapped, Esc closes, focus returns to the ribbon button or the palette's invoker), titled by `edit.shapeStyle.title`, described by `edit.shapeStyle.intro`.
- Tab order: outline colour, Fill checkbox, fill colour, width, OK, Cancel. Enter in the width field is OK. Native inputs, so colour and number entry follow each browser's own keyboard rules (Chromium's colour picker is keyboard-operable; Firefox and Safari open the system picker).
- The fill colour input is `disabled` (not hidden) while Fill is off, so its label stays announced.
- An invalid width sets `aria-invalid="true"` and `aria-describedby` to the inline error (`edit.shapeStyle.widthInvalid`), and OK is disabled; nothing is clamped silently.
- The preview SVG is `aria-hidden`; the summary text `edit.shape.styleSummary` is what assistive technology reads. The same summary is added to each `ShapeLayer`'s `aria-describedby`, so a screen-reader user who Tabs to the page with a shape tool on hears the style that Enter will draw.
- Forced colours: the swatch keeps its real colours (`forced-color-adjust: none` on the swatch only), since it shows the PDF's colours, not the theme's.

## 7. Risks

- **Web ahead of the desktop** if 3b is not done: the guide table would show a web-only option. Mitigation: Question 1.
- **Validation change reaches the desktop**: the desktop UI never sends a no-paint spec or a line with a fill, so nothing visible changes there; the refusal tests guard it.
- **Colour fidelity**: `<input type="color">` gives 8-bit sRGB; the engine writes DeviceRGB floats. A round trip `#ff0000` → `1 0 0 RG` is exact; others are within 1/255. Tests compare with that tolerance.
- **Snapshot cost** is unchanged (one snapshot per shape, slice 1 §3).

## Questions for the owner

1. **The desktop has no shape-style control. Should the web get one, and should the desktop match it?** Options: (a) web only (3a); (b) web and desktop (3a and 3b); (c) neither: drop "shape styling" from the W6.7b note and tick W6.7b when 2b merges. **Recommended: (b).** The engine and both tools already carry the three fields, so each side is small, and the two products stay the same, which is what "match the desktop" asks for.
2. **One style for all three tools, or one per tool?** **Recommended: one shared style**, as the desktop's text tool keeps one `last_style`; a line simply ignores the fill.
3. **Remember the style after a reload (preferences), or only for the session?** **Recommended: session only.** The desktop tool doesn't remember it either (it is rebuilt on each use, `ui/edit_controller.py:55`); a preference can follow if users ask, and Redaction Properties shows the pattern.
4. **Refuse a no-paint spec and drop a line's fill in the shared action (a behaviour change for any caller)?** **Recommended: yes.** It is reachable only from untrusted web input and would otherwise write an invisible path that costs an undo snapshot, the same reason slice 1 refused a zero width.
5. **Opacity and "no outline" are left out. Agree?** **Recommended: yes.** The desktop has neither; opacity needs an `ExtGState` writer in `engine/mupdf` and a pdfium check for blending, which is its own task if wanted.
6. **Restyling a shape already on the page.** **Recommended: not in W6.7b.** It needs a new action that rewrites operators in an existing content stream and an object list that reports colours and width; neither exists on desktop. If wanted, it belongs in a later plan item for both products.
