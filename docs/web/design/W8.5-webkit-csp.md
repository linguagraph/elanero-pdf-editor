## 1. Verified status

### 1.1 The policy and the page

- `web/app/src/csp.ts:3`: `style-src 'self'` (no `'unsafe-inline'`, no hashes, no nonces).
- `web/app/index.html:6-9`: the same policy in a `<meta http-equiv>`; `csp.test.ts` fails on drift.
- `web/app/index.html:14-17`: an inert `<meta id="react-aria-pressable-style">`. react-aria's
  `usePress` injects `<style id="react-aria-pressable-style">` unless an element with that id
  exists; `style-src 'self'` blocks that inline style. The rule it would add lives in
  `web/app/src/app.css:1-7` (`[data-react-aria-pressable] { touch-action: ... }`). Added by
  `6e30871` ("Fix CSP inline style violation on load", 2026-11-20), with
  `web/app/src/pressableStyle.test.tsx` (no `<style>` in `<head>` after a pressable renders, with
  `NODE_ENV=development` so react-aria does not skip the injection).
- `web/app/vite.config.ts:41-61`: only the dev server (`apply: 'serve'`) relaxes `style-src`; the
  build keeps the strict policy.

### 1.2 The built page (checked here)

A local `vite build` of `origin/main` writes this `<head>` (build output, not committed):

```html
<script type="module" crossorigin src="/assets/index-TxQbhNrV.js"></script>
<link rel="stylesheet" crossorigin href="/assets/index-CLlS05je.css">
```

- The only stylesheet is one same-origin `<link>`, which `style-src 'self'` allows.
- The built CSS has no `@import` and no `url()` to another origin.
- The built JS has no `setAttribute('style', ...)`, no `cssText` and no `<style>` string. The
  one `createElement('style')` is React DOM's `<style precedence>` hoisting, which the app does not
  use (`git grep "precedence="` in `web/app/src` finds nothing). JSX `style={...}` props
  (for example `web/app/src/crop/CropLayer.tsx:66`) are set through CSSOM, which CSP does not
  block.
- The react-aria guard is in the bundle (`Xs="react-aria-pressable-style"`), so the marker in
  `index.html` stops the injection.
- The one constructed stylesheet is the print frame's `@page` sheet,
  `web/app/src/print/printPages.ts:97-103` (`new win.CSSStyleSheet()`, `replaceSync`,
  `adoptedStyleSheets`). Constructed sheets are not fetched, and Chromium does not apply
  `style-src` to them. Whether WebKit does is **To confirm** by the run in §3; the `catch` at
  `printPages.ts:101` would hide a refusal, but a CSP refusal would still fire
  `securitypolicyviolation`, which the specs now record (§1.4).

**Conclusion:** no source of a refused stylesheet is left in the production build that this
analysis can find. The likely cause, the react-aria inline `<style>`, was fixed in `6e30871`. This
is not yet proven in WebKit for the flows that were skipped.

## 2. Design

### 2.1 Proof method (recommended: a Playwright WebKit job on demand)

| Option | Verdict |
|---|---|
| A. Manual run in Safari | Not reproducible, no log, needs macOS. Optional extra, not the proof. |
| B. Playwright `webkit` project on demand in `web-e2e` | **Recommended.** It runs the real production build under the real meta CSP, the specs already fail on any CSP violation and name what was blocked (§1.3), and the log and HTML report are kept as artifacts. |
| C. CSP report-only check | Not possible as asked: a `<meta>` CSP cannot be report-only, and GitHub Pages sets no headers. A `Content-Security-Policy-Report-Only` header on `vite preview` adds nothing that the `securitypolicyviolation` event does not already give. Rejected. |

Option B needs the dispatch to be able to choose WebKit, which #760 took away. Running it from a
throwaway branch that edits the matrix (what the `fix-webkit-*` branches did) works too, but is not
reproducible on main and leaves AGENTS.md wrong. Slice 1 restores the choice for dispatch only.

### 2.3 Proof run, then slice 2 only if it is needed

The coordinator dispatches `web-e2e` with `browsers=webkit` on main after slice 1. The run counts as
the proof for #420 when all of these pass on WebKit with an empty `problems` list:
`crop.spec.ts:31`, `marks.spec.ts:32`, `print.spec.ts:21`, `print.spec.ts:69`,
`save-as.spec.ts:31`, `save-as.spec.ts:69` and `security.spec.ts:33`. A failure in one of them that
is not a CSP message (locator, timing, storage) goes to #718, not here.

If the run shows a `csp: style-src ...` line, slice 2 fixes what it names, without loosening the
policy (no `'unsafe-inline'`, no hash, no nonce):

| Blocked | Smallest fix |
|---|---|
| A library's inline `<style>` | The same pattern as `6e30871`: an inert marker element if the library checks one, and its rule moved into `app.css`. |
| A `style` attribute written as a string | Set the property through CSSOM (`element.style.x = ...`) or a class. |
| The print frame's constructed `@page` sheet | Add `print-frame.css` (`@page { margin: 0; }`) to `public/` and link it from the frame with `<link rel="stylesheet">` built with `createElement`, which `'self'` allows; keep the constructed sheet as the first try. |
| A stylesheet from another origin or `blob:` | Serve it from the app's origin. |

Each fix gets a Vitest test that fails without it (as `pressableStyle.test.tsx` does), and then a
second `browsers=webkit` dispatch. Slice 2 is expected to be well under 50 production lines; the
cap is 400.

## 4. Risks

- **The cause is already gone, so no fix is found.** Expected outcome; then #420 closes on the run
  evidence and slice 2 is not opened.
- **The WebKit run fails for other reasons** (#718 lists about 60 Firefox and WebKit failures).
  Only a CSP line counts against #420; the other failures are reported to #718, so #420 is not
  held open by them.
- **The cause depended on a flow the six specs do not reach.** The CSP check runs in every
  feature spec, so the whole WebKit run (not only the seven tests) is read for `csp:` lines.
- **Playwright WebKit differs from Safari** in CSP details. Accepted; the optional Safari check
  covers it.
- **Slice 1 makes manual runs cost more** when someone picks `all`. Dispatch only; the nightly is
  unchanged.
- **The engine wheel cache is cold** and the dispatch fails early (`web-e2e.yml:8-10`). Run a
  `web-pytest` on main first.
