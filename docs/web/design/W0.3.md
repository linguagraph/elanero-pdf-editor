# W0.3: Translation CORS check

Stage: W0 (#133) · Role: design Opus 5.5, implementation Haiku 5.5, review Sonnet 5.5 · Branch: `phase-w-w0.3-translation-cors` · Reuses the Playwright setup in `web/spike/` (PR #144); start after it is merged, and merge `origin/main` first.

## Question this task answers

Which of the four translation services can a page on **`https://linguagraph.github.io`** call directly with `fetch`? There's no backend or proxy (plan: static hosting, no third-party relays). A service the browser blocks is dropped from the web build. The answer also fixes the exact `connect-src` list for the web app's static CSP (plan, R4).

## What the desktop sends (from `src/pdfeditor/services/translation/`)

| Service | Request | Headers that matter for CORS |
|---|---|---|
| MyMemory | `GET https://api.mymemory.translated.net/get?q=…&langpair=…` | `Accept: application/json` only, so a "simple" request with no preflight |
| DeepL Free | `POST https://api-free.deepl.com/v2/translate` (JSON); `GET /v2/usage` (Test connection) | `Authorization: DeepL-Auth-Key …`, `Content-Type: application/json`, so a preflight |
| Azure AI Translator | `POST https://api.cognitive.microsofttranslator.com/translate?api-version=3.0…` (JSON array) | `Ocp-Apim-Subscription-Key`, optional `Ocp-Apim-Subscription-Region`, `Content-Type: application/json`, so a preflight |
| LibreTranslate | `POST https://libretranslate.com/translate` (JSON); `GET /languages` | `Content-Type: application/json`, so a preflight; the key goes in the body |

Browsers don't allow setting `User-Agent`, and the web transport (W2.4) will simply leave it out. Record whether any service needs it. Custom LibreTranslate servers and custom Azure endpoints are already out of scope on the web (plan, R4).

## Method

Two independent probes per service and endpoint, so a failure can be diagnosed rather than guessed.

1. **Raw probe (Node 22 `fetch`, no CORS enforcement).**
   - Send the preflight a browser would send: `OPTIONS` with `Origin: https://linguagraph.github.io`, `Access-Control-Request-Method` and `Access-Control-Request-Headers` set to exactly the headers above, in lower case and comma-separated.
   - Record the status and every `Access-Control-*` response header.
   - Then send the real request with the same `Origin`, and record the status and `Access-Control-Allow-Origin`.
   - Repeat both with `Origin: http://localhost:5173`, a dev origin.
2. **Browser probe (Playwright, Chromium, Firefox and WebKit).**
   - Load a test page whose **origin really is** `https://linguagraph.github.io`. Use `page.route('https://linguagraph.github.io/elanero-pdf-editor/app/cors-probe.html', …)` to fulfil the document locally, so nothing is deployed; the external API calls still go to the real network.
   - In the page, run `fetch` exactly as the web transport would (method, headers, JSON body, `mode: 'cors'`, `credentials: 'omit'`).
   - Record: resolved with a readable body / rejected with `TypeError` (CORS or network) / HTTP status. Collect the console messages too, since browsers log the CORS reason there.

**Keys.**
- CI and default runs use **obviously fake keys** (`fake-key-for-cors-probe`). A service that returns `Access-Control-Allow-Origin` even on its 401/403 response, with a preflight that allows the headers, is **conclusive: allowed**. A preflight that is rejected, or lacks the origin or a needed header, is **conclusive: blocked**.
- Anything else is **inconclusive**, for example when the CORS headers appear only on a successful response.
- For inconclusive services only, the maintainer *may* run a local probe with a real key from an environment variable (`ELANERO_PROBE_DEEPL_KEY`, `ELANERO_PROBE_AZURE_KEY`, `ELANERO_PROBE_AZURE_REGION`, `ELANERO_PROBE_LIBRE_KEY`). The script never prints, logs or writes a key, and redacts key headers from every recorded output. Never use keys in CI, and never commit them.

**Politeness and privacy.** One request per service, endpoint and origin per run. The text sent is the fixed word `Hello` (no document content). No retries.

## Out of scope

The web transport itself (W2.4) and any change under `src/` or `tests/`. Proxies or relays of any kind; if a service is blocked, it's dropped, not worked around.

## The report

- Per service and endpoint: the preflight result, `Access-Control-Allow-Origin`, the allowed headers and methods, the browser result in each of the three engines, and a verdict: **allowed / blocked / inconclusive** (with the reason).
- Whether the result differs between the two origins (some APIs allow-list origins).
- The recommendation:
  - the services in the web build;
  - the exact CSP `connect-src` entries (scheme and host, no wildcards);
  - which preferences fields the web build hides;
  - what the privacy text (W9.4) has to say.
- Anything that affects W2.4. Examples: a header that must be dropped; `/v2/usage` blocked while `/v2/translate` is allowed, which changes "Test connection"; a service that needs `credentials: 'omit'`.

## Acceptance
