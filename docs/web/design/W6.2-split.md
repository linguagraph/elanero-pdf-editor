# W6.2: Split dialog — end-to-end test, ZIP output, preview

Design note for the remainder of W6.2 ([plan.md](../plan.md), R3 and the W6.2 row). The dialog,
its four modes and the split job already exist (`web/app/src/split/`, `_run_split` in
`src/pdfeditor/webapi/jobs.py`). This note covers what is left: (a) a test through the real run
path, (b) a ZIP built in Python with stdlib `zipfile`, (c) a preview of the file names and page
counts before the split runs. Design only; no production code changes in this PR.

## Summary

- **Names are made once, in Python.** A new `part_names(plan, stem)` in `services/assembly.py`
  applies `safe_name`, keeps document order and makes names unique. `write_split` (desktop and
  web), the new preview call and the ZIP all use it, so the preview shows exactly the names the
  user downloads.
- **ZIP extends the split job's arguments** (`zip: bool`, plus `name` for the file stem). No new
  job type and no second call: the parts never cross to the page and back.
- **Preview is a new read-only engine call, `split.plan`**, on the engine worker, under
  `session.lock`. It writes nothing. Mode "size" is not previewed, since sizes are known only by
  writing the parts.
- **Two layers of end-to-end test:** Vitest drives the dialog through the real `runSplit` /
  `runFileJob` with a scripted job-worker double; a Playwright feature spec drives the app shell
  with the real workers and checks the downloaded ZIP in pikepdf and pypdfium2 (host check).

## 1. Findings in the current code

1. **Order.** `_run_split` returns `_collect(folder)`, which sorts by file name. For bookmark
   splits that is alphabetical, not document order ("Intro" comes after "Chapter 1"). The tests
   miss it because the `outline` fixture's titles sort in document order. Fixed by returning the
   files in `part_names` order.
2. **Collisions.** `write_split` names a part `f"{stem}_{safe_name(name)}.pdf"`. Two bookmarks with
   the same title, or titles that `safe_name` maps to the same text ("A/B" and "A_B"), give one
   path: the second part overwrites the first, silently, on desktop too. In a ZIP, `zipfile` would
   write two entries with one name. `part_names` adds " (2)", " (3)" (compared case-insensitively,
   because Windows and macOS file systems are).
3. **Stem.** The web job hard-codes the stem `"split"` (`split_part01.pdf`); the desktop uses the
   document's name. The job gets `name` (the tab's display name) and uses the existing `_stem()`.
4. **Peak memory.** The parts are on MEMFS (the wasm heap) and `_collect` reads all of them into
   `bytes` before any is freed, so the output is held twice; the size is checked only after the job
   (`jobworker.run_job`, against `MAX_JOB_BYTES`). Section 4 bounds this.

## 2. File names (`safe_name`, where it runs)

```python
def part_names(plan: SplitPlan, stem: str) -> list[str]:
    """File names of the parts, in plan order: "<stem>_<name>.pdf", unique (case-insensitive)."""
```

- Rule (unchanged from desktop): `f"{stem}_{safe_name(name)}.pdf"` when the part has a name, else
  `f"{stem}_{n + 1}.pdf"`; plus the " (k)" suffix on a collision. `safe_name` keeps letters
  (Unicode included), digits, space, `-_.`, replaces the rest with `_`, trims, cuts to 80 chars.
- It runs **only in Python**: in `write_split` (desktop and the job) and in `split.plan`. The
  browser never derives a name; it shows what the reply says (`downloadName` takes the last path
  segment as now).
- The web stem is `_stem(args.name)`, which already strips leading dots and falls back to
  `"document"`. The ZIP is `f"{stem}-split.zip"`, as extract images uses `-images.zip`.
- Non-ASCII names in the ZIP: `zipfile` sets the UTF-8 flag itself; nothing to do.
- Desktop effect: only the collision suffix is new (a bug fix). It goes in `docs/guide/pages.md`.

## 3. ZIP: RPC shape

`dto.SplitArgs` gains two fields (TS sends every field, as now):

```python
@dataclasses.dataclass(frozen=True, slots=True)
class SplitArgs:
    mode: SplitMode
    pages_per_file: int = 1
    ranges: tuple[tuple[int, ...], ...] = ()
    max_bytes: int = 0
    name: str = ""      # the document's display name: the stem of the part names
    zip: bool = False   # one ZIP instead of one file per part
```

Result: unchanged `kind: "files"`. With `zip` and two or more parts, one file
`{name: "<stem>-split.zip", mime: "application/zip"}`; with one part, the PDF itself (as
`_as_archive` does). Without `zip`, one file per part, in document order.

**Why not a new call.** A separate "zip these" call would send every part from the job worker to
the page and back into a worker: three crossings of the full output instead of one. A ZIP built
in TypeScript would need a new runtime npm package (licence entry) or a hand-written writer. The
plan names stdlib `zipfile`, which is already used by `_as_archive` and runs in Pyodide.

**Building it.** `_run_split` writes the parts with `write_split` (unchanged code path), then
either reads them back in name order (no ZIP) or adds them with `archive.write(path, arcname)`
into a `BytesIO`, deleting each part from MEMFS after it is added. Compression `ZIP_STORED`: the
parts' streams are already compressed by the save, and DEFLATE in wasm costs seconds per 100 MB
for a few percent (question 2).

`splitArgs(choice)` in `splitJob.ts` becomes `splitArgs(choice, { name, zip })`. The organizer's
extract (`organizer/extract.ts`) passes `zip: false` and its own name; its download name is
still set on the TS side as now.

## 4. Memory and size limits

The job worker's reply carries one buffer per file, as a list (`jobworker.ts` adapter:
`{reply, buffer: list[0], buffers: list}`); each is copied out of the wasm heap into a JS
`ArrayBuffer`. Parts repeat shared resources (a font used on every page is in every part), so the
total can be many times the document: 500 one-page parts of a document with a 1 MB font is 500 MB.

| Stage | Held in the wasm heap |
|---|---|
| Job start | document copy (bytes) + open MuPDF document |
| Parts written | + every part on MEMFS |
| No ZIP: read back | + every part as `bytes` (MEMFS file deleted after each read: peak about 1× output) |
| ZIP: archive | + `BytesIO` growing to the output (parts deleted as added), + `getvalue()` copy at the end (about 2× output) |

Rules:

1. **A split output cap, checked while writing**: new `limits.MAX_SPLIT_BYTES = 512 MiB` (half
   `MAX_JOB_BYTES`, because the ZIP needs two copies in a 32-bit heap that also holds a document
   of up to 1 GiB). `_run_split` wraps `ctx.progress`: after each part it stats that part's file
   (its name is known in advance from `part_names`) and adds it to a running total; above the cap
   it raises `FILE_TOO_LARGE {max_bytes, size}` at once, before the next part and before any ZIP.
   The same cap applies with and without ZIP, so switching the option never changes whether a
   split fits.
2. Read-back deletes each MEMFS file once read, so the non-ZIP peak stays near 1× output.
3. The page side: unchanged `memoryWarner.check` after the job; one object URL per file. The
   preview's file count lets the dialog suggest ZIP for many files (section 6).
4. The part count is bounded by `MAX_PAGES` (5000); no separate cap.

## 5. The planning call (preview)

**Does `plan_split` need the document open, and does it write?** It reads `doc.page_count` (all
modes) and `doc.outline()` (bookmarks), so it needs the open document; the engine worker has it.
It writes nothing for "pages", "ranges" and "bookmarks". For "size" it calls `size_of`, which
extracts and serialises temporary documents O(log n) times per part: real work, too slow for a
preview on the engine worker, and its answer is the split itself. So "size" is not previewed.

New engine call (engine worker, not a job; `DEADLINE_CLASS` "instant", like `session.outline`):

```python
@dataclasses.dataclass(frozen=True, slots=True)
class SplitPlanParams:
    handle: str
    mode: SplitMode                       # "size" is refused: INVALID_ARGS, path params.mode
    pages_per_file: int = 1
    ranges: tuple[tuple[int, ...], ...] = ()
    name: str = ""

@dataclasses.dataclass(frozen=True, slots=True)
class SplitPartDto:
    name: str          # the file name, as the job will write it
    first_page: int    # 0-based
    page_count: int

@dataclasses.dataclass(frozen=True, slots=True)
class SplitPlanResult:
    parts: tuple[SplitPartDto, ...]
```

- Handler `jobs.split_plan(params)`: `REGISTRY.get`, then under `session.lock` the same validation
  and planning helper `_run_split` uses (`_check_split_args`, `_check_pages`, `plan_split`,
  `part_names(plan, _stem(name))`). One helper for both, so preview and job cannot drift.
- Read-only: no command, no `structure_version` bump, no events beyond the normal call scope.
- Registered in `METHODS` as `"split.plan"`; `generated.ts` regenerated by
  `scripts/make_web_types.py`.

**In the dialog.** When the mode's input is valid (`choiceFrom` succeeds and the mode is not
"size"), the dialog calls `split.plan` after a 200 ms debounce; a sequence number drops stale
replies. Invalid input clears the preview quietly (errors still show only on Split, as now). The
preview is a list "name — pages 3–4 (2 pages)", at most 100 rows then "and N more files", under a
summary line "N files" in an `aria-live="polite"` region (the summary is announced, not the
list). For "size": a hint that names and counts are known after the split. A failed plan call
hides the preview; it never blocks Split.

**Vitest (`SplitDialog.test.tsx`, `splitJob.test.ts`): the real run path with a job-worker double.**

- engine: the existing `fakeEngine` (prepare, apply, abort, memory) plus `split.plan`;
- job worker: `scriptedJobWorker(files, { notices })`, which implements `JobWorker` and checks

## 12. Risks

- **Memory in the wasm heap** for large outputs: bounded by the running cap (section 4); the cap is
  a guess until measured on a 1 GiB-class document (W8 performance pass).
- **Desktop behaviour change** from `part_names` (collision suffix): small, a fix, but desktop
  users see it. Covered by the desktop test and the guide sentence.
- **Preview/job drift:** avoided by one helper; the Python test compares them directly.
- **Debounced calls while a job runs:** the engine worker is idle during a job, so plan calls do
  not wait on it; the dialog does not call `split.plan` while running.
- **Download blocking:** browsers may ask before many separate downloads; the ZIP default above 10
  files avoids that.
- **Line budget:** about 365 lines; the fallback split is noted in section 10.

## Questions for the maintainer

1. **Fix the desktop's duplicate-name overwrite in the same PR** (shared `part_names` with
   " (2)" suffixes)? Recommended: yes. One rule for both apps, and the web ZIP needs unique names
   anyway.
2. **ZIP compression:** `ZIP_STORED` or `ZIP_DEFLATED`? Recommended: `ZIP_STORED`. The parts'
   streams are already compressed; DEFLATE in wasm adds seconds per 100 MB for little gain, and
   `extract_images` already makes the same choice.
3. **Default output:** ZIP when the preview shows more than 10 files, else separate files, until
   the user chooses? Recommended: yes. Many separate downloads trigger the browser's
   multiple-download prompt; one or a few files are easier unzipped.
4. **Output cap of 512 MiB** (`MAX_SPLIT_BYTES`), checked while writing? Recommended: yes, for
   both outputs, revisited with the W8 measurements.
5. **No preview for "Largest file size"** (a hint instead), since sizes are known only by writing
   the parts? Recommended: yes. A preview would be a second full split.
6. **Web part names use the document's name** (`Report_part1.pdf`) instead of `split_part1.pdf`?
   Recommended: yes, as the desktop does.
