So F7 is still open exactly as the review describes: any script running in the page (a
compromised or new dependency included) may call `trustedTypes.createPolicy` under any name,
including `default`, and so turn any string into a `TrustedScriptURL` or `TrustedScript`. A
`default` policy is the worst case: it is called for every plain string reaching a sink, which
would silently undo the `require-trusted-types-for` protection.

## 2. Design

### 2.1 The directive

Append one directive, in both `csp.ts` and `index.html`:

```
trusted-types elanero-worker-url elanero-sw-url
```

The full policy becomes:

```
default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self' blob:; connect-src 'self' https://api.mymemory.translated.net; img-src 'self' blob: data:; style-src 'self'; font-src 'self'; object-src 'none'; base-uri 'none'; require-trusted-types-for 'script'; trusted-types elanero-worker-url elanero-sw-url
```

Choices and why:

- **A named list, not `'none'`.** `trusted-types 'none'` forbids every `createPolicy` call, so
  both app policies throw, the engine worker never starts (`start.ts:54`) and the service
  worker never registers (`register.ts:28`; that failure is swallowed, so offline use would be
  lost silently). `'none'` would only be right if the app used no sink at all, and both the
  `Worker` constructor and `serviceWorker.register` are script-URL sinks.
- **No `'allow-duplicates'` in production.** Each module creates its policy once (`??=`), so a
  second creation means a second copy of the module or foreign code using the same name. Both
  should fail loudly.
- **No `default` in the list.** Nothing in the app needs a default policy; leaving it out stops a
  dependency from installing one.
- **No `*`.** That is the current behaviour, just written down.

### 2.2 What each browser does with it

- **Chromium (and Edge):** enforces the list. `createPolicy` with an unlisted name, or a second
  call with a listed name, throws `TypeError` and reports a `trusted-types` violation. The two
  app policies are listed and created once, so nothing changes for the app.
- **Firefox and Safari/WebKit:** both enforce `require-trusted-types-for` on main (evidence in
  §1). Both shipped the full Trusted Types API, including the `trusted-types` directive, in the
  same releases; the exact versions are **to confirm** in the implementation PR from the browsers
  Playwright pins, not assumed here. Where the directive is supported, behaviour is as in
  Chromium.
- **A browser without Trusted Types:** it ignores both directives (it may log "unrecognised
  directive" to the console), `globalThis.trustedTypes` is undefined, and the app already falls
  back to plain strings (`start.ts:53`, `register.ts:27`). Nothing breaks; the list gives no
  protection there, but neither does `require-trusted-types-for` today.
- **Workers.** The engine and job workers start from a `blob:` URL and inherit the page CSP
  (`start.ts:86-91`), so the directive applies inside them too. No worker code calls
  `createPolicy` (Pyodide's probe is already neutralised by `withoutImportScripts`, which needs no
  policy), so nothing changes there. `sw.js` is not covered by a meta CSP at all.

### 2.3 Dev server

Vite's HMR may re-evaluate `start.ts` or `register.ts` after an edit. The module-level `??=`
cache is then new, `createPolicy` is called again with the same name, and without
`'allow-duplicates'` it throws, so the dev engine fails to restart until a full reload. This
only affects `npm run dev`.

The design adds `'allow-duplicates'` to the **dev** policy only, in `devRelaxedCsp`
(`vite.config.ts:45-56`), by the same `.replace` pattern it already uses for `script-src`. The
built output keeps the strict list; `build.test.ts` already asserts the built meta equals
`CSP_POLICY`, so the dev relaxation cannot leak. (Owner question 3 offers the alternative of
accepting the dev nuisance.)

## 4. Tests and where each runs

| # | Test | Where it runs | Fails when |
|---|---|---|---|
| 1 | `csp.test.ts`: `trusted-types` equals exactly `['elanero-worker-url', 'elanero-sw-url']` (order-free set); no `'none'`, `'allow-duplicates'`, `*` or `default` | Vitest, every PR (`web` check) | The directive is dropped, widened or emptied |
| 2 | `csp.test.ts` source scan: read every non-test `.ts`/`.tsx` under `web/app/src`, collect the first argument of each `createPolicy(` call, and assert the set equals the directive's list | Vitest, every PR | A new policy is added without listing it (it would throw at runtime in Chromium), or a listed policy is removed from code but kept in the CSP |

| 4 | `engine-load.spec.ts` and `security.spec.ts` on **Chromium** | `web-e2e` (nightly, or by hand on the PR branch: `npm run e2e:features:chromium` after staging) | Worker start is blocked (engine never loads) or a `trusted-types` violation is reported |
| 5 | The same two specs on **Firefox and WebKit** | **Manual only**, on the implementer's machine: `npx playwright test engine-load.spec.ts features/security.spec.ts --project=firefox --project=webkit` after staging. `web-e2e` cannot run them: its matrix is Chromium only under #718, and several specs skip non-Chromium under #420 | As row 4, in that browser |
| 6 | Service worker registers with the directive in place | Covered by row 4/5 only if the spec runs against a build with the service worker on; otherwise a manual check in the browser's devtools (Application > Service workers) | `register()` is refused; the app hides this, so only a check of the registration shows it |

What can be verified where:

- **On every PR:** rows 1-3 (string, source and bundle). They prove the list matches the code and
  the bundle, not that a browser accepts it.
- **On Chromium, by CI:** rows 4 and 6, but only nightly or by a manual `web-e2e` dispatch; not
  a required check. The PR must link a checked run (auto-merge gate in AGENTS.md).
- **On Firefox and WebKit:** only by hand, until #718 re-enables those browsers in `web-e2e`.
  This design cannot verify them, and the implementation PR must say which of them it ran.

## 5. Risks

- **A browser rejects or mis-parses the list** and blocks worker start: the engine never loads
  in that browser. Mitigation: the gate in §3 (rows 4-5 on all three browsers before merge);
  rollback is a one-line revert.
- **Silent service-worker loss.** `registerServiceWorker` swallows errors by design, so a blocked
  policy would only cost offline use, with no visible failure. Mitigation: row 6.
- **Unrecognised-directive console warning** in an older browser could trip `security.spec.ts`'s
  console checks. Only matters if Playwright pins a browser without the directive; the manual run
  shows it.
- **Future dependency or Pyodide upgrade creates a policy.** It would throw in production.
  Mitigation: row 3 fails at build time, and the fix is a deliberate CSP change with review.
- **Dev HMR** re-creating a policy (§2.3). Mitigation: `'allow-duplicates'` in the dev policy
  only, pinned out of the build by `build.test.ts`.
- **Firefox and WebKit stay unverified in CI** until #718. Mitigation: the manual run is part of
  the slice's gate; if it cannot be done, F7 stays deferred (question 1).

## 6. Questions for the owner

1. **Gate: may the directive ship with Firefox and WebKit verified only by a manual local run of
   `engine-load.spec.ts` and `security.spec.ts`, since `web-e2e` is Chromium-only under #718?**
   Recommended: **yes.** Those two specs exercise exactly what the directive can break (worker
   start, policy creation, CSP violations); the #718 failures are in unrelated feature specs. If
   either spec fails or cannot run in a browser, ship nothing and keep F7 deferred with a note.
2. **Named list or `'none'`?** Recommended: **the named list `elanero-worker-url
   elanero-sw-url`**. `'none'` blocks both app policies, so the engine would never start (§2.1).
3. **`'allow-duplicates'` in the dev policy only?** Recommended: **yes**; it keeps HMR working and
   `build.test.ts` already keeps it out of the build. The alternative is no dev change, with a
   full reload needed after editing `start.ts` or `register.ts`.
4. **Add the bundle scan (test row 3) to `build.test.ts`, which already takes about a minute?**
   Recommended: **yes**, in the existing build of the first test, so it adds no second build.

No question blocks the design itself. Question 1 decides whether the slice can merge before #718
is fixed.
