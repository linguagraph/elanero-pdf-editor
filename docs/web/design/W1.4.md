# W1.4: Rendering and viewport design

Stage: W1 (#134) · Role: design Opus 5.5 · Branch: `phase-w-w1.4-rendering` · Builds on [W1.1](W1.1.md) (workers, limits, page revisions in action replies, §4). The wire format of every call named here follows W1.2's envelope.

This note decides how pages get from MuPDF in the engine worker onto the screen: what is rendered and at which scale, how it is cached and scheduled, how the layout, text layer and selection work in the browser, how night mode and printing are done, and which Python code is ported to TypeScript (with shared test vectors) versus called in the worker. It is the design for W5.1a–c, W5.2 (thumbnails), W5.4 and W6.5.

## 1. What the desktop does today (the reference)

| Piece | Where | Behaviour |
|---|---|---|
| Zoom | `ui/view/document_view.py` | `zoom` 1.0 = physical size: 1 pt = `logicalDpi / 72` px. Range 0.05–64. Steps `ZOOM_STEPS` (0.1 … 64). Presets Fit Width, Fit Page, 50–400 % (`ui/view/pill.py`) |
| Device scale | `page_item.paint` | `zoom × dpi/72 × devicePixelRatio`, snapped to ~2 % steps by `core/render_cache.quantize_scale` |
| Tiles | `ui/view/tiles.py` | 512 device-px tiles over the exposed part of a page; key `TileKey(doc, page, revision, scale_milli, rotation, tx, ty, variant)` |
| Placeholder | `tiles.thumbnail` | a 160 px wide whole-page image drawn under the tiles until they arrive |
| Renderer | `ui/view/renderer.py` | one worker thread, priority queue (visible > thumbnail), queued requests for other zoom levels cancelled, skips requests whose page revision changed; RGB, night mode inverts the pixels (`variant="night"`) |
| Cache | `core/render_cache.RenderCache` | LRU of `QImage`s, 256 MiB |
| Layout | `core/layout.py` | `compute_layout` for continuous, single, two-up and two-up-cover; `view_matrix`, `rotated_size`, `layout_bounds`, `page_at` |
| Text | `services/text.py` | `PageTextIndex` (chars in reading order with line separators, hit test, word/line ranges, rects, extract), `TextIndexCache` (300 pages LRU), `TextSelection` (anchor/focus `TextPos`) |
| Search | `services/search.py` | regex over each page's `PageTextIndex.text`, page by page, streaming hits |
| Overlays | `page_item.paint` | selection and search hits filled with multiply blending; object outlines dotted |
| Zoom animation | `document_view.zoom_at` | ~150 ms; only cached tiles are drawn while it runs, then tiles at the final scale are requested |

The web keeps these behaviours and numbers unless this note says otherwise.

## 2. Measured costs (W0.2, M5 and M6)

Local desktop, Chromium, median / p95; CI is about twice as slow, and a mid-range laptop is assumed to be 2–3 times slower than local.

| Operation | Local | Notes |
|---|---|---|
| Render a page at scale 1.0 (about 0.5 MP), Python | 2.0–4.7 ms / ≤ 6.9 ms | end to end, including the `ImageBitmap` on the main thread: 3.3–6.1 ms |
| Render a page at scale 2.0 (about 1.9 MP), Python | 6.7–12.9 ms / ≤ 18.4 ms | end to end 11.8–17.6 ms |
| Text page, one page | 1.1–2.0 ms | |
| Search one word | about 1.26 ms per page | 1000 pages: 1.26 s |

So a whole page up to a few megapixels renders in well under one frame budget of work on the engine worker, and the per-call overhead (postMessage, JSON, bitmap creation) is 1–5 ms. Tiling matters only at high zoom; the bigger risks are queueing (a single-threaded worker can't reorder its inbox) and memory.

## 3. Coordinates and scale

- Scene space is points, as on desktop (`compute_layout` output). The front end maps scene to CSS pixels with `k = zoom × 96 / 72` (a CSS pixel is 1/96 inch, the same as the desktop's 96-DPI logical pixel), so 100 % shows a page at physical size, as on desktop.
- **Device scale** for rendering is `zoom × 96/72 × devicePixelRatio`, snapped with `quantizeScale` (the port of `quantize_scale`, 2 % steps, expressed in thousandths). `devicePixelRatio` is read live: a `matchMedia("(resolution: …dppx)")` listener re-requests when the window moves to another monitor or the browser zoom changes.
- **Rotation** (view rotation, 0/90/180/270) is part of the render matrix (`view_matrix`), as on desktop, so tiles stay axis-aligned and text boxes rotate with the same maths.
- Zoom range, steps and presets are the desktop's (`MIN_ZOOM`, `MAX_ZOOM`, `ZOOM_STEPS`, `ZoomBox.PRESETS`), copied into the TS constants module with a comment naming their source. Fit Width and Fit Page use the scroll viewport's size minus `PAGE_GAP`, as on desktop.

## 4. Render units: whole pages and tiles

**Decision:** a page is rendered as **one whole-page image** when its device size is at most **4 MP**; above that it is rendered as **1024 × 1024 device-pixel tiles** covering the visible part plus a one-tile margin.

- 4 MP covers a Letter/A4 page up to 200 % zoom on a DPR 1.5 screen, and 150 % on DPR 2: the common reading range needs one call per page, and fewer, larger calls amortise the per-call overhead (W0.2: scale 2.0 pages render in about 7–13 ms locally).
- 1024 instead of the desktop's 512: per-call overhead is higher in the browser (a round trip through `postMessage`), and a 1 MP tile still renders in a few ms. Tiles share the display list MuPDF already caches per page, so a tile doesn't re-interpret the content stream.
- Whole-page images and tiles use the same cache key type (`tileX = tileY = -1` for a whole page, the desktop's `THUMBNAIL_TILE` convention generalised), so the cache doesn't care which one it holds.
- The **placeholder** under every page is its thumbnail (section 9), as on desktop: a white or black page with the page's thumbnail stretched over it, then the sharp image.
- Requests larger than W1.1's render limit (16 MP per tile, 64 MP per page image) don't happen in viewing: whole pages stop at 4 MP and tiles are 1 MP. The limit protects print and export.

**Pixel format.** The worker renders `ColorMode.RGBA` (a transparent background, which the page element's white or black fill shows through). The worker's JS wraps the tightly packed samples in `ImageData`, calls `createImageBitmap` in the worker and **transfers the `ImageBitmap`** to the main thread, as W0.2 measured (1–2 ms). The main thread never touches raw RGBA when viewing. (W1.2: the render reply's binary part is an `ImageBitmap`, not an `ArrayBuffer`; both are Transferable.)

## 5. Scheduling: the main thread owns the queue

The engine worker handles messages strictly in order and can't be interrupted (W1.1 §1), so a queue of 40 prefetch tiles would delay the tile the user just scrolled to. Therefore:

1. The main thread keeps a **priority queue** of render requests and has **at most 2 in flight** to the engine worker (one rendering, one queued, so the worker never idles between calls).
2. Priorities: (1) visible tiles/pages at the current scale, nearest the viewport centre first; (2) the text layer of visible pages; (3) prefetch at the current scale; (4) thumbnails (the panel and placeholders).
3. Every scroll, zoom or resize re-plans the queue: requests no longer wanted are dropped before they're sent (the equivalent of `TileRenderer.cancel`). A request already sent can't be recalled; its result is cached if still useful and otherwise discarded.
4. **Zoom gestures** (Ctrl+wheel, pinch, the zoom animation): the existing bitmaps are scaled with a CSS transform, nothing is requested, and 150 ms after the last zoom event the queue is re-planned at the final scale (the desktop's `zoom_animating` rule).
5. **Prefetch** only when the queue is empty: the next viewport in the scroll direction at the current scale, then the thumbnails of the 5 pages before and after the visible range.
6. Renders, text layers and thumbnails share the queue with other engine calls (actions, hit tests) through the RPC client: an action or edit call jumps ahead of prefetch and thumbnails but not ahead of the two requests already in flight.

A render request carries the **page revision** it expects. If the page has changed since, the worker replies with the current revision and no pixels, and the front end requests again (the desktop renderer's "skip if the revision changed").

## 6. Caches

| Cache | Where | Key | Budget | Eviction |
|---|---|---|---|---|
| Page images and tiles | main thread, `ImageBitmap` | `(doc, page, revision, scaleMilli, rotation, tileX, tileY)` | **256 MiB of pixels** (W1.1), 128 MiB when `navigator.deviceMemory ≤ 4` or on iPad | LRU; bitmaps covering the visible area are pinned; evicted bitmaps are `close()`d (memory is released only then) |
| Thumbnails | main thread, `ImageBitmap` | `(doc, page, revision, rotation, widthPx)` | 32 MiB | LRU, `close()` on eviction |
| Text layers | main thread | `(doc, page, revision)` | 300 pages (as desktop `TextIndexCache`) | LRU |
| Text indexes for search and copy | engine worker, `TextIndexCache` | page, revision | 300 pages (unchanged) | LRU |
| Display lists and MuPDF page objects | engine worker, backend (`MuPage._display_lists`, `_fz_page`) | page, revision | **new bound: 64 pages** | LRU (see below) |

The engine worker keeps **no pixel cache**: the bitmaps live on the main thread, where they are drawn. `core.render_cache.RenderCache` is therefore not used on the web (it stays as it is for the desktop).

**Finding: the backend's per-page caches are unbounded.** `MuDocument.page()` keeps every `MuPage` it has created, and each one keeps its `pymupdf.Page` and up to two display lists until the page changes. Scrolling through a 1000-page document leaves 1000 display lists in the wasm heap; this likely explains much of W0.2's growth to 314 MiB after 1000 pages (M7). W5.1b bounds it: the document keeps the MuPDF objects (page and display lists) of the 64 most recently used pages and releases the rest (`MuPage.invalidate()`), under the engine lock. The change is in the backend, so the desktop gets the same bound; its behaviour doesn't change except for memory.

## 7. Layout and the scroll container

- The front end gets every page's visible size once (`session.open`, and again after a structure change) and computes the layout itself with the ported `computeLayout` on each zoom, rotation or mode change. It is pure arithmetic over at most a few thousand rectangles.
- **Virtualisation:** only pages intersecting the viewport ± one viewport height exist in the DOM; each is an absolutely positioned element at its layout rectangle. The scroll container's size comes from `layoutBounds`.
- **Very tall documents.** Browsers cap element sizes (about 33.5 million CSS px in Chromium, about 17.9 million in Firefox). A 1000-page document is 1.1 million px tall at 100 %, but 17.6 million at 1600 %. When the layout exceeds **8 million CSS px**, the scroll container switches to a scaled scroll space (scroll position × factor = scene position); the page elements are positioned relative to the viewport, not the container. W5.1a implements and tests this with a 1000-page fixture at 6400 %.
- Modes: continuous, single (only the current page is shown, as on desktop), two-up, two-up with cover. `pageAt` (the port) gives the current page for the page box and for the navigation history, which stores `(page, yFraction)` as on desktop.

## 8. Drawing a page

Each visible page element holds, bottom to top:

1. the page fill (white, or black in night mode) and its shadow (CSS box-shadow, the desktop's `SHADOW_LAYERS` look);
2. the placeholder: the thumbnail bitmap drawn into a small `<canvas>` stretched with CSS;
3. the sharp layer: one `<canvas>` per whole-page image or tile, sized in device pixels and placed in CSS pixels, drawn with `drawImage(bitmap)` (the bitmap stays in the cache);
4. the **overlay**: one `<svg>` per page whose `viewBox` is the page's visible space in points (rotated by the view rotation), holding selection and search-hit rectangles with `mix-blend-mode: multiply` (the desktop's multiply composition), and later the editing overlays of W1.5. Vector overlays stay sharp at every zoom and need no re-render;
5. the accessible text layer (section 10).

Comments are drawn into the page image by MuPDF (`RenderRequest.annotations=True`), as on desktop; interactive comment selection and handles are W1.5's overlay.

**Night mode** is a CSS `filter: invert(1)` on the page elements (and on thumbnails where the desktop inverts them). This matches the desktop's `invertPixels` on the composed white page, and needs no second render and no `variant` in the cache key: switching is instant. Overlays sit outside the filtered element so highlight colours aren't inverted (the desktop draws its overlays after the inversion too).

**Revision changes.** Every action reply lists the pages whose revision changed and whether the structure changed (W1.2 events, from `Change`). For a changed page, the front end keeps drawing the old bitmap until the new one arrives (no white flash) and then `close()`s the old revision's bitmaps. For a structure change (pages added, removed, moved, rotated by `/Rotate`), it fetches the page sizes again, re-lays out, and drops the document's cache entries whose page index no longer means the same page.

## 9. Thumbnails

The thumbnails panel (W5.2) and the placeholders use the same render call, whole page at width 160 CSS px × `devicePixelRatio` (the desktop's `THUMBNAIL_WIDTH_PX`), lowest priority. The panel is virtualised and asks only for visible thumbnails. The page organizer (W6.1) uses the same thumbnails at its own size.

## 10. Text layer, selection and copy

**Decision:** the selection model is the desktop's, ported to TypeScript, not the browser's native selection over a DOM text layer.

Reasons: positions, word and line rules and the copied text then match the desktop exactly; it works the same across the three browser engines (native selection over absolutely positioned spans differs between them, which is PDF.js's long-standing pain); and it is what W1.5's annotation tools (highlight from a selection) and the redaction "mark selection" need.

- **Text layer call.** `text.layer(page)` returns, for one page and revision, what `PageTextIndex` holds: `text` (with `LINE_SEP` between lines, so offsets map 1:1 to chars), the line rectangles, and a binary part with each char's box as `Float32Array` (4 per char, visible page space, points) and its line number as `Uint32Array`. A dense page of 3000 chars is about 60 KB. The index is built in Python (`PageTextIndex.__init__`, unchanged); TypeScript only queries it.
- **Ported query methods** (`web/src/text/pageTextIndex.ts`): `hitTest`, `nearest`, the per-line nearest char, `wordRange`, `lineRange`, `rects`, `extract`, with `_box_gap`, `_distance` and `_is_word_char` (Python's `isalnum() or "_" or category Mn`; in TS `/[\p{L}\p{N}_\p{Mn}]/u`, with the difference for the few `No`/`Nl` characters accepted and covered by the vectors). `TextSelection` (`anchor`, `focus`, `pageSpans`, `pageRects`, `text`) is ported too. Mouse moves during a drag are answered locally from the cached layers, with no round trip.
- **Copy.** For a selection within cached pages (up to 20 pages), the text is assembled locally. Larger selections, including Select All on a long document, call `text.extract` (chunked) in the worker. Copy uses the `copy` event and `navigator.clipboard.writeText` where allowed.
- **Accessibility.** For the pages in the DOM, the text layer is also rendered as transparent, absolutely positioned `<span>`s, one per line, inside a page element with `role="region"` and `aria-label="Page N"`. Screen readers read the text, and browser find-in-page does not replace the app's search (Ctrl+F opens the app's search, W1.6). The spans have `user-select: none` so the custom selection is the only one.
- **Search** (W5.4) runs in the worker as a chunked call over `services.search` (`compile_query`, `search_index`, `TextIndexCache`), unchanged, so regex, whole-word and case rules are Python's. A slice is 50 pages or about 100 ms (W0.2: 1.26 ms per page locally). Hits stream into the panel and are drawn as overlay rectangles; the current hit uses the desktop's colour.

## 11. Printing (R7, W6.5)

- Pages are rendered as images at **150 dpi** by default (option: 300 dpi), with "include comments" mapped to `RenderRequest.annotations`. Print of up to 10 pages runs in the engine worker; more runs as a read-only job in the job worker (W1.1 §1), so editing and viewing continue.
- Each page is encoded to **PNG in the worker's JS** (`OffscreenCanvas.convertToBlob`; no Python encoder), streamed to the main thread page by page (W1.2's job protocol must allow per-item partial results), and turned into a blob URL.
- A hidden same-origin `<iframe>` gets one `<img>` per page sized to the page's physical size in points (`width: <w>pt; height: <h>pt; break-after: page`), with `@page { margin: 0 }`. When all images have loaded, the iframe's `print()` opens the browser dialog. On `afterprint` (or when the dialog is closed), the blob URLs are revoked and the iframe removed.
- Memory: a 150 dpi Letter page is about 1.9 MP and typically 0.2–0.8 MB as PNG. Above 200 pages the dialog warns and suggests a lower resolution or a page range; the blobs are compressed and browsers may keep large blobs on disk, but all must exist when `print()` is called.
- Raster only, as the plan says. Page size per page follows each image's size; mixed page sizes print in the browser's chosen paper size unless the browser supports per-page `@page` sizes.

## 12. What is ported to TypeScript and what stays in the worker

| Python | Decision | Why |
|---|---|---|
| `core/layout.py`: `LayoutMode`, `PAGE_GAP`, `rotated_size`, `view_matrix`, `compute_layout`, `layout_bounds`, `page_at` | **Port** (`web/src/view/layout.ts`), shared vectors | Needed synchronously on every scroll, zoom and pointer move |
| `core/render_cache.quantize_scale` | **Port**, shared vectors | Cache keys must be identical in both apps' terms |
| `core/render_cache.TileKey`, `THUMBNAIL_TILE` | **Mirror** as a TS type | A key, no logic |
| `core/render_cache.RenderCache` | **Reimplement** (Vitest behaviour tests, no vectors) | Holds `ImageBitmap`s, must `close()` them and pin visible ones; unused on the web in Python |
| `ui/view/tiles.tile_specs` (grid maths) | **Move the pure part to `core/layout.py`** as `tile_grid(page_rect, rotation, scale_milli, exposed, tile_px)`, desktop `tiles.py` calls it; **port** with vectors | It is Qt-free maths sitting in `ui/`; the move lets the vector generator call it without Qt and keeps one definition |
| `services/text.PageTextIndex` construction | **Worker** | Needs the engine's text model |
| `PageTextIndex` queries, `TextPos`, `TextSelection` | **Port**, shared vectors | Per-mouse-move latency |
| `services/search` | **Worker** (chunked) | Python regex semantics |
| `services/thumbnails.render_fitted`, `Page.render` | **Worker** | Engine |
| Zoom constants (`MIN_ZOOM`, `MAX_ZOOM`, `ZOOM_STEPS`, presets, `THUMBNAIL_WIDTH_PX`) | **Copy** as constants, listed in the vectors file so a change on desktop fails the check | Values, no logic |

### Shared test vectors

- **Generator:** `scripts/make_web_vectors.py` calls the Python functions on a fixed set of inputs and writes JSON files to `web/test/vectors/`: `layout.json` (page-size sets, including mixed sizes, landscape, empty, one page; every mode; rotations 0/90/180/270; `page_at` probes), `scale.json` (`quantize_scale` over 0.01–100 and the constants), `tiles.json` (`tile_grid` cases at several scales, rotations and exposed rects), `text.json` (text indexes of pages from three fixtures in `scripts/make_fixtures.py`, including a rotated page and a two-column page, with hit-test points, word/line ranges, rects, extracts and multi-page selections).
- **Format:** `{"generator": "scripts/make_web_vectors.py", "format": 1, "constants": {…}, "cases": [{"fn": "compute_layout", "args": {…}, "expect": …}]}`. `Rect` as `[x0, y0, x1, y1]`, `Matrix` as `[a, b, c, d, e, f]`, enums by value. Floats are compared with an absolute tolerance of 1e-6 points; integers and strings exactly.
- **Drift check:** the files are committed (small: under 200 KB each, the text vectors are sampled), so Vitest runs without Python. `make_web_vectors.py --check` exits 1 when they no longer match the Python code, run by a desktop unit test (`tests/unit/test_web_vectors.py`), the same pattern as `make_shortcut_docs.py --check`.

## 13. Calls

Names and deadline classes as reconciled in [W1.2 §17](W1.2.md): `snake_case` fields, documents named by `handle`, the W1.2 deadline classes.

Names and arguments for W1.2's catalogue; the envelope, error mapping and deadline values are W1.2's. All coordinates are visible page space in points; `page` is 0-based.

| Call | Args | Reply | Binary | Chunked | Deadline class |
|---|---|---|---|---|---|
| `session.page_sizes` | `doc` | `[{width, height, rotation, revision}]` per page | – | no | short |
| `render.page` | `doc, page, revision, scaleMilli, rotation, annotations` | `{width, height, revision}`; `revision` differs and no pixels when the page changed | `ImageBitmap` | no | render |
| `render.tile` | as `render.page` plus `tileX, tileY, tilePx` | as `render.page` | `ImageBitmap` | no | render |
| `text.layer` | `doc, page` | `{revision, text, lineRects}` | `Float32Array` char boxes, `Uint32Array` line numbers | no | short |
| `text.extract` | `doc, start: TextPos, end: TextPos`, cursor | `{text, done}` | – | yes (pages per slice) | chunk |
| `text.search` | `doc, query: SearchQuery, startPage`, cursor | `{hits: SearchHit[] grouped by page, pagesDone, total, done}` | – | yes (50 pages or ~100 ms) | chunk |
| `print.render` (job, or engine for ≤ 10 pages) | `doc, pages, dpi, annotations` | per page `{page, widthPt, heightPt}` streamed | PNG `Blob`/`ArrayBuffer` per page | job with partial results | job |

`render.page` with a thumbnail width is how thumbnails are requested; there is no separate thumbnail call.

## 15. Plan corrections (applied in this PR)

- W5.1a: layout ported to TS with shared vectors (`scripts/make_web_vectors.py`); the scaled scroll space above 8 million CSS px.
- W5.1b: whole page up to 4 MP, 1024-px tiles above; the main-thread render queue (2 in flight, priorities, dropping stale requests); `tile_grid` moved into `core/layout.py`; the 64-page bound on the backend's page and display-list caches (desktop too).
- W5.1c: night mode as a CSS `invert(1)` filter (no re-render).
- W5.4: the desktop selection model ported to TS with vectors; DOM text spans for screen readers; large copies and search as chunked worker calls.
- W6.5: 150 dpi PNG pages encoded in the worker, streamed, printed from a hidden iframe; job worker above 10 pages; warning above 200 pages.
- W8.2: web renders are compared with desktop renders of the same fixtures (same MuPDF version, so near-identical; tolerance as for the desktop goldens).
- W8.3: the budgets in section 14.

## 16. Questions for the maintainer

**Answered 2026-11-17: all three as recommended.**

1. **Night mode as a CSS filter** instead of re-rendering inverted pixels. Same result as desktop, instant switch, no extra cache. Recommended: yes.
