# W6.3a: Page ranges per source in Combine

Stage: W6 · Role: design Opus 5.5 · Branch: `phase-w-w6.3a-combine-ranges` · Inputs: [plan](../plan.md) (R6, W6.3), `src/pdfeditor/services/assembly.py` (`merge`, `_shift`, `describe_source`), `src/pdfeditor/services/pages.py` (`parse_page_ranges`), `src/pdfeditor/webapi/jobs.py` (`_convert_merge`, `_run_merge`), `src/pdfeditor/webapi/dto.py` (`MergeSourceArgs`), `src/pdfeditor/ui/combine/model.py` (desktop), `web/app/src/combine/` (#252), `web/app/src/split/ranges.ts`, `web/app/src/print/printRange.ts`.

This note designs the one piece of W6.3 that #252 left out: choosing which pages of each PDF source go into the combined file. It is a design only; nothing here is implemented yet.

## 1. What exists today

- **Service.** `MergeSource.pages: list[int] | None` (0-based, `None` = all) already exists and `merge()` already honours it (`assembly.py:138-141`), in the order given, duplicates allowed. The desktop Combine panel uses it: `CombineEntry.pages` holds the text as typed and `chosen()` turns it into indices with `parse_page_ranges(text, page_count)` (`ui/combine/model.py:55-60`). Image sources ignore `pages`.
- **Wire.** `MergeSourceArgs.pages: tuple[int, ...] | None` (0-based) already exists (`dto.py:839`) and `_run_merge` passes it through (`jobs.py:536`). The web app never sends it (`merge.ts:52-55` sends only `name` and `data`).
- **Gaps in the current service.** `pages=[]` inserts nothing but still adds the source's top-level bookmark at `Destination(start)`, which then points at the next source's first page or past the end. An out-of-range index raises `EngineError("source page N out of range")` from `engine/mupdf/pages.py:168`, which reaches the web as `ENGINE_ERROR`, not `INVALID_ARGS`, and names no source.
- **Web dialog.** It knows file names and sizes only, never page counts: nothing in the web app or `pdfeditor.webapi` calls `describe_source`, and the job worker is started fresh for each run (`run.ts:51`).

## 2. The range rule (exact grammar of `parse_page_ranges`)

The desktop's split, print, export, extract and Combine dialogs all use `pdfeditor.services.pages.parse_page_ranges(spec, page_count)` (`services/pages.py:6-31`). Its exact behaviour today:

1. `text = spec.strip().lower()`. If `text` is `""` or `"all"`, the result is `list(range(page_count))` (so `[]` when `page_count` is 0, with no error).
2. Every `;` becomes `,`; the text is split on `,`. Each item is `.strip()`ped; **empty items are skipped** (`"1,,2"` and a trailing comma are fine).
3. An item containing `-` is cut at the **first** `-` (`str.partition`). An empty left side means 1, an empty right side means `page_count`; otherwise each side goes through `int()`. So `"-4"` is 1–4, `"8-"` is 8 to the end, `"-"` alone is every page, `"1 - 3"` is accepted (`int` strips whitespace).
4. An item without `-` is `int(item)`, a single page.
5. `int()` accepts more than ASCII digits: a leading `+` (`"+3"`), underscores between digits (`"1_0"` is 10) and any Unicode decimal digit (`"٣"` is 3). `"1-2-3"` fails in `int("2-3")`; `"1--3"` gives `hi = -3` and fails the range check.
6. Range check per item: `lo < 1 or hi > page_count or lo > hi` raises `ValueError(f"page range {part!r} is outside 1-{page_count}")`; this one message covers page 0, a page past the end and a reversed span (`"3-2"`). `part` is the lower-cased, stripped item.
7. A malformed number raises `int()`'s own `ValueError` (`invalid literal for int() with base 10: 'x'`).
8. If no item added a page (only separators, e.g. `","`), `ValueError("no pages selected")`.
9. The result is **sorted and unique**: the typed order is not kept (`"5, 1-2"` gives `[0, 1, 4]`).
10. The first bad item stops parsing; errors are plain `ValueError` with English text, which the desktop dialogs show as is (`ui/combine/panel.py:335-336`).

The web already has **two different TypeScript parsers**, neither equal to this one:

- `print/printRange.ts` `parsePageRange` (also used by crop and mark pages): items must match `^(\d+)(?:-(\d+))?$` after trim; refuses `""`, `"all"`, `"3-"`, `"-2"`, `"1,,2"`, `"1 - 3"` and `;`; returns `undefined` with no reason.
- `split/ranges.ts` `parseRanges`: each item is a separate part in typed order; allows spaces around `-`; refuses empty text and empty items; reports `empty`, `invalid` (including reversed) or `outOfRange`.

**Decision: Combine on the web uses the desktop rule**, so a range typed in either app means the same pages, and Python stays the authority. Two small tightenings of `parse_page_ranges`, which also apply to the desktop (see question 1):

- **ASCII digits only**: a number is `[0-9]+`. `"+3"`, `"1_0"` and non-ASCII digits become invalid. Nobody types these on purpose, and mirroring `int()` in TypeScript would be fragile.
- **Structured errors**: a new `PageRangeError(ValueError)` with `kind` (`"invalid"`, `"out_of_range"`, `"empty"`) and `item` (the item as typed, original case). Page 0 and reversed spans are `invalid` (wrong whatever the page count); `out_of_range` is only a page above `page_count`. The **messages stay word-for-word as today**, so the desktop dialogs that show `str(exc)` do not change. `"all"` is matched case-insensitively without lower-casing the rest, so `item` keeps the user's case.

The resulting grammar, the single shared rule (named **the page-range rule**):

```
spec  := blank | "all" (any case) | item ((","|";") item)*      -- blank or "all": every page
item  := blank                                               -- skipped
       | num                                                 -- one page
       | [num] ws* "-" ws* [num]                             -- span; missing start = 1, missing end = last page
num   := [0-9]+
ws    := whitespace as str.strip() / String.prototype.trim() remove (vectors use space and tab only)
```

Errors, first bad item wins: not matching `item`, page 0 or start > end → `invalid`; end > page count → `out_of_range`; no page at all → `empty`. Result: sorted, unique, 0-based.

## 3. Data model and default

- **Web state.** `SourceItem` (`combine/sources.ts`) gains `pages: string`, the text as typed, default `""`. `""` (or `"all"`) means every page, so a dialog where the user never touches the field behaves exactly as today.
- **Images.** No Pages field; `pages` stays `""` and is never sent. `isImageSourceName(name)` is added next to `isSupportedSourceName`.
- **What is sent.** A PDF source whose trimmed text is blank sends no range field (every page). Any other text is sent as typed, in a new wire field `ranges` (section 4). The web never sends the 0-based `pages` field.
- **Why text, not indices.** The dialog has no page count (section 1), and `"8-"` cannot become indices without one. Sending the text lets the job, which opens the file anyway, resolve it with the authoritative Python rule. A later page-count probe (question 3) would only add earlier feedback; the wire contract would not change.

## 4. Service and wire changes

**`merge()`: no signature change.** `merge(engine, sources, bookmarks=True, token=None, progress=no_progress)` and `MergeSource(path, pages=None, password=None)` stay as they are, so the desktop panel and every existing caller and test are untouched. The only service change is validation inside the loop, before `insert_pages`:

- `source.pages` not `None` and empty, or holding an index outside `0..page_count-1`, raises `SourcePagesError(ValueError)` with `.index` (the source's position) and `.page_count`. This replaces today's silent bad bookmark (empty list) and the late `EngineError` (out of range). For image sources `pages` stays ignored, as today.

Resolving text ranges stays out of `merge()`: like the desktop panel, the caller turns text into indices, so the service keeps one input form.

**Wire: `MergeSourceArgs` gains `ranges: str | None = None`** (the page-range rule, 1-based text). Rules in `_convert_merge` (no document is open yet):

- `pages` and `ranges` both given → `INVALID_ARGS`, path `args.sources[i].ranges`.
- `ranges` on an image source → `INVALID_ARGS`, path `args.sources[i].ranges` ("page ranges are for PDF sources"). `pages` on an image stays accepted and ignored, as today (no behaviour change for existing callers).
- `ranges` longer than 2,000 characters → `INVALID_ARGS` (a bound, not a real limit; the field has the same `maxLength`).

In `_run_merge`, after writing the files and before `merge()`, for each PDF source with `ranges`: open it (`engine.open(path)`), read `page_count`, close it, and `parse_page_ranges(ranges, page_count)`. Doing this as a first pass means a bad range on the last source fails in under a second, not after the other sources are merged. `PasswordRequired` here maps to the existing `REFUSED` / `encrypted_source`.

**Backward compatibility.** `merge()`, `MergeSource` and the existing `pages` wire field keep their meaning; only invalid `pages` input changes from `ENGINE_ERROR` (or a wrong bookmark) to `INVALID_ARGS`. `ranges` is optional. `from_json` is strict about unknown keys, so a new web app against an old worker would fail with `INVALID_ARGS`. The app and the worker are one deploy (`pdfeditor-web.zip` with the app), so `PROTOCOL_VERSION` is not bumped. Job args are not in `rpc/generated.ts`, so `make_web_types.py` has nothing to regenerate. `docs/web/design/W1.2.md` §13 needs no edit (it does not list merge's arg fields).

## 5. Validation and error codes

| Case | Checked by | Code | `details` |
|---|---|---|---|
| Range text breaks the grammar, page 0, start > end, only separators | TypeScript while typing (inline, no job starts); Python again in `_run_merge` | `INVALID_ARGS` | `{path: "args.sources[i].ranges", reason: "page_range", kind: "invalid" \| "empty", item}` |
| Page above the source's page count | Python only (the page count is known only there) | `INVALID_ARGS` | `{path, reason: "page_range", kind: "out_of_range", item, page_count}` |
| `pages` and `ranges` both; `ranges` on an image; `ranges` too long; wrong type | Python, `_convert_merge` / `from_json` | `INVALID_ARGS` | `{path}` |
| `pages` empty or index out of range | `merge()` (`SourcePagesError`), mapped in `_run_merge` | `INVALID_ARGS` | `{path: "args.sources[i].pages", page_count}` |
| Encrypted source | existing | `REFUSED` | `{reason: "encrypted_source"}` |

`kind` and `item` are stable values the app translates; the English `message` is for logs only (W1.2 §4). `reason: "page_range"` follows the existing `details.reason` convention of `errors.py`.

**Client side.** `checkSources` (`run.ts`) also runs the page-range rule in syntax mode (section 8) on every PDF row. Any error refuses the run before a worker starts. A `page_range` reply from the job is recognised in `runCombine` (code `INVALID_ARGS`, `details.reason === "page_range"`, index taken from `details.path` with `/^args\.sources\[(\d+)\]\.ranges$/`) and returned as a new outcome `{status: "rangeError", index, kind, item, count}`. The job is finished with `quiet: true` (no toast, `feedback/jobRun.ts:31-34`) because the dialog shows the error on the row. Any other failure keeps today's toast.

## 6. Bookmarks rule

The current behaviour, confirmed from `_shift` (`assembly.py:91-109`) and `merge` (`assembly.py:143-149`), is kept unchanged:

- Each source gets one top-level bookmark titled with the file stem, pointing at the **first page it contributed**. On the web the stem is `safe_name(stem)`, because `_run_merge` writes each source as `safe_name(stem) + suffix`, so `"Report (2024).pdf"` gives the title `"Report _2024_"`. This is existing behaviour, out of scope here (question 5).
- A bookmark whose target page was dropped **is removed**. Its children are not: each child whose own page survived is **promoted** to the removed bookmark's level, in order (`out.extend(children)`). So dropping a chapter's first page keeps its later sections.
- A surviving bookmark is remapped to the page's new position (`keep[old] + offset`), keeping its point and zoom. With duplicates (only possible through `pages`, since the range rule returns unique pages) it goes to the first copy (`reversed(enumerate)`).
- A bookmark with no destination (a heading or a URI bookmark) is always kept, even if none of its children survive (question 4).
- Since the range rule sorts pages, the outline order always follows document order.

The requirement "a bookmark whose page is dropped goes with it" is met. The nuance is that its surviving children stay, promoted one level, and that is kept for desktop parity. The `outline` fixture (6 pages; Chapter k on page 2k-1, Section k.1 on 2k-1, k.2 on 2k) with range `"2-4"` gives, under the source bookmark: `Section 1.2` (promoted, page 1), `Chapter 2` with `Section 2.1` and `Section 2.2` (pages 2-3); Chapter 1, Section 1.1, Chapter 3 and its sections are gone.

## 7. UI

In `CombineDialog.tsx`, each **PDF** row gets a compact text field after the name:

- Visible label `Pages` (`combine.pages.label`); accessible name `Pages of {name}` (`combine.pages.labelFor`); placeholder `All` (`combine.pages.placeholder`); `maxLength` 2000; `inputMode="text"`, `spellCheck={false}`. One dialog-level hint under the drop hint: `combine.pages.hint`.
- Disabled while `phase === "working"`, like the other row controls.
- **Inline error.** It is validated with the syntax mode of the rule on blur and when Combine is pressed, not on every keystroke (`"3-2"` on the way to `"3-20"` must not flash). An error sets `aria-invalid="true"`, adds `combine-row--error` and renders `<p id="combine-pages-error-{id}" class="combine-pages-error">` linked by `aria-describedby`. The dialog-level `role="alert"` message says `combine.error.ranges.summary`, and focus moves to the first bad field. Editing a field clears its error.
- A `rangeError` outcome from the job puts the `out_of_range` message on that row the same way (index → `items[index].id`).
- Image rows show `Image` (`combine.image`) where the field would be, so the columns line up.
- Reordering keeps each row's text and error (they live on the `SourceItem`, keyed by `id`), and Remove drops them.
- CSS: a grid column for the field, the error colour token for text and border (`combine.css`, tokens only, no inline style, per the CSP rule).

## 8. The TypeScript mirror and keeping it in step

- **New module `web/app/src/pages/pageRanges.ts`**: `parsePageRanges(text: string, pageCount: number | null): PageRangeResult`, where `PageRangeResult = {ok: true, pages: readonly number[] | null} | {ok: false, error: {kind: "invalid" | "out_of_range" | "empty", item: string}}`. With `pageCount === null` (**syntax mode**, what the dialog uses) it applies every check except `out_of_range` and returns `pages: null`. It lives in a neutral folder because print, crop and mark pages may move to it later (question 2); W6.3a changes only Combine.
- **Shared vectors.** `scripts/make_web_vectors.py` gains a third output, `web/test/vectors/page-ranges.json`, made by calling the real `parse_page_ranges` on a fixed list of `(text, page_count)` cases and recording `{pages}` or `{error: {kind, item}}`. That covers every grammar branch in section 2: blank, `all`/`ALL`, `;`, empty items, `-4`, `8-`, `-`, spaces around `-`, unsorted and repeated items, page 0, reversed, past the end, `1-2-3`, `1--3`, `+3`, `1_0`, `٣`, `1.5`, `x`, only commas, tabs, `page_count` 1 and 0, and a 25-digit number. `web/app/src/pages/pageRanges.vectors.test.ts` replays every case in full mode. It then checks syntax mode against the same cases: the result equals the vector's error unless that error is `out_of_range`, and an `ok` or `out_of_range` vector is `ok` in syntax mode.
- **Drift.** `make_web_vectors.py --check` covers the new file, and `tests/unit/test_web_vectors.py` already runs that check on the desktop. A change to the Python rule without regenerating the vectors fails pytest; a regenerated file the TypeScript disagrees with fails Vitest. The file carries the usual `_about`/`generator` header and is never edited by hand.

## 13. Risks

- **Desktop behaviour change.** The ASCII-digit tightening changes what the desktop accepts in every range box (print, split, extract, Combine). Impact is near zero, but it is a desktop change in a web PR; the PR body must say so. Messages are unchanged, so no desktop UI test should move.
- **Late out-of-range errors.** Without page counts, "page 9 of a 5-page file" shows only after the job worker has booted (seconds). The error lands on the right row and nothing is downloaded, but it is slower than the desktop. A page-count probe (question 3) fixes it.
- **Whitespace edge.** `str.strip()` also removes `\x1c`–`\x1f` and `\x85`; `trim()` does not. A pasted control character could be invalid on one side only. The vectors stick to space and tab, and the server stays the authority, so the worst case is a server-side `invalid` after the client said yes.
- **Two other TypeScript range parsers** stay (print/crop/mark pages, split) with different grammars. Users could notice that `8-` works in Combine but not in Print on the web. That is tracked by question 2, not fixed here.
- **Opening each ranged source twice** (range pass, then merge) costs a second parse of the xref, which is small next to the copy. Very large files make it visible but not costly.
- **Sorted order surprises.** `"5, 1"` gives pages 1 and 5 in that order, not 5 then 1. This matches the desktop and the guide says so, but some users expect typed order.
