# W5.4: Text selection by touch and pen under the Select tool

Design only. This is the last W5.4 item (PLAN.md: "touch selection under Select (W8.5)"), raised as
question 4 of [W5.4-reroute.md](W5.4-reroute.md). It also closes a gap in the W8.5 note: the 44 px
touch rule must cover the new selection handles.

## 1. Where things stand

- `text/useTextSelection.ts` (#514) builds the model selection from a pointer drag. `startPress`
  returns false for `pointerType === 'touch'`, so a touch press under Select falls through to
  `useHandPan`, which also ignores touch, and the browser scrolls. Mouse and pen start a selection
  on press.
- Under Select the page text spans carry `page-text-layer--model`, so `user-select: none`. A touch
  user therefore can't select text under Select at all: not with the model, not natively. Under Hand
  the native selection (long-press) still works, and Copy reads it (reroute section 5).
- The scroller (`.doc-view-scroll`) has the default `touch-action`, so one-finger touch scrolls and
  two fingers pinch-zoom the browser's visual viewport. The app has no touch pinch handler of its
  own (its zoom gestures are Ctrl+wheel and the trackpad pinch, `view/wheel.ts`).
- Pen on Chromium (Windows, Android) is a direct-manipulation pointer: `touch-action` applies to it,
  so a pen drag on the page is taken by the browser as a pan and the drag gets `pointercancel` after
  a few pixels. Today's immediate pen press therefore selects a word's worth at best.
- `PageTextIndex` already has `hitTest`, `nearest`, `wordRange` and `rects`; `TextSelection`
  normalizes `start`/`end` from `anchor`/`focus`. Nothing in the index changes.

## 2. Pointer types and the gesture

| Pointer | Start | Extend | Notes |
|---|---|---|---|
| mouse | press on text, as today | drag | unchanged |
| touch | long-press on text | keep the finger down and drag; afterwards the handles | a short move is a scroll |
| pen | as touch | as touch | see question 1 |

The touch and pen path is a small state machine, kept pure in a new `text/touchPress.ts` so it is
tested without a DOM:

- **idle** → `pointerdown` (touch or pen, primary, Select on) on a text span within the touch hit
  tolerance → **pending**. The press is not prevented, so the browser can still scroll.
- **pending** → the pointer moves more than `TOUCH_SLOP_PX` = 8 CSS px from the press, or
  `pointercancel`, or a second touch pointer goes down (a pinch), or `pointerup` → **idle**, with no
  selection change. A `pointerup` in time is a tap: it clears the selection, as a mouse click on the
  page does, and a tap on a link still follows it (`linkTap.ts` is unchanged).
- **pending** → `LONG_PRESS_MS` = 500 ms passes, or the browser sends `contextmenu` for this press
  first (Chrome on Android and Windows sends one for a long-press at about the same time) →
  **selecting**. The word under the press is selected (`wordRange`), `contextmenu` is prevented, and
  the link press is dropped (`linkPress.current = null`), so lifting the finger never follows a link.
- **selecting** → `pointermove`: the focus goes to `caretAtPointer` (as the mouse drag), with the
  word kept: a focus before the word anchors at the word's end, after it at the word's start, inside
  it selects just the word (`extendFromWord`, a pure helper in `textSelection.ts`).
  `pointerup` → **idle**, selection kept, announced (section 6). `pointercancel` or a second touch
  pointer → **idle**, selection kept as it was.

Thresholds:

- `LONG_PRESS_MS` = 500: Android's default long-press timeout, and what users of the native
  selection expect. A press that holds still for half a second is not a scroll.
- `TOUCH_SLOP_PX` = 8: the Chromium touch slop is about this. A scroll moves past it within the
  first frames, so it cancels the pending press long before 500 ms.
- Touch hit tolerance: 12 CSS px, converted to points at the current zoom and passed to `hitTest`
  (the mouse keeps `HIT_TOLERANCE` = 4 pt). A fingertip covers more than the glyph.

**Keeping the drag from the browser.** After the long-press the finger is still down and the browser
would pan on the first move. While in **selecting** (touch only), a non-passive `touchmove` listener on
the scroller element calls `preventDefault()`. The finger has stayed inside the slop, so no scroll has
started and the event is still cancelable (the delay-then-drag pattern drag libraries use). It is
registered on the scroller, not on `window` or `document`, where Chromium makes it passive by
default. Pen sends no touch events, so the pen path can extend only with the handles once the browser
takes the drag; section 9 and question 1 cover this.

Mouse is unchanged: `startPress` keeps its path for `pointerType === 'mouse'`, and every existing
`useTextSelection` and `DocumentView.copy` test stays as it is.

## 3. Selection handles

Two handles, start and end, drawn when the selection is non-empty and the last pointer that pressed
the scroller was touch or pen (`lastPointerType`, read in the scroller's `onPointerDown`). A mouse
press hides them; Select All made from the ribbon after a touch shows them. The keyboard alone never
shows them.

- **Where.** The start handle sits in the start page's element at the left edge and bottom of the
  first rectangle `selection.pageRects` gives on that page; the end handle at the right edge and
  bottom of the last rectangle on the end page. Both hang below the line (Android style), so the
  finger doesn't cover the text being selected. A handle whose page isn't mounted is not drawn.
  The positions are derived from the model and the zoom at each render, never stored in pixels.
- **Size.** The visible knob is a 14 px circle with a 2 px stem up to the line. The hit area is a
  transparent 44 × 44 CSS px box (the W8.5 rule; W1.6 section 12 names handles), always, not only
  under `pointer: coarse`, since a pen on a fine-pointer device needs it too. The start handle's box
  extends to the left of its caret and the end handle's to the right, so on a one-letter selection
  they overlap by at most 16 px; there the end handle is on top (extending is the common action).
- **Behaviour.** Each handle has `touch-action: none` (as the comment, crop and edit handles), so a
  drag on it never scrolls, for touch and pen. `pointerdown` records the offset from the press to
  the caret's line middle; `pointermove` (window listeners, as the mouse drag, so a page that
  remounts doesn't end the drag) puts the moving end at `caretAtPointer(x, y - offset)`.
- **Mapping to the model.** Dragging the start handle makes `new TextSelection(end, caret)`;
  dragging the end handle `new TextSelection(start, caret)`. The fixed end becomes the anchor and
  the handle the focus. When a handle crosses the other end, `TextSelection` swaps `start` and `end`,
  and the handles swap roles on the next render, as native handles do. A handle can't make the
  selection empty: a caret equal to the fixed end keeps the previous caret.
- **Auto-scroll.** While a handle is dragged within 32 px of the scroller's top or bottom, the
  scroller scrolls by up to 12 px per frame (`requestAnimationFrame`), and the caret is re-read
  after each step. This is the only way to extend a touch selection past the viewport.
- **Look.** `--color-accent` knob; in forced colours `Highlight` with a `CanvasText` outline. No
  animation, so reduced motion has nothing to switch off.
- **Accessibility tree.** The handles are `aria-hidden` and not focusable: they are a pointer
  affordance only (section 6).

## 4. Pinch zoom and scroll

- A second touch pointer during **pending** cancels it: a pinch never selects. During
  **selecting** or a handle drag it ends the gesture and keeps the selection.
- The browser's pinch zoom scales the visual viewport. The marks and handles are inside the page
  elements, so they scale with the page; the handles get larger or smaller with it (question 6).
- An app zoom (Ctrl+wheel, zoom buttons, fit modes) re-renders marks and handles from the model at
  the new zoom.
- A scroll keeps the selection and its handles; they move with the pages. A handle scrolled out of
  the mounted range is not drawn and comes back when its page remounts.
- Hand is unchanged: under Hand, touch still scrolls and the native long-press selection still works.

## 5. Contexts that must not change

- Passive layers (an armed comment, redaction or shape tool): `selecting` is false, so neither the
  long-press nor the handles appear.
- `contextmenu` is prevented only for the touch or pen press that started a selection; a mouse
  right-click and a long-press off text are left alone.
- Spans get `-webkit-touch-callout: none` under `page-text-layer--model`, so iOS shows no callout
  over the model's selection (untested here: no Safari; section 9).
- A revision change that covers the selection clears it (existing), and the handles go with it.

## 6. Accessibility

- **Announce the size.** When a touch or pen gesture ends with a selection (finger up after a
  long-press drag, or after a handle drag), and also at the end of a mouse drag, a visually hidden
  polite live region in `DocumentView` (`<p role="status" className="visually-hidden">`) gets the
  selection's size. Not a toast: a toast after every handle drag is noise on screen. The count is the
  code points of `pageSpans` without line separators, when every covered page's index is ready;
  otherwise only the pages are announced. A one-page selection says the characters; a longer one
  adds the pages. The region is cleared when the selection is.
- **Keyboard path.** Unchanged: Ctrl+A (Select All, announced by its toast) and Ctrl+C, and the
  Hand tool's native selection for screen-reader selection commands (reroute section 5). Extending
  the model selection with Shift+arrows is not part of this task.
- **Screen readers on touch** (TalkBack, VoiceOver) take the touch gestures themselves; their users
  reach text through the spans and the keyboard path above, which this task doesn't change.
- **Targets.** The handles meet 44 × 44 CSS px (section 3). A new source test, beside the existing
  W8.5 S5 touch-target test, reads the handle rule from `textLayer.css`.

## 11. Risks

- **`touchmove` cancelability.** If Chromium has already started the scroll (a finger drifting just
  under the slop for 500 ms), the guard can't stop it: `pointercancel` arrives and the selection
  stays at the word. The handles still extend it (S2). Spec 1 checks the normal case.
- **Pen.** Without touch events, a pen can't drag on after the long-press while the browser owns the
  drag; it extends with the handles. A real pen check goes in the RELEASING.md manual list.
- **Safari / iOS and Firefox Android** are untested here (owner has chromium only). iOS has its own
  long-press magnifier and timing; `-webkit-touch-callout` and `user-select: none` should hold it
  off, but this is unverified and noted in the guide's known limits if it fails.
- **Browser pinch scales the handles**, below 44 physical px when zoomed out (question 6).
- **Long-press on a link** now selects instead of the browser's link menu under Select. Hand keeps
  the browser's menu.
- **Accidental selections** while reading: 500 ms still is deliberate, and a tap clears it.

## Questions for the maintainer

1. **Pen: touch path or mouse path?** Recommended: touch path (long-press, handles). In Chromium the
   browser pans with a pen drag, so the mouse path selects a few pixels and then is cancelled.
   Revisit with a real pen; if the browser doesn't pan with it, the pen can move to the mouse path in
   one line.
2. **Long-press delay.** Recommended: 500 ms (Android's default). 400 ms feels quicker but catches
   slow scroll starts.
3. **What a long-press selects.** Recommended: the word, as native selection does; an empty caret
   gives nothing to see or copy.
4. **Announce mouse selections too?** Recommended: yes, the same live region; it costs nothing and
   keeps one rule.
5. **A Copy bubble after a touch selection** (W1.6's contextual bar after a selection)? Recommended:
   not here; a separate W8.5 follow-up. The ribbon Copy works on touch meanwhile.
6. **Counter-scale the handles against browser pinch** (`visualViewport.scale`)? Recommended: no;
   the app zoom is the supported zoom and the handles are 44 px at scale 1.
7. **Two slices (S1, S2) or one PR?** Recommended: two, both on `phase-w-w5.4-touch-select`-style
   branches (`phase-w-w5.4-touch-select-s1`, `-s2`); W5.4 is ticked with S2.
