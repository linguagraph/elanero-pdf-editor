# W6.4: decision on the compress spec assertion

**Status: decided by the design owner's delegate (Opus 5.5) on 2026-11-22; no production code in this change.**

Inputs: `web/app/e2e/features/compress.spec.ts`, web-e2e run 45042247041 (chromium, test and retry),
[W6.4 compress audit](W6.4-compress-audit.md), `docs/guide/optimize-compare.md`.

## 1. The failure

`compress.spec.ts:43` expects the Images row of the space table to say "less" after **Smallest
(screen)** on `images.pdf`. The run got `Images 5.1 KB 5.1 KB No change`. The test never reached
the download check (`:54`) or the second run (`:59-73`).

## 2. Decision

**The fixture is wrong for this test, and the product is right about Images.** Point the spec at
`heavy.pdf`, the generated fixture made to be compressed. Keep every assertion. Separately, the
second half of the spec (`:59-73`) checks a real promise that the web reduce job breaks. That is a
**product bug**, recorded in §4 and not fixed here.

The options were (a) relax the assertion, (b) change the fixture, (c) a product bug. Line 43 is (b),
done with an existing fixture so that `scripts/make_fixtures.py` does not change. Lines 69-73 are (c).

## 3. Why the Images row does not shrink on `images.pdf` (not a bug)

Reproduced on the desktop with PyMuPDF/MuPDF 1.28.2, the version the web build pins
(`web/spike/versions.json`). It runs the same `services.optimize.reduce_size` that the web job
calls (`webapi/jobs.py:311, 320`).

- `images.pdf` (`scripts/make_fixtures.py:69-77`) holds one 320 x 200 px image
  (`_gradient_png`, `:47-55`): a smooth gradient that Flate stores in 2 738 bytes. It is drawn twice,
  but both draws use the same image object (xref 7). The larger draw is 320 x 200 pt, which is
  **72 dpi**.
- Smallest is `image_dpi=72, jpeg_quality=50` (`services/optimize.py:32-35`). The engine sets the
  downsample threshold above 72 dpi (`engine/mupdf/optimize.py:100-114`). MuPDF measures an image at
  its largest draw, so this image is not downsampled.
- Re-encoded as JPEG at quality 50, the same pixels take 3 578 bytes, more than the 2 738-byte Flate
  stream. MuPDF keeps the smaller original. The reduced file still holds the same FlateDecode stream
  of 2 738 bytes.
- The whole file still gets smaller: 7 078 to 6 650 bytes (structure and garbage collection), so
  `:54` would pass.

So "Images: No change" is the honest report, which is what the table promises: the change is in
words, and "No change" is a valid result (`web/app/src/i18n/en.ts:1365-1367`,
`docs/guide/optimize-compare.md:47-51`). Nothing the product says promises that every row shrinks.

The assertion is still worth keeping. `:54` passes on `images.pdf` even if image rewriting were
completely broken in the WASM engine, because the structure alone saves 6 %. Line 43 is the only
browser check that the lossy image path (MuPDF `rewrite_images` under Pyodide) actually runs. If it
is removed or relaxed, the test loses the reason it uses Smallest at all. Hence (b), not (a).

`heavy.pdf` (`make_fixtures.py:824-853`, "Wasteful on purpose: a 600-dpi photo-like image") is the
fixture made for this. It has one page (so `:56`, `pages: 1`, holds). With Smallest: the file goes
from 7 762 723 to 22 942 bytes, and Images from 6 054 690 to 15 656 bytes. The reduce took 0.09 s on
the desktop, well within the spec's 120 s timeout even under WASM. 7.8 MB is far below
`MAX_FILE_BYTES` (`web/app/src/documents/openFile.ts:9`). Other fixtures (`report.pdf`,
`several_images.pdf`, `mixed_content.pdf`, `scanned.pdf`) show the same "No change" on Images.
`skewed_scan.pdf` shrinks but belongs to the deskew tests. Changing `images.pdf` itself was rejected:
16 test files use it.

## 4. The second half: a product bug in the web reduce job

The spec reopens the reduced copy and runs **Lossless**. It expects "do not make the file smaller"
and no download (`compress.spec.ts:69-73`). That is the documented promise: "offers the copy only
when it is smaller" (`docs/guide/web.md:386`, `docs/guide/optimize-compare.md:45-46`,
`en.ts:1352-1353`, design W6.4 §5).

The web job does not compare with the file the user opened. `_run_reduce` calls `reduce_size` without
`before` (`src/pdfeditor/webapi/jobs.py:311, 320`). So `before` falls back to the size of a default
re-save (`services/optimize.py:130-131`). That re-save has no object streams and no garbage
collection, so it is larger than the compact file that was opened. The dialog then compares `after`
with this inflated `before` (`web/app/src/compress/compressJob.ts:190-192`). The desktop does it
right: when the document is clean it passes the size on disk (`ui/optimize_controller.py:49-52, 62`).

Reproduced (Smallest, then Lossless on the reduced bytes):

| Fixture | Reduced file opened | Job `before` | Job `after` | Dialog |
|---|---|---|---|---|
| heavy.pdf | 22 942 | 25 369 | 22 942 | "10 % smaller", download offered |
| images.pdf | 6 650 | 6 763 | 6 650 | "2 % smaller", download offered |
| perf_mixed_10.pdf | 29 204 | 31 572 | 29 205 | download offered of a **larger** file |

The table's "Original" size is also wrong in this case: it is not the size of the file the user has.
Lines 69-73 will therefore fail on any fixture until the job is fixed.

**Fix (separate product PR, not here):** the web reduce job compares with the opened file's byte
length while the document is unchanged (`not session.is_dirty`), as the desktop does. It falls back
to the re-save only for an edited document. The fix PR needs a web-pytest test: a reduce of an
already reduced file reports `after >= before`.

## 5. The exact change to the spec

In `web/app/e2e/features/compress.spec.ts`:

1. `:3`, the header comment: "reduce images.pdf with Smallest" becomes "reduce heavy.pdf (the
   fixture made to be compressed) with Smallest".
2. `:25` `fixture('images.pdf')` becomes `fixture('heavy.pdf')`, and `:27` `openPdf(page,
   'images.pdf', original)` becomes `openPdf(page, 'heavy.pdf', original)`.
3. Keep `:43` (Images row contains "less"), `:54` (the download is smaller than the original) and
   `:56-57` (pikepdf one page, pdfium render) unchanged.
4. Split the not-smaller flow (`:59-73`) into its own test, "an already reduced file is not offered
   again", which first makes the reduced copy the same way (Smallest on `heavy.pdf`). Mark it
   `test.fixme(true, 'web reduce compares with a re-save, not the opened file: see
   docs/web/design/W6.4-compress-spec-decision.md §4')` until the §4 fix merges. The fix PR removes
   the `fixme`. Its assertions (`:69-73`) stay as they are: they protect a real promise.

Don't touch `scripts/make_fixtures.py`, the product strings or the guide. The guide already
describes the right behaviour.
