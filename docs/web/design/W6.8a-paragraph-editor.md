## Summary

What remains is front end only, plus a five-line loader fix. The Edit tool's double-click on an editable text block (or the Add Text tool's rectangle) opens a native `<textarea>` placed over the block in the page overlay. While the face loads, the textarea shows the generic family that `content.preview_font` names, then the document's own embedded program through `new FontFace(...)`. Typing, IME, clipboard and in-editor undo are the browser's, and nothing goes to the worker before commit. A commit sends exactly one `actions.run`: `content.replace_text` for an existing block or `content.add_text` for a new one. That is one `SnapshotCommand`, so one undo step on the engine's history, offered in the usual Undo toast. A `FontChoice` with `substituted` shows the substitution notice. `STALE_OBJECT` and other refusals change nothing and offer "Copy text", so the typing isn't lost.

At about 490 changed lines (section 9) this is over the 400-line task size, so it is split: **8a-1** edits existing paragraphs, and **8a-2** adds the Add Text tool.

## 1. The content model the editor reads

Nothing new crosses the RPC. The editor reads what W6.7a already caches per `(handle, page, revision)` from `content.objects`:

| Field of `PageObjectDto` | Use in the editor |
|---|---|
| `type == 'text'` | only text blocks open the editor |
| `key`, plus the list's `revision` | the `ObjectRef {page, key, revision}` of the commit |
| `bbox` (visible-space points) | where the textarea goes and how wide it is: the wrap width is the block's width, as on desktop |
| `text` | the opening content, all selected on open. Lines are joined by `\n` as the engine reports them; the engine re-flows on commit |
| `style` (`TextStyleDto`: `font`, `size`, `color`, `bold`, `italic`, `align`, `line_height`, `char_spacing`, `word_spacing`) | the textarea's CSS: `font-size` = size × zoom × 96/72 px, `line-height` = `line_height`, `color`, `font-weight`/`font-style`, `text-align`, `letter-spacing` = `char_spacing`, `word-spacing`. `font` is the name passed to `content.preview_font` |
| `editable`, `reason` | a non-editable block (rotated, vertical, Type3) doesn't open: the existing tooltip (`edit.reason.*`) stays the only feedback, as on desktop |

**Runs.** The engine's `PageObject` is a block with one dominant style, not a list of styled runs, and `content_objects()` reports exactly that. A block that mixes fonts or sizes is edited as plain text in its dominant style, and the engine re-typesets the whole block in that style on commit, which is the desktop's behaviour too (`InlineTextEditor` is a `QPlainTextEdit`). The design adds no run model: per-run styling would be a new feature for both apps (Question 3).

**Coordinates.** The web viewer has no view rotation, so the box maps to CSS with `pointsToCss` from `comments/coordinates.ts` (points × zoom × 96/72), like the other layers. Page rotation and CropBox are already applied by the engine (visible space).

## 2. The editor (8a-1)

New component `edit/ParagraphEditor.tsx`, rendered by `EditLayer` (existing text) or by the Add Text layer (new text) inside the page box, absolutely positioned. It ports `ui/view/text_editor.py::InlineTextEditor` as W1.5 §5 tabulates; the points that need decisions:

- **Open.** Double-click on an editable text object with the Edit tool (single click keeps selecting and moving, as on desktop). Enter on a single selected editable text object opens it too, which is the keyboard path (section 7). The textarea gets `value = obj.text`, focus, and `select()`.
- **Size.** Left and top at the block's `bbox`; width the block's width; height at least one line (`size × line_height`) and at least 120×40 CSS px, growing with `scrollHeight` up to the page's bottom edge, then scrolling. `white-space: pre-wrap; overflow-wrap: anywhere; resize: none`. A pale yellow background (`--edit-editor-bg`, a token in light and dark) hides the page text beneath.
- **Zoom follow.** `left`, `top`, `width` and `font-size` are derived from `zoom` in render, so a zoom change re-places the box without remounting, and the textarea keeps its value, caret and native undo stack.
- **Commit.** Ctrl+Enter (Cmd+Enter on macOS), or `blur` to anything outside the editor. In 8a nothing else is "inside" (the style bar comes in W6.8b, which extends the check with `relatedTarget`). Commits only if the text differs from the opening text. An unchanged text, or blank text for a new block, closes without a call.
- **Cancel.** Escape closes with no call. Switching the tool commits, as the desktop's `deactivate` does. Closing the tab or the document drops the editor (no call; the document is gone).
- **Wheel.** When the textarea isn't scrollable in the wheel's direction, or Ctrl is held, the event is not stopped, so the viewport scrolls or zooms (W1.4). Otherwise the textarea scrolls.
- **Composition.** Ctrl+Enter and Escape are ignored while `event.isComposing` is true, so committing or cancelling an IME candidate doesn't close the editor. No other IME handling, since nothing is sent before commit.
- **One editor at a time.** `DocumentView` holds `editing: {page, revision, key | null, rect, text, style} | null`. Opening another closes (commits) the current one first.
- **Empty text on an existing block** is passed through: `Page.replace_text` deletes the block on empty text (engine contract), as on desktop. The step is labelled "Edit Text" either way.

## 3. The commit path

One commit is one `actions.run`, so one engine Command and one undo step. The Command is `SnapshotCommand` (disk-backed, real undo by snapshot), because reflowing text into a content stream has no cheap exact inverse. This is already how `actions/content.py` does it, and the desktop shares it.

| Case | Call | Args |
|---|---|---|
| Existing block | `actions.run` `content.replace_text` | `{object: {page, key, revision}, text, style: null}` |
| New block (8a-2) | `actions.run` `content.add_text` | `{page, rect, text, style}` |

- **`style: null` for an edit.** Until W6.8b's style bar exists the style can't change, and `null` makes the engine keep the block's own style (`ReplaceText.style` default). Sending back the DTO would lose `font_ref` (the DTO leaves it out) and risk float drift. W6.8b sends a style only when the user changed it.
- **Add Text style.** The desktop's `DEFAULT_TEXT_STYLE` (Helvetica 12, black, left, line height 1.2), and from the second box on the style used last in the tab (`AddTextTool.last_style`). In 8a that is always the default, since there's no style bar; the "last style" slot is kept so W6.8b only fills it.
- **Code.** `edit/commit.ts` gains `commitText(deps, change, settle)` beside `commitEdit`, sharing `refreshStale`, the revision note (`scheduler.noteRevisions`) and `offerUndo`. Undo labels: `edit.textEdited` "Text changed." and `edit.textAdded` "Text added."
- **Reply value.** `RunResult.value` is the `FontChoice` (`{name, embedded_reused, substituted, missing}`) or `null`. A small TS type guard reads it (`RunParams.args` and `value` are untyped in `generated.ts`, as for shapes).
- **After the commit,** the selection is the block nearest the old box in the new list (`reselect` from `hitTest.ts`, as for moves). A new block is selected the same way. A failed reselection selects nothing.
- **fontTools.** The worker already installs it before these two actions (S1). The first commit of a session can take a few hundred ms longer; the editor stays open (read-only, `aria-busy`) until the reply.

## 4. Fonts: preview, fallback, non-embeddable fonts

### 4.1 Preview (8a-1, `edit/previewFont.ts`)

1. On open, in parallel with placing the box: `content.preview_font {handle, page, font_name: style.font}`.
2. Until it answers, the textarea uses the fallback stack: `family` from the reply when present, else `familyOf(style.font)` ported as three lines (`sans-serif`, `serif`, `monospace`), so the box never renders in the browser's default serif.
3. `found` with `program` → `new FontFace('pdf-' + sha1(program).slice(0, 12), program)`, then `face.load()`, `document.fonts.add(face)`, and the textarea's `font-family` becomes `"pdf-…", <fallback>`. The hash is `crypto.subtle.digest('SHA-1', …)`. Loaded faces are cached by hash for the tab's life (one `Map<string, Promise<string | null>>` in the module), so reopening the same block costs nothing.
4. A face the browser's sanitiser rejects (`load()` rejects: bare CFF, Type 1, broken tables) is cached as `null`, and the fallback stays. Nothing is logged to the user: the preview is a preview.
5. A reply that arrives after the editor closed is ignored (the editor checks that it is still open on the same key).

### 4.2 Fallback at commit (engine, unchanged)

The committed text is typeset by the engine, not by the preview. With no `font_ref` (all of 8a), `_font_for_known` reuses the embedded program when it covers the new characters. Otherwise it uses the base-14 font of the same family, style and weight, and reports `substituted: true` (a subset that lacks a typed character, or a non-embedded non-standard font). The front end then shows the desktop's notice as a **warning** toast: "The document's font can't show this text in this style; used {name} instead." plus " Missing: {chars}" when `missing` isn't empty (key `edit.text.substituted`). The edit is kept; the user can undo it.

### 4.3 Loader fix (8a-1)

`needsFontTools` in `engine/loader.ts` also returns true for `method === 'content.preview_font'`, so the worker installs fontTools before the preview check. That's about 5 lines plus a test in `fonttools.test.ts`. Without the fix the first preview of every session falls back (see Status).

### 4.4 Fonts that can't be embedded

- **The document's own font** is already embedded in the PDF. Showing it in the tab is a private, in-memory `FontFace` that never leaves the page and is never written anywhere, so `fsType` doesn't apply to the preview. At commit the engine only reuses what the document already embeds (subset with a new cmap), as on desktop.
- **A non-embedded font** (base-14 names, or a font the PDF names but doesn't carry) is "not found" by `content.preview_font`. The preview uses the generic family, and the commit typesets in the matching base-14 font. A non-base-14 name gives `substituted: true` and the notice.
- **A licence-restricted font file** (`fsType` restricted or bitmap-only) can only reach the engine as a `FILE` `font_ref`, that is, an uploaded font chosen in the picker. That is W6.8b/W6.9: upload refuses it with `FONT_NOT_EMBEDDABLE`, and the engine's `_check_embeddable` raises `UnsupportedFeature` → `NOT_SUPPORTED` if one slips through. 8a sends no `font_ref`, so it can't hit this path. It still handles the code like any refusal (section 5).

## 5. Errors and stale objects

| Reply | Front end |
|---|---|
| `STALE_OBJECT` (the page changed since the list was read, e.g. an undo or a save renamed keys) | close the editor, clear the selection, `refreshStale` (refetch `content.objects`, note the revision), warning toast `edit.text.stale` "The page changed, so your text wasn't applied." with the action **Copy text** (writes the typed text to the clipboard via `navigator.clipboard.writeText`). Nothing is applied |
| `BUSY` (a job is running) | keep the editor open with its text and show the usual busy toast (`reportRpcError`), so the user can commit again later |
| `NOT_SUPPORTED`, `REFUSED`, `ENGINE_ERROR`, others | close the editor, error toast through `reportRpcError`'s text, with **Copy text**. The document is unchanged (the Command never ran, or the snapshot rolled back) |
| Worker lost (W1.1 watchdog) | the existing worker-lost flow. The editor closes; its text is offered with **Copy text** before closing |

`ToastAction` holds one action. Copy text is the action on failures, and Undo on success, so they never compete.

## 7. Accessibility

- The textarea has `aria-label` = `t('edit.text.editorLabel')` "Edit text" (new block: "New text") and `aria-describedby` a visually hidden hint `edit.text.hint` "Ctrl+Enter to apply, Escape to cancel."
- Keyboard path to open: with the Edit tool, Tab reaches the page layer, arrows or Tab move the selection (W6.7a), and **Enter** opens the editor on a single selected editable text object. For Add Text, Enter on the focused page opens a default-size box (200×40 pt) in the middle of the page, as `ShapeLayer`'s keyboard fallback does.
- On close, focus returns to the page layer with the edited block selected, so screen-reader users hear where they are.
- A result is announced through the toast region (`role=status`), which already exists.
- Colours: `--edit-editor-bg` and the text keep at least 4.5:1 in both themes. The text colour is the block's own colour, so a light-on-light block falls back to the theme's text colour when the contrast against the background is under 3:1. The preview is never the stored result.
- `web-a11y` (axe) gains the open editor state in its edit spec.

## 12. Risks

| Risk | Mitigation |
|---|---|
| Preview and committed layout differ (browser shaping and line breaking vs MuPDF's typesetting), so a line may wrap differently after commit | accepted, as on desktop; the page re-renders within the 500 ms budget, and the text is what matters. Noted in the guide |
| Browser sanitiser rejects many embedded programs (CFF, Type 1, subset tables) | fallback family, so the editor is always usable; Playwright checks a TrueType fixture loads the face |
| First edit of a session waits for fontTools installation | install is triggered by the preview call (4.3), which happens while the box opens, so the commit rarely waits; busy state covers the rest |
| Blur commits by accident (e.g. a toast button, the browser's own UI) | blur to `null` (window switch) doesn't commit; only blur to an element inside the app does, as desktop's `_focus_left` ignores application deactivation |
| Large preview programs (CJK fonts, many MB) | the call caps at 16 MB (`MAX_PREVIEW_BYTES`), and the cache is per tab; the editor never waits for the face |
| Keys go stale under the open editor (undo from the toolbar, autosave rename) | the commit carries the list's revision, so the engine refuses with `STALE_OBJECT` and the text is offered for copying. A revision change arriving while the editor is open doesn't close it, so the user's typing stays until the commit reports the stale state |
| Mixed-style blocks flatten to one style on commit | same as desktop; called out in the guide ("a paragraph is re-set in its main style") and Question 3 |

## Questions for the maintainer

1. **Split into 8a-1 (edit existing text) and 8a-2 (Add Text)?** The total is about 485 lines, over the 400-line task size. Recommended: yes, as section 9 lays out. 8a-1 is usable alone, and 8a-2 reuses its editor.
2. **Send `style: null` on an edit until W6.8b?** It keeps the block's exact engine-side style, including `font_ref`, which the DTO doesn't carry. Recommended: yes. W6.8b sends a style only when the user changes it.
3. **No run-level styling: a mixed-style block is re-set in its dominant style,** as on desktop. Recommended: keep parity. Per-run editing would be a new feature for both apps and needs an engine model of runs first.
4. **Does blur commit?** Recommended: yes for focus moving inside the app (desktop parity), no for the window losing focus (switching apps shouldn't apply half-typed text).
5. **Copy text as the recovery for failed commits** (instead of keeping the editor open on every error). Recommended: yes, except `BUSY`, where the editor stays open because a retry is likely to succeed.
