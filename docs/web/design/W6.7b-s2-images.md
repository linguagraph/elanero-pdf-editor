# W6.7b slice 2: add, replace and export images

Stage: W6 · Role: design Opus 5.5; implementation Haiku 5.5, review Sonnet 5.5 · Branches: `phase-w-w6.7b-s2a-add-image`, `phase-w-w6.7b-s2b-replace-export-image` (section 9) · Builds on [W6.7b slice 1](W6.7b-shapes.md) (the shape tools, `ShapeLayer`, `shapes.ts`), W6.7a (Edit tool, object cache, selection, `edit/commit.ts`), [W1.3](W1.3.md) (`content.*` actions), W1.2 §5 (`$bin` buffers) and W7.9 S2 (`attachments.get`, the read-only bytes call this slice copies).

## Summary

The engine and the actions already exist and have round trips on desktop:

| Piece | Where | State |
|---|---|---|
| `content.add_image` (`AddImage(page, rect, data)`) | `actions/content.py` | `SnapshotCommand`, label "Add Image"; no validation beyond `_check_page` |
| `Page.stamp_image(ImageStamp)` | `engine/mupdf/page.py` → `pages.stamp_image` | `unshare_page`, then PyMuPDF `insert_image(rect, keep_proportion=True, overlay=True, rotate=page.rotation)`; the same code the stamp and signature-appearance features use (`services/stamping.py`, `services/signing/_pdf.py`) |
| `content.replace_image` (`ReplaceImage(object, data)`) | `actions/content.py` | `SnapshotCommand`, label "Replace Image", `StaleObject` check |
| `Page.replace_image(key, data)` | `engine/mupdf/content.replace_image` | PyMuPDF `Page.replace_image(xref, stream=…)`; global by design (no `unshare_page`), then `structure_changed()` |
| `Page.image_data(key)` | `engine/mupdf/content.image_data` | `extract_image(xref)` → `(bytes, ext)`; no action and no RPC (desktop reads it under the lock) |
| Round trips | `tests/actions/test_content.py` | `test_round_trip_add_image` (pikepdf + pdfium, `pixel_green_pdfium`), `test_round_trip_replace_image`, undo tests |

So, as in slice 1, most of the work is the front end: an Add Image tool (file picker, then place), Replace Image and Export Image on a selected image, plus three engine-side additions that web input needs: **format and size validation** on the two actions, a **read-only `content.image` call** for export, and a clear refusal for **inline images** (`BI … EI`), which the object list reports as `IMAGE` but which have no XObject to swap or extract. The rotated-and-cropped offset (issue #537) applies to added images too (section 6). The change is over 400 lines, so it ships as **2a (add)** and **2b (replace and export)**.

## 1. Actions, calls and arguments

### 1.1 `content.add_image` (2a)

`AddImage(page: int, rect: Rect, data: bytes, keep_proportion: bool = True)`. The new field (default `True`) is passed to `ImageStamp.keep_proportion`; the desktop tool doesn't send it, so nothing changes there.

| Field | Web sends | Notes |
|---|---|---|
| `page` | the page under the gesture (0-based) | `_check_page` |
| `rect` | `{x0,y0,x1,y1}` visible-space points: the dragged box ∩ page, or the default box | the image is fitted inside it, centred, keeping its aspect |
| `data` | the file's `ArrayBuffer` | `rpc/client.encodeValue` turns it into `{"$bin": 0}` and transfers it (the main thread's copy is detached, no second copy there) |
| `keep_proportion` | `true` | kept in the args so a later "stretch to box" needs no RPC change (as slice 1 kept the shape style) |

### 1.2 `content.replace_image` (2b)

Unchanged: `ReplaceImage(object: ObjectRef, data: bytes)`, with `object = {page, key, revision}` from the W6.7a selection and `data` a `$bin` buffer. The image keeps the **placement of the old one** (section 4), so the arguments carry no rect.

### 1.3 `content.image` (2b, new read-only RPC, not an action)

Export changes nothing, so it is a call like `attachments.get`, not an action: no Command, no undo step, no dirty flag.

- Params `ImageParams(handle, page, key, revision)`; result `ImageDataResult(ext: str, mime: str, width: int, height: int, data: bytes)`; deadline class `io`.
- Under the lock: page in range (`INVALID_ARGS`), `page.revision == revision` (`STALE_OBJECT`, the `_check_fresh` rule), object present and of type `IMAGE` (`STALE_OBJECT` otherwise), not an inline image (`REFUSED`, section 3.3), `width × height ≤ MAX_RENDER_PIXELS` (`FILE_TOO_LARGE` with `max_pixels`, the Extract Images ceiling) before any bytes are read, then `page.image_data(key)`.
- Format for the browser: `ext` `jpeg` → `.jpg`/`image/jpeg`; `png` → `image/png`; `jpx` is converted to PNG (the helper `browser_image(data, ext)` moved out of `services/export/images.extract_images`, which then calls it, so Extract Images and Export Image agree); any other stored format (`jb2`, `tiff`, …) is returned as stored with `application/octet-stream`. `len(data) > MAX_JOB_BYTES` → `FILE_TOO_LARGE`.
- Registered in `webapi/__init__.py` and in `engineConnection.ts`'s method list; `generated.ts` regenerated with `scripts/make_web_types.py`.

## 2. Command and undo

Both actions stay **`SnapshotCommand`** (disk-backed, in MEMFS on the web within `WEB_SNAPSHOT_BUDGET`). No real inverse:

- **Add**: `insert_image` appends a content stream, wraps the existing content in `q … Q` (overlay), adds an XObject and a `/Resources` entry, and `unshare_page` may first copy shared content. An inverse would have to undo edits to objects it didn't create (the slice 1 argument, unchanged).
- **Replace**: PyMuPDF writes a new image object (new filters, colour space, a new `/SMask` xref when the PNG has alpha) and copies it over the old xref, so the old stream, `/Decode`, `/SMask` and `/ImageMask` are gone; a faithful inverse would need the old object graph byte for byte. The swap is also document-wide (section 4), and AGENTS.md rule 5 names content edits as snapshot operations.

Cost: one full in-memory save before each add or replace. A large image also grows every later snapshot. Same risk as slice 1, measured in W8.3.

Revisions: add ends with `mark_page_changed(page)`; replace calls `structure_changed()`, so every page's revision moves (correct: a shared image shows on other pages). The front end passes `changed.revisions` to `scheduler.noteRevisions` and clears the object cache, as `edit/commit.ts` does.

## 3. Formats, limits and validation

### 3.1 Accepted formats

**PNG and JPEG only on the web; refuse everything else.** The desktop picker also offers TIFF, BMP, GIF and WebP, and keeps them. The rule is a platform flag, not an OS check (`model/platform.py`):

- `PlatformCapabilities.image_formats: frozenset[str] | None = None` (None = whatever MuPDF reads); web: `frozenset({"PNG", "JPEG"})`.
- `PlatformCapabilities.max_image_bytes: int | None = None`, `max_image_pixels: int | None = None`; web: `limits.MAX_IMAGE_BYTES = 50 MiB`, `limits.MAX_IMAGE_PIXELS = 25_000_000` (a 24 MP camera photo fits; Question 2).

### 3.2 Where it is checked

A new `services/image_input.probe_image(data) -> ImageProbe(format, width, height)` opens the bytes with Pillow (`Image.open` reads only the header, no pixel decode; Pillow is already in the web package for Extract Images and `_with_opacity`). `actions/content._check_image(data)` (shared, before the snapshot) refuses with `Refused`:

- empty data, or a header Pillow can't read: "This file is not an image the editor can read.";
- a format not in `image_formats`: "Only PNG and JPEG images can be added here.";
- more bytes or pixels than the platform limits (checked before Pillow's own bomb check, which raises at 2 × 89 MP).

`content.add_image` and `content.replace_image` both call it. The desktop gets the "unreadable" refusal instead of today's `EngineError` from MuPDF; with its limits None, nothing else changes there. The front end checks too (section 5.1) so a wrong file never crosses to the worker, but the engine check is the one that counts.

### 3.3 Inline images

`content_objects` reports `INLINE_IMAGE` as `ObjectType.IMAGE`, and `_image_xref` then raises `EngineError("… is not an image XObject")`. In 2b, `_image_xref` raises `UnsupportedFeature("This picture is stored inside the page content and can't be replaced or exported.")` for an `INLINE_IMAGE` (instead of the generic `EngineError`). `webapi/errors.py` already maps `UnsupportedFeature` to `NOT_SUPPORTED`, and the desktop shows the message as it does for other unsupported edits. The raise happens inside the snapshot op, before anything is written; a test asserts the failure leaves no undo step and an unchanged revision. If `SnapshotCommand` turns out to keep a step on a failed op, the action checks first through a small engine query (`Page.is_inline_image(key)`, about 8 lines) before calling `snapshot()`. `content.image` catches the same exception and answers `NOT_SUPPORTED`. Moving and deleting inline images keep working.

### 3.4 Memory on the engine worker

Per add or replace of an image of `B` bytes and `P` pixels, peak extra heap is about:

| Copy | Size |
|---|---|
| transferred `ArrayBuffer` → Python `bytes` (Pyodide copies once) | B |
| MuPDF's buffer in `insert_image` | B |
| PNG only: MuPDF decodes and re-deflates (`P × channels`, up to 4) | ≤ 4P (100 MB at 25 MP) |
| the snapshot save before the edit (whole document into MEMFS) | document size |

With the 50 MiB and 25 MP caps, about 200 MB above the document at worst; the Python `bytes` is released when the action returns. A JPEG is passed through as `DCTDecode` without decoding, so it costs about 2B. The wasm heap only grows, so a very large insert raises the high-water mark (`HEAP_WARN_BYTES` warns at 1.5 GiB); that is why the pixel cap is lower than the 64 MP render ceiling. Export (`content.image`) holds the stored bytes once, plus a decode for `jpx` → PNG, bounded by `MAX_RENDER_PIXELS`.

## 4. Replace: placement and shared XObjects

- **Rect stays valid**: the page content is not touched. The `cm … /ImN Do` that places the image draws the unit square, so the new picture fills exactly the old picture's box. A different aspect ratio is stretched to that box (the desktop does the same; Question 3).
- **References stay valid**: the replacement is written into the **same object number** (PyMuPDF copies the new object over the old xref). Every `/Resources /XObject` entry that points at it, on this page, on other pages, in Form XObjects and in annotation appearances, still resolves, and now shows the new picture. That is why `Page.replace_image` deliberately skips `unshare_page`.
- **Side effect to test**: PyMuPDF's `replace_image` inserts the new image on the calling page first (one more content stream and resource name) and then blanks that stream. On a page whose `/Contents` is shared (`shared_objects_contents`), that touches the shared array. A test asserts both pages still render the same and that the extra stream draws nothing (section 7). If it leaves junk, the fix is engine-side (call `unshare_page` only for `/Contents`, or drop the extra stream and resource), not in this slice's front end.
- **User expectation**: replacing a logo that appears on every page replaces it everywhere. The guide says so, and the undo toast undoes it everywhere in one step.

## 5. The web tools

### 5.1 Add Image (2a)

Command `add-image` (exists, group `edit.add`, no handler yet): `CAN_EDIT_CONTENT`, `checked` while the tool `'image'` is on.

1. **Pick first.** The handler goes through `requestEditTool(tab, signed, 'image')` (the signed-document warning), then opens a hidden `<input type="file" accept="image/png,image/jpeg,.png,.jpg,.jpeg">` (new helper `files/pickFile.ts`, about 25 lines; the click comes from the ribbon, so the browser's user-activation rule is met). The desktop places the box first and asks for the file after; on the web, picking first keeps the picker inside the ribbon click and catches a bad file before the user draws anything.
2. **Check in TS** (`edit/images.ts`): the first bytes are `89 50 4E 47 0D 0A 1A 0A` (PNG) or `FF D8 FF` (JPEG), and `file.size ≤ MAX_IMAGE_BYTES` (a TS constant mirrored from `limits.py`, with a Vitest test against `generated.ts` if the limit is exported there, else a comment). Failures show `edit.image.wrongType` or `edit.image.tooLarge`, and the tool doesn't turn on. The file is read with `file.arrayBuffer()`; nothing is decoded on the main thread.
3. **Place.** The tool `'image'` turns on, holding the bytes. `ShapeLayer` is reused: it takes a `kind` of `'image'` that previews a dashed box and calls `shapeGesture('rectangle', a, b, page)` with the image default size `200 × 150` (the desktop `AddImageTool.default_size`; `DEFAULT_SHAPE_*` becomes a per-kind table). Click = default box at the press point, drag = that box, Enter = default box centred, Escape = cancel (the bytes are dropped).
4. **Send** one `actions.run` `content.add_image` with `{page, rect, data, keep_proportion: true}`. On success: `noteRevisions`, `cache.clear()`, Undo toast `edit.image.added`, tool back to Select (one-shot, as in slice 1). On failure: `reportRpcError` (`REFUSED` shows the engine's message), the tool stays on with the same bytes so the user can place again.

### 5.2 Replace Image (2b)

Command `replace-image` (exists, group `edit.objects`): enabled when the Edit tool is on and the selection is **exactly one object of type `IMAGE`** (new `CommandState.singleImageSelected: boolean`, set by `DocumentView` from `editSelection` and the cached list; desktop: `single_image`). The handler opens the same picker and TS check, then sends `content.replace_image` with `{object: {page, key, revision}, data}`. On success: `noteRevisions(changed.revisions)` (all pages), clear the cache, keep the selection on the object at the same box (`reselect` from `hitTest.ts`, since keys may change once the list is re-read), Undo toast `edit.image.replaced`. `STALE_OBJECT` goes through `commit.ts`'s `refreshStale` path and `edit.stale`.

### 5.3 Export Image (2b)

Command `extract-image` (exists; its label changes from "Extract Image" to **"Export Image"**, the desktop's name, to avoid confusion with the Tools tab's "Extract Images"). Same enable rule as Replace; it doesn't change the document, so it is allowed on a signed document without the warning, and the command doesn't need `CAN_EDIT_CONTENT` beyond the Edit tool being available. The handler calls `content.image` with the selected ref, then `downloadBytes(name, data, mime)` from `files/downloads.ts`. File name: `<document stem>-page<N>-image.<jpg|png|…>`, the stem passed through the existing safe-name rule used for job downloads. Errors: `FILE_TOO_LARGE` → `edit.image.exportTooLarge`; `REFUSED` (inline image) → the message; `STALE_OBJECT` → `edit.stale`.

### 5.4 Keyboard and accessibility

The place layer is the slice 1 `ShapeLayer` (focusable on the current page, Enter places, Escape cancels) with its own `aria-label` (`edit.image.layer`). Replace and Export are commands, so the ribbon, the palette and shortcuts reach them. The file picker is the browser's.

## 6. Rotated and cropped pages (inherits issue #537)

`pages.stamp_image` maps the rect with `derotation_matrix` and lets PyMuPDF apply `transformation_matrix`, the same path as `add_shape`. So on a page that is both rotated and cropped, an **added** image lands offset by the crop origin, exactly like shapes (issue #537). `insert_image(rotate=page.rotation)` keeps it upright. Not fixed here; slice 2a adds a strict `xfail` (`test_image_on_rotated_cropped_page`, `desktop_only`, reason linking #537) next to the shape one, which the engine fix turns green. **Replace** is unaffected (it doesn't touch placement); **export** is unaffected.

## 10. Risks

- **EXIF orientation.** A phone JPEG with `Orientation = 6` shows upright in the browser picker but MuPDF may insert it sideways (to confirm by a probe in 2a, with a fixture JPEG). If it does, the fix is in `pages.stamp_image` (rotate by the EXIF tag, read by `probe_image`), for desktop too.
- **Snapshot cost and heap growth** (section 3.4): large images make every later undo snapshot larger and raise the wasm heap's high-water mark. Caps chosen to keep one insert under about 200 MB extra; W8.3 measures.
- **Global replace surprises users** who expected one occurrence to change. Mitigated by the toast text and the guide; per-page replace is Question 3.
- **PyMuPDF `replace_image` side effects** on shared content (section 4): covered by `test_replace_shared_image`; any leftover is an engine fix.
- **Stretch on replace** when aspect ratios differ (section 4), as on desktop.
- **Rotated and cropped pages** (section 6, #537): added images are offset like shapes until the engine fix.
- **Signed documents**: add and replace invalidate signatures (shared warning); export doesn't change anything.
- **Formats stored oddly** (`jb2`, CCITT, `/Decode`-inverted, CMYK JPEG): export returns the stored bytes, which some viewers show inverted or not at all. Same behaviour as Extract Images; noted in the guide only if a real sample shows it.

## Questions for the maintainer

1. **PNG and JPEG only on the web, desktop unchanged?** Recommended: yes, through the platform flag. GIF, WebP and BMP would need MuPDF or Pillow decoding in wasm with no clear demand; the desktop keeps its wider list.
2. **Limits: 50 MiB and 25 MP per inserted image?** Recommended: yes. 25 MP takes a 24 MP camera photo; a larger PNG decodes to over 100 MB in the 32-bit heap. Tune in W8.3.
3. **Replace: global and stretched, as on desktop?** Recommended: yes for this slice. A "replace on this page only" (unshare the XObject) and "keep the new image's proportions" (rewrite the `cm`) are later options, for both front ends at once.
4. **Pick the file first, then place (web), while the desktop places first?** Recommended: yes. The browser's file picker must open from the user's click, and a refused file is reported before the user draws. The desktop can stay as it is.
5. **Rename the web command "Extract Image" to "Export Image"?** Recommended: yes, to match the desktop and to keep it apart from the Tools tab's "Extract Images".
6. **Inline images: refuse replace and export?** Recommended: yes, with the clear message. Converting an inline image to an XObject first is possible but is a content rewrite with its own tests; it can come with the engine fix for #537 or later.
7. **Two PRs (2a add, 2b replace and export)?** Recommended: yes; together they exceed the 400-line task size.
