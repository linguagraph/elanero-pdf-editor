# W1.7: Test strategy

Stage: W1 (#134) · Role: design Opus 5.5 · Branch: `phase-w-w1.7-test-strategy` · Inputs: [W1.1](W1.1.md), [W1.3](W1.3.md), [W0.1 results](../spikes/W0.1-results.md) (condition C1), [W0.2 results](../spikes/W0.2-results.md) (budgets), `tests/`, `web/spike/`, `.github/workflows/`, `scripts/ci_changes.py`.

This note decides how the web version is tested: which Python suites run under Pyodide and how, how the round-trip rule of `AGENTS.md` (saved files checked by pikepdf and pypdfium2) works when the edit happens in Pyodide, TypeScript unit tests, end-to-end tests in three browsers, visual goldens, performance budgets, fuzzing, accessibility, and the CI jobs that run all of it. It closes condition C1 of W0.1 by fixing the mechanism and the order of migration.

## 1. The layers at a glance

| Layer | Tool | Runs in | Covers | CI job (§13) |
|---|---|---|---|---|
| Python on the host | pytest (+ xdist `-n auto`) | CPython 3.11, Windows (desktop CI) | everything, as today, plus `tests/actions/` and `tests/webapi/` | `test-windows` (existing) |
| Python under Pyodide | pytest in Pyodide on Node | CPython 3.14 in wasm | engine contract, core, actions, services and webapi in the web set | `web-pytest` |
| Host halves of those | `scripts/web_host_verify.py` | host CPython with pikepdf and pypdfium2 | the pikepdf/pypdfium2 checks of files saved in Pyodide (§3) | `web-pytest` (a later step) |
| TypeScript units | Vitest | Node (jsdom where needed) | RPC client, DTO validation, generated-type drift, layout ports, command registry, catalogue | `web-unit` |
| End to end | Playwright | Chromium, Firefox, WebKit | user flows R1–R7 and the viewer, security behaviour, offline, accessibility | `web-e2e` |
| Visual | host `tests/golden/compare.py`; Playwright screenshots | worker renders; Chromium for UI | rendering equals desktop; UI regressions | `web-e2e` |
| Performance | the W0.2 harness, promoted | Chromium | load size, start-up, render, scroll, save | `web-perf` |
| Robustness | corpus + seeded mutations | Pyodide on Node; a browser subset | no hang, no crash, an error code instead | `web-fuzz` |

## 2. Python tests under Pyodide

**Suites.** `tests/engine/`, `tests/unit/` (the core and model tests), `tests/services/`, `tests/actions/` (W2.1) and `tests/webapi/` (W3). Excluded by marker, not by path list:

- `gui` (existing): needs Qt.
- `desktop_only` (new marker): tests of features that aren't in the web set (OCR, signing, PDF/A and tagging, Store updates, file association, Office import, system fonts, DPAPI secrets), and tests of the desktop build and packaging (`tests/unit/test_build_bootloader.py`, `test_msix.py`, `test_packaging.py`, `test_store_*`, `test_app.py` and similar). Applied as a module-level `pytestmark` in each such module. A host test in `tests/unit/` checks that every test module importing a module from the web package's `EXCLUDED` list carries the marker, so a new desktop-only test can't silently break the Pyodide run.
- `network` (existing) and `slow` (existing; nightly only under Pyodide).

The Pyodide run uses `-m "not gui and not desktop_only and not network"` on PRs, adding `slow` tests nightly.

**What is under test.** The run installs the **built web wheel** (W2.6) into Pyodide, plus the PyMuPDF wasm wheel, fontTools and Pillow, and mounts only `tests/` (read-only, NODEFS at `/repo/tests`) and a writable output folder (`/out`). Testing the wheel rather than the source tree also proves the trimmed package is complete; a module missing from the wheel fails the import, not production.

**Runner.** The W0.1 spike files move out of `spike/` (W2.7a):

| From | To |
|---|---|
| `web/spike/run_engine_tests.mjs` | `web/test/pyodide/run_pytest.mjs` (`prepare` and `run` stay; `run` takes pytest arguments and the wheel paths) |
| `web/spike/pyodide_conftest.py` | `web/test/pyodide/pyodide_plugin.py` (the stub modules, the engine-return counting, the summary JSON, and the host-check recorder of §3) |
| `web/spike/verify_host.py` | `scripts/web_host_verify.py` (the generic replay of §3; the smoke check becomes one registered host check) |

The Qt stub in the plugin (W0.1 item 3) goes away: W2.7a makes the autouse fixture in `tests/conftest.py` import `pdfeditor.ui.settings` lazily and skip itself when PySide6 is absent.

**Python versions.** The desktop runs 3.11 and Pyodide 3.14 (W1.1 §8). This job is the only 3.14 coverage, so a failure here that doesn't happen on the desktop is a real bug in shared code, not noise.

**xdist.** Not under Pyodide: there are no processes. If the Pyodide run passes 15 minutes, the job shards by suite into a matrix (engine, unit + actions + webapi, services), not by `-n`.

## 3. Condition C1: the host halves

W0.1 found 85 tests that stop at their first pikepdf or pypdfium2 call under Pyodide (48 after engine work, 37 before any) and are verified only on the desktop. The plugin's stubs keep doing that (skip at the first host-only call) for tests not yet migrated. Migrated tests use **declared host checks**:

**`tests/hostcheck.py`** holds every pikepdf and pypdfium2 check that tests in the web suites use, as registered functions:

```python
@host_check
def valid_elsewhere(path: Path, pages: int, password: str = "") -> None:
    """Saved output opens in pikepdf and pdfium with ``pages`` pages."""
    with pikepdf.open(path, password=password) as pdf:
        assert len(pdf.pages) == pages
    ...

@host_check
def annotation_subtypes(path: Path, page: int, expected: list[str]) -> None: ...
@host_check
def pdfium_text_contains(path: Path, page: int, text: str) -> None: ...
```

Rules for a host check:
1. Its first argument is the path of a PDF the test produced; the rest are JSON values (numbers, strings, booleans, lists, dicts with string keys).
2. It asserts and returns `None`. A check never returns a value that later assertions use, because under Pyodide it runs later, elsewhere. A test that today reads a value with pikepdf and then compares it passes the expected value into the check instead.
3. It imports pikepdf and pypdfium2 inside its body, so `tests/hostcheck.py` imports fine under Pyodide.

**On the host** (desktop CI, local runs) `@host_check` is a pass-through: the check runs inline, and the tests behave exactly as now.

**Under Pyodide** the plugin replaces the decorator's behaviour with a recorder: the call copies the file to `/out/hostcheck/<sha256>.pdf`, appends `{"test": nodeid, "check": name, "args": {...}, "file": "<sha256>.pdf", "sha256": ...}` to `/out/hostcheck/manifest.jsonl`, and returns, so the test goes on to its engine assertions. A recorded test reports as passed in Pyodide.

**Replay.** `scripts/web_host_verify.py <manifest>` runs on host CPython after the Pyodide step in the same job. For each entry it checks the file's sha256, calls the registered check with the recorded arguments, and writes JUnit XML with one case per entry named `<nodeid>::<check>`. A failure fails the job and names the test that produced the file. The browser end-to-end tests (§4) write the same manifest format, so one replay script serves both.

**Inputs made with pikepdf.** The 37 tests that never reach the engine mostly build their *input* with pikepdf (`pikepdf.new`, damaged or specially encrypted copies). Those inputs move into `scripts/make_fixtures.py`, which runs on the host and may use pikepdf, and the tests take them through `fixture_pdf`. Where the input depends on test parameters, the fixture script generates each variant.

**Ratchet.** The plugin's summary counts host-only skips per test module. `web/test/pyodide/host_only_baseline.json` holds those counts (85 + 37 at the start, per module). The job fails when any module's count rises, and a migration PR lowers the baseline. So no new test can add an unverified host half, and the debt is visible.

**Order of migration** (C1's priority): `test_contract` (30 functions, mostly `assert_valid_elsewhere`), then `test_content_edit` and `test_text_edit_forms` (R1), `test_page_ops` and `test_mupdf_pagecopy` (R2, R6), `test_redaction` (A7), `test_security` (A8), then the rest. The first two groups land in W2.7b, before W2.1's content and page slices rely on them in the browser; the rest in W2.7c. A static host test (an `ast` scan) keeps pikepdf and pypdfium2 imports out of web-suite test modules once they are migrated: it allows them only in `tests/hostcheck.py`, in `desktop_only` modules, and in modules still listed in the baseline.

## 4. Round trips across the boundary

AGENTS.md requires every editing feature to have a test that edits, saves, reopens and checks the saved file in pikepdf and pypdfium2. On the web this holds at two levels:

1. **Python level.** The action tests (`tests/actions/`, W2.1) and the webapi tests do edit → `save_bytes` → reopen → assert, with the independent-reader assertions as host checks (§3). They run on the desktop (inline checks) and under Pyodide (recorded and replayed).
2. **Browser level.** Each R1–R7 end-to-end test (W8.1) performs the edit through the UI, saves (a download, or a mocked `showSaveFilePicker` in Chromium), reopens the saved file in the app and checks what it shows, then writes the saved bytes and a manifest entry with the checks to run (for example `valid_elsewhere` with the page count, `pdfium_text_contains` with the edited text). The `web-e2e` job replays that manifest with `scripts/web_host_verify.py` after Playwright finishes.

## 5. TypeScript unit tests (Vitest)

Under `web/src/**/*.test.ts`, run with Vitest in Node, jsdom only for component tests. No Pyodide in Vitest: worker-facing code is tested against a fake worker that answers with recorded replies, so units stay fast (target: the whole suite under 60 s).

Must-cover modules: the RPC client (timeouts, deadlines, error-code mapping, cancellation, reply validation against the schema), the generated DTO types (W1.2's drift check runs in the same job: regenerate, then `git diff --exit-code`), the TypeScript ports of layout and hit-test maths against the **shared test vectors** (JSON files in `tests/vectors/`, also read by a host pytest test against the Python original; W1.4 and W1.5 own their contents), the command registry and capability gating, the shortcut table (W1.3 slice (f)), and the message catalogue (every RPC error code and every catalogue key used in the code has an English entry).

Coverage: 80% lines for `web/src/rpc/` and the ported maths; no global threshold, since UI glue is covered end to end.

## 6. End-to-end tests (Playwright)

**Target.** The production build (not the dev server), served by a small static server under the real base path `/elanero-pdf-editor/app/`, with the CSP meta tag and the service worker, and with the Pyodide assets from the build. One test build flag adds a `debug` RPC group (for example a call that hangs, to drive the watchdog); a unit test checks that the production bundle doesn't contain it.

**Browsers.** Chromium, Firefox and WebKit from Playwright's pinned builds. WebKit stands in for Safari; iPad stays best effort and manual. On a PR: the full suite on Chromium and the `@smoke` subset (open, render, one edit, save, reopen) on Firefox and WebKit. Nightly and before a release: the full suite on all three.

**Specs.**
- One spec per required feature R1–R7 and per viewer area (A1–A3), each with its round trip (§4).
- A smoke spec per added feature A4–A15 when it lands.
- **Security specs:** from the main page and from inside each worker, a `fetch` to an origin not in `connect-src` is blocked (W1.1 §10: workers start from a `blob:` URL so the page's CSP applies; this test proves it in each browser); the app refuses to run in a frame; a test page route fails the test on any request that isn't our origin (translation is mocked with `page.route`, and the live translation check stays in `web-cors.yml`); a PDF link with `javascript:` or `file:` does nothing, and an `https` link asks first; a PDF with JavaScript and a launch action runs neither.
- **Lifecycle specs:** offline after the first load (service worker); Cancel of a job terminates the job worker and the document stays editable; the watchdog dialog appears for a hung call and Restart reopens from the autosave; open and close a document 20 times and the engine worker's heap returns near its baseline (Chromium only, through the DevTools protocol, since `measureUserAgentSpecificMemory` needs cross-origin isolation).
- **Print:** the print dialog can't be driven, so the test stubs `window.print`, then checks the hidden iframe (page count, image sizes) and that the blob URLs are revoked afterwards.

**Flakiness.** One retry on CI. A test that needs its retry twice in a week gets an issue and is fixed or quarantined (`test.fixme` with the issue number), never left retrying.

## 7. Visual golden tests

**Rendering.** The worker renders the pages listed in `tests/golden/test_golden_render.py` at the same scales; the e2e job saves the RGBA as PNG artifacts; a host step compares them with the **desktop references** in `tests/golden/data/` using `tests/golden/compare.py` and the same tolerance (`max_mean=1.5`, `max_bad_fraction=0.004`). There are no separate web references: the engine is the same MuPDF version (plan decision 9), so a difference is a bug or a version skew, and the test should say so. On failure the diff images are uploaded.

**UI.** A handful of Playwright `toHaveScreenshot` checks (start page, each ribbon tab, the organizer, a dialog, both themes) on Chromium on Linux only, because font rendering differs across systems; `maxDiffPixelRatio` 0.002. References are updated only through a manual `workflow_dispatch` run with `--update-snapshots`, whose result is committed in a PR.

## 8. Performance budgets

The W0.2 harness (`web/spike/perf/`, `perf.spec.ts`) moves to `web/test/perf/` (W8.3).

| Metric | Gate | Where |
|---|---|---|
| First-load bytes (gzip of the full set, computed from the build) | ≤ 40 MB, hard | `web-unit`, every web PR (deterministic, costs seconds) |
| Main-thread long tasks while scrolling a 1000-page document | none over 50 ms | `web-perf` |
| Repeat visit to page 1, job-worker start, render p95 at scale 1 and 2, save of 200 pages | paired comparison, below | `web-perf` |
| Repeat visit to page 1 on a mid-range laptop | ≤ 4 s (plan decision 10) | the reference machine, before each release |

**Paired comparison.** CI runners vary by up to about 40% (W0.2), so absolute times can't gate a PR. `web-perf` builds the base commit and the PR in the same job on the same runner and runs them interleaved (5 runs each, persistent profiles as in W0.2). It fails when the PR's median is more than 15% *and* more than 300 ms slower than the base. The numbers go to the job summary and an artifact, and nightly runs keep a trend file.

**When.** On PRs that touch the worker bootstrap, the view, the RPC layer, the packaging scripts or shared Python in the engine (paths listed in `ci_changes.py`, §13), and nightly. The absolute 4 s gate can't run in CI; it is a release step (`RELEASING.md`, W9.6).

## 9. Robustness and fuzzing (W8.4)

**Corpus.** The damaged and foreign files of `tests/engine/test_damaged_files.py` (generated by `make_fixtures.py` once their pikepdf-built inputs move there, §3), the real samples in `tests/fixtures/real/` (with the licences noted in its README), and every minimised crasher found later.

**Two levels.**
1. **Engine level, Pyodide on Node.** For each file: `webapi.dispatch` open, render page 1, text of page 1, close, with the limits of W1.1 §7 and the call deadlines of W1.2. Pass: a reply or a stable error code within the deadline. Fail: a hang past the deadline, a wasm abort, or an `INTERNAL` error code.
2. **Browser level.** A subset of ten files through Playwright on Chromium: the app shows an error or the watchdog, never a frozen tab.

**Mutation fuzzing.** Nightly, 1000 seeded mutations (byte flips, truncations, duplicated objects, broken xref offsets) of the generated fixtures; the seed is the date and is printed, so any failure reproduces with one command. A failure opens an issue with the seed and the minimised file (minimised by bisecting the mutation list). On a PR only the fixed corpus runs.

## 10. Accessibility (W8.5)

- `@axe-core/playwright` on each main screen (start page, document view, each ribbon tab, each side panel, the main dialogs) in both themes. Violations rated serious or critical fail; moderate and minor are listed in the job summary.
- A keyboard-only spec: open a file, move through pages, use a ribbon command, open and close a dialog, edit a comment, save, all without the mouse, checking focus is always visible and never trapped.
- Theme contrast is also checked at the source: a host test computes the contrast of the text and background token pairs of `ui/style/tokens.py` in both themes (WCAG AA), so the web and the desktop share the check.
- Screen readers can't be automated reliably: a short manual checklist (NVDA with Firefox, VoiceOver with Safari) runs before each release (`RELEASING.md`).

## 12. Fixtures

`scripts/make_fixtures.py` stays the one source: no generated PDF is committed. The Pyodide runner and the Playwright server serve the same generated folder (`tests/fixtures/generated`); Playwright reaches it through a test-only route of the static server, never through the app's build. The W0.2 performance fixtures (`perf_mixed_*`) are already there.

## 13. CI jobs

All web jobs live in web workflows (`web-*.yml`), are named with a `web-` prefix and never use the required names `changes`, `checks`, `test-windows` or `build`.

**Which changes run what.** `scripts/ci_changes.py` gains a `web` output (W9.1). It is true for `web/*`, the web workflows, the shared Python in the web set (`src/pdfeditor/{model,engine,core,services,actions,webapi}/`, `data/`, `bundle.py`, `licenses.py`), the test folders those suites use, `scripts/make_fixtures.py`, `scripts/build_web_wheel.py` and `pyproject.toml`. Changes only under `src/pdfeditor/ui/` or desktop-only modules don't run the web jobs. Shared Python runs both the desktop and the web jobs. Docs-only PRs run nothing, as today. The web workflow's first job, `web-changes`, runs `ci_changes.py --web`, since a job can't depend on a job in another workflow.

| Job | Trigger | Runner | What | Expected time |
|---|---|---|---|---|
| `web-changes` | every PR, nightly | ubuntu | classify | < 1 min |
| `web-wheel` | `web` | ubuntu | restore or build the PyMuPDF wasm wheel (cache keyed on versions.json; cold build about 7 min, W0.1), build the pdfeditor web wheel | 1 min cached |
| `web-pytest` | `web` | ubuntu | Pyodide pytest (§2), then the host replay (§3) and the ratchet | ≤ 15 min |
| `web-unit` | `web` | ubuntu | ESLint, `tsc`, Vitest, type drift, shortcut and catalogue checks, size gate | ≤ 5 min |
| `web-e2e` | `web` | ubuntu | build the app; Playwright: Chromium full, Firefox and WebKit `@smoke` (nightly: all full); host replay; render goldens; axe | ≤ 20 min on a PR |
| `web-perf` | perf paths, nightly | ubuntu | paired comparison, long tasks | about 20 min |
| `web-fuzz` | nightly | ubuntu | corpus and seeded mutations | about 30 min |

`web-pytest` and `web-unit` start after `web-wheel` and in parallel with each other; `web-e2e` needs `web-wheel`. On the desktop side, `tests/actions/` and `tests/webapi/` run in `test-windows` like the rest, and `-n auto` speeds up local runs (#150); xdist doesn't apply under Pyodide (§2).

Whether any web job becomes a required check is a ruleset change the owner makes (plan W9.1); see question 3.

## 15. Questions for the maintainer

**Answered 2026-11-17: all four as recommended.**

1. **Where is the absolute 4 s repeat-visit gate measured?** CI can only compare a PR with its base. Recommended: you name one mid-range laptop as the reference machine, and the perf harness runs on it before each release (a `RELEASING.md` step).
2. **Firefox and WebKit run only the smoke subset on PRs**, the full suite nightly. Recommended: yes; it keeps a PR's e2e under about 20 minutes, and nightly failures open issues.
3. **Required checks.** Recommended: no web job is required at first; after a month without flaky failures, make `web-pytest` and `web-unit` required (a ruleset change by you), and keep `web-e2e` advisory until it has been stable as long.
4. **C1 by ratchet**, not all at once. Recommended: migrate the contract, R1 and R2/R6 modules in W2.7b, and the rest in W2.7c, with the ratchet preventing new debt.
