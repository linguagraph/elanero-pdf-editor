### 1.3 Checked by experiment (PyMuPDF 1.26 in `.venv`, `layers.pdf` fixture)

1. **A layer toggle is never written to the file.** After `set_layer_ui_config(0, 2)`, `/OCProperties` is byte-identical, and the file reopened after `tobytes(garbage=0/1/3/4)` and after an incremental save shows the layer on again. So the desktop toggle is view state only, and "save round trip" for layers means: the saved file keeps the file's own default states.
2. **The `_edits` bump in `set_layer_visible` (`document.py:486`) is wrong for a change that writes nothing.** `incremental_bytes` reuses its cached update only when `_lineage_edit == self._edits` (`document.py:833-844`); after one in-place save of a signed document, a toggle followed by a second save raises "can only be saved in place once" although nothing changed. Slice L1 removes the bump.
3. **`embfile_add` / `embfile_del`** exist; `embfile_add` raises `ValueError` on a duplicate name. After `embfile_del`, a save with `garbage=0` **still contains the attachment's bytes**; `garbage>=1` drops them. The web full save uses garbage 3 or 4 (`core/session.py:275-276`), so a removed attachment leaves a full save. An incremental save (signed document, `session.py:270-273`) would keep the bytes in the earlier revision.

## 2. Layers: visibility toggle

### 2.1 Behaviour (as the desktop)

- A checkbox per row. Changing it shows or hides that layer's content in the view, at once, on every page.
- **View state only**: no Undo entry, the document does not become dirty, and saving never writes it (1.3.1). The file's default states survive every save. This is the desktop's behaviour and Acrobat's eye icon (question 1).
- A locked layer's checkbox is disabled, as on the desktop (`layers.py:43-44`).
- Radio-button groups (`/RBGroups`): MuPDF turns the other members off itself; the reply returns the whole list, so the panel shows that.
- The view state is lost, back to the file's defaults, when the document is reloaded: after Undo or Redo of a snapshot step (flatten, sanitize, content edit), after a worker restart (W3.9), and on reopen. The panel reloads its list then (2.3), so it never shows a stale state.
- Print, export and the job worker work from the document's bytes, so they use the file's default states, not the view's. This matches what a save would give; the guide says so (risk R3).

### 2.2 Engine, core and RPC

- **Engine:** remove `self._edits += 1` from `MupdfDocument.set_layer_visible` (`document.py:486`), with a comment that the toggle writes nothing (1.3.1). Unknown ids: MuPDF ignores them; the webapi checks first.
- **Core:** a new `DocumentSession.set_layer_visible(layer_id: int, visible: bool) -> None` that takes `self.lock`, calls the engine and `_announce((Change(ChangeKind.CONTENT, frozenset(range(page_count))),))`. Not a Command (it changes no document data, AGENTS.md rule 5 covers mutations), and it does not check `busy`: it holds the engine lock like any read. Announcing a CHANGED event is what makes the web reply carry `changed` with the new page revisions through the existing `CallRecorder` (`webapi/events.py:41-47`, `:50-73`), which the render scheduler already consumes (`view/renderScheduler.ts:100-104`). The desktop panel switches to this method (two lines; `view.refresh()` stays).
- **RPC `layers.set_visible`** in `webapi/layers.py`: params `LayerVisibleParams { handle, id, visible }`; result the fresh `LayersResult` (the same DTO as `layers.list`). Errors: `REFUSED` with reason `layers_unsupported` when `capabilities.layers` is off; `STALE_OBJECT` when `id` is not in `document.layers()` (the list changed under the panel); `REFUSED` with reason `layer_locked` for a locked layer. Deadline class `instant` (one engine call, no render). Registered in `webapi/__init__.py`; `generated.ts` regenerated; `'layers.set_visible'` added to `PageRpc`.

### 2.3 Web panel

- Each row becomes a `<label>` with a native `<input type="checkbox">` (name as the label text, Locked as a description via `aria-describedby`), so keyboard and screen readers get a real checkbox. The Visible/Hidden text goes (the checkbox carries it).
- On change: disable that checkbox, call `layers.set_visible`, then replace the list with the reply. No optimistic update: a refusal leaves the old state. Errors go through `reportActionError` with new keys.
- Reload: the panel takes a `revision` prop, as Bookmarks does; `App.tsx` passes `structureRevision` plus a new `reloadRevision` bumped on a `changed` event with a `structure` change (snapshot restore) and on engine restart. Changing it re-runs `layers.list`.
- The `LayersPanel.tsx` header comment and `layers.visible`/`layers.hidden` keys are updated or removed.

## 3. Attachments: add, open, remove

### 3.1 Behaviour

- **Add.** An **Add file** button (also shown in the empty state) opens the browser's file picker; any file type. The file is embedded under its own name; if that name is taken, `name (2).ext`, `name (3).ext` and so on. Description empty (the desktop and the merged panel show it; editing it is not in scope). One Undo step, "Add Attachment".
- **Remove.** A **Remove** button in the details section asks for confirmation ("Remove {name} from this PDF? You can undo this until you close the document."), then removes it. One Undo step, "Remove Attachment".
- **Open.** Shown **only for an attachment whose bytes start with `%PDF-`** (checked in the first 1024 bytes after `attachments.get`, not trusted from the name). It opens the PDF as a new tab through `Documents.openFiles([new File([bytes], saveName(filename), { type: 'application/pdf' })])` (`documents/useDocuments.ts:86-107`), so it goes through the normal open path in the engine worker (password prompt, size limits, no JavaScript). Any other file type has Save only and is never opened, previewed or handed to the browser as anything but a download (W1.1 threat E; question 2).
- **Signed documents.** Add and Remove are refused, with the reason `signed_document` and the message pattern `security.py` uses (`actions/security.py:29-36`, `:70-72`): adding or removing an embedded file is not an allowed change after signing, and an in-place save is incremental, so a "removed" file would stay in the earlier revision (1.3.3). The buttons are disabled with a hint when `session.info` reports `has_signatures` (question 3).
- **Encrypted documents** behave as any other edit (the save re-encrypts).
- **Size.** A new `PlatformCapabilities.max_attachment_bytes` (`model/platform.py:26-30`, `None` on the desktop); the web sets it to 100 MiB in `webapi/platform.py`, alongside `MAX_IMAGE_BYTES`. Larger files are refused with reason `attachment_too_large` before the bytes reach the engine. The front end checks `File.size` first so a large file is never read.

### 3.2 Engine

- `Capabilities.attachments_write: bool = False` (`engine/base.py:58-80`); MuPDF sets it.
- Protocol: `add_embedded_file(name: str, data: bytes, filename: str, description: str = "") -> None` (raises `EngineError` on a duplicate name) and `remove_embedded_file(name: str) -> None`.
- MuPDF: `embfile_add(name, data, filename=filename, ufilename=filename, desc=description)` and `embfile_del(name)`, each with `self._edits += 1`. No page revision changes (no page content changes).

### 3.3 Commands and actions

- **`AddAttachmentCommand`** in `core/commands/document_cmds.py`: reversible. `do`/`redo` add with the held bytes; `undo` removes by name. Change kind METADATA (no pages). Holding the bytes is bounded by `max_attachment_bytes` on the web.
- **Remove uses the snapshot step** (`actions/base.py:98-110`), as flatten does: undo must restore the exact file specification (dates, MIME subtype, `/AF` relationships of a PDF/A-3 file, collection fields), which a re-add from bytes and description would lose. `long=True`, as `annotations.flatten`.
- New `actions/attachments.py`:
  - `attachments.add` (`AddAttachment { data: bytes, filename: str, description: str = "" }`, `requires=("attachments_write",)`): `ensure_idle`; refuse signed; refuse empty or too large; clean the declared name (last path part, no control characters, as `saveName`) and pick a free name; value is the name used.
  - `attachments.remove` (`RemoveAttachment { name: str }`, `requires=("attachments_write",)`, `long=True`): `ensure_idle`; refuse signed; `STALE_OBJECT` when the name is gone; snapshot step.
- Both run through `actions.run` on the web, so they get `changed`/`state` and Undo like every other action, and the web reasons go in `rpc/errors.ts` `REFUSED_REASON`.

### 3.4 Web panel

- `AttachmentsPanel` gets a footer bar (Add file) and, in the details section, Open (PDF only, after the bytes are read) and Remove next to Save. A hidden `<input type="file">` drives Add, as the image tools do.
- Add: read the file (`arrayBuffer`), run `attachments.add` with the bytes as a `$bin` buffer, then reload and select the new entry; a toast with Undo, as other actions.
- Remove: a small confirmation dialog on the shared `Overlay`, as `flatten/FlattenDialog.tsx` confirms (the app has no generic confirm dialog), then `attachments.remove`; reload and clear the selection.
- Reload on `revision` (as 2.3, plus the history counter, so Undo and Redo of Add or Remove refresh the list).
- Names and descriptions stay text nodes only (unchanged).

## 7. Risks

- **R1: Hidden content is not secret.** A layer toggled off in the view, or off by default, still holds its content in the file. The guide says so and points to Sanitize, which already removes hidden layers (`hidden_layers` fixture, `make_fixtures.py:520`).
- **R2: Removed attachment bytes.** Safe only because the web full save collects garbage (1.3.3); the A1 leak test pins it, and signed (incremental) documents are refused. If a later change lowers the garbage level to 0, the leak test fails.
- **R3: Print and export ignore the view's layer state.** They use the file's defaults (2.1). Making print follow the view would need the state passed to the job worker; out of scope, stated in the guide.
- **R4: Layer UI entries that are labels.** `layer_ui_configs()` can include non-toggleable label rows; `LayerInfo` carries no kind today, so the panel would show a checkbox that does nothing. L1 checks the `layers` and `hidden_layers` fixtures; if a real file shows labels, add a `kind` field to `LayerInfo` in a follow-up.
- **R5: PDF/A.** Adding a file to a PDF/A-1 or PDF/A-2 document breaks conformance, and PDF/A-3 needs `/AFRelationship`. Not handled here; the add is allowed, as other edits that break PDF/A are.
- **R6: Memory.** An added attachment is held by its Undo step (up to 100 MiB on the web) and the snapshot of a remove is a document copy in the worker's snapshot store, as for flatten.

## 8. Questions for the owner

1. **Layer toggling: view state only (desktop and Acrobat behaviour: not saved, no Undo, not dirty), or saved into the file as the new default state?** *Recommended: view state only.* It matches the desktop and the merged contract test, keeps signed files untouched, and the experiment in 1.3 shows MuPDF never writes it. Saving default states is a separate "Layer Properties" feature if wanted.
2. **Opening an attachment: only PDFs, as a new tab in the editor; every other type Save only?** *Recommended: yes.* A PDF opens through the same engine path as any file the user picks; anything else would have to be handed to the browser or OS, which W1.1 threat E forbids.
3. **Adding and removing attachments on a signed document: refuse (as Sanitize and Encrypt do), or allow with a warning?** *Recommended: refuse.* The change is not an allowed post-signing modification, and the in-place incremental save would keep a "removed" file's bytes in the earlier revision; the user can save a copy first and edit that.
