## Recommendation: GO with conditions

Over the 209 test items, the engine evidence is:

- **119 fully passed**, 0 failed, 0 errored. Of these, 117 ran engine code and 2 ran none.
- **48 engine part passed, host check pending.** The test ran engine code and passed up to its
  first pikepdf or pypdfium2 call, then skipped there. The assertions after that call did not run.
- **37 host check not reached.** The test skipped at a host-only call before any engine function
  returned.
- **5 OCR skipped** (the runner has no English OCR data). Locally they fail as (b); see triage.

Strictly, fully passed against failed is **119 / 119**. Counting the 48 partial tests as engine
passes, criterion 3 (>= 95 % pass) is met over the tests that ran engine code: **165 / 165**
(117 + 48). Read that number with the next paragraph: "ran engine code" can mean a single `open`
call, so it says the engine was reached, not how much of the test passed.

What is still unverified is the part of each partial test after its first host call, and the 37
tests that never reached the engine on the runner. Condition **C1 closes that gap**: give those
tests a Pyodide-capable check, or accept the desktop run as their verification. C2 to C6 cover OCR,
the build patches, budgets, pinning and threads. No failure is a (c) blocker, and nothing blocks
opening, rendering, editing or saving. The NO-GO fallback is not needed.

### Reproducibility of the wheel

Three cold builds gave three archive hashes: `dab0aa15…` (43962980323, 407 s), `3f866491…`
(43967344580, 214 s) and `b88d53f2…` (43968453081, 372 s). I compared the members of all three: each
wheel holds the same 118 files, and every file hashes identically across the three builds. The
difference is in the zip archive metadata, not in the content. So the build is reproducible at the
content level, not at the byte level. The cache keeps `wheel.sha256` next to the wheel, and the workflow
re-hashes it on every restore, so a swapped or damaged cache entry fails the run.

Total items: 209 (JUnit `tests="209"`). Host-only skip sites: `pikepdf.open` 43, `pikepdf.new` 34,

Engine returns are counted with `sys.monitoring` PY_RETURN, which fires only for a normal return. A

tell the two apart, and counted one more test).

What "ran engine code" means here: at least one `src/pdfeditor/engine` function returned during the
test's call phase. It does not measure how much of the test ran. A test that makes one `open` call
and then fails a host check counts as "engine passed, host check pending".

## Deviations from the design note

Each is the smallest change that got a working wheel or a usable test run. All keep MuPDF and
PyMuPDF at 1.28.2.

1. **Limited C API off** (`PYMUPDF_SETUP_PY_LIMITED_API=0`). The first build failed with
   `PyString_FromString` (a Python 2 name) in MuPDF's SWIG bindings for Python 3.14's limited API.
2. **One line patched in MuPDF's generator** (`scripts/wrap/swig.py`, in dead code under `if (0)`,
   but compiled): `PyString_FromString` -> `PyUnicode_FromString`. The MuPDF 1.28.x branch already
   has the Python 3 name there. The workflow requires exactly one match before the patch and none
   after it.
3. **One line patched in PyMuPDF's `src/extra.i`** (live code, `messagev`, which passes warnings to
   `pymupdf.message`): `PyString_FromString` -> `PyUnicode_FromString`. The same exactly-one rule
   applies.
4. **MuPDF from its release tarball** (`https://mupdf.com/downloads/archive/mupdf-1.28.2-source.tar.gz`,
   sha256 `44075a84e329db55b9bef5f342a70fd26d69e48ad1d33cb89d9664581c641156`), not the git tag. The
   tarball is what PyMuPDF's `setup.py` would download anyway. Its directory name is read from
   `versions.json`.
5. **Host Python 3.14 and pyodide-build 0.39.3**, not upstream's `scripts/test.py`. Upstream's
   `pyodide_setup` asserts Python 3.12 and clones emsdk at `git pull`; here pyodide-build fetches the
   Emscripten version from the pinned xbuildenv (5.0.3).
6. **Pyodide 314.0.8 kept** (the design's preference). Routes 1 and 2 do not provide 1.28.2 for
   314, so there was no fallback to 0.29.x in CI.
7. **Package closure fetched in `prepare`** (a setup step, not test time): `fonttools`, `pillow`,
   `numpy`, `pytest` and their dependencies from the Pyodide CDN, each checked against the sha256 in
   `pyodide-lock.json`. The test runs fetch nothing (the CDN is pointed at a dead port).
8. **Spike-only Qt stub.** `tests/conftest.py` imports `pdfeditor.ui.settings` (PySide6) in an autouse
   fixture. `pyodide_conftest.py` stubs the one name it reads. Nothing under `tests/` changed.
9. **Engine test failures don't fail the job.** The job is green when the harness runs; the gate is
   this report. Smoke failures do fail the job. `run` exits 0 on failing tests and 2 only when pytest
   cannot run.
10. **Cache key** includes `versions.json` and the workflow file, so a change to either rebuilds. The
    restored wheel is re-hashed against `wheel.sha256` on every run.
11. **The design note's module-level skip was replaced.** The note says modules that import pikepdf
    or pypdfium2 are skipped at import as "host-verified". That skipped 17 modules and 145 of the
    158 test functions, so only 13 tests ran and criterion 3 was measured on almost nothing. The
    plugin now puts lazy stubs in `sys.modules`: imports, `from x import Y` and annotations work,
    and the first call, index, iteration, comparison or truth test raises a skip with the reason
    "needs host-side verification: <name>". Engine returns are counted per test, so the report
    separates "engine passed, host check pending" from "host check not reached". The design's intent
    (host-only checks are not failures, and are verified on the host) is kept; only the granularity
    changed.

## Known unpinned build dependencies

These are not pinned to a hash and can change between runs. They are listed in `web/spike/README.md`
too.

- pyodide-build 0.39.3's own dependencies (only its top-level version is pinned).
- The Pyodide xbuildenv: `pyodide xbuildenv install 314.0.8` downloads it from the jsdelivr CDN, and
  its hash is not checked.
- Emscripten: pyodide-build installs the version the xbuildenv names (5.0.3) from upstream emsdk.
- SWIG, from the build tooling's PyPI dependency, not a pinned version.
- The host pins' transitive dependencies (five packages pinned exactly; theirs not).
- `npx playwright install --with-deps chromium`: Chromium and the system packages from apt.

## Conditions (GO with conditions)

- **C1: the host half of the 85 host-only tests, and the 37 that never reach the engine on the
  runner.** Their engine part runs under Pyodide when it gets that far; the assertions after the first
  pikepdf or pypdfium2 call do not, and are verified on the desktop only. Before W2 relies on the
  affected behaviour, either give each test a Pyodide-capable check (for example a pure-Python reader
  for the post-call assertions) or accept the desktop run as its verification (the W1.7 pattern).
  Priority: the Protocol contract tests in `test_contract` (30 functions), then `test_content_edit`
  and `test_text_edit_forms` (R1), `test_page_ops` and `test_mupdf_pagecopy` (R2, R6),
  `test_redaction` (A7), `test_security` (A8).
- **C2: no OCR on the web.** Tesseract is off in the Pyodide build and multiprocessing is absent.
  OCR is out of scope for the web (`docs/web/plan.md`). Any future OCR goes through a different path
  (a Worker-hosted engine or a service); record it with the task that adds it.
- **C3: remove the two source patches.** Build from a MuPDF and PyMuPDF release that already has the
  Python 3 names (the 1.28.x branch has the MuPDF one). Until then the patches live in the workflow,
  guarded by the exactly-one-match check.
- **C4: memory and size budgets.** Measure wasm heap, load size and render time on 10, 200 and 1000
  page documents (W0.2). The 200 MiB heap after one small document is the baseline.
- **C5: Pyodide pinning.** A Pyodide bump means a new wheel build (route 3) and the patches in C3
  re-checked. Route 2 needs its own Pyodide 0.29.5 pin, so the two routes are not interchangeable.
- **C6: threads and processes.** Pyodide cannot start threads or helper processes (`core/jobs.py`,
  `core/render_cache.py`). The W0.4 import audit covers this; the engine itself did not need them.
