## Recommendation: GO with conditions

Criterion 3 now holds on the tests that run engine code: 166 of 166 passed (118 passed outright, 48
passed their engine part and skip only at their first host-only call). No test failed in CI, and no
failure is a (c) blocker. The earlier 13-test figure was a flaw of the module-level skip, which hid
92 % of the tests; that is now replaced (see deviation 11).

The conditions are narrowed to what is still unverified. The 85 tests that stop at a host-only call
(pikepdf or pypdfium2) have their engine part run under Pyodide, but their assertions after that
call are checked only on the desktop. C1 below covers that gap. The NO-GO fallback is not needed:
nothing blocks opening, rendering, editing or saving, and every failure has a workaround.

## Deviations from the design note

Each is the smallest change that got a working wheel or a usable test run. All keep MuPDF and
PyMuPDF at 1.28.2.

1. **Limited C API off** (`PYMUPDF_SETUP_PY_LIMITED_API=0`). The first build failed with
   `PyString_FromString` (a Python 2 name) in MuPDF's SWIG bindings for Python 3.14's limited API.
2. **One line patched in MuPDF's generator** (`scripts/wrap/swig.py`, in dead code under `if (0)`,
   but compiled): `PyString_FromString` -> `PyUnicode_FromString`. The MuPDF 1.28.x branch already
   has the Python 3 name there.
3. **One line patched in PyMuPDF's `src/extra.i`** (live code, `messagev`, which passes warnings to
   `pymupdf.message`): `PyString_FromString` -> `PyUnicode_FromString`.
4. **MuPDF from its release tarball** (`https://mupdf.com/downloads/archive/mupdf-1.28.2-source.tar.gz`,
   sha256 `44075a84e329db55b9bef5f342a70fd26d69e48ad1d33cb89d9664581c641156`), not the git tag. The
   tarball is what PyMuPDF's `setup.py` would download anyway.
5. **Host Python 3.14 and pyodide-build 0.39.3**, not upstream's `scripts/test.py`. Upstream's
   `pyodide_setup` asserts Python 3.12 and clones emsdk at `git pull`; here pyodide-build fetches the
   Emscripten version from the pinned xbuildenv (5.0.3).
6. **Pyodide 314.0.8 kept** (the design's preference). Routes 1 and 2 do not provide 1.28.2 for
   314, so there was no fallback to 0.29.x in CI.
7. **Package closure fetched in `prepare`** (a setup step, not test time): `fonttools`, `pillow`,
   `numpy`, `pytest` and their dependencies from the Pyodide CDN, each checked against the sha256 in
   `pyodide-lock.json`. The test runs fetch nothing (the CDN is pointed at a dead port).
8. **Spike-only Qt stub.** `tests/conftest.py` imports `pdfeditor.ui.settings` (PySide6) in an autouse
   fixture. `pyodide_conftest.py` stubs the one name it reads. Nothing under `tests/` changed.
9. **Engine test failures don't fail the job.** The job is green when the harness runs; the gate is
   this report. Smoke failures do fail the job.
10. **Cache key** includes `versions.json` as well as the workflow file, so a version change rebuilds.
11. **The design note's module-level skip was replaced.** The note says modules that import pikepdf
    or pypdfium2 are skipped at import as "host-verified". That skipped 17 modules and 145 of the
    158 test functions, so only 13 tests ran and criterion 3 was measured on almost nothing. The
    plugin now puts lazy stubs in `sys.modules`: imports, `from x import Y` and annotations work,
    and the first call, index, iteration, comparison or truth test raises a skip with the reason
    "needs host-side verification: <name>". A profile hook counts engine returns per test, so the
    report separates "engine passed, host check pending" from "host check not reached". The design's
    intent (pikepdf and pypdfium2 are verified on the host, not failures) is kept; only the
    granularity changed.

Not deviations, but worth knowing: the route-2 PyPI wheel for 0.29.x was tested locally (scratch
tree, Pyodide 0.29.5) and gave the same passes, the same five OCR failures and the same six smoke
steps. It is in `versions.json` as the fallback, not in CI.

## Conditions (GO with conditions)

- **C1 (narrowed): the host half of the 85 host-only tests.** Their engine part runs under Pyodide;
  the assertions after their first pikepdf or pypdfium2 call do not. Those assertions are verified
  on the desktop only. Before W2 relies on the affected behaviour, either give the test a
  Pyodide-capable check (for example a pure-Python reader for the post-call assertions) or accept
  the desktop run as its verification (the W1.7 pattern). Priority: the Protocol contract tests in
  `test_contract` (30 functions), then `test_content_edit` and `test_text_edit_forms` (R1),
  `test_page_ops` and `test_mupdf_pagecopy` (R2, R6), `test_redaction` (A7), `test_security` (A8).
- **C2: no OCR on the web.** Tesseract is off in the Pyodide build and multiprocessing is absent.
  OCR is out of scope for the web (`docs/web/plan.md`). Any future OCR goes through a different path
  (a Worker-hosted engine or a service); record it with the task that adds it.
- **C3: remove the two source patches.** Build from a MuPDF and PyMuPDF release that already has the
  Python 3 names (the 1.28.x branch has the MuPDF one). Until then the patches live in the workflow,
  checked by `grep`, with the sha256 of the tarball pinned.
- **C4: memory and size budgets.** Measure wasm heap, load size and render time on 10, 200 and 1000
  page documents (W0.2). The 200 MiB heap after one small document is the baseline.
- **C5: Pyodide pinning.** A Pyodide bump means a new wheel build (route 3) and the patches in C3
  re-checked. Route 2 has no 314 wheel today.
- **C6: threads and processes.** Pyodide cannot start threads or helper processes (`core/jobs.py`,
  `core/render_cache.py`). The W0.4 import audit covers this; the engine itself did not need them.
