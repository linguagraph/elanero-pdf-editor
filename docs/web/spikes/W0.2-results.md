### Mid-range proxy: what it does and does not measure

`Emulation.setCPUThrottlingRate` at rate 4 slows the page's main thread (calibration loop: 101.5 ms throttled versus about 20 ms unthrottled). Chromium refuses the same command for dedicated workers: `Operation is only supported for pages, not workers`. A fresh dedicated worker ran the same loop in 24.4 ms (median of 6), so the worker was not throttled. Pyodide, the wheel, and the engine run in that worker, so the proxy does not slow the work the budgets measure. The proxy numbers below are therefore close to the unthrottled ones, and they are not a mid-range result. Recorded per run in `perf-laptop-cpu4.json` (`throttle.workers`, `throttle.calibration`).

### Where the cold start goes (local, unthrottled, perf_mixed_10 medians)

| Phase | ms | Share of 2475 ms phase sum |
|---|---:|---:|
| Pyodide ready (runtime + stdlib) | 947 | 38% |
| engine ready (PyMuPDF import, inside `get_engine`) | 898 | 36% |
| PyMuPDF wheel loaded | 290 | 12% |
| full package set loaded (fonttools, pillow) | 141 | 6% |
| harness and pdfeditor imported | 137 | 6% |
| all other phases | 62 | 2% |

The 898 ms `get_engine` phase covers the first PyMuPDF import and the backend import chain; it is not split further in this harness. Warm loads save almost nothing (Pyodide ready 929 ms, engine ready 947 ms): Pyodide's compile and init are not cached by the HTTP cache. Whether a service worker would help is untested (W4.6).

### The budget as written cannot be met at 32 MB

The cold budget is localhost plus download at 50 Mbit/s <= 6 s. The download alone at 32.26 MB is 5.16 s. With the local localhost time of 2.46 s, the download allowance is 3.54 s, which is about **22.1 MB gzip** (about 13.0 MB on the CI localhost time of 3.92 s). Reaching the budget therefore needs about 10 MB less gzip (local), or about 19 MB less (CI). The maintainer decides how to close the gap. Options, none of which are applied here:

1. Shrink the payload: split or trim the PyMuPDF wheel, trim `data/` for the web zip, lazy-load fonttools and Pillow only when editing (W2.6, W3.1).
2. Reduce the fixed startup cost (900 ms engine import, 950 ms Pyodide init) so localhost time falls, which relaxes the byte target.
3. Show the first page progressively, so the user sees content before the full stack is ready.
4. Restate the budget as "<= 6 s on a repeat visit, with a progress screen on the first visit". This is a plan change; the plan's budget is not changed here.

## M4: job worker start (decision 5)

Warm: the engine worker is ready, then a second worker boots and opens perf_mixed_200.

| Env | Spawn to opened (median, min-max) | Bootstrap to engine ready | Open call in Python | Wasm heap after open |
|---|---:|---:|---:|---:|
| Local, unthrottled | 2517 (2246-2662) ms | 2506 ms | 0.9 ms | 181.8 MiB |
| Proxy (page only, n=3) | 2941 (2876-2968) ms | 2927 ms | 0.9 ms | 181.8 MiB |
| CI | 3517 (3462-3585) ms | 3502 ms | 1.1 ms | 181.8 MiB |

Verdict: the design sets no M4 budget; M4 answers decision 5 below. Every worker boot pays the same 2.5 s to 3.5 s, so a second worker costs as much as the first load.

**Decision 5 answer.** A disposable job worker is affordable for long jobs (OCR, compare, export, optimize), which already take seconds, if the worker is spawned once when a document opens and kept warm, not spawned per operation: 2.5 s to 3.5 s and 182 MiB of wasm heap per worker. It is not affordable for short operations. Memory doubles: two workers hold about 364 MiB of wasm heap before any work, and the engine worker's heap grows to 314 MiB after 1000 pages (M7). The job worker is still worth it for cancellation, but spawn it ahead of time.

## Recommendations, ranked by gain

1. **Shrink the payload.** The PyMuPDF wheel is 18.07 MB gzip. Splitting or trimming it, and trimming the 5.46 MB gzip of `data/` in the web zip, is the only route to the 6 s cold budget. Each 1 MB of gzip costs 0.16 s on a 50 Mbit/s link. Map: W2.6 (web package split), W3.1 (lazy editing code).
2. **Investigate the 0.9 s `get_engine` import** (36% of cold start, about 1.3 s on CI). It is not split further here. Profile what runs inside it: wasm instantiation, the PyMuPDF module init, or backend imports. It is the largest single controllable cost. Map: W2.x (engine init, before the first document is opened).
3. **Lazy-load fonttools and Pillow** until editing needs them (141 ms of package loading plus their import share, and about 6 MB of their gzip). Map: W2.6, W3.1. Also consider pre-rendering page 1 while packages load (the render takes 26 ms, so it is cheap to overlap), and a progressive first page (map: W1.x, W4.x).

Other items, not in the top three: the render cache can be sized generously because renders take single-digit ms (W1.4); search and save over 1000 pages need a progress or job path with a warning (W3.9); the job worker should be spawned ahead of time (decision 5).

## Deviations from the design

1. The Pyodide core file is `pyodide.asm.mjs` (the design says `pyodide.asm.js`). The viewer set uses it.
2. An `ocr_worker` stub shim is added to the web zip (`web/spike/perf/shim_zip.py`). `engine/mupdf/ocr.py` imports `ocr_worker` at module level, and W0.4 found the same. The real fix belongs to W2.2.
3. The fixture font is "Perf Sans" (a generated font in `make_fixtures.py`) instead of a bundled one.
4. Brotli: the CLI on Windows locally, and `/usr/bin/brotli` on CI. Both measured; the design allowed "n/a in CI", but CI had it.
5. The full package set (fonttools, pillow and deps) loads at startup, not lazily. This is measured as the "full set" and is the reason the budget misses.
6. The local-only OCR data and the scanned sample were copied into this worktree (git-ignored). The scanned sample is measured locally only.
7. M8 is Chromium only.
8. Firefox and WebKit cross-browser runs (the 10-page check) were not run in this round.
9. The wheel member check compared the W0.1 artifact (run 43971516130) with the W0.2 wheel artifact (run 43973748625): 118 members each, identical content hashes; the archive sha256 differs.
10. **New: Chromium cannot CPU-throttle dedicated workers.** The mid-range proxy throttles the page only (see above). It is therefore not a mid-range result, and the budget verdicts below rest on the unthrottled local and CI runs. A real mid-range laptop run is needed.
11. **New: `flatten: false`** for the throttle's `Target.setAutoAttach`. Playwright's public CDP session cannot address flattened child sessions.
12. **New: the local "laptop" is a desktop** (Ryzen 9 9950X), so the local unthrottled numbers are optimistic for the budget. CI is a 4-core server, which is slower but not a laptop either.
13. **New: the throttled run skipped perf_mixed_1000 (optional) and the scanned sample.**
