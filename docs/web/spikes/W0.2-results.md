## The warm measurement had a cache fault (fixed)

The first warm runs were not warm. Each run used a fresh `browser.newContext()`, and the 18 MB PyMuPDF wheel was refetched on every reload: its `transferSize` was 18,085,060 bytes on all 35 local and 15 CI warm runs, while the other files came from cache (0). The cause is that the context's HTTP cache did not keep this large entry across the reload. I confirmed the fix on a persistent profile: the same reload then served the wheel with `transferSize` 0.

The fix: each run now uses `launchPersistentContext` with a fresh, empty profile directory. Cold is the first load in it; warm is a reload in the same profile, so the disk cache is used. The report has a cache check (`Cache check (the PyMuPDF wheel)`) and an M4 row for the job worker's wheel transfer. Result: the wheel is served from cache on 20 of 20 local warm runs, 20 of 20 job-worker boots, and 3 of 3 proxy warm runs.

The superseded numbers are kept, labelled, in `out/superseded/` (`perf-laptop-newcontext.json`, `perf-laptop-cpu4-newcontext.json`, `perf-ci-newcontext.json`). They show a 10-page warm total of 2501 ms (local), against 2618 ms now. On localhost the 18 MB refetch is nearly free, so the old warm totals were not materially wrong. What was wrong was the implied claim that a warm reload fetches everything from cache, and the warm download cost a real link would pay (about 2.9 s for the wheel alone at 50 Mbit/s).

With the cache working, warm reloads still do the same initialisation work: Pyodide ready 892 ms warm versus 1023 ms cold, and `get_engine` 1020 ms warm versus 948 ms cold (10-page medians). The HTTP cache removes the transfer, not the compile and init work, so the warm budget is limited by initialisation. Whether Pyodide's own compiled-module cache helps was not measured.

## Mid-range proxy: what it does and does not measure

`Emulation.setCPUThrottlingRate` at rate 4 slows the page's main thread (calibration loop: 99.4 ms throttled, median of 6, against about 20 ms unthrottled). Chromium refuses the same command for dedicated workers: `Operation is only supported for pages, not workers`. A fresh dedicated worker ran the same loop in 21.1 ms (median of 6), so it was not throttled. Pyodide, the wheel and the engine run in that worker, so the proxy does not slow the work the budgets measure. Its numbers are therefore close to the unthrottled ones and are not a mid-range result. Per run, `perf-laptop-cpu4.json` records `throttle.workers` and `throttle.calibration`.

### What payload would meet the cold budget

Download allowance: 6 s minus the 2.80 s local cold localhost time = 3.20 s, which at 50 Mbit/s (6.25 MB/s) is **about 20 MB gzip**, against 32.26 MB now. The payload must shrink by about 12 MB. The maintainer decides how to close the gap. Options, none applied here:

1. Shrink the payload (wheel split or trim, branding, lazy fonttools and Pillow).
2. Reduce the fixed startup cost (about 2 s of initialisation), which shrinks the localhost term and relaxes the byte target.
3. Show the first page progressively, so content appears before the full stack is ready.
4. Restate the budget as "<= 6 s on a repeat visit, with a progress screen on the first visit". This is a plan change; the plan's budget is not changed here.

## M4: job worker start (decision 5)

Warm: the engine worker is ready, then a second worker boots and opens perf_mixed_200.

| Env | Spawn to opened, median (min-max) | Bootstrap to engine ready | Open call in Python | Job worker wasm heap | Job worker wheel transfer |
|---|---:|---:|---:|---:|---|
| Local, unthrottled (n=20) | 2567 ms (2276-6255) | 2522 ms | 0.9 ms | 181.1 MiB | 0 bytes on 20 of 20 runs (from cache) |
| Proxy, page only (n=6) | 2881 ms (2266-5060) | not extracted | not extracted | 181.8 MiB | 0 bytes on 6 of 6 runs |
| CI (n=15) | 4619 ms (4516-4663) | 4598 ms | 1.2 ms | 181.4 MiB | 0 bytes on 15 of 15 runs (from cache) |

The M4 boot does not refetch the wheel after the fix: the job worker shares the browser HTTP cache with the engine worker, so its boot is initialisation only, about 2.5 s. A first boot in a cold browser still pays the download; that is the cold figure, not M4. The local M4 has a long tail (a few runs at 4 to 6 s), which the medians do not show. On CI the job-worker boot took 4.6 s (about 1.8 times the local median); this was not profiled, so the cause is not known.

**Decision 5 answer.** A disposable job worker is affordable for long jobs (OCR, compare, export, optimize), if it is spawned once when a document opens and kept warm, not per operation. Measured here on a desktop (local) and a 4-core server (CI), not a mid-range laptop, so the numbers are optimistic for the budget: about 2.6 s locally and 4.6 s on CI, and 181 MiB of wasm heap per worker in both, with the wheel served from cache. Two workers hold about 362 MiB of wasm heap before any work, and the engine heap grows to 314 MiB after 1000 pages (M7). It is not affordable per short operation.

## Recommendations, ranked

Gains are estimated from the measured numbers. Localhost has no download time, so byte gains apply only to a real link at 50 Mbit/s.

1. **Shrink the payload (W2.6).** The PyMuPDF wheel is 18.07 MB gzip (56%). Each 10 MB of gzip saves **up to about 1.6 s** of download on a first visit (50 Mbit/s). A repeat visit already skips this through the HTTP cache. Split or trim the wheel as part of W2.6.
2. **Trim the branding assets (W2.6).** `data/` is 5.46 MB gzip in total, nearly all of it `data/branding` (25 files, 6.08 MB raw). Removing all of it saves **up to about 0.9 s** of download on a first visit at 50 Mbit/s. Check which branding assets the editor needs at startup.
3. **Start-up initialisation (W3.1).** The `get_engine` import (948 ms, 34% of cold) and Pyodide init (1023 ms, 37%) are the largest costs in the warm budget too, since warm reloads do not skip them. Measure what runs inside `get_engine` (wasm instantiation, PyMuPDF module init, backend imports). A Pyodide memory snapshot is an option for this cost, not evaluated here. Pre-rendering page 1 while packages load (27 ms render, cheap to overlap) belongs in the same task. Gain: unknown until the `get_engine` cost is split; it is the largest item for the warm budget.

Other items:
- Lazy-load fonttools and Pillow until editing needs them (W3.1, W2.6): 2.15 MB gzip, so **about 0.34 s** of download on a first visit, plus about 0.15 s of package load on cold start.
- Caching (W4.6): the HTTP cache already serves the warm reload (verified above). The service worker's gain is reliability offline and on repeat visits, not a lower cold cost.
- Search and save over large documents need a progress path and a warning (W2.5, W3.9): 1.26 s search and 0.95 s save for 1000 pages locally.
- The render cache can be sized generously, since renders take single-digit ms (W1.4).

## Deviations from the design

1. The Pyodide core file is `pyodide.asm.mjs` (the design says `pyodide.asm.js`).
2. An `ocr_worker` stub shim is added to the web zip (`web/spike/perf/shim_zip.py`). `engine/mupdf/ocr.py` imports `ocr_worker` at module level, and W0.4 found the same. The real fix belongs to W2.2.
3. The fixture font is "Perf Sans", a generated square-glyph font, not a real typeface. Text render, extraction and search (M5, M6) are optimistic compared with real fonts.
4. Brotli: Python `brotli` locally this round (CLI earlier), `/usr/bin/brotli` on CI.
5. The full package set (fonttools, pillow and deps) loads at startup, not lazily. It is measured as the full set, and it is a reason the budget misses.
6. The local-only OCR data and the scanned sample were copied into this worktree (git-ignored). The scanned sample is measured locally only.
7. M8 is Chromium only.
8. Firefox and WebKit cross-browser runs (the 10-page check) were not run in this round.
9. The wheel member check compared the W0.1 artifact (run 43971516130) with the W0.2 wheel artifact (run 43973748625): 118 members each, identical content hashes. The archive sha256 differs.
10. **New: Chromium cannot CPU-throttle dedicated workers.** The mid-range proxy throttles the page only and is not a mid-range result. A real mid-range measurement is needed.
11. **New: `flatten: false`** for the throttle's `Target.setAutoAttach`. Playwright's public CDP session cannot address flattened child sessions.
12. **New: the local "laptop" is a desktop** (Ryzen 9 9950X), so local numbers are optimistic for the budget. CI is a 4-core server, slower but also not a laptop.
13. **New: warm runs use a persistent profile per run.** The earlier `newContext` warm numbers refetched the wheel; they are superseded (see above).
14. **New: `perf_mixed_*` fixtures are byte-identical across builds.** `make_fixtures.py` pins the Perf Sans font's `head` timestamps and saves with `no_new_id=True`. Checked: two builds each of perf_mixed_10 and perf_mixed_200 give identical bytes. The `_perf_photo` docstring now says "deterministic for a given Pillow version".
15. **New: the web zip changed size.** Its gzip is now 5,705,887 bytes (earlier `sizes.json` 5,706,713), after the merge brought `web_package.py` from `main`.
16. **New: the throttled run skipped perf_mixed_1000 (optional) and the scanned sample.**
