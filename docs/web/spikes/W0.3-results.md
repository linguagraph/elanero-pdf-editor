# W0.3: Translation CORS check

Stage: W0 (#133). Design: `docs/web/design/W0.3.md`. Probes: `web/spike/cors/` and `web/spike/cors.spec.ts`. Run locally on Windows 11 with Node 22.21.0 and Playwright 1.65.1, on 2026-11-17, from a fresh `npm ci`. The `translation-cors` job has not run in CI yet: GitHub refuses to dispatch `web-cors.yml` until it is on `main` (see Deviations).

## Answer

- **MyMemory, Azure AI Translator and LibreTranslate can be called from `https://linguagraph.github.io` directly.** The verdict is the same in Chromium, Firefox and WebKit.
- **DeepL Free is blocked, on both of its endpoints.** Its preflight answers `204` with no `Access-Control-Allow-Origin`, and its real responses carry none either. The browsers reject the request before any status reaches the page. DeepL is dropped from the web build, as the plan allows.
- The result is the same for `http://localhost:5173`. No service in this run keeps an origin allow-list.
- Nothing was inconclusive, so the maintainer's real-key path was not needed and was not run.

## Recommendation

**Services in the web build:** MyMemory (no key), Azure AI Translator (global endpoint, the user's key and optional region), and LibreTranslate on its public instance `https://libretranslate.com`. The public instance answered the fake key with `403 Invalid API key`, so it needs the user's own key in practice. Custom LibreTranslate servers and custom Azure endpoints stay out of scope on the web (plan R4).

**CSP `connect-src` (translation entries only; the app adds `'self'` and what other tasks need):**

```
connect-src 'self' https://api.mymemory.translated.net https://api.cognitive.microsofttranslator.com https://libretranslate.com
```

No wildcards, no DeepL host.

**Preferences fields the web build hides:** the DeepL key row (so no DeepL Test connection either), and the LibreTranslate server address row, since the public instance is fixed by the CSP. The Azure key and region, the LibreTranslate key and the MyMemory email stay.

**Privacy text (W9.4):** the selected text goes straight from the user's browser to MyMemory (Translated.net), to Microsoft (Azure) or to the operator of the LibreTranslate public instance. The user's own key goes with the request to Azure or LibreTranslate. The operator sees the user's IP address, since there is no relay. DeepL is not mentioned, because it is not in the web build.

## What changes for W2.4

- **Drop the DeepL transport**, including `/v2/usage`. Both endpoints are blocked, so there is no "usage allowed, translate blocked" case to handle.
- **Keep `credentials: 'omit'` on every call.** LibreTranslate sends `Access-Control-Allow-Credentials: true` next to `Access-Control-Allow-Origin: *`. A browser refuses that pair when `credentials` is `include`.
- **Keep the Azure headers.** The preflight allows `Ocp-Apim-Subscription-Key`, `Ocp-Apim-Subscription-Region` and `content-type`, with `POST`.
- **Keep JSON bodies.** The Azure and LibreTranslate preflights allow `Content-Type: application/json`.
- **Drop `User-Agent`.** Browsers can't set it, and each browser matched the raw probe, which does send it. It is not needed.
- **A blocked or failed request is a `TypeError` with no status.** That is `Failed to fetch` in Chromium, `NetworkError when attempting to fetch resource` in Firefox and `Load failed` in WebKit. A CORS block and an offline network look the same to the page, so the transport should show one generic "couldn't reach the service" message for both. Every other error comes from an HTTP status.
- **Error bodies can be read.** Azure and LibreTranslate send `Access-Control-Allow-Origin` on their 401 and 403 answers, so the page can read their error messages and map them as the desktop does.
- **MyMemory needs no preflight.** Its GET has only the `Accept` header, so a plain `fetch` works.

## Deviations

1. **CI dispatch.** The job lives in a new workflow, `.github/workflows/web-cors.yml` (`workflow_dispatch` only), as decided, not in `web-spike.yml`. `gh workflow run web-cors.yml --ref phase-w-w0.3-translation-cors` was refused with HTTP 404: `workflow web-cors.yml not found on the default branch`. No run URL exists yet. The verdicts come from the local run. The Linux job is untested until the workflow is on `main`. I did not add a `pull_request` trigger to get around this.
2. **DeepL fake key has the `:fx` suffix** (`fake-key-for-cors-probe:fx`). `deepl.py` `host_for` picks the free host from that suffix, and the design names the free host. A bare fake key would have gone to `api.deepl.com`, the Pro host.
3. **Fake values sent that the desktop sends only when configured.** The LibreTranslate POST carries a fake `api_key` in the body, and the Azure request always carries a fake `Ocp-Apim-Subscription-Region`, so the preflight covers the region header.
4. **The browser probe runs both origins.** The design names only the production origin. The dev origin was added so the origin comparison has browser data too.
5. **A separate Playwright config** (`web/spike/playwright.cors.config.ts`, three engines, no web server). The W0.1 config is Chromium-only and `web-spike.yml` runs it with `npx playwright test`, which must keep its current behaviour.
6. **No preflight for simple requests.** MyMemory's GET and LibreTranslate's `GET /languages` are simple requests, so no `OPTIONS` was sent. A browser sends none either.
7. **Plan text.** The R4 row in `docs/web/plan.md` now says DeepL is dropped. The decision list there does not name DeepL, so it is unchanged. `PLAN.md` is not ticked.
8. **Commit trailer.** The commits carry `Co-Authored-By: Claude Haiku 5.5`, the model that made them, not the Opus 5.5 line in the brief.
9. **Not probed:** the DeepL Pro host (`api.deepl.com`). DeepL is dropped for the web build, so this only matters if DeepL returns.

## Limits

- One run per browser and origin, so this is a snapshot. CORS policies can change.
- Every verdict uses a fake key. The preflight does not depend on the key, and Azure and LibreTranslate sent CORS headers on their error responses. What the success path sends with a real key was not measured. The real-key path exists for the maintainer if that needs checking.
- Only two origins were tried. Both are treated the same by every service here.
- The Azure and LibreTranslate verdicts rest on CORS headers seen on 401/403 responses (a gateway-level policy), not on a 200 response with a real key. The maintainer's optional real-key probe would confirm it.
- The public LibreTranslate instance needs the user's own key (a fake key gets `Invalid API key`). So without a key, the web build effectively offers MyMemory only, plus Azure and LibreTranslate for users who have a key.

## Method (as run)

- Raw probe (`web/spike/cors/raw_probe.mjs`, Node 22.21.0 `fetch`): preflight with the exact non-safelisted headers (lower case, sorted, comma-separated), then the real request with the same `Origin` and `User-Agent: Elanero`.
- Browser probe (`web/spike/cors.spec.ts`, Playwright 1.65.1): `cors/probe.html` served under each real origin by `page.route`, so nothing is deployed. The page runs `fetch` in CORS mode with `credentials: 'omit'` and no `User-Agent`. Chromium 159.0.8154.6, Firefox 159.0, WebKit 27.2.
- Verdicts (`web/spike/cors/report.mjs`): a preflight that is rejected, or that lacks the origin or a needed header or method, is **blocked**. An origin on the response is **allowed**, on any status. No origin on a 2xx is **blocked**. No origin on an error status, or a network failure, is **inconclusive**. A browser that disagrees with the raw verdict makes it **inconclusive**.
- Every output is redacted (`web/spike/cors/redact.mjs`). Key headers are written as `[redacted]`, and every secret value is replaced wherever it appears. The probe refuses to write a file that still holds a secret. Grepping `web/spike/out/` for the fake key finds nothing, and no key header carries a value.

Console evidence: Chromium reports `No 'Access-Control-Allow-Origin' header is present on the requested resource` for DeepL. Firefox reports `Reason: CORS header 'Access-Control-Allow-Origin' missing. Status code: 204`. WebKit reports `Origin https://linguagraph.github.io is not allowed by Access-Control-Allow-Origin. Status code: 204`.
