# W3.1 spike: Pyodide memory snapshot

Probe: `web/spike/snapshot_probe.mjs` (Node, spike only, not in CI). Run: `node web/spike/snapshot_probe.mjs` from the repo root, after the engine assets are staged in `web/spike/dist/engine-assets` (a copy of `web/app/public/engine-assets`, git-ignored). The probe writes its raw results to `web/spike/dist/snapshot-results.json` (git-ignored).

Scope: slice 3 of the W3.1 brief. Nothing in `src/`, `web/app/src/` or the product build changes. Shipping a snapshot stays blocked (W4.6, W9.1/W9.2, W8.3).

## Verdict: not adopted

The rule in the brief needs all three of (a), (b) and (c). Only (c) holds.

- (a) The restore covers the PyMuPDF import: **no**. Pyodide refuses to take a snapshot after any `loadPackage` call, so no snapshot contains PyMuPDF or Pillow.
- (b) The restore saves at least 0.8 s of the warm start: **no**. The restored path to ready has the same median as the cold path (3283 ms against 3275 ms).
- (c) The gzip size is at most 15 MB: **yes**, 5.92 MiB for the only snapshot that could be made.

Reason, in short: the only snapshot Pyodide accepts is taken before any package is loaded. It saves about 0.95 s of `loadPyodide`, but the packages, the PyMuPDF import and the adapter take longer after a restore in this run, and that gives the saving back. The snapshot API is also private (see below), so any pin bump would need a new snapshot and a new check.

Re-open this only if a Pyodide pin allows a snapshot after `loadPackage`, and the restored path to ready is measured again on the browser, not Node.

## The API (Pyodide 314.0.8)

The API is private. Its typings mark it `@private` and `@ignore`, and the options start with an underscore:

- `loadPyodide({ _makeSnapshot: true, ... })` makes the instance snapshot-capable.
- `pyodide.makeMemorySnapshot({ serializer? })` returns a `Uint8Array`. It throws unless the instance was made with `_makeSnapshot`.
- `loadPyodide({ _loadSnapshot: bytes, _snapshotDeserializer? })` restores from the snapshot.

It exists in the pinned version and works for the bare core. It is not a supported public contract, and it may change between pins.

## Can it be taken after the shared libraries are loaded?

No, in this build. Every attempt after a `loadPackage` call failed with `Unexpected hiwire entry at index 6`:

- after Pillow (`loadPackage("pillow")`): failed;
- after Pillow and the PyMuPDF wheel: failed (`packages` variant);
- after `import pymupdf`, the web zip unpacked and the adapter imported: failed (`pymupdf` variant).

A `serializer` argument did not change the error in a separate check on the Pillow-only case. So the answer to the brief's question is "only before", and "before" means before any package.

## Correctness

The check runs after the ready step: hello, `session.open` on the fixture, `render.page` on page 0 at scale 1000, `save.save_bytes` in copy mode, and `session.open` on the saved bytes.

- Page count: 10 on every cold and restored run, and 10 on the reopened save.
- Page 0 render (595 x 842 px): the same SHA-256 on every cold and restored run.
- Saved file size: 222,274 bytes on 9 of 10 runs, and 222,270 bytes on one restored run.
- Saved file bytes are not identical from run to run, even on the cold path, so they cannot serve as the check. The difference is in the saved output (probably a timestamp or ID), not in the restore.

The restore therefore gives the same pages and the same render. Byte identity is not a usable test for this engine: it needs a normalised comparison, which was not done here.

## CSP and the job worker (not measured)

- The snapshot is binary data fetched as an `ArrayBuffer`. It needs no `eval` beyond `'wasm-unsafe-eval'`, which `web/app/src/csp.ts` already allows. Not tested in a browser.
- The job worker has no network, so it would get the snapshot as a transferred buffer from the main thread. Not built, because the verdict is not adopted.

## Notes for a future pin bump

- The snapshot is tied to the exact Pyodide, wheel and zip build (the brief's risk 8). Any pin bump would need a new snapshot and a re-run of this probe.
- Re-check the `Unexpected hiwire entry` failure first. A pin that allows a snapshot after `loadPackage` would change verdict (a).
